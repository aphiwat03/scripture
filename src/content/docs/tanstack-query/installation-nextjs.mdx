## 1. แนวคิด (Concept)

การติดตั้ง **TanStack Query v5** ใน **Next.js 16 (App Router)** และ **React 19** มีข้อควรระวังสำคัญทางสถาปัตยกรรมที่แตกต่างจาก React Single Page Application (SPA) ทั่วไปอย่างสิ้นเชิง

ใน Next.js App Router เซิร์ฟเวอร์จะประมวลผลคำขอ (Request) จากผู้ใช้หลายคนพร้อมๆ กัน หากเราประกาศอินสแตนซ์ `QueryClient` ไว้เป็นตัวแปร Global นอกคอมโพเนนต์เหมือนในสมัย React SPA:
```ts
// ❌ ห้ามทำเด็ดขาดใน Next.js App Router
const queryClient = new QueryClient(); 
```
จะเกิดปัญหาความปลอดภัยร้ายแรงที่เรียกว่า **Cross-Request State Pollution (การรั่วไหลของข้อมูลข้ามคำขอ)** ข้อมูลส่วนตัวของผู้ใช้ A (เช่น ตะกร้าสินค้า หรือที่อยู่จัดส่ง) ที่ถูกแคชไว้บนเซิร์ฟเวอร์อาจรั่วไหลไปปรากฏในหน้าเว็บของผู้ใช้ B ที่เปิดเข้ามาในเวลาเดียวกัน

ดังนั้น สถาปัตยกรรมที่ถูกต้องใน Next.js 16 คือ:
1. **บน Server**: ต้องสร้าง `QueryClient` ตัวใหม่แบบ **Request-scoped** (1 instance ต่อ 1 server request)
2. **บน Browser**: ต้องใช้ `QueryClient` เพียงตัวเดียวที่เป็น **Singleton** ตลอดอายุการใช้งานของหน้าเว็บ

## 2. หลักการเบื้องหลัง (Under the Hood)

### วงจรชีวิตของ QueryClient ใน Server Component และ Client Hydration

```
[Server Execution (Node.js / Edge)]
Client Request A ---> makeQueryClient() ---> QueryClient A (Fresh / Isolated)
Client Request B ---> makeQueryClient() ---> QueryClient B (Fresh / Isolated)
                     (ถูกทำลายทิ้งทันทีเมื่อ Response ส่งเสร็จ ป้องกัน Memory Leak)

--------------------------------------------------------------------------------

[Client Execution (Browser)]
Initial Render ---> browserQueryClient === undefined ? makeQueryClient() : reuse
                    (คงอยู่ตลอดอายุการใช้งาน Session ของแท็บนั้น)
```

เมื่อใช้ฟังก์ชันตรวจสอบ `isServer`:
```ts
const isServer = typeof window === 'undefined';
```
- ถ้าทำงานบน Server (`isServer === true`): ทุกครั้งที่ฟังก์ชัน `getQueryClient()` ถูกเรียก จะสร้างอินสแตนซ์ใหม่เอี่ยมเสมอ เพื่อความปลอดภัย 100%
- ถ้าทำงานบน Client (`isServer === false`): หากมี `browserQueryClient` อยู่แล้วให้ส่งตัวเดิมกลับไป หรือหากยังไม่มีให้สร้างขึ้นมาและเก็บลงตัวแปร Singleton ของเบราว์เซอร์

นอกจากนี้ การตั้งค่า `defaultOptions` แนะนำให้กำหนด `staleTime: 60 * 1000` (1 นาที) เพื่อป้องกันไม่ให้ Client Component ทำการยิง Refetch ซ้ำซ้อนทันทีหลังจาก Hydration สำเร็จ

## 3. ตัวอย่างโค้ด (TypeScript / TSX)

การสร้างโครงสร้างแบบโปรดักชันใน Next.js 16 มี 3 ไฟล์หลัก:

### ไฟล์ที่ 1: สร้าง Factory และ Helper สำหรับ QueryClient

```ts filename="src/lib/query-client.ts"
import { QueryClient, defaultShouldDehydrateQuery, isServer } from '@tanstack/react-query';

function makeQueryClient(): QueryClient {
  return new QueryClient({
    defaultOptions: {
      queries: {
        // ตั้ง staleTime 1 นาที เพื่อไม่ให้ Client ยิงซ้ำทันทีหลัง Server Hydration
        staleTime: 60 * 1000,
        // กำหนด gcTime (เดิมคือ cacheTime) 5 นาที
        gcTime: 5 * 60 * 1000,
        // ปิดการ retry บนเซิร์ฟเวอร์ แต่เปิดบนไคลเอนต์
        retry: (failureCount, error) => {
          if (isServer) return false;
          return failureCount < 2;
        },
        refetchOnWindowFocus: process.env.NODE_ENV === 'production',
      },
      dehydrate: {
        // ให้ dehydrate รวม query ที่อยู่ในสถานะ pending ไปด้วยสำหรับ streaming
        shouldDehydrateQuery: (query) =>
          defaultShouldDehydrateQuery(query) || query.state.status === 'pending',
      },
    },
  });
}

let browserQueryClient: QueryClient | undefined = undefined;

export function getQueryClient(): QueryClient {
  if (isServer) {
    // Server: สร้าง client ใหม่เสมอสำหรับแต่ละ request
    return makeQueryClient();
  } else {
    // Browser: สร้าง client ครั้งแรกเพียงตัวเดียว แล้วใช้ซ้ำตลอด
    if (!browserQueryClient) {
      browserQueryClient = makeQueryClient();
    }
    return browserQueryClient;
  }
}
```

### ไฟล์ที่ 2: สร้าง Provider Component ฝั่ง Client

```tsx filename="src/providers/query-provider.tsx"
'use client';

import React, { ReactNode } from 'react';
import { QueryClientProvider } from '@tanstack/react-query';
import { ReactQueryDevtools } from '@tanstack/react-query-devtools';
import { getQueryClient } from '@/lib/query-client';

interface QueryProviderProps {
  children: ReactNode;
}

export function QueryProvider({ children }: QueryProviderProps) {
  // ดึง instance ที่ปลอดภัยต่อทั้ง SSR และ Client
  const queryClient = getQueryClient();

  return (
    <QueryClientProvider client={queryClient}>
      {children}
      {/* Devtools จะแสดงเฉพาะในโหมด Development และไม่ถูกรวมใน Production bundle */}
      <ReactQueryDevtools initialIsOpen={false} buttonPosition="bottom-right" />
    </QueryClientProvider>
  );
}
```

## 4. เทียบกับวิธีเดิม (useEffect vs TanStack Query)

| ด้านสถาปัตยกรรม | วิธีเดิม (React SPA แบบคลาสสิก) | Next.js 16 App Router + TanStack Query v5 |
| :--- | :--- | :--- |
| **การสร้าง QueryClient** | `const client = new QueryClient()` ในไฟล์ต้นทางแบบ Global | แยก Server Request Scoped และ Browser Singleton ผ่าน `getQueryClient()` |
| **ความเสี่ยง Data Leak** | ต่ำ (เพราะรันบนเบราว์เซอร์เครื่องเดียว) | สูงมาก หากไม่ระวัง ข้อมูลผู้ใช้จะปนเปื้อนข้าม Session บน Node.js runtime |
| **Hydration Mismatch** | ไม่มี SSR จึงไม่มีปัญหานี้ | มีโอกาสเกิด หากไม่มีการตั้ง `staleTime` ที่เหมาะสม Client จะยิง fetch ทันทีทำให้หน้ากระพริบ |
| **Devtools** | มักลืมถอดออกใน Production | TanStack Devtools v5 ตัด bundle ออกจาก production อัตโนมัติใน bundler ยุคใหม่ |

## 5. ผิด vs ถูก

### แบบที่ผิด ❌: ประกาศ `QueryClient` ทิ้งไว้นอก Component ใน Client Provider

```tsx
// ❌ ผิด: ประกาศนอก Component ใน Client File
'use client';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

// เมื่อ Next.js ทำ Pre-rendering ฝั่ง Server ตัวแปรนี้จะกลายเป็น Shared Instance ทันที!
const globalClient = new QueryClient();

export function BadProvider({ children }: { children: React.ReactNode }) {
  return <QueryClientProvider client={globalClient}>{children}</QueryClientProvider>;
}
```

### แบบที่ถูก ✅: ใช้ `useState` หรือ `getQueryClient()` ป้องกันการสร้างซ้ำและปลอดภัยข้าม Request

```tsx
// ✅ ถูกต้อง: ใช้ useState ใน Client Component เพื่อให้สร้างครั้งเดียวตลอดอายุ Component
'use client';
import { useState } from 'react';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

export function GoodProvider({ children }: { children: React.ReactNode }) {
  // useState initializer function จะถูกเรียกเพียงครั้งเดียวเมื่อ Mount
  const [queryClient] = useState(
    () =>
      new QueryClient({
        defaultOptions: {
          queries: {
            staleTime: 60 * 1000,
          },
        },
      })
  );

  return <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>;
}
```

## 6. ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่

### ควรใช้ QueryClientProvider ทั่วทั้งแอปเมื่อ:
- แอปมีฟีเจอร์ฝั่ง Client ที่ต้องการแชร์แคช เช่น ข้อมูลผู้ใช้ที่ล็อกอิน, ยอดสินค้าในตะกร้า, การค้นหาแบบมี Filter ซับซ้อน
- ต้องการใช้ Prefetching บน Server Components ผ่าน `HydrationBoundary` และส่งต่อแคชมาให้ Client Components แสดงผลแบบ Zero-Loading

### ไม่จำเป็นต้องใช้เมื่อ:
- เว็บไซต์เป็น Static Blog หรือหน้า Landing Page ล้วนที่ไม่มี Client-side Interactivity (ใช้ Native Server Fetching ใน Server Component โดยไม่ต้องห่อ QueryProvider)
- การดึงข้อมูลชั่วคราวใน Micro-frontend ที่มีระบบแคชแยกอิสระอยู่แล้ว

## 7. คำถามสัมภาษณ์งาน (Interview Questions)

### Q1: ทำไมการประกาศ `const queryClient = new QueryClient()` ไว้ที่ Module Scope (นอก Component) จึงเป็นอันตรายอย่างยิ่งใน Next.js App Router?
**แนวทางตอบ**:
บน Next.js App Router โมดูล JavaScript จะถูกนำมาใช้ซ้ำ (Shared) ข้ามคำขอของผู้ใช้หลายๆ คนที่ยิงเข้ามายัง Node.js Server Process เดียวกัน หากเราประกาศ `new QueryClient()` ไว้ที่ Module Scope ตัวแปรนั้นจะกลายเป็น Shared Global State ส่งผลให้:
1. **Cross-Request State Pollution**: แคชข้อมูลของผู้ใช้คนแรก (เช่น ข้อมูลโปรไฟล์ บัตรเครดิต หรือออเดอร์) จะติดอยู่ในแคช และถูกส่งต่อไปยังผู้ใช้คนที่สองที่เปิดหน้านั้น
2. **Memory Leak**: แคชจะสะสมคำขอและข้อมูลไปเรื่อยๆ โดยไม่มีการเคลียร์หน่วยความจำ จนทำให้เซิร์ฟเวอร์ Out of Memory (OOM) และล่มในที่สุด

### Q2: ในการตั้งค่า QueryClient บน Next.js 16 ทำไมจึงควรกำหนด `staleTime` มากกว่า 0 เป็นค่าเริ่มต้น?
**แนวทางตอบ**:
ค่าเริ่มต้นของ TanStack Query คือ `staleTime: 0` ซึ่งหมายความว่าข้อมูลจะถือว่า "เก่าทันที" เมื่อถูกดึงมา หากเรา Prefetch ข้อมูลมาจาก Server Component แล้วส่งต่อผ่าน HydrationBoundary เมื่อ Client Component โหลดขึ้นมาบนเบราว์เซอร์ มันจะมองว่าข้อมูลเก่าทันทีและสั่งยิง Network Request ไปดึงซ้ำอีกรอบ (Double Fetching) ทำให้เสียประโยชน์ของการทำ Server-Side Rendering การตั้ง `staleTime` เช่น `60 * 1000` (1 นาที) จะช่วยให้ Client นำข้อมูลที่ Server ส่งมาให้ไปแสดงผลทันทีโดยไม่ต้องยิงซ้ำ
