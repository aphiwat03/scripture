## 1. แนวคิด (Concept)
การบริหารจัดการฐานข้อมูลระดับมืออาชีพ เปรียบเหมือนการขับเครื่องบินพาณิชย์:
- **GUI Tools (DBeaver, pgAdmin 4):** เปรียบเหมือน "แผงหน้าปัดดิจิทัลและแผนที่การบินบนจอสัมผัส" เหมาะสำหรับการสำรวจข้อมูลภาพรวม ออกแบบความสัมพันธ์ ER Diagram และดู Visual Explain Plan ในช่วงการพัฒนาบนเครื่อง Local
- **`psql` CLI:** เปรียบเหมือน "คันโยกและระบบควบคุมโดยตรงของเครื่องบิน" ที่วิศวกรทุกคนต้องเชี่ยวชาญ เพราะในโลกความเป็นจริง เมื่อระบบ Production เกิดปัญหาบน Kubernetes Cluster, Docker Container หรือ Remote Linux Server ที่ไม่มี GUI สิ่งเดียวที่คุณจะสามารถเข้าถึงได้ผ่าน SSH หรือ `kubectl exec` คือหน้าจอดำของ **`psql`**

## 2. หลักการเบื้องหลัง (Under the Hood)
- `psql` ทำงานบน Client Library พื้นฐานของ PostgreSQL คือ `libpq`
- **Meta-Commands (คำสั่งที่ขึ้นต้นด้วย `\`):** คำสั่งเหล่านี้ **ไม่ใช่คำสั่ง SQL** และไม่ได้ถูกประมวลผลบนเซิร์ฟเวอร์โดยตรง แต่ตัวโปรแกรม `psql` ในฝั่ง Client จะเป็นตัวตีความ แล้วแปลงเป็นคำสั่ง SQL สลับซับซ้อนเพื่อวิ่งไปดึงข้อมูลจาก Catalog Tables (`pg_catalog.pg_class`, `pg_catalog.pg_attribute`, `pg_catalog.pg_roles` ฯลฯ) แล้วนำมาจัดรูปแบบเป็นตารางสวยงามบนหน้าจอ Terminal

## 3. รายการคำสั่ง Meta-commands ของ psql ที่ Developer ต้องรู้

| คำสั่ง psql | หน้าที่การทำงาน | ตัวอย่างสถานการณ์ใช้งานจริง |
| :--- | :--- | :--- |
| `\l` หรือ `\l+` | แสดงรายชื่อ Database ทั้งหมด พร้อมขนาด พื้นที่จัดเก็บ และ Encoding | เช็กดูว่ามีกี่ฐานข้อมูลในเซิร์ฟเวอร์ และขนาดโตไปกี่ GB |
| `\c dbname` | สลับการเชื่อมต่อไปยัง Database อื่น (`CONNECT`) | เปลี่ยนจากฐานข้อมูล `postgres` ไปทำงานที่ `smart_butcher_db` |
| `\dt` หรือ `\dt+` | แสดงรายชื่อตารางทั้งหมดใน Schema ปัจจุบัน พร้อมขนาดตาราง | สำรวจดูว่า Migration ตารางเนื้อสัตว์เข้ามาครบหรือไม่ |
| `\d+ table_name` | **คำสั่งยอดฮิต:** แสดงรายละเอียดโครงสร้างตารางอย่างลึกซึ้ง | เช็กคอลัมน์, Data Types, Constraints, Default, Indexes, Foreign Keys, Triggers |
| `\dn` หรือ `\dn+` | แสดงรายชื่อ Schemas ทั้งหมดใน Database | ตรวจสอบว่ามี Schema `tenant_a` หรือ `audit` อยู่หรือไม่ |
| `\du` หรือ `\du+` | แสดงรายชื่อ Roles ทั้งหมด พร้อมสิทธิ์ (Attributes/Members) | ตรวจดูว่า User แอปพลิเคชันมีสิทธิ์ Superuser หลุดมาหรือไม่ |
| `\x` หรือ `\x auto` | เปิดโหมด **Expanded Display** (แสดงผลแนวตั้งแทนแนวนอน) | **จำเป็นอย่างยิ่ง:** ใช้เมื่อตารางมีหลายคอลัมน์ หรือมีฟิลด์ JSONB ยาวๆ |
| `\timing` | เปิด/ปิด ตัวจับเวลาการประมวลผล Query (มิลลิวินาที) | ใช้วัดประสิทธิภาพความเร็วของคำสั่ง SQL ได้ทันที |
| `\q` | ออกจากโปรแกรม psql | ปิด Terminal เพื่อกลับสู่ OS Shell |

### 3. การรัน SQL Script จากไฟล์ด้วย `psql -f`
คำสั่งสำหรับการทำ Automation, Seeding หรือรัน Database Migration:

```bash filename="run_database_setup.sh"
# 1. รันไฟล์สคริปต์ SQL บนเซิร์ฟเวอร์แบบ Non-interactive
psql -h localhost -p 5432 -U butcher_app_user -d smart_butcher_db -f 05_production_schema.sql

# 2. รันสคริปต์และหยุดการทำงานทันทีหากพบ Error (สำคัญมากสำหรับ CI/CD!)
psql -v ON_ERROR_STOP=1 -h localhost -U butcher_app_user -d smart_butcher_db -f 06_seed_data.sql

# 3. สั่ง Export ข้อมูลผลลัพธ์เป็นไฟล์ CSV ตรงๆ จาก CLI
psql -U butcher_app_user -d smart_butcher_db -c "COPY (SELECT name, sku, price_per_kg FROM products) TO STDOUT WITH CSV HEADER" > products_catalog.csv
```

## 5. ผิด vs ถูก (Common Pitfalls & Best Practices)

### ❌ สิ่งที่ผิด: รันสคริปต์ขนาดใหญ่บน Production โดยไม่ใส่ `ON_ERROR_STOP=1`
```bash filename="terminal.sh"
# เมื่อคำสั่งที่ 2 เกิด Error เช่น Table Duplicate ตัว psql จะยังคงฝืนรันคำสั่งที่ 3, 4, 5 ต่อไป!
# ส่งผลให้ฐานข้อมูลเกิดสถานะครึ่งๆ กลางๆ (Inconsistent Schema)
psql -d smart_butcher_db -f migration_v2.sql
```

### ✅ สิ่งที่ถูก: สั่ง `ON_ERROR_STOP=1` และครอบสคริปต์ทั้งหมดด้วย `BEGIN; ... COMMIT;`
```bash filename="terminal.sh"
# เมื่อมีบรรทัดใดเกิด Error ระบบจะหยุดรันทันทีและ Rollback ทุกอย่างกลับสู่จุดเดิม
psql -v ON_ERROR_STOP=1 -d smart_butcher_db -f migration_v2_safe.sql
```

## 6. ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **`psql` CLI:** ควรใช้เป็นเครื่องมือหลักสำหรับ Automation Scripts, CI/CD Deployment, Backup/Restore Verification, และการเข้าแก้ปัญหาเร่งด่วนในเซิร์ฟเวอร์จริง
- **GUI Tools (DBeaver / pgAdmin):** เหมาะกับการดู Explain Execution Plan แบบ Graphic Tree ในจังหวะที่ทำการ Tuning Query ที่มีความซับซ้อนสูง และการสำรวจ Entity-Relationship Diagrams (ERD) ของระบบ

## 7. คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: ในการเข้าตรวจสอบปัญหา Slow Query ฉุกเฉินบน Production Server ที่ไม่มีหน้าจอ GUI คุณจะใช้คำสั่งและขั้นตอนใดใน `psql` เพื่อวิเคราะห์?**
  - *แนวคำตอบ:* 
    1. รันคำสั่ง `\timing` เพื่อเปิดระบบจับเวลา
    2. รันคำสั่งตรวจสอบการล็อกและคิวรีที่กำลังทำงานค้างอยู่ผ่านแค็ตตาล็อก:
       `SELECT pid, now() - query_start AS duration, query, state FROM pg_stat_activity WHERE state != 'idle' ORDER BY duration DESC;`
    3. เมื่อพบคิวรีต้องสงสัย ให้นำคิวรีนั้นมารันด้วย `EXPLAIN (ANALYZE, BUFFERS) <query>;` เพื่อดู Plan จริง เวลาที่ใช้ และจำนวน Shared Buffers Hit/Read บนดิสก์
    4. ใช้ `\d+ <table_name>` เพื่อตรวจสอบว่าคอลัมน์ในเงื่อนไข `WHERE` หรือ `JOIN` มี Index รองรับหรือไม่
