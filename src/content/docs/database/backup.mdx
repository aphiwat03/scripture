# Backup

ในโลกของวิศวกรรมซอฟต์แวร์ เซิร์ฟเวอร์สามารถพังได้ ดิสก์สามารถเสียได้ และมนุษย์สามารถเผลอรันคำสั่ง `DELETE` โดยลืมใส่ `WHERE` ได้ทุกเมื่อ สิ่งเดียวที่คั่นกลางระหว่าง "อุบัติเหตุทางเทคนิค" กับ "การปิดกิจการของบริษัท" คือระบบ **Database Backup & Disaster Recovery** ที่สามารถกู้คืนกลับมาใช้งานได้จริง เอกสารฉบับนี้เจาะลึกสถาปัตยกรรมการสำรองและกู้คืนข้อมูลบน **PostgreSQL 16** สำหรับระบบ **Smart Butcher Marketplace** ครอบคลุมตั้งแต่ระดับคำสั่ง CLI, การทำงานผ่าน Docker, แนวคิด Point-in-Time Recovery (PITR) ไปจนถึงการบริหารจัดการบนคลาวด์

| หัวข้อในหน้านี้ | สาระสำคัญ |
| :--- | :--- |
| **1. การทำ Backup และ Restore ด้วย pg_dump, pg_restore และ psql** | ความแตกต่างของรูปแบบไฟล์ `.sql` (Plain) กับ `.dump` (Custom Format `-Fc`) และการกู้คืนแบบขนาน |
| **2. การสำรองและกู้คืนข้อมูล PostgreSQL 16 ที่รันอยู่บน Docker Container** | การใช้ `docker exec` ร่วมกับ Pipe Stream และข้อควรระวังเรื่อง TTY Flags (`-i` vs `-it`) |
| **3. เปรียบเทียบ Logical Backup vs Physical Backup และแนวคิด PITR** | กลไก Write-Ahead Log (WAL) Archiving, `pg_basebackup`, ค่า RPO และ RTO |
| **4. กลยุทธ์ตั้งเวลา Backup อัตโนมัติ, การแยกพื้นที่จัดเก็บ และการซ้อมกู้คืนข้อมูล** | กฎ 3-2-1 Backup Rule, สคริปต์อัตโนมัติขึ้น S3/R2 และการทำ Restore Drill |
| **5. ระบบ Backup ของ Supabase และข้อจำกัดของแพ็กเกจ Free Tier** | นโยบายการสำรองข้อมูลแยกตามแพ็กเกจและวิธีการทำ Backup ด้วยตัวเองสำหรับ Free Tier |

<Callout type="warning" title="กฎเหล็กของวิศวกรฐานข้อมูล: Backup ที่ยังไม่เคยลอง Restore คือไม่มี Backup">
การตั้งเวลาให้สคริปต์รันสร้างไฟล์ `.dump` ทุกคืนไม่ได้แปลว่าคุณปลอดภัย จนกว่าคุณจะได้ทดลองนำไฟล์นั้นมากู้คืนลงฐานข้อมูลจำลองและเปิดดูข้อมูลในตาราง `orders` และ `payments` ว่ากลับมาครบถ้วนสมบูรณ์
</Callout>
