## 1. แนวคิด (Concept)
ลองนึกภาพว่าฐานข้อมูลของร้าน **Smart Butcher Marketplace** มีการสำรองข้อมูลด้วย `pg_dump` ทุกวันตอนเที่ยงคืน (`00:00 น.`)
แต่วันหนึ่งเวลา **`14:32:15 น.`** พนักงานดูแลระบบเผลอรันคำสั่ง `DELETE FROM order_items;` โดยลืมใส่เงื่อนไข `WHERE` ทำให้รายการเนื้อสเต๊กที่ลูกค้าสั่งซื้อเข้ามาตั้งแต่เที่ยงคืนจนถึงบ่ายสองครึ่งหายไปทั้งหมด!

หากเรามีแค่ไฟล์ `pg_dump` ตอนเที่ยงคืน เรากู้คืนกลับมาได้แค่ข้อมูลของเมื่อวาน แต่คำสั่งซื้อตลอด 14 ชั่วโมงครึ่งของวันนี้จะสูญหายไปตลอดกาล นี่คือเหตุผลที่ระบบระดับองค์กรต้องเข้าใจความแตกต่างระหว่าง **Logical Backup** กับ **Physical Backup** และต้องใช้เทคโนโลยีที่เรียกว่า **PITR (Point-in-Time Recovery)** เพื่อย้อนเวลากลับไปที่เวลา **`14:32:14 น.`** (1 วินาทีก่อนเกิดหายนะ) ได้อย่างแม่นยำ

## 2. หลักการเบื้องหลัง (Under the Hood)
1. **Logical Backup (`pg_dump` / `pg_dumpall`):**
   สกัดข้อมูลออกมาในระดับตรรกะ (ตาราง, แถว, คอลัมน์, โครงสร้าง SQL) เป็นภาพนิ่ง ณ จุดเวลาใดเวลาหนึ่ง (Point-in-Time Snapshot)
2. **Physical Backup (`pg_basebackup`) + WAL Archiving:**
   คัดลอกไฟล์ไบนารีระดับระบบไฟล์ของ PostgreSQL 16 ทั้งหมด (Base Backup) ควบคู่ไปกับการจัดเก็บไฟล์บันทึกการเปลี่ยนแปลงรายธุรกรรมที่เรียกว่า **WAL (Write-Ahead Log)** อย่างต่อเนื่อง:
   - ทุกครั้งที่มีการ `INSERT` คำสั่งซื้อเนื้อ หรือ `UPDATE` สถานะการจ่ายเงินในตาราง `payments` PostgreSQL 16 จะเขียนบันทึกเหตุการณ์นั้นลงในไฟล์ WAL ขนาดไฟล์ละ 16MB (ในโฟลเดอร์ `pg_wal`) ก่อนเสมอ
   - เมื่อเปิดโหมด `archive_mode = on` ทันทีที่ไฟล์ WAL เต็มหรือถึงเวลาที่กำหนด ระบบจะส่งไฟล์ WAL นั้นไปเก็บไว้ในคลังภายนอก (WAL Archive)
3. **กลไกการย้อนเวลาด้วย PITR (Point-in-Time Recovery):**
   เมื่อต้องการกู้คืนข้อมูลไปที่เวลา `14:32:14 น.` เราจะนำ **Physical Base Backup** ก้อนล่าสุดมาวางตั้งต้น แล้วสั่งให้ PostgreSQL 16 อ่านไฟล์ **WAL Archive** ไล่ทำซ้ำ (Replay) ทุกธุรกรรมตั้งแต่วินาทีที่ทำ Base Backup เรื่อยมา และหยุดการทำงานทันทีเมื่อถึงประทับเวลา `2026-10-17 14:32:14+07`!

```text filename="docs/database/backup.txt"
[ 00:00 น. Base Backup ] ══════► (บันทึก WAL Segments ต่อเนื่องทุกวินาที) ══════► [ 14:32:15 น. เผลอลบตาราง! ]
         │                                     │
         └──────────► นำ Base Backup + Replay WAL หยุดที่เวลา 14:32:14 น. ◄─────┘
                               (กู้คืนข้อมูลกลับมาได้ 100% ก่อนถูกลบ 1 วินาที)
```

### ตารางเปรียบเทียบ Logical Backup vs Physical Backup + PITR

| มิติการเปรียบเทียบ | Logical Backup (`pg_dump`) | Physical Backup (`pg_basebackup` + WAL PITR) |
| :--- | :--- | :--- |
| **ลักษณะข้อมูลที่เก็บ** | คำสั่ง SQL หรือโครงสร้างข้อมูลระดับตาราง (`.sql` / `.dump`) | สำเนาไฟล์ระบบฐานข้อมูลระดับไบนารี + ไฟล์บันทึกธุรกรรม WAL |
| **RPO (ข้อมูลที่ยอมให้หายได้)** | ขึ้นอยู่กับรอบการรัน (เช่น ถ้ารันวันละครั้ง ข้อมูลอาจหายได้สูงสุด 24 ชม.) | **ใกล้เคียงศูนย์ (วินาที)** สามารถย้อนกลับไปวินาทีใดก็ได้ |
| **RTO (เวลาที่ใช้ในการกู้คืน)** | ช้าเมื่อข้อมูลมีขนาดใหญ่ เพราะต้องรันคำสั่ง `INSERT/COPY` และสร้าง Index ใหม่ทั้งหมด | **เร็วมากสำหรับข้อมูลขนาดใหญ่** เพราะไฟล์ Data Page และ Index ถูกสร้างไว้พร้อมแล้ว แค่ Replay WAL เพิ่มเติม |
| **การเลือกกู้คืนบางตาราง** | ทำได้ง่ายมาก (`pg_restore -t orders`) | ทำโดยตรงไม่ได้ (ต้องกู้ทั้งคลัสเตอร์ขึ้นมาก่อนแล้วค่อยดึงตารางออก) |
| **การข้ามเวอร์ชันหลัก (Major Upgrade)** | ใช้ย้ายข้ามเวอร์ชันได้ (เช่น ดึงจาก PG 15 ไปใส่ PG 16) | ใช้ข้ามเวอร์ชันหลักไม่ได้ และต้องเป็นสถาปัตยกรรม OS/CPU เดียวกัน |

<Callout type="note" title="นิยามของ RPO และ RTO ที่วิศวกรต้องตอบได้ทันที">
RPO (Recovery Point Objective) คือ ปริมาณข้อมูลย้อนหลังมากที่สุดที่ธุรกิจยอมรับได้หากสูญหาย (วัดเป็นเวลา เช่น ไม่เกิน 5 นาที) ส่วน RTO (Recovery Time Objective) คือ ระยะเวลาสูงสุดที่ระบบสามารถล่มได้นับตั้งแต่เกิดเหตุจนกระทั่งกู้คืนกลับมาเปิดให้บริการได้อีกครั้ง (เช่น ต้องกู้เสร็จภายใน 30 นาที)
</Callout>

## 3. ตัวอย่างโค้ด (Smart Butcher Marketplace)

### ตัวอย่างที่ 1: การตั้งค่า `postgresql.conf` เพื่อเปิดใช้งาน WAL Archiving และการทำ `pg_basebackup`
การกำหนดค่าให้ PostgreSQL 16 ส่งไฟล์ WAL ออกไปเก็บสะสมไว้สำหรับทำ PITR:

```ini filename="postgresql.conf"
# 1. กำหนดระดับข้อมูลใน WAL ให้เพียงพอสำหรับการทำ Archiving และ Replication
wal_level = replica

# 2. เปิดโหมดส่งไฟล์ WAL ที่เขียนเต็มแล้วออกไปเก็บในคลังสำรอง
archive_mode = on

# 3. คำสั่งคัดลอกไฟล์ WAL (%p = พาธไฟล์ต้นทาง, %f = ชื่อไฟล์) ไปยังโฟลเดอร์ Archive (หรือส่งขึ้น S3 ด้วย pgBackRest / WAL-G)
archive_command = 'test ! -f /var/lib/postgresql/wal_archive/%f && cp %p /var/lib/postgresql/wal_archive/%f'

# 4. บังคับให้สลับไฟล์ WAL อย่างน้อยทุกๆ 5 นาที (300 วินาที) แม้มีคำสั่งซื้อน้อย เพื่อจำกัด RPO ไม่ให้เกิน 5 นาที
archive_timeout = 300
```

คำสั่งสร้าง Physical Base Backup ก้อนตั้งต้น:
```bash filename="run_basebackup.sh"
# สร้างสำเนาฐานข้อมูลระดับ Physical แบบบีบอัดด้วย zstd พร้อมตรวจสอบ Checksum ของ Data Pages
pg_basebackup -h localhost -p 5432 -U replication_user \
  -D /var/lib/postgresql/basebackups/backup_20261017 \
  -Ft --compress=server-zstd:5 --checkpoint=fast --progress
```

### ตัวอย่างที่ 2: การตั้งค่ากู้คืนย้อนเวลา (PITR) ไปยังวินาทีก่อนที่ตาราง `order_items` จะถูกลบ
ใน PostgreSQL 12 ขึ้นไปจนถึง PostgreSQL 16 (ที่ยกเลิกไฟล์ `recovery.conf` แบบเก่าแล้ว) เราใช้การสร้างไฟล์สัญญาณชื่อ **`recovery.signal`** คู่กับการระบุเวลาเป้าหมายใน `postgresql.auto.conf`:

```ini filename="postgresql.auto.conf"
# สั่งให้ PostgreSQL ดึงไฟล์ WAL จากคลังที่เราเก็บสะสมไว้มาทำซ้ำ (Replay)
restore_command = 'cp /var/lib/postgresql/wal_archive/%f %p'

# ระบุเวลาเป้าหมายที่ต้องการย้อนกลับไป (1 วินาทีก่อนที่พนักงานจะเผลอรันคำสั่ง DELETE ผิดเวลา 14:32:15)
recovery_target_time = '2026-10-17 14:32:14+07'

# เมื่อ Replay WAL มาถึงเวลาที่กำหนดแล้ว ให้ปรับสถานะฐานข้อมูลเป็นพร้อมใช้งาน (Read/Write) ทันที
recovery_target_action = 'promote'
```

```bash filename="trigger_pitr_recovery.sh"
# สร้างไฟล์สัญญาณบอกให้ PostgreSQL 16 เข้าสู่โหมด Point-in-Time Recovery ตอนเปิดเครื่อง
touch /var/lib/postgresql/data/recovery.signal

# เริ่มต้นโปรเซส PostgreSQL 16 เพื่อเริ่มกระบวนการย้อนเวลา
systemctl start postgresql@16-main
```

## 4. ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การพึ่งพา Backup เพียงรูปแบบเดียว** | ใช้เฉพาะ `pg_dump` วันละครั้งกับระบบการเงิน ทำให้ข้อมูลระหว่างวันมีความเสี่ยงสูงมาก | ผสมผสานทั้ง Physical Backup + WAL PITR (เพื่อ RPO ระดับวินาที) และ `pg_dump -Fc` รายวัน (เพื่อความคล่องตัว) |
| **การตั้งค่า `archive_command`** | เขียนสคริปต์คัดลอกไฟล์ทับของเดิมโดยไม่เช็คว่ามีไฟล์อยู่แล้วหรือไม่ และไม่คืนค่า Exit Code เมื่อพัง | ตรวจสอบก่อนเขียนทับและหากส่งไฟล์ขึ้น Cloud ไม่สำเร็จต้องคืนค่า Exit Code != 0 เพื่อให้ Postgres เก็บไฟล์ WAL นั้นไว้ส่งใหม่ |
| **การปล่อยให้ WAL เต็มดิสก์** | เปิด `archive_mode = on` แต่ปลายทางที่เก็บไฟล์พัง ทำให้ PostgreSQL ไม่กล้าลบไฟล์ WAL จนดิสก์เต็มและฐานข้อมูลล่ม | ตั้งระบบแจ้งเตือน (Monitoring Alert) ติดตามขนาดโฟลเดอร์ `pg_wal` และสถานะ `pg_stat_archiver` เสมอ |

## 5. ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Physical Backup + PITR เมื่อ:** ระบบเกี่ยวข้องกับคำสั่งซื้อและการชำระเงินจริงที่ไม่สามารถยอมให้ข้อมูลสูญหายระหว่างวันได้ หรือฐานข้อมูลมีขนาดใหญ่เกินกว่าที่ `pg_dump` จะกู้คืนได้ทันภายในเวลา RTO ที่กำหนด
- **ไม่ควรตั้งค่า WAL Archiving เองแบบดิบๆ ด้วยสคริปต์ `cp` บน Production ขนาดใหญ่:** แนะนำให้ใช้เครื่องมือมาตรฐานระดับ Enterprise อย่าง **pgBackRest** หรือ **WAL-G** มาจัดการเรื่องการบีบอัด เข้ารหัส และส่งไฟล์ขึ้น Object Storage แทน

## 6. คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: จงอธิบายความแตกต่างระหว่าง RPO และ RTO พร้อมยกตัวอย่างว่าหากธุรกิจกำหนด RPO = 5 นาที เราสามารถใช้ `pg_dump` ที่รันทุกเที่ยงคืนเพียงอย่างเดียวได้หรือไม่?**
  - **แนวคำตอบ:** RPO (Recovery Point Objective) คืออายุของข้อมูลที่ยอมให้สูญหายได้ย้อนหลังเมื่อเกิดเหตุ ส่วน RTO (Recovery Time Objective) คือระยะเวลาที่ใช้ในการกู้ระบบให้กลับมาทำงานได้ หากธุรกิจกำหนด RPO = 5 นาที เราไม่สามารถใช้ `pg_dump` ที่รันวันละครั้งได้ เพราะหากระบบพังตอน 23:50 น. ข้อมูลจะหายไปถึง 23 ชั่วโมง 50 นาที เราจึงต้องใช้ Continuous WAL Archiving (ควบคู่กับการตั้ง `archive_timeout = 300`) หรือ Streaming Replication เพื่อให้ข้อมูลสูญหายไม่เกิน 5 นาทีตามข้อกำหนด
- **Q2: ทำไมการกู้คืนด้วย Physical Backup (`pg_basebackup`) บนฐานข้อมูลขนาด 500 GB จึงใช้เวลา (RTO) เร็วกว่าการกู้คืนจากไฟล์ `pg_dump` อย่างมหาศาล?**
  - **แนวคำตอบ:** เพราะการกู้คืนจาก `pg_dump` ต้องให้ PostgreSQL ประมวลผลคำสั่งสร้างตาราง แปลงข้อมูลใส่ลงตารางทีละแถว และที่กินเวลามากที่สุดคือ **ต้องคำนวณและสร้าง B-Tree / GIN Index ใหม่ทั้งหมดตั้งแต่ต้น** ซึ่งใช้ CPU และ Disk I/O มหาศาล ในขณะที่ Physical Backup คือการคัดลอกไฟล์ Data Pages และไฟล์ Index ที่สร้างเสร็จเรียบร้อยแล้วมาวางลงดิสก์โดยตรง แล้วอ่านเฉพาะไฟล์ WAL ส่วนต่างเพิ่มเติมเท่านั้น
