# Connection Pooling

หนึ่งในสาเหตุอันดับต้นๆ ที่ทำให้ระบบที่ใช้ฐานข้อมูล **PostgreSQL 16** ล่มกลางอากาศเมื่อมีผู้ใช้งานหลั่งไหลเข้ามาพร้อมกัน (เช่น ช่วงจัดโปรโมชันลดราคาเนื้อวากิว Flash Sale) ไม่ใช่เพราะคิวรีช้าเสมอไป แต่เป็นเพราะ **"การเปิดการเชื่อมต่อ (Database Connections) เข้ามามากเกินไปจนหน่วยความจำและซีพียูของฐานข้อมูลหมดสภาพ"** เอกสารฉบับนี้เจาะลึกสถาปัตยกรรมระดับโปรเซสของ PostgreSQL, สูตรคำนวณขนาด Connection Pool มาตรฐานโลก, การตั้งค่า Prisma Client, สถาปัตยกรรม **PgBouncer** สำหรับระบบ Serverless ไปจนถึงการตรวจวินิจฉัยปัญหาด้วย `pg_stat_activity`

| หัวข้อในหน้านี้ | สาระสำคัญ |
| :--- | :--- |
| **1. ต้นทุนของการสร้าง Connection ใน PostgreSQL (Process-per-Connection)** | สถาปัตยกรรม `postmaster` `fork()` โปรเซสแยก, ต้นทุน RAM 5-10 MB ต่อสาย และขั้นตอน TCP + TLS + SCRAM Handshake |
| **2. กลไกการทำงานของ Connection Pool และสูตรคำนวณ Pool Size ที่เหมาะสม** | ทำไมการเพิ่ม Pool Size ถึงทำให้ฐานข้อมูลช้าลง (Context Switching) และสูตรคำนวณตามจำนวน CPU Cores |
| **3. ปัญหา Too Many Connections และการตั้งค่า Connection Limit ใน Prisma** | การคำนวณโควตาเมื่อขยายแอปหลาย Instances, พารามิเตอร์ `connection_limit` และรูปแบบ Singleton |
| **4. สถาปัตยกรรม PgBouncer (Session Mode vs Transaction Mode) และ Serverless** | การทำ Connection Multiplexing, ความต่างของพอร์ตและโหมดการทำงาน และการใช้ `?pgbouncer=true` |
| **5. การตรวจสอบและวิเคราะห์ Connection ที่เปิดใช้งานด้วย pg_stat_activity** | การตรวจจับ `idle in transaction`, การตั้งเวลาตัดสายอัตโนมัติ และการสั่ง `pg_terminate_backend()` |

<Callout type="tip" title="ความจริงที่สวนทางกับความรู้สึกของนักพัฒนา (Counter-Intuitive Truth)">
สำหรับเซิร์ฟเวอร์ PostgreSQL 16 ที่มีซีพียู 4 Cores การเปิด Connection วิ่งทำงานพร้อมกันเพียง **9 ถึง 10 Connections** จะสามารถประมวลผลคำสั่งซื้อต่อวินาที (Throughput/TPS) ได้เร็วกว่าการปล่อยให้เปิดเข้ามาพร้อมกัน 500 Connections อย่างเทียบไม่ติด!
</Callout>

## 1. ต้นทุนของการสร้าง Connection ใน PostgreSQL (Process-per-Connection)

### แนวคิด (Concept)
หากเปรียบเซิร์ฟเวอร์ฐานข้อมูลเป็นห้องครัวตัดแต่งเนื้อของ **Smart Butcher Marketplace**:
- การสร้าง Connection ใหม่เข้าหา PostgreSQL ทุกครั้งที่มีลูกค้ากดดูหน้าเว็บ เปรียบเสมือน **"ทุกครั้งที่มีลูกค้าเดินเข้าร้าน 1 คน เราต้องโทรศัพท์เรียกเชฟคนใหม่เดินทางมาจากบ้าน ตรวจบัตรประชาชน เปลี่ยนชุดยูนิฟอร์ม ล้างมือ แล้วหั่นเนื้อให้ลูกค้าแค่ 1 ชิ้น จากนั้นไล่เชฟคนนั้นกลับบ้านทันที!"**
- เมื่อมีลูกค้าเข้าร้านพร้อมกัน 500 คน เราจะเสียเวลาไปกับการตรวจบัตรและเปลี่ยนชุดเชฟจนหมดวัน และห้องครัวก็จะอัดแน่นไปด้วยเชฟ 500 คนที่เบียดเสียดแย่งเขียงกันจนไม่มีใครหั่นเนื้อได้เลย

ตรงกันข้ามกับ MySQL ที่ใช้โมเดล Thread-based (ใช้เธรดเบาๆ ภายในโปรเซสเดียว) **PostgreSQL 16 ใช้สถาปัตยกรรมแบบ Process-per-Connection** ซึ่งให้ความเสถียรและการแยกส่วนความจำที่ปลอดภัยสูงสุด (หากโปรเซสของลูกค้าคนหนึ่งเกิด Crash โปรเซสของลูกค้าคนอื่นจะไม่ล่มตาม) แต่แลกมาด้วยต้นทุนในการสร้างและถือครองแต่ละ Connection ที่สูงมาก

### หลักการเบื้องหลัง (Under the Hood)
ทุกครั้งที่แอปพลิเคชันสั่งเปิดการเชื่อมต่อใหม่ (`new Connection`) ไปยัง PostgreSQL 16 จะเกิดขั้นตอนที่กินเวลาและทรัพยากรถึง 4 ด่าน:
1. **TCP 3-Way Handshake (1 RTT):** สร้างการเชื่อมต่อระดับเครือข่าย (`SYN`, `SYN-ACK`, `ACK`)
2. **TLS/SSL Handshake (1-2 RTTs):** แลกเปลี่ยนกุญแจเข้ารหัสและตรวจสอบใบรับรองความปลอดภัย
3. **Postmaster Process Forking (`fork()`):** โปรเซสแม่ของ PostgreSQL (`postmaster`) จะสั่งระบบปฏิบัติการ Linux ให้ทำการ `fork()` สร้าง **OS Process ใหม่แยกออกมา 1 ตัวเต็มๆ (`postgres` backend process)** สำหรับการเชื่อมต่อนี้โดยเฉพาะ ซึ่งแต่ละโปรเซสจะจองหน่วยความจำส่วนตัว (Private Memory เช่น `work_mem`, Catalog Cache, Prepared Statement Cache) เฉลี่ย **5 MB ถึง 10 MB ต่อ 1 Connection** ทันที!
4. **SCRAM-SHA-256 Authentication (2 RTTs):** คำนวณแฮชยืนยันตัวตนหลายพันรอบเพื่อตรวจสอบรหัสผ่าน

รวมเวลาในการเปิดการเชื่อมต่อใหม่ 1 ครั้งอาจสูงถึง **30 - 150 มิลลิวินาที** ทั้งที่ตัวคำสั่ง SQL `SELECT * FROM products WHERE id = $1` ใช้เวลาทำงานจริงเพียง **0.5 มิลลิวินาที** เท่านั้น!

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: เปรียบเทียบโค้ดที่สร้าง Connection ใหม่ทุก Request (อันตราย) กับการใช้ Connection Pool
การใช้ไดรเวอร์ `pg` ใน Node.js เพื่อแสดงให้เห็นความต่างระหว่างการเปิด-ปิดสายใหม่ทุกครั้ง กับการยืมสายที่เปิดค้างไว้แล้วจาก Pool:

```typescript filename="src/database/raw-connection-comparison.ts"
import { Client, Pool } from 'pg';

// ❌ อันตรายร้ายแรง: เปิดและปิด OS Process ใหม่ใน PostgreSQL ทุกครั้งที่ลูกค้าขอดูราคาเนื้อ!
// หากมีคนเข้าพร้อมกัน 200 คน เซิร์ฟเวอร์จะเสียเวลาทำ TCP+TLS+Fork จน CPU พุ่ง 100%
export async function getProductPriceAntiPattern(productId: string) {
  const client = new Client({ connectionString: process.env.DATABASE_URL });
  await client.connect(); // <-- เสียเวลา 50-100ms ตรงนี้ทุกครั้ง!
  try {
    const res = await client.query(
      'SELECT id, name, price_per_kg FROM products WHERE id = $1',
      [productId]
    );
    return res.rows[0];
  } finally {
    await client.end(); // <-- สั่งทำลายโปรเซสใน Postgres ทิ้ง
  }
}

// ✅ Best Practice: สร้าง Pool เพียงครั้งเดียวตอนเปิดเซิร์ฟเวอร์ แล้วนำ Connection เดิมมาหมุนเวียนใช้ซ้ำ
const sharedPool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10, // เปิดโปรเซสค้างไว้สูงสุดแค่ 10 ตัว
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000,
});

export async function getProductPriceWithPool(productId: string) {
  // ยืม Connection ที่ทำ Handshake เสร็จพร้อมใช้งานอยู่แล้วในหน่วยความจำ (ใช้เวลา 0ms!)
  const res = await sharedPool.query(
    'SELECT id, name, price_per_kg FROM products WHERE id = $1',
    [productId]
  );
  return res.rows[0];
}
```

#### ตัวอย่างที่ 2: การวัดปริมาณหน่วยความจำและตรวจสอบ OS Process ของแต่ละ Connection ใน PostgreSQL 16
เราสามารถรันคิวรีใน PostgreSQL 16 เพื่อดูหมายเลขโปรเซสของระบบปฏิบัติการ (`PID`) และตรวจสอบการตั้งค่าหน่วยความจำต่อโปรเซสได้โดยตรง:

```sql filename="inspect_backend_processes.sql"
-- 1. ตรวจสอบค่าหน่วยความจำที่แต่ละ Connection สามารถจองใช้ได้และเพดานการเชื่อมต่อสูงสุด
SELECT name, setting, unit, short_desc
FROM pg_settings
WHERE name IN ('max_connections', 'superuser_reserved_connections', 'work_mem', 'shared_buffers');

-- 2. แสดงรายการ OS Process ID (pid) ที่ถูก fork() ออกมารับใช้แต่ละการเชื่อมต่อของร้าน Smart Butcher
SELECT
    pid AS os_process_id,
    usename AS db_role,
    application_name,
    client_addr,
    backend_start,
    state
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY backend_start DESC;
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **วงจรชีวิตของ Connection** | เปิด Connection ใหม่ในทุกฟังก์ชัน HTTP Handler แล้วสั่งปิดเมื่อจบฟังก์ชัน | เปิด Connection Pool ทิ้งไว้ตั้งแต่เริ่มรันเซิร์ฟเวอร์ และนำกลับมาใช้ซ้ำ (Reuse) ตลอดอายุการทำงาน |
| **การตั้งค่า `max_connections`** | ตั้งค่า `max_connections = 2000` ใน `postgresql.conf` โดยคิดว่ายิ่งเยอะยิ่งดี จน RAM หมดเครื่อง (OOM Kill) | ตั้งค่า `max_connections` บน PostgreSQL ให้อยู่ในระดับพอเหมาะ (เช่น 100 - 300) แล้วใช้ Pooler คั่นข้างหน้า |
| **การจัดการ `work_mem`** | ตั้ง `work_mem = 256MB` พร้อมเปิดรับ 500 Connections ทำให้เสี่ยงกิน RAM สูงถึง `256MB * 500 = 128GB` | คำนวณ `work_mem` ให้สอดคล้องกับจำนวน Active Connections สูงสุดที่ทำงานพร้อมกันจริง |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Connection Pooling เสมอเมื่อ:** พัฒนาเว็บแอปพลิเคชัน, API Server หรือระบบใดๆ ที่มีการเรียกใช้ฐานข้อมูลซ้ำๆ ต่อเนื่องกัน
- **ไม่ควรใช้การต่อตรงแบบไร้ Pool เมื่อ:** ระบบรับโหลดจากผู้ใช้งานจริงบน Production (ยกเว้นสคริปต์ CLI เฉพาะกิจที่รันคำสั่งเดียวแล้วจบการทำงาน เช่น สคริปต์ `pg_dump` หรือ `prisma migrate deploy`)

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: จงอธิบายสถาปัตยกรรม Process-per-Connection ของ PostgreSQL และอธิบายว่าทำไมมันจึงมีต้นทุนสูงกว่าการเชื่อมต่อในฐานข้อมูลแบบ Thread-based?**
  - **แนวคำตอบ:** ใน PostgreSQL ทุกครั้งที่มี Client เชื่อมต่อเข้ามาสำเร็จ โปรเซสหลัก (`postmaster`) จะทำการ `fork()` สร้าง OS Process ใหม่ขึ้นมา 1 ตัวต่อ 1 การเชื่อมต่อ ซึ่งแต่ละโปรเซสมีการจัดสรรหน่วยความจำแยกของตัวเองราว 5-10 MB และเมื่อมีโปรเซสจำนวนมากทำงานพร้อมกัน ระบบปฏิบัติการจะมีภาระสูงในการสลับโปรเซส (OS Process Context Switching) และจัดการ Page Tables ซึ่งหนักกว่าการสลับ Thread เบาๆ ที่แชร์พื้นที่หน่วยความจำเดียวกัน
- **Q2: นอกจากเรื่องการ `fork()` โปรเซสแล้ว การเปิด Connection ใหม่ทุกครั้งที่ยิงคิวรีทำให้เกิดความหน่วง (Latency) ในระดับเครือข่ายอย่างไรบ้าง?**
  - **แนวคำตอบ:** ต้องเสียเวลาเดินทางไป-กลับผ่านเครือข่าย (Network Round-Trip Time - RTT) อย่างน้อย 3-4 รอบก่อนจะได้เริ่มส่งคำสั่ง SQL ได้แก่: (1) TCP 3-Way Handshake, (2) TLS Encryption Handshake และ (3) การแลกเปลี่ยนข้อความยืนยันตัวตนแบบ SCRAM-SHA-256 ซึ่งหากฐานข้อมูลอยู่ต่างโซน เวลาในการเชื่อมต่ออาจนานกว่าเวลาในการรันคิวรีจริงถึง 50 เท่า

## 2. กลไกการทำงานของ Connection Pool และสูตรคำนวณ Pool Size ที่เหมาะสม

### แนวคิด (Concept)
เมื่อใช้ **Connection Pool** แอปพลิเคชันจะทำการเปิดการเชื่อมต่อจริงไปยัง PostgreSQL 16 ค้างไว้ล่วงหน้าจำนวนหนึ่ง (เช่น 10 สาย) เปรียบเสมือน **"การจ้างเชฟประจำ 10 คนมายืนสแตนด์บายพร้อมหั่นเนื้ออยู่ที่เขียงตลอดเวลา"**
1. เมื่อคำสั่งซื้อของลูกค้าคนที่ 1 เข้ามา แอปพลิเคชันจะหยิบเชฟที่ว่างอยู่ (Borrow Connection) ไปรันคิวรีใช้เวลาเพียง **2 มิลลิวินาที**
2. ทันทีที่คิวรีเสร็จ แอปพลิเคชันจะไม่ไล่เชฟกลับบ้าน แต่จะคืนเชฟคนนั้นกลับเข้าแถวสแตนด์บาย (Return to Pool) เพื่อรับออเดอร์ของลูกค้าคนที่ 2 ต่อในเสี้ยววินาทีถัดไป!
3. หากมีลูกค้ากดสั่งเนื้อพร้อมกัน 50 คนในเสี้ยววินาทีเดียวกัน 10 คนแรกจะได้ใช้เชฟทันที ส่วนอีก 40 คนจะเข้าแถวรอคิวอยู่ในหน่วยความจำ (Pool Queue) ซึ่งเนื่องจากคิวรีใช้เวลาแค่ 2 มิลลิวินาที คนที่ 50 จึงรอคิวเพียงแค่ **10 มิลลิวินาที** ก็ได้รับบริการจนเสร็จสิ้น!

### หลักการเบื้องหลัง (Under the Hood)
ทำไมเราไม่ควรตั้งค่า Pool Size ให้สูงถึง 200 หรือ 500 ต่อเซิร์ฟเวอร์ที่มี CPU เพียง 4 Cores?
- **CPU Context Switching & Disk I/O Contention:** ซีพียู 1 Core สามารถรันคำสั่งได้ทีละ 1 โปรเซสในเวลาเดียวกันเท่านั้น (หากไม่นับการรอดิสก์) หากเรามี 4 CPU Cores แต่ส่งคิวรีเข้าไปพร้อมกัน 200 โปรเซส ระบบปฏิบัติการ Linux จะต้องสั่งหยุดโปรเซสที่ 1 กลางคันเพื่อสลับให้โปรเซสที่ 2 เข้ามาใช้ซีพียู (Context Switch) สลับไปมาวินาทีละหลายหมื่นครั้ง เสียเวลาไปกับการล้าง CPU L1/L2 Cache และการแย่งชิง Spinlock/LWLock ใน Shared Buffers ของ PostgreSQL จนประสิทธิภาพรวมดิ่งลงเหว
- **สูตรคำนวณขนาด Pool มาตรฐานโลก (PostgreSQL / HikariCP Formula):**
  ได้รับการพิสูจน์ทางคณิตศาสตร์และผลการทดสอบจริงบน PostgreSQL ว่า จำนวนการเชื่อมต่อที่ทำงานพร้อมกันแล้วได้ Throughput สูงสุดคำนวณจาก:

$$\text{Optimal Pool Size} = (\text{CPU Cores} \times 2) + \text{Effective Spindle Count}$$

สำหรับเซิร์ฟเวอร์คลาวด์ยุคใหม่ที่ใช้ดิสก์ SSD / NVMe ค่าตัวบวกท้ายสุดมักกำหนดไว้ที่ `1` ถึง `2` (หรือใช้สูตรของ Prisma คือ `(CPU Cores * 2) + 1`):
- เครื่องฐานข้อมูล **2 vCPUs:** ขนาด Pool รวมที่เหมาะสมคือ $(2 \times 2) + 1 = \mathbf{5\text{ Connections}}$
- เครื่องฐานข้อมูล **4 vCPUs:** ขนาด Pool รวมที่เหมาะสมคือ $(4 \times 2) + 1 = \mathbf{9\text{ ถึง }10\text{ Connections}}$
- เครื่องฐานข้อมูล **8 vCPUs:** ขนาด Pool รวมที่เหมาะสมคือ $(8 \times 2) + 1 = \mathbf{17\text{ ถึง }20\text{ Connections}}$

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: เครื่องคำนวณและจัดสรรโควตา Connection Pool สำหรับคลัสเตอร์ของ Smart Butcher
ฟังก์ชันช่วยคำนวณขนาด Pool ที่เหมาะสมต่อ 1 Application Instance เมื่อทราบสเปกของเซิร์ฟเวอร์ฐานข้อมูลและจำนวน Container ที่รันอยู่:

```typescript filename="src/config/pool-sizing.calculator.ts"
export interface PoolSizingInput {
  dbCpuCores: number;
  maxDbConnectionsLimit: number; // ค่า max_connections ใน postgresql.conf (เช่น 100)
  reservedForAdminAndMigrations: number; // กันไว้ให้แอดมินและ CI/CD (เช่น 10)
  appInstanceCount: number; // จำนวน Pods / Containers ของ NestJS ที่รันอยู่ (เช่น 4)
}

export function calculateOptimalPrismaPoolSize(input: PoolSizingInput) {
  // 1. คำนวณจุดที่ CPU ของฐานข้อมูลทำงานได้มีประสิทธิภาพสูงสุดตามสูตร (Cores * 2) + 1
  const cpuOptimalTotal = input.dbCpuCores * 2 + 1;

  // 2. คำนวณเพดานปลอดภัยสูงสุดที่ไม่ทำให้เกิด Too Many Connections (ใช้ไม่เกิน 80% ของที่เหลือ)
  const safeMaxTotal = Math.floor(
    (input.maxDbConnectionsLimit - input.reservedForAdminAndMigrations) * 0.8
  );

  // 3. แบ่งโควตาให้แต่ละ Application Instance เท่าๆ กัน
  const recommendedPerInstance = Math.max(
    2,
    Math.floor(Math.min(cpuOptimalTotal * 2, safeMaxTotal) / input.appInstanceCount)
  );

  return {
    cpuOptimalTotalConnections: cpuOptimalTotal,
    safeMaxTotalConnections: safeMaxTotal,
    recommendedConnectionLimitPerInstance: recommendedPerInstance,
    recommendedPoolTimeoutSeconds: 10,
  };
}

// ตัวอย่างการใช้งานสำหรับระบบ Smart Butcher (DB 4 vCPUs, max_connections=100, รันแอป 4 Containers)
const sizing = calculateOptimalPrismaPoolSize({
  dbCpuCores: 4,
  maxDbConnectionsLimit: 100,
  reservedForAdminAndMigrations: 15,
  appInstanceCount: 4,
});
// ผลลัพธ์แนะนำ: connection_limit = 4 ถึง 5 ต่อ Container (รวม 4 Containers = 16-20 Connections)
```

#### ตัวอย่างที่ 2: การควบคุมเวลาทำงานของคิวรีเพื่อหมุนเวียน Connection กลับเข้า Pool ให้เร็วที่สุด
เพื่อให้ Pool ขนาดเล็ก (เช่น 10 Connections) สามารถรองรับผู้ใช้งานได้หลักพันคนต่อวินาที กฎสำคัญคือ **"ห้ามมีโปรเซสไหนยึด Connection ไว้กับตัวนานเกินไป"** เราจึงควรตั้งค่า `statement_timeout` และเขียนคิวรีให้กระชับ:

```typescript filename="src/orders/fast-checkout.service.ts"
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';

@Injectable()
export class FastCheckoutService {
  constructor(private readonly prisma: PrismaService) {}

  async createMeatOrderFast(userId: string, productId: string, quantityGrams: number) {
    // ✅ เตรียมข้อมูลและคำนวณนอก Transaction / นอกการถือครอง Connection ก่อนเสมอ!
    const orderReference = `SB-${Date.now()}`;

    // ✅ เปิด Transaction ยืม Connection จาก Pool เฉพาะจังหวะที่ยิงคำสั่ง SQL จริงเท่านั้น
    // และกำหนด timeout ไม่ให้ถือครอง Connection เกิน 3 วินาที
    return this.prisma.$transaction(
      async (tx) => {
        const product = await tx.product.update({
          where: { id: productId, stockWeightGr: { gte: quantityGrams } },
          data: { stockWeightGr: { decrement: quantityGrams } },
          select: { id: true, pricePerKg: true },
        });

        const subtotal = product.pricePerKg.mul(quantityGrams).div(1000);

        return tx.order.create({
          data: {
            userId,
            status: 'PENDING',
            totalAmount: subtotal,
            items: {
              create: {
                productId: product.id,
                quantityGrams,
                unitPricePerKg: product.pricePerKg,
                subtotal,
              },
            },
          },
        });
      },
      {
        maxWait: 2000, // รอคิวจาก Pool ไม่เกิน 2 วินาที
        timeout: 3000, // ห้ามยึด Connection ทำงานนานเกิน 3 วินาที
      }
    );
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การแก้ปัญหาเมื่อเว็บช้า** | พอเว็บช้าก็ปรับเพิ่ม Pool Size จาก 10 เป็น 200 ทันที ทำให้ฐานข้อมูลเกิด Context Switching จนล่มหนักกว่าเดิม | ตรวจสอบและใส่ Index ให้คิวรีทำงานจบในระดับมิลลิวินาที เพื่อคืน Connection กลับเข้า Pool ให้ไวที่สุด |
| **การทำงานภายนอกใน Transaction** | ยืม Connection มาเปิด `$transaction` แล้วสั่ง `await sendEmail()` หรือเรียก API ธนาคารข้างใน ทำให้ยึดสายค้างไว้ | ย้ายการเรียก API ภายนอกและการส่งอีเมลออกไปทำ **นอกบล็อก `$transaction`** ทั้งหมด |
| **การกำหนด Timeout ของ Pool** | ปล่อยให้คิวรอ Connection ไม่มีกำหนดเวลา จนเกิดปรากฏการณ์ Cascading Failure ล่มทั้งระบบ | กำหนด `pool_timeout` (เช่น 10 วินาที) เพื่อให้ Fail Fast หากฐานข้อมูลมีปัญหา |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้สูตร `(CPU Cores * 2) + 1` เมื่อ:** แอปพลิเคชันเชื่อมต่อตรงเข้าสู่ PostgreSQL 16 หรือใช้ในการกำหนดค่า `default_pool_size` ของ PgBouncer ที่ส่งต่อไปหาฐานข้อมูลจริง
- **ไม่ควรตั้งค่า Pool Size สูงเกินกว่าจำนวนคอร์ซีพียูมากๆ:** เว้นแต่จะมี Connection Pooler ตัวกลางอย่าง PgBouncer คอยทำหน้าที่รับหน้าเสื่อจัดคิวให้ก่อนเข้าถึงตัว PostgreSQL

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ทำไมการตั้งค่า Connection Pool ขนาดเล็ก (เช่น 10-20 Connections) บนฐานข้อมูลที่มี 4 CPU Cores จึงให้ผลลัพธ์จำนวนธุรกรรมต่อวินาที (TPS) สูงกว่าการตั้งค่าไว้ที่ 200 Connections?**
  - **แนวคำตอบ:** เพราะซีพียู 4 Cores สามารถประมวลผลคำสั่งพร้อมกันได้จริงๆ เพียง 4 เธรดในเสี้ยววินาทีเดียวกัน หากปล่อยให้โปรเซสทำงานพร้อมกันถึง 200 ตัว ระบบปฏิบัติการจะต้องเสียเวลา CPU Cycles มหาศาลไปกับการทำ Context Switching สลับโปรเซสเข้าออก ล้าง CPU Cache และเกิดการแย่งชิง Lock ภายในหน่วยความจำของ PostgreSQL การจำกัดให้มีเฉพาะโปรเซสจำนวนน้อยที่วิ่งงานจนจบอย่างรวดเร็วโดยไม่ถูกขัดจังหวะ แล้วรับคิวถัดไปเข้ามาทำต่อ จึงทำงานเสร็จเร็วกว่ามาก
- **Q2: หากขนาดของ Connection Pool ถูกจำกัดไว้แค่ 10 Connections แล้วถ้ามีลูกค้ากดสั่งซื้อเนื้อพร้อมกัน 100 คนในวินาทีเดียวกัน อีก 90 คนที่เหลือจะเกิด Error ทันทีหรือไม่?**
  - **แนวคำตอบ:** ไม่เกิด Error ทันที เพราะ Connection Pool มีกลไก **In-Memory Request Queue (คิวรอรับสาย)** คำขออีก 90 รายการจะเข้าแถวรออยู่ในหน่วยความจำของแอปพลิเคชัน หากคิวรีสั่งซื้อใช้เวลาทำงานเพียงรายการละ 3 มิลลิวินาที สายทั้ง 10 สายจะช่วยกันระบายคิวทั้ง 100 รายการเสร็จสิ้นภายในเวลาเพียง `10 รอบ × 3 ms = 30 มิลลิวินาที` เท่านั้น โดยจะเกิด Error (`P2024 Timed out fetching a new connection from the connection pool`) ก็ต่อเมื่อรอคิวนานเกินค่า `pool_timeout` ที่ตั้งไว้ (ค่าเริ่มต้นคือ 10 วินาที)

## 3. ปัญหา Too Many Connections และการตั้งค่า Connection Limit ใน Prisma

### แนวคิด (Concept)
ค่าเริ่มต้นของ PostgreSQL 16 กำหนดเพดานการเชื่อมต่อสูงสุดไว้ที่ **`max_connections = 100`** (และกันไว้ให้ Superuser 3 สาย เหลือให้ใช้งานจริง **97 สาย**)
ลองดูสิ่งที่มักเกิดขึ้นในสถาปัตยกรรมยุคใหม่ของร้าน **Smart Butcher Marketplace**:
- เราตั้งค่า `connection_limit = 20` ใน Prisma Client
- วันปกติ เรารันเซิร์ฟเวอร์ Backend ไว้แค่ **2 Containers** -> ใช้สายรวมกัน $2 \times 20 = 40\text{ สาย}$ (ระบบทำงานปกติสุข)
- วันจัดโปรโมชันใหญ่ ระบบ Auto-scaling ขยาย Backend ออกเป็น **8 Containers**!
- ทันใดนั้น 8 Containers พยายามเปิดสายรวมกัน $8 \times 20 = \mathbf{160\text{ สาย}}$ ซึ่งทะลุเพดาน 97 สายของ PostgreSQL 16 ทันที!
- ผลลัพธ์คือ Containers ตัวใหม่ๆ จะพังด้วยข้อผิดพลาด **`FATAL: sorry, too many clients already (SQLSTATE 53300)`**

นอกจากนี้ ในโหมดการพัฒนาด้วย Next.js หรือ NestJS หากไม่ได้สร้าง `PrismaClient` ในรูปแบบ **Singleton Pattern** ทุกครั้งที่เราแก้โค้ดแล้วเซฟ (Hot Module Replacement - HMR) ระบบจะสร้าง `new PrismaClient()` ตัวใหม่ขึ้นมาเรื่อยๆ โดยไม่ปิดตัวเก่า จนสายเต็ม 100 สายภายในไม่กี่นาที!

### หลักการเบื้องหลัง (Under the Hood)
1. **สถาปัตยกรรม Connection Pool ภายใน Prisma Engine:**
   ตัว `PrismaClient` แต่ละอินสแตนซ์จะมี Connection Pool ของตัวเองฝังอยู่ใน Query Engine โดยควบคุมผ่านพารามิเตอร์ใน Query String ของ `DATABASE_URL` ได้แก่:
   - `connection_limit`: จำนวนการเชื่อมต่อสูงสุดที่อินสแตนซ์นี้จะเปิดไปยังฐานข้อมูล (หากไม่ระบุ Prisma จะคำนวณจากจำนวนคอร์ของเครื่องที่รันแอปพลิเคชันตามสูตร `num_physical_cpus * 2 + 1`)
   - `pool_timeout`: จำนวนวินาทีสูงสุดที่คิวรีจะยอมเข้าแถวรอรับ Connection ที่ว่างจาก Pool (ค่าเริ่มต้นคือ `10` วินาที หากเกินเวลานี้จะโยน Error `P2024`)
   - `connect_timeout`: จำนวนวินาทีสูงสุดในการพยายามเชื่อมต่อระดับ TCP ครั้งแรก (ค่าเริ่มต้นคือ `5` วินาที)
2. **การรั่วไหลของ Connection จากการสร้าง `new PrismaClient()` ซ้ำซ้อน:**
   เนื่องจากแต่ละอินสแตนซ์ของ `PrismaClient` ถือครอง Pool แยกของตัวเอง หากนักพัฒนาเผลอเขียน `const prisma = new PrismaClient()` ไว้ภายในฟังก์ชัน Controller หรือถูกเรียกซ้ำจากการทำ Hot Reload ในโหมด Development อินสแตนซ์เก่าจะยังคงถือสาย TCP ค้างไว้กับ PostgreSQL จนกว่าจะเต็มเพดาน

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การตั้งค่า `connection_limit` และ `pool_timeout` ใน `DATABASE_URL` และการทำ Global Singleton
รูปแบบการประกาศ `PrismaClient` มาตรฐาน Production ที่ป้องกันปัญหา Connection รั่วไหลทั้งในโหมด Development (Hot Reload) และ Production:

```ini filename=".env"
# กำหนดเพดานการเชื่อมต่อต่อ 1 Container ไว้อย่างชัดเจน (เช่น 10 สาย) และเวลารอคิวสูงสุด 10 วินาที
DATABASE_URL="postgresql://butcher_app:SecretPass@db.smartbutcher.internal:5432/smart_butcher_db?schema=public&connection_limit=10&pool_timeout=10&connect_timeout=5"
```

```typescript filename="src/lib/prisma-singleton.ts"
import { PrismaClient } from '@prisma/client';

// ประกาศ Type บน globalThis เพื่อเก็บอินสแตนซ์เดียวของ PrismaClient ข้ามรอบการทำ Hot Reload
const globalForPrisma = globalThis as unknown as {
  prismaInstance: PrismaClient | undefined;
};

export const prisma =
  globalForPrisma.prismaInstance ??
  new PrismaClient({
    log:
      process.env.NODE_ENV === 'development'
        ? ['query', 'warn', 'error']
        : ['error'],
  });

// ในโหมดที่ไม่ใช่ Production ให้ผูกอินสแตนซ์ไว้กับ globalThis เสมอเพื่อป้องกันการสร้าง Pool ซ้ำซ้อน
if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prismaInstance = prisma;
}
```

#### ตัวอย่างที่ 2: การจัดการ Lifecycle และการคืน Connection อย่างสะอาดใน NestJS (`PrismaService`)
ในเฟรมเวิร์ก NestJS เราใช้ `@Injectable()` คู่กับ `OnModuleInit` และ `OnModuleDestroy` (พร้อมเปิด `app.enableShutdownHooks()`) เพื่อรับประกันว่าเมื่อ Container ถูกสั่งปิดหรือรีสตาร์ทตอน Deploy ระบบจะสั่ง `await this.$disconnect()` เพื่อคืนสายให้ PostgreSQL 16 ทันทีโดยไม่ทิ้งสายผีดิบ (`Zombie Connections`) ค้างไว้:

```typescript filename="src/prisma/prisma.service.ts"
import { Injectable, OnModuleInit, OnModuleDestroy, Logger } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  private readonly logger = new Logger(PrismaService.name);

  constructor() {
    super({
      log: ['warn', 'error'],
    });
  }

  async onModuleInit() {
    await this.$connect();
    this.logger.log('✅ Connected to Smart Butcher PostgreSQL 16 Pool successfully.');
  }

  async onModuleDestroy() {
    this.logger.log('🔌 Gracefully disconnecting Prisma Pool from PostgreSQL 16...');
    await this.$disconnect();
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การสร้างอินสแตนซ์ Prisma** | เรียก `new PrismaClient()` ภายในฟังก์ชัน API Route หรือสร้างหลายอินสแตนซ์ในโปรเจกต์เดียว | สร้าง `PrismaClient` แบบ **Global Singleton** เพียงตัวเดียวตลอดทั้งแอปพลิเคชัน |
| **การคำนวณโควตาตอน Auto-scale** | ตั้ง `connection_limit=30` แล้วปล่อยให้ Kubernetes ขยายเป็น 10 Pods ($30 \times 10 = 300 > 100$) | คำนวณให้ `(จำนวน Pods สูงสุด × connection_limit) + สายสำรอง < max_connections` เสมอ หรือใช้ PgBouncer |
| **การปิด Container ตอน Deploy** | สั่ง Kill โปรเซสแอปพลิเคชันทันทีโดยไม่เรียก `$disconnect()` ทำให้สายค้างใน Postgres นานหลายนาที | ดักจับสัญญาณ `SIGTERM` / `OnModuleDestroy` เพื่อเรียก `await prisma.$disconnect()` อย่างสะอาด |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรตั้งค่า `connection_limit` ใน URL ด้วยตัวเองเมื่อ:** รันแอปพลิเคชันหลาย Instances (Horizontal Scaling) เพื่อควบคุมจำนวนสายรวมไม่ให้เกินเพดานของฐานข้อมูล
- **ไม่ควรพึ่งพาเพียง Connection Pool ภายใน Prisma เพียงลำพังเมื่อ:** รันแอปพลิเคชันในรูปแบบ **Serverless Functions (เช่น Vercel Functions, AWS Lambda)** หรือมีจำนวน Containers หลายสิบตัว ในกรณีนั้นต้องติดตั้ง External Connection Pooler อย่าง **PgBouncer** หรือ **Supavisor** คั่นกลางเสมอ

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ทำไมในขณะพัฒนาเว็บด้วย Next.js บนเครื่องตัวเอง นักพัฒนาจึงมักเจอปัญหา `FATAL: sorry, too many clients already` หลังจากกดเซฟไฟล์โค้ดไปได้สักพัก และมีวิธีแก้อย่างไร?**
  - **แนวคำตอบ:** เพราะฟีเจอร์ Fast Refresh / Hot Module Replacement (HMR) ของ Next.js จะทำการรันไฟล์โมดูลใหม่ทุกครั้งที่มีการแก้ไขและบันทึกโค้ด หากเราเขียน `export const prisma = new PrismaClient()` แบบปกติ ทุกครั้งที่กดเซฟจะมีการสร้าง `PrismaClient` อินสแตนซ์ใหม่พร้อมเปิด Connection Pool ชุดใหม่เพิ่มเข้าไปเรื่อยๆ โดยที่อินสแตนซ์เก่าไม่ถูกปิด วิธีแก้คือต้องเก็บอินสแตนซ์ไว้ในตัวแปรระดับโกลบอล (`globalThis.prisma`) เพื่อให้การโหลดโมดูลซ้ำหยิบอินสแตนซ์เดิมมาใช้งาน
- **Q2: รหัสข้อผิดพลาด `P2024` ของ Prisma (`Timed out fetching a new connection from the connection pool`) เกิดจากสาเหตุใด และแตกต่างจากข้อผิดพลาด `too many clients already` ของ PostgreSQL อย่างไร?**
  - **แนวคำตอบ:**
    - `too many clients already` เกิดขึ้นที่ฝั่ง **PostgreSQL Server** เมื่อจำนวนการเชื่อมต่อจริงจากทุกแอปพลิเคชันรวมกันทะลุค่า `max_connections`
    - ส่วน `P2024` เกิดขึ้นที่ฝั่ง **Prisma Client ภายในแอปพลิเคชันเอง** เมื่อการเชื่อมต่อใน Pool ของอินสแตนซ์นั้น (ตามค่า `connection_limit`) ถูกยืมไปใช้งานเต็มทุกสาย และคิวรีใหม่ที่เข้ามาต่อแถวรอนานเกินค่า `pool_timeout` (10 วินาที) โดยยังไม่ได้สายว่างกลับมา ซึ่งมักมีสาเหตุมาจากคิวรีที่ทำงานช้ามากหรือเกิดการล็อกกันในฐานข้อมูล

## 4. สถาปัตยกรรม PgBouncer (Session Mode vs Transaction Mode) และ Serverless

### แนวคิด (Concept)
ในสถาปัตยกรรมยุค Cloud-Native หรือ **Serverless (เช่น Vercel, AWS Lambda, Cloud Run)** เมื่อมีลูกค้า 1,000 คนกดสั่งซื้อเนื้อวากิวพร้อมกัน แพลตฟอร์ม Serverless อาจปลุกฟังก์ชันขนาดจิ๋วขึ้นมาพร้อมกันถึง **500 Instances**!
ต่อให้เราบังคับให้แต่ละฟังก์ชันใช้ `connection_limit=1` (น้อยที่สุดเท่าที่จะทำได้แล้ว) จำนวนสายที่พุ่งเข้าหา PostgreSQL 16 ก็ยังสูงถึง **500 สาย** อยู่ดี ซึ่งทำให้ฐานข้อมูลล่มทันที!

ทางออกเดียวของปัญหานี้คือการวางตัวจัดการการเชื่อมต่อความเร็วสูงที่เขียนด้วยภาษา C ชื่อว่า **PgBouncer** (หรือ **Supavisor** บน Supabase) คั่นกลางระหว่างแอปพลิเคชันกับ PostgreSQL 16 เพื่อทำหน้าที่ **Connection Multiplexing**:
- ฝั่งหน้าบ้าน: PgBouncer เปิดรับการเชื่อมต่อจาก Serverless Functions ได้ถึง **2,000 - 10,000 สาย** อย่างสบายๆ (ใช้หน่วยความจำเพียง 2 KB ต่อสาย!)
- ฝั่งหลังบ้าน: PgBouncer เปิดการเชื่อมต่อจริงไปยัง PostgreSQL 16 ค้างไว้เพียงแค่ **20 สาย (`default_pool_size = 20`)** แล้วสลับคิวรีจาก 2,000 ฟังก์ชันให้หมุนเวียนกันใช้ 20 สายนั้นในระดับไมโครวินาที!

```text filename="docs/database/connection-pooling.txt"
[ Serverless Instances 1..1,000 ]  (เปิด 1,000 Connections เข้ามาพร้อมกัน)
                 │
                 ▼
      ┌─────────────────────┐
      │      PgBouncer      │  (Transaction Pooling Mode - พอร์ต 6432 / 6543)
      │  Multiplexing Queue │
      └──────────┬──────────┘
                 │  (ส่งต่อเพียง 20 Active Connections จริง!)
                 ▼
      ┌─────────────────────┐
      │    PostgreSQL 16    │  (พอร์ต 5432 - ทำงานนิ่งสนิท CPU ไม่กระตุก)
      └─────────────────────┘
```

### หลักการเบื้องหลัง (Under the Hood)
PgBouncer มีโหมดการหมุนเวียนสาย (Pooling Modes) 3 โหมด ซึ่งมีผลต่อการทำงานของฟีเจอร์ใน PostgreSQL 16 และ Prisma อย่างมาก:

1. **Session Pooling Mode (`pool_mode = session`):**
   เมื่อ Client เชื่อมต่อเข้ามา PgBouncer จะมอบสายจริงของ PostgreSQL ให้ Client รายนั้นยึดครองไปตลอดจนกว่า Client จะสั่งตัดการเชื่อมต่อ (`Disconnect`)
   - *ข้อดี:* รองรับทุกฟีเจอร์ของ PostgreSQL 100% (รวมถึง Prepared Statements, `SET` session variables, `LISTEN/NOTIFY` และ Advisory Locks สำหรับทำ Migration)
   - *ข้อเสีย:* ไม่ช่วยลดจำนวนสายกรณีที่แอปพลิเคชันเปิดสายค้างไว้เฉยๆ (ไม่เหมาะกับ Serverless)
2. **Transaction Pooling Mode (`pool_mode = transaction` - หัวใจสำคัญของ Production & Serverless):**
   PgBouncer จะมอบสายจริงของ PostgreSQL ให้ Client ยืมใช้ **เฉพาะชั่วขณะที่มีการรันคำสั่งหรืออยู่ในบล็อก `BEGIN ... COMMIT` เท่านั้น!** ทันทีที่สั่ง `COMMIT` (แม้ Client จะยังเปิดสาย TCP ค้างอยู่) PgBouncer จะดึงสายจริงของ PostgreSQL กลับมาให้ Client รายอื่นใช้งานต่อทันที!
   - *ข้อจำกัดสำคัญ:* เนื่องจากคิวรีที่ 1 และคิวรีที่ 2 ของ Client คนเดียวกันอาจถูกรันบนโปรเซสคนละตัวกันใน PostgreSQL ดังนั้น **Protocol-level Named Prepared Statements จะใช้งานข้ามคิวรีไม่ได้!**
   - *การตั้งค่าใน Prisma:* เมื่อเชื่อมต่อผ่าน PgBouncer ในโหมด Transaction เราต้องเติมพารามิเตอร์ **`?pgbouncer=true`** ท้าย `DATABASE_URL` เสมอ เพื่อสั่งให้ Prisma ยกเลิกการสร้าง Named Prepared Statements ซ้ำซ้อน (แก้ปัญหา Error `prepared statement "s0" already exists` หรือ `does not exist`)
3. **Statement Pooling Mode (`pool_mode = statement`):**
   ยึดสายคืนทันทีหลังจบทุกๆ คำสั่งเดี่ยว **ไม่อนุญาตให้เปิด Multi-statement Transaction (`BEGIN ... COMMIT`) เลย** จึงไม่นำมาใช้กับระบบร้านค้าออนไลน์ทั่วไป

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การตั้งค่า `docker-compose.yml` และ `pgbouncer.ini` สำหรับ PostgreSQL 16 + PgBouncer
สถาปัตยกรรมพร้อมใช้งานจริงที่วาง PgBouncer ในโหมด `transaction` คั่นหน้า PostgreSQL 16 สำหรับระบบ **Smart Butcher Marketplace**:

```ini filename="docker/pgbouncer/pgbouncer.ini"
[databases]
smart_butcher_db = host=postgres-db port=5432 dbname=smart_butcher_db

[pgbouncer]
listen_addr = 0.0.0.0
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt

; ใช้โหมด Transaction Pooling เพื่อรองรับการขยายตัวระดับสูงและ Serverless
pool_mode = transaction

; รับการเชื่อมต่อจากแอปพลิเคชัน/Serverless ด้านหน้าได้สูงสุดถึง 1,000 สาย
max_client_conn = 1000

; แต่เปิดการเชื่อมต่อจริงไปยัง PostgreSQL 16 ด้านหลังเพียงแค่ 20 สายเท่านั้น!
default_pool_size = 20
min_pool_size = 5
reserve_pool_size = 5
reserve_pool_timeout = 3

; ใน PostgreSQL 16 + PgBouncer 1.21+ สามารถตั้งค่าให้ PgBouncer ช่วยจัดการ Prepared Statements ได้ด้วย
max_prepared_statements = 200
server_idle_timeout = 600
```

#### ตัวอย่างที่ 2: การตั้งค่า Prisma (`url` + `directUrl`) เมื่อใช้งานร่วมกับ PgBouncer ในโหมด Transaction
การแยกสายระหว่างสายรับโหลดหน้าร้าน (ผ่าน PgBouncer โหมด Transaction) กับสายรัน Migration (ต่อตรงเข้า PostgreSQL 16):

```prisma filename="prisma/schema.prisma"
datasource db {
  provider  = "postgresql"
  // ใช้รับโหลดคำสั่งซื้อทั้งหมดผ่าน PgBouncer พอร์ต 6432 โหมด Transaction
  url       = env("DATABASE_URL")
  // ใช้เฉพาะตอนรัน npx prisma migrate deploy ต่อตรงเข้าพอร์ต 5432
  directUrl = env("DIRECT_URL")
}
```

```ini filename=".env.production"
# 1. สำหรับแอปพลิเคชันรันไทม์ (Serverless / Containers):
# ต้องระบุ ?pgbouncer=true เสมอ และในสภาพแวดล้อม Serverless ควรตั้ง connection_limit=1 ต่อฟังก์ชัน
DATABASE_URL="postgresql://butcher_app:StrongAppPass@pgbouncer.smartbutcher.internal:6432/smart_butcher_db?pgbouncer=true&connection_limit=1&pool_timeout=15"

# 2. สำหรับ CI/CD รัน Migration (ต้องการ Session-level Advisory Lock จึงต้องต่อตรงไปที่พอร์ต 5432):
DIRECT_URL="postgresql://butcher_migrator:StrongMigratorPass@postgres.smartbutcher.internal:5432/smart_butcher_db"
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การลืมใส่ `?pgbouncer=true`** | ต่อผ่าน PgBouncer โหมด Transaction โดยไม่ใส่ `?pgbouncer=true` ทำให้เกิด Error `prepared statement "s0" already exists` | ระบุ `?pgbouncer=true` ใน `DATABASE_URL` เสมอเมื่อต่อผ่าน Transaction Pooler |
| **การรัน Migration ผ่านโหมด Transaction** | รัน `prisma migrate deploy` ผ่านพอร์ตของ PgBouncer โหมด Transaction ทำให้คำสั่งค้างเพราะทำ Advisory Lock ไม่ได้ | กำหนด `directUrl` ให้ชี้ไปยังพอร์ต 5432 (Direct หรือ Session Mode) สำหรับการทำ Migration |
| **การตั้งค่าใน Serverless** | ตั้ง `connection_limit=20` บน Vercel Serverless Function ทำให้ทุกฟังก์ชันพยายามเปิดค้างไว้ฟังก์ชันละ 20 สาย | บน Serverless ให้ตั้ง `connection_limit=1` ต่อฟังก์ชัน แล้วปล่อยให้ PgBouncer ด้านหลังเป็นตัวกระจายงาน |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ PgBouncer (Transaction Mode) เมื่อ:** ระบบรันบนสถาปัตยกรรม Serverless (Vercel, AWS Lambda), ระบบที่มี Microservices/Containers จำนวนมากเชื่อมต่อเข้าฐานข้อมูลก้อนเดียวกัน หรือระบบที่มี Traffic กระชากสูง (Spiky Traffic)
- **ไม่ควรใช้ Transaction Mode กับฟีเจอร์ที่ผูกติดกับ Session:** เช่น การใช้ `LISTEN / NOTIFY`, การสร้างตารางชั่วคราวแบบไม่ลบเมื่อจบธุรกรรม (`CREATE TEMP TABLE` นอก `ON COMMIT DROP`), หรือการใช้ Session-level `pg_advisory_lock()` (หากต้องการใช้ฟีเจอร์เหล่านี้ต้องเชื่อมต่อผ่านพอร์ต Session Mode แยกต่างหาก)

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ทำไมเมื่อเราเชื่อมต่อ Prisma Client เข้ากับ PgBouncer ที่ตั้งค่า `pool_mode = transaction` โดยไม่ได้ใส่พารามิเตอร์ `?pgbouncer=true` ระบบจึงเกิดข้อผิดพลาด `prepared statement "s0" already exists`?**
  - **แนวคำตอบ:** เพราะโดยค่าเริ่มต้น Prisma จะใช้ฟีเจอร์ Prepared Statements ของ PostgreSQL เพื่อเพิ่มความเร็ว โดยส่งคำสั่ง `PREPARE s0 AS SELECT ...` ไปเก็บไว้ในหน่วยความจำของโปรเซส PostgreSQL ตัวนั้น แต่ในโหมด Transaction Pooling ของ PgBouncer เมื่อคิวรีถัดไปถูกส่งมาจากแอปพลิเคชัน PgBouncer อาจสลับไปใช้โปรเซส PostgreSQL ตัวอื่นที่ยังไม่รู้จัก `s0` หรือสลับไปเจอโปรเซสที่ Client คนอื่นเพิ่งสร้าง `s0` ทิ้งไว้แล้วเกิดชื่อชนกัน การใส่ `?pgbouncer=true` จะสั่งให้ Prisma ปิดการใช้ Named Prepared Statements แบบข้ามธุรกรรม ทำให้ทำงานในโหมด Transaction Pooling ได้อย่างราบรื่น
- **Q2: หากเราใช้โหมด Transaction Pooling ของ PgBouncer เรายังสามารถใช้ `prisma.$transaction([...])` เพื่อตัดสต็อกเนื้อและสร้างใบสั่งซื้อพร้อมกันได้หรือไม่?**
  - **แนวคำตอบ:** **ใช้งานได้ 100%!** เพราะคำว่า Transaction Pooling หมายถึง PgBouncer จะรับประกันว่าคำสั่งทั้งหมดที่อยู่ภายในบล็อกตั้งแต่วินาทีที่ส่ง `BEGIN` ไปจนถึงวินาทีที่ส่ง `COMMIT` หรือ `ROLLBACK` จะถูกส่งไปรันบน Connection จริงของ PostgreSQL ตัวเดิมตลอดทั้งบล็อก และจะดึงสายคืนเมื่อจบ `COMMIT` แล้วเท่านั้น

## 5. การตรวจสอบและวิเคราะห์ Connection ที่เปิดใช้งานด้วย pg_stat_activity

### แนวคิด (Concept)
เมื่อระบบร้าน **Smart Butcher Marketplace** เกิดอาการหน่วงหรือการเชื่อมต่อเริ่มเต็มเพดาน ผู้ดูแลระบบต้องสามารถเปิด "กล้องเอ็กซเรย์" ของ PostgreSQL 16 ที่ชื่อว่า System View **`pg_stat_activity`** เพื่อดูได้ทันทีว่า ณ วินาทีนี้มีใครเชื่อมต่อเข้ามาบ้าง แต่ละสายกำลังทำอะไรอยู่ และมีสายไหนที่กำลังสร้างปัญหาคอขวดให้กับระบบ

### หลักการเบื้องหลัง (Under the Hood)
ใน `pg_stat_activity` คอลัมน์ที่สำคัญที่สุดในการวินิจฉัยสุขภาพของ Connection Pool คือคอลัมน์ **`state`** ซึ่งมีสถานะหลัก 4 รูปแบบ:
1. **`active`:** โปรเซสกำลังใช้ CPU/Disk รันคำสั่ง SQL อยู่ ณ วินาทีนี้จริงๆ
2. **`idle`:** เปิดการเชื่อมต่อค้างไว้ใน Pool เรียบร้อยแล้ว และกำลังว่างรอรับคำสั่งถัดไปจากแอปพลิเคชัน (เป็นสถานะปกติของ Connection Pool)
3. **`idle in transaction` (อันตรายสูงสุด!):** แอปพลิเคชันสั่งเปิด `BEGIN;` ค้างไว้แล้ว และตอนนี้ไม่ได้รันคำสั่ง SQL อะไรเลย (เช่น กำลังรอผลลัพธ์จาก API ภายนอก หรือนักพัฒนาเขียนโค้ดลืมสั่ง `COMMIT`) สถานะนี้เลวร้ายมากเพราะ **มันทั้งยึดครอง Connection ใน Pool เอาไว้ไม่ยอมคืน และยังถือครอง Row Locks รวมถึงขัดขวางไม่ให้ Autovacuum ล้างข้อมูลเก่าได้!**
4. **`idle in transaction (aborted)`:** เหมือนข้อ 3 แต่มีคำสั่งภายใน Transaction พังไปแล้ว และแอปพลิเคชันยังไม่ยอมส่งคำสั่ง `ROLLBACK` มาปิดธุรกรรม

```text filename="docs/database/connection-pooling.txt"
                   ┌───► [ active ] ──► รันคิวรีเสร็จ (ไม่มี BEGIN) ──► [ idle ] (ปกติ ปลอดภัย)
                   │
[ Connection Pool ]┤
                   │
                   └───► [ BEGIN; ] ──► รอ API ภายนอกค้างไว้ ───────► [ idle in transaction ]
                                                                     (อันตราย! ยึดทั้งสาย ยึดทั้ง Lock!)
```

ใน PostgreSQL 16 เราสามารถป้องกันปัญหาสายค้างเหล่านี้ได้ตั้งแต่ระดับ Engine ด้วยการตั้งค่า **`idle_in_transaction_session_timeout`** เพื่อให้ PostgreSQL ตัดสายที่เปิด Transaction ทิ้งไว้เฉยๆ เกินเวลาที่กำหนดโดยอัตโนมัติ!

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: คิวรีตรวจสอบจำนวน Connection แยกตามสถานะและค้นหาตัวการที่ค้างอยู่ใน `pg_stat_activity`
ชุดคำสั่ง SQL สำหรับวิศวกรในการตรวจสอบสุขภาพของ Connection Pool และค้นหาคิวรีที่ค้างนานผิดปกติ:

```sql filename="01_diagnose_connections.sql"
-- 1. สรุปภาพรวมจำนวน Connections ปัจจุบันแยกตามสถานะ (state) และชื่อแอปพลิเคชันเทียบกับเพดานสูงสุด
SELECT
    application_name,
    usename AS db_role,
    state,
    COUNT(*) AS connection_count,
    (SELECT setting::int FROM pg_settings WHERE name = 'max_connections') AS max_limit
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY application_name, usename, state
ORDER BY connection_count DESC;

-- 2. ค้นหาโปรเซสที่เป็นตัวปัญหา: ค้างอยู่ในสถานะ 'idle in transaction' หรือรันคิวรีนานเกิน 5 วินาที
SELECT
    pid,
    usename,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    NOW() - xact_start AS transaction_duration,
    NOW() - state_change AS idle_duration,
    LEFT(query, 120) AS last_executed_query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'idle in transaction (aborted)', 'active')
  AND (NOW() - xact_start) > INTERVAL '5 seconds'
  AND pid <> pg_backend_pid()
ORDER BY transaction_duration DESC;
```

#### ตัวอย่างที่ 2: การตั้งค่าเวลาตัดสายอัตโนมัติและการสั่งตัดโปรเซสที่ค้างด้วย `pg_terminate_backend`
การกำหนดค่าป้องกันตัวเองใน PostgreSQL 16 และคำสั่งฉุกเฉินสำหรับเตะโปรเซสที่ค้างออกจากระบบ:

```sql filename="02_auto_timeout_and_terminate.sql"
-- 1. ตั้งค่าระดับฐานข้อมูลหรือระดับ Role:
-- หากใครเปิด Transaction (BEGIN) ทิ้งไว้เฉยๆ โดยไม่ส่งคำสั่งต่อเกิน 15 วินาที ให้ Rollback และตัดสายทันที!
ALTER DATABASE smart_butcher_db SET idle_in_transaction_session_timeout = '15s';

-- จำกัดเวลาการรันของแต่ละคำสั่ง SQL ของแอปพลิเคชันไม่ให้เกิน 10 วินาทีเพื่อป้องกัน Pool เต็ม
ALTER ROLE butcher_app SET statement_timeout = '10s';

-- 2. คำสั่งฉุกเฉินระดับเบา: สั่งยกเลิกเฉพาะคิวรีที่กำลังรันค้างอยู่ แต่ไม่ตัดสาย Connection
SELECT pg_cancel_backend(14829); -- แทนที่ด้วยหมายเลข pid ที่พบจาก pg_stat_activity

-- 3. คำสั่งฉุกเฉินระดับเด็ดขาด: สั่งตัดสายและทำลายโปรเซสทั้งหมดที่ค้าง 'idle in transaction' เกิน 1 นาที
SELECT
    pid,
    usename,
    pg_terminate_backend(pid) AS is_terminated
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'idle in transaction (aborted)')
  AND (NOW() - state_change) > INTERVAL '1 minute'
  AND pid <> pg_backend_pid();
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การจัดการเมื่อพบคิวรีค้าง** | สั่งรีสตาร์ทเซิร์ฟเวอร์ PostgreSQL ทั้งเครื่องทันทีที่เว็บค้าง ทำให้ทุกระบบที่ใช้งานอยู่ล่มทั้งหมด | ตรวจสอบผ่าน `pg_stat_activity` แล้วใช้ `pg_cancel_backend(pid)` หรือ `pg_terminate_backend(pid)` เฉพาะตัวที่เป็นปัญหา |
| **การตั้งค่า `idle_in_transaction_session_timeout`** | ปล่อยเป็นค่าเริ่มต้น `0` (ไม่จำกัดเวลา) ทำให้เมื่อโค้ดมีบั๊กจะยึดทั้งสายและล็อกตารางค้างไปตลอดกาล | ตั้งค่า `idle_in_transaction_session_timeout = '15s'` หรือ `'30s'` เสมอในสภาพแวดล้อม Production |
| **การKill โปรเซสระดับ Linux** | เข้าเครื่องเซิร์ฟเวอร์แล้วรัน `kill -9 <pid>` ใส่โปรเซสของ PostgreSQL โดยตรง! | ห้ามใช้ `kill -9` เด็ดขาด (เพราะจะทำให้ Shared Memory เสียหายและบังคับให้ Postgres รีสตาร์ททั้งคลัสเตอร์) ให้ใช้ `pg_terminate_backend()` เท่านั้น |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `pg_cancel_backend(pid)` ก่อนเมื่อ:** พบคิวรี `SELECT` ที่รันช้าผิดปกติและต้องการยกเลิกเฉพาะคิวรีนั้นโดยไม่ทำให้ Connection Pool ของแอปพลิเคชันหลุด
- **ควรใช้ `pg_terminate_backend(pid)` เมื่อ:** โปรเซสค้างอยู่ในสถานะ `idle in transaction` (ซึ่งไม่ได้กำลังรันคิวรีอยู่ ดังนั้น `pg_cancel_backend` จะไม่มีผล) จึงต้องสั่งตัดสายเพื่อปลดล็อกตารางและคืนโควตา Connection

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ในตาราง `pg_stat_activity` สถานะ `idle` กับ `idle in transaction` แตกต่างกันอย่างไร และสถานะใดที่เป็นอันตรายต่อระบบ Production?**
  - **แนวคำตอบ:**
    - `idle` คือสถานะปกติของ Connection ใน Pool ที่เปิดรอรับคำสั่งอยู่เฉยๆ โดยไม่ได้เปิด Transaction ค้างไว้ ไม่มีการถือ Lock ใดๆ และหากใช้ PgBouncer โหมด Transaction สายเหล่านี้สามารถนำไปหมุนเวียนให้คนอื่นใช้ได้ทันที
    - ส่วน `idle in transaction` คือสถานะอันตรายที่โปรเซสเปิด `BEGIN` ค้างไว้แต่หยุดส่งคำสั่ง ซึ่งจะยึดสายไว้ไม่ยอมปล่อย ถือล็อกแถวที่แก้ไขไว้จนคนอื่นแก้ต่อไม่ได้ และบล็อกการทำงานของ Autovacuum ทั่วทั้งฐานข้อมูล
- **Q2: ทำไมผู้ดูแลระบบจึงห้ามใช้คำสั่ง `kill -9 <pid>` ของ Linux เพื่อฆ่าโปรเซสของ PostgreSQL ที่ค้างอยู่โดยเด็ดขาด และควรใช้วิธีใดแทน?**
  - **แนวคำตอบ:** เพราะโปรเซสย่อยทั้งหมดของ PostgreSQL แชร์หน่วยความจำร่วมกัน (Shared Buffers / Locks) หากโปรเซสตัวหนึ่งถูก `kill -9` (`SIGKILL`) อย่างกะทันหันในขณะที่กำลังแก้ไขข้อมูลใน Shared Memory อยู่ โปรเซสหลัก (`postmaster`) จะไม่มั่นใจว่าข้อมูลในหน่วยความจำส่วนกลางเสียหายหรือไม่ จึงต้องทำการ **สั่งหยุดโปรเซสของลูกค้าคนอื่นทั้งหมดทันทีแล้วเข้าสู่โหมด Crash Recovery** ทำให้ฐานข้อมูลล่มทั้งระบบ วิธีที่ถูกต้องคือต้องใช้ฟังก์ชัน SQL `SELECT pg_terminate_backend(pid);` (ซึ่งส่งสัญญาณ `SIGTERM` ให้โปรเซสทำความสะอาด Shared Memory และปลดล็อกอย่างปลอดภัยก่อนปิดตัวเอง)

## ข้อผิดพลาดที่พบบ่อย (Anti-patterns)

1. **การสร้าง `new PrismaClient()` หลายครั้งหรือสร้างใหม่ในทุก Request**
   - **สาเหตุ:** ไม่ได้ใช้รูปแบบ Singleton Pattern ในการประกาศ `PrismaClient`
   - **ผลกระทบ:** แต่ละอินสแตนซ์จะสร้าง Connection Pool แยกของตัวเองขึ้นมาเรื่อยๆ จนฐานข้อมูลเกิด `FATAL: sorry, too many clients already`
   - **วิธีแก้:** สร้าง `PrismaClient` เป็น Global Singleton เพียงตัวเดียวตลอดทั้งโปรเจกต์

2. **การตั้งค่า Pool Size สูงเกินไปโดยคิดว่ายิ่งเยอะยิ่งเร็ว**
   - **สาเหตุ:** ตั้ง `connection_limit = 100` บนทุก Container โดยไม่คำนวณจำนวน CPU Cores ของฐานข้อมูล
   - **ผลกระทบ:** เกิดภาวะ CPU Context Switching และแย่งชิง Lock ในฐานข้อมูลจนเวลาตอบสนองช้าลงหลายเท่าตัว
   - **วิธีแก้:** คำนวณขนาด Pool ที่ทำงานพร้อมกันจริงตามสูตร `(CPU Cores * 2) + 1` และใช้ PgBouncer จัดการคิวด้านหน้า

3. **การเชื่อมต่อ Serverless Functions เข้าหา PostgreSQL โดยตรงโดยไม่มี External Pooler**
   - **สาเหตุ:** นำ Connection String พอร์ต 5432 ปกติไปใส่ใน Vercel หรือ AWS Lambda
   - **ผลกระทบ:** เมื่อมีผู้ใช้งานเข้าพร้อมกัน Serverless จะขยายตัวเป็นร้อยฟังก์ชันและยิง Connection ทะลุเพดานฐานข้อมูลทันที
   - **วิธีแก้:** เชื่อมต่อผ่าน PgBouncer หรือ Supavisor ในโหมด Transaction Pooling พร้อมระบุ `?pgbouncer=true&connection_limit=1`

4. **การเรียกใช้ API ภายนอก (เช่น ส่งอีเมล หรือตัดบัตรเครดิต) อยู่ภายในบล็อก `$transaction`**
   - **สาเหตุ:** นำ Business Logic ทั้งหมดยัดไว้ในฟังก์ชัน `prisma.$transaction(async (tx) => { ... })`
   - **ผลกระทบ:** โปรเซสจะค้างอยู่ในสถานะ `idle in transaction` ยึด Connection ใน Pool ไว้นานหลายวินาทีจนสายใน Pool หมดเกลี้ยง
   - **วิธีแก้:** ทำงานที่เกี่ยวกับเครือข่ายภายนอกให้เสร็จก่อนหรือหลังบล็อก `$transaction` เสมอ

5. **การใช้ `kill -9` ในระดับ OS เพื่อตัด Connection ที่ค้าง**
   - **สาเหตุ:** พยายามปิดโปรเซสที่ค้างด้วยวิธีเดียวกับแอปพลิเคชันทั่วไป
   - **ผลกระทบ:** บังคับให้ PostgreSQL ทั้งคลัสเตอร์ต้องรีสตาร์ทและทำ Crash Recovery เพื่อป้องกัน Shared Memory เสียหาย
   - **วิธีแก้:** ใช้คำสั่ง `SELECT pg_cancel_backend(pid)` หรือ `SELECT pg_terminate_backend(pid)` ภายใน SQL เท่านั้น

## Checklist สรุป

ตรวจสอบการตั้งค่าระบบจัดการการเชื่อมต่อสำหรับ **Smart Butcher Marketplace** ให้พร้อมรับโหลดระดับ Production:

- [ ] **Singleton Prisma Instance:** ตรวจสอบแล้วว่ามีการสร้าง `new PrismaClient()` เพียงจุดเดียวในรูปแบบ Singleton และมีการเรียก `$disconnect()` เมื่อปิดแอปพลิเคชัน
- [ ] **Pool Size Calculated:** กำหนดค่า `connection_limit` และ `pool_timeout` ใน `DATABASE_URL` สอดคล้องกับจำนวน Containers สูงสุดและสเปก CPU ของฐานข้อมูล
- [ ] **External Pooler for Scale/Serverless:** ติดตั้ง PgBouncer หรือใช้ Supavisor ในโหมด `transaction` คั่นหน้าฐานข้อมูล พร้อมเติม `?pgbouncer=true` ใน `DATABASE_URL`
- [ ] **Direct URL Separated:** แยก `DIRECT_URL` ที่ชี้ไปยังพอร์ต 5432 ไว้สำหรับการรัน `prisma migrate deploy` โดยเฉพาะ
- [ ] **Short Transactions Only:** ตรวจสอบโค้ดทั้งหมดว่าไม่มีการเรียก HTTP API ภายนอกอยู่ภายในบล็อก `prisma.$transaction`
- [ ] **Engine Timeouts Set:** ตั้งค่า `idle_in_transaction_session_timeout = '15s'` และ `statement_timeout` ใน PostgreSQL 16 เพื่อป้องกันสายค้างอัตโนมัติ
