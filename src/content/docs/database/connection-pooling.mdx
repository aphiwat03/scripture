# Connection Pooling

หนึ่งในสาเหตุอันดับต้นๆ ที่ทำให้ระบบที่ใช้ฐานข้อมูล **PostgreSQL 16** ล่มกลางอากาศเมื่อมีผู้ใช้งานหลั่งไหลเข้ามาพร้อมกัน (เช่น ช่วงจัดโปรโมชันลดราคาเนื้อวากิว Flash Sale) ไม่ใช่เพราะคิวรีช้าเสมอไป แต่เป็นเพราะ **"การเปิดการเชื่อมต่อ (Database Connections) เข้ามามากเกินไปจนหน่วยความจำและซีพียูของฐานข้อมูลหมดสภาพ"** เอกสารฉบับนี้เจาะลึกสถาปัตยกรรมระดับโปรเซสของ PostgreSQL, สูตรคำนวณขนาด Connection Pool มาตรฐานโลก, การตั้งค่า Prisma Client, สถาปัตยกรรม **PgBouncer** สำหรับระบบ Serverless ไปจนถึงการตรวจวินิจฉัยปัญหาด้วย `pg_stat_activity`

| หัวข้อในหน้านี้ | สาระสำคัญ |
| :--- | :--- |
| **1. ต้นทุนของการสร้าง Connection ใน PostgreSQL (Process-per-Connection)** | สถาปัตยกรรม `postmaster` `fork()` โปรเซสแยก, ต้นทุน RAM 5-10 MB ต่อสาย และขั้นตอน TCP + TLS + SCRAM Handshake |
| **2. กลไกการทำงานของ Connection Pool และสูตรคำนวณ Pool Size ที่เหมาะสม** | ทำไมการเพิ่ม Pool Size ถึงทำให้ฐานข้อมูลช้าลง (Context Switching) และสูตรคำนวณตามจำนวน CPU Cores |
| **3. ปัญหา Too Many Connections และการตั้งค่า Connection Limit ใน Prisma** | การคำนวณโควตาเมื่อขยายแอปหลาย Instances, พารามิเตอร์ `connection_limit` และรูปแบบ Singleton |
| **4. สถาปัตยกรรม PgBouncer (Session Mode vs Transaction Mode) และ Serverless** | การทำ Connection Multiplexing, ความต่างของพอร์ตและโหมดการทำงาน และการใช้ `?pgbouncer=true` |
| **5. การตรวจสอบและวิเคราะห์ Connection ที่เปิดใช้งานด้วย pg_stat_activity** | การตรวจจับ `idle in transaction`, การตั้งเวลาตัดสายอัตโนมัติ และการสั่ง `pg_terminate_backend()` |

<Callout type="tip" title="ความจริงที่สวนทางกับความรู้สึกของนักพัฒนา (Counter-Intuitive Truth)">
สำหรับเซิร์ฟเวอร์ PostgreSQL 16 ที่มีซีพียู 4 Cores การเปิด Connection วิ่งทำงานพร้อมกันเพียง **9 ถึง 10 Connections** จะสามารถประมวลผลคำสั่งซื้อต่อวินาที (Throughput/TPS) ได้เร็วกว่าการปล่อยให้เปิดเข้ามาพร้อมกัน 500 Connections อย่างเทียบไม่ติด!
</Callout>
