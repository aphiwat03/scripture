# SQL vs NoSQL

หนึ่งในคำถามระดับคลาสสิกในการออกแบบสถาปัตยกรรมระบบ (System Design) คือ **"โปรเจกต์นี้ควรใช้ SQL หรือ NoSQL?"** ในยุคปัจจุบัน คำตอบของวิศวกรอาวุโสไม่ใช่การเลือกข้างใดข้างหนึ่งแบบสุดโต่งอีกต่อไป แต่คือการเข้าใจจุดแข็งและข้อจำกัดเชิงลึกของแต่ละเทคโนโลยี เพื่อนำมาประกอบกันอย่างลงตัว เอกสารฉบับนี้เจาะลึกการเปรียบเทียบสถาปัตยกรรมระหว่าง **SQL (PostgreSQL 16)** และ **NoSQL (MongoDB, Redis, Elasticsearch, SQLite)** พร้อมทฤษฎีบท **CAP Theorem** และเหตุผลทางวิศวกรรมว่าทำไมระบบร้านค้าเนื้อพรีเมียม **Smart Butcher Marketplace** จึงเลือกใช้ **PostgreSQL 16 เป็นฐานข้อมูลหลักควบคู่กับ Redis (Polyglot Persistence)**

| หัวข้อในหน้านี้ | สาระสำคัญ |
| :--- | :--- |
| **1. เปรียบเทียบสถาปัตยกรรม SQL (Relational) vs NoSQL (Non-Relational)** | โครงสร้างตาราง vs เอกสาร/คีย์-แวลู, ACID vs BASE, การขยายตัว (Scale-up vs Scale-out) และการใช้ `JSONB` ใน PostgreSQL 16 |
| **2. เมื่อไหร่ควรเลือกใช้ MongoDB (Document Database)** | โมเดล BSON Document, การฝังข้อมูล (Embedding vs Referencing) และกรณีศึกษา IoT Cold-Chain Sensor Logs |
| **3. การใช้ Redis สำหรับ Caching, Session, Queue และ Rate Limiting** | โครงสร้างข้อมูลในหน่วยความจำ (In-Memory), รูปแบบ Cache-Aside Pattern และ Token Bucket Rate Limiting |
| **4. ฐานข้อมูลเฉพาะทางที่ควรรู้จัก (SQLite, Elasticsearch) และทฤษฎีบท CAP Theorem** | การทำงานของ Inverted Index, Embedded DB และการวิเคราะห์ CP vs AP เมื่อเกิด Network Partition |
| **5. แนวคิด Polyglot Persistence และเหตุผลที่ระบบร้านค้าเลือก PostgreSQL 16** | การผสาน PostgreSQL 16 + Redis ในระบบเดียว และทำไมระบบตัดสต็อกและคิดเงินจึงห้ามสูญเสีย ACID |

<Callout type="tip" title="คำจำกัดความที่แท้จริงของคำว่า NoSQL ในยุคปัจจุบัน">
คำว่า **NoSQL** ในทางวิศวกรรมสมัยใหม่ไม่ได้แปลว่า "No SQL (ห้ามใช้ SQL)" แต่ย่อมาจาก **"Not Only SQL (ไม่ได้มีแค่ตารางเชิงสัมพันธ์เพียงอย่างเดียว)"** และในทางกลับกัน ฐานข้อมูลอย่าง **PostgreSQL 16** ก็ได้พัฒนาชนิดข้อมูล **`JSONB`** พร้อมดัชนี **GIN Index** จนสามารถจัดเก็บและค้นหาข้อมูลกึ่งโครงสร้าง (Semi-structured Document) ได้เร็วเทียบเท่าหรือเหนือกว่าฐานข้อมูล NoSQL หลายตัวภายใต้ร่มเงาของ ACID Transaction เดียวกัน!
</Callout>

## 1. เปรียบเทียบสถาปัตยกรรม SQL (Relational) vs NoSQL (Non-Relational)

### แนวคิด (Concept)
เพื่อให้เห็นภาพความแตกต่างชัดเจนที่สุด ลองเปรียบเทียบการจัดเก็บข้อมูลในร้าน **Smart Butcher Marketplace**:
- **SQL / Relational Database (เช่น PostgreSQL 16):** เปรียบเสมือน **"สมุดบัญชีแยกประเภทและคลังสินค้าที่มีช่องตารางมาตรฐานบังคับตายตัว"** ข้อมูลลูกค้า (`users`), สินค้า (`products`), และใบสั่งซื้อ (`orders`) ถูกแยกเก็บคนละตารางอย่างเป็นระเบียบ (Normalization) เพื่อไม่ให้ข้อมูลซ้ำซ้อน และเชื่อมโยงกันด้วยรหัสอ้างอิง (Foreign Keys) หากใครพยายามใส่ราคาเนื้อเป็นตัวหนังสือ หรือพยายามสร้างใบสั่งซื้อของลูกค้าที่ไม่มีตัวตน ระบบจะปฏิเสธทันที
- **NoSQL / Non-Relational Database (เช่น MongoDB, Redis, DynamoDB):** เปรียบเสมือน **"แฟ้มเอกสารอิสระหรือตู้ล็อกเกอร์ความเร็วสูง"** ที่เน้นความยืดหยุ่นของโครงสร้างข้อมูล (Schema-flexible) หรือเน้นการเข้าถึงด้วยคีย์เดียวด้วยความเร็วระดับไมโครวินาที โดยยอมแลกความเข้มงวดของความสัมพันธ์ระหว่างตารางออกไป เพื่อให้กระจายข้อมูลไปเก็บไว้บนเซิร์ฟเวอร์หลายสิบเครื่อง (Horizontal Sharding) ได้ง่ายขึ้น

### หลักการเบื้องหลัง (Under the Hood)
1. **ACID vs BASE Consistency Model:**
   - **SQL (ACID):** ยึดหลัก **Atomicity** (พังจุดเดียวต้องยกเลิกทั้งหมด), **Consistency** (ข้อมูลถูกต้องตามกฎ Constraint เสมอ), **Isolation** (ธุรกรรมที่รันพร้อมกันไม่กวนกัน), และ **Durability** (ข้อมูลถูกเขียนลง WAL บนดิสก์ไม่สูญหาย)
   - **NoSQL ยุคแรก (BASE):** ยึดหลัก **Basically Available** (ระบบพร้อมตอบสนองเสมอ), **Soft state** (สถานะข้อมูลอาจเปลี่ยนแปลงได้แม้ไม่มี Input ใหม่เพราะกำลังซิงค์ข้อมูล), และ **Eventually consistent** (ข้อมูลในแต่ละโหนดอาจไม่ตรงกันชั่วคราว แต่สุดท้ายจะซิงค์จนตรงกันในที่สุด)
2. **การอ่านข้อมูล: Join-on-Read (SQL) vs Denormalized Pre-joined Document (NoSQL):**
   - ใน SQL เราแยกตาราง `orders` กับ `order_items` ออกจากกัน เวลาต้องการแสดงผลใบเสร็จ เราใช้คำสั่ง `JOIN` เพื่อประกอบร่างข้อมูลตอนอ่าน
   - ใน Document NoSQL เรามักฝังอาร์เรย์ของ `items` เข้าไปอยู่ในเอกสาร `order` ก้อนเดียวกันเลย ทำให้การอ่านใบเสร็จ 1 ใบทำได้ในการอ่านดิสก์ครั้งเดียว แต่หากชื่อสินค้าเปลี่ยน เราจะต้องตามไปอัปเดตเอกสารใบสั่งซื้อเก่าทุกใบที่เคยฝังชื่อนั้นไว้!
3. **อาวุธลับของ PostgreSQL 16 (`JSONB` + GIN Index):**
   PostgreSQL 16 ทลายเส้นแบ่งระหว่าง SQL กับ Document NoSQL ด้วยชนิดข้อมูล **`JSONB` (Binary JSON)** เราสามารถใช้ตารางเชิงสัมพันธ์ที่เคร่งครัดกับคอลัมน์หลัก (`id`, `sku`, `price_per_kg`, `stock_weight_gr`) และเพิ่มคอลัมน์ `butcher_metadata JSONB` สำหรับเก็บคุณสมบัติเฉพาะของเนื้อแต่ละสายพันธุ์ที่มีฟิลด์ไม่เหมือนกันเลยได้ในตารางเดียวกัน!

#### ตารางเปรียบเทียบเชิงวิศวกรรม: PostgreSQL 16 (SQL) vs MongoDB (Document) vs Redis (Key-Value)

| มิติการเปรียบเทียบ | PostgreSQL 16 (ORDBMS / SQL) | MongoDB (Document NoSQL) | Redis (In-Memory Key-Value) |
| :--- | :--- | :--- | :--- |
| **หน่วยจัดเก็บข้อมูลหลัก** | ตาราง (Tables), แถว (Tuples) และ `JSONB` | เอกสาร **BSON** (Binary JSON) ใน Collections | คีย์และโครงสร้างข้อมูลใน RAM (Strings, Hashes, Sets) |
| **การบังคับโครงสร้าง (Schema)** | **Schema-on-Write** (เข้มงวดระดับ Engine + ยืดหยุ่นในคอลัมน์ `JSONB`) | **Schema-flexible** (แต่ละเอกสารใน Collection เดียวกันมีฟิลด์ต่างกันได้) | ไม่มี Schema ตายตัว (กำหนดโครงสร้างตามชื่อ Key) |
| **ความสัมพันธ์และการทำ JOIN** | ยอดเยี่ยมที่สุด (Hash Join, Merge Join, Nested Loop + Foreign Keys) | ไม่เน้นการทำ Join (มี `$lookup` แต่ช้ากว่า SQL Join มาก) | ไม่มีการทำ Join ระหว่างคีย์ |
| **การรับประกันธุรกรรม** | **ACID เต็มรูปแบบ 100%** (ทั้งข้อมูลตาราง, `JSONB` และ DDL) | รองรับ Multi-document ACID แต่มี Overhead สูงกว่าการอัปเดตเอกสารเดี่ยว | อะตอมมิกในระดับคำสั่งเดี่ยว หรือผ่านสคริปต์ **Lua Script** |
| **ความเร็วในการตอบสนอง (Latency)** | เร็วมาก (**0.5 - 5 มิลลิวินาที** จาก RAM Buffer / SSD) | เร็วมากสำหรับการดึงเอกสารเดี่ยวด้วย `_id` (**1 - 5 มิลลิวินาที**) | **เร็วระดับขีดสุด (< 0.1 - 0.5 มิลลิวินาที)** เพราะอยู่ใน RAM ล้วนๆ |
| **หน้าที่หลักใน Smart Butcher** | **ฐานข้อมูลหลัก (System of Record):** ลูกค้า, สต็อกเนื้อ, ออเดอร์, การเงิน | เก็บ Log อุณหภูมิตู้แช่ IoT หรือแค็ตตาล็อกที่มีโครงสร้างหลากหลายสุดขั้ว | **Caching Layer, ตะกร้าสินค้าชั่วคราว, คิวงาน และ Rate Limiting** |

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การผสานจุดเด่นของ SQL (Relational Constraints) เข้ากับ NoSQL (`JSONB`) ในตาราง `products` ของ PostgreSQL 16
แทนที่จะต้องติดตั้ง MongoDB แยกเพียงเพื่อเก็บข้อมูลใบรับรองฟาร์มวัวที่มีฟิลด์ต่างกันในแต่ละประเทศ เราใช้ `JSONB` พร้อม `GIN Index` ใน PostgreSQL 16:

```sql filename="01_hybrid_relational_jsonb.sql"
-- สร้างตารางสินค้าที่ใช้ความเคร่งครัดของ SQL ในส่วนราคาและสต็อก
-- แต่ใช้ความยืดหยุ่นแบบ Document NoSQL (JSONB) ในส่วนข้อมูลจำเพาะของฟาร์ม (origin_metadata)
CREATE TABLE "products" (
    "id" UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    "category_id" UUID NOT NULL REFERENCES "categories"("id") ON DELETE RESTRICT,
    "sku" VARCHAR(50) NOT NULL UNIQUE,
    "name" VARCHAR(200) NOT NULL,
    "price_per_kg" NUMERIC(10, 2) NOT NULL CHECK ("price_per_kg" > 0),
    "stock_weight_gr" INTEGER NOT NULL DEFAULT 0 CHECK ("stock_weight_gr" >= 0),
    "origin_metadata" JSONB NOT NULL DEFAULT '{}'::jsonb,
    "created_at" TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- สร้าง GIN Index บนคอลัมน์ JSONB เพื่อให้ค้นหาฟิลด์ข้างใน JSON ได้เร็วระดับมิลลิวินาที!
CREATE INDEX "idx_products_origin_metadata_gin"
ON "products" USING GIN ("origin_metadata" jsonb_path_ops);

-- บันทึกเนื้อวากิวญี่ปุ่น (มีฟิลด์ prefecture และ nose_print_id) และเนื้อแองกัสออสเตรเลีย (มีฟิลด์ pasture_region)
INSERT INTO "products" ("category_id", "sku", "name", "price_per_kg", "stock_weight_gr", "origin_metadata")
VALUES
(
    '11111111-1111-1111-1111-111111111111',
    'SB-KOBE-RIB-A5',
    'Kobe Beef A5 Ribeye',
    9500.00,
    5000,
    '{"country": "Japan", "prefecture": "Hyogo", "bms_score": 12, "cattle_id": "JP-9876543210", "halal_certified": true}'
),
(
    '22222222-2222-2222-2222-222222222222',
    'SB-ANGUS-TMAHWK',
    ' Tasmanian Grass-Fed Tomahawk',
    3200.00,
    12000,
    '{"country": "Australia", "pasture_region": "Tasmania", "grass_fed_days": 450, "hormone_free": true}'
);

-- ค้นหาสินค้าด้วย JSONB Containment Operator (@>) ซึ่งวิ่งผ่าน GIN Index ทันที!
SELECT sku, name, price_per_kg, origin_metadata->>'cattle_id' AS cattle_id
FROM "products"
WHERE "origin_metadata" @> '{"country": "Japan", "halal_certified": true}';
```

#### ตัวอย่างที่ 2: การค้นหาข้อมูลภายในคอลัมน์ `JSONB` ควบคู่กับเงื่อนไขปกติผ่าน Prisma Client
Prisma ORM รองรับการกรองข้อมูลภายในคอลัมน์ `Json` (`JSONB`) ของ PostgreSQL 16 ได้โดยตรง:

```typescript filename="src/products/jsonb-catalog.service.ts"
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';

@Injectable()
export class JsonbCatalogService {
  constructor(private readonly prisma: PrismaService) {}

  async findJapaneseHalalWagyuInStock(minWeightGrams: number) {
    return this.prisma.product.findMany({
      where: {
        // 1. เงื่อนไข Relational มาตรฐานบนคอลัมน์มีโครงสร้าง
        stockWeightGr: { gte: minWeightGrams },
        // 2. เงื่อนไขค้นหาลึกเข้าไปใน JSONB Document (originMetadata)
        originMetadata: {
          path: ['country'],
          equals: 'Japan',
        },
        AND: [
          {
            originMetadata: {
              path: ['halal_certified'],
              equals: true,
            },
          },
        ],
      },
      orderBy: { pricePerKg: 'desc' },
    });
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การใช้ `JSONB` ผิดวัตถุประสงค์** | ยัดข้อมูลทุกอย่าง (รวมถึง `price`, `stock`, `user_id`) ลงในคอลัมน์ `JSONB` ก้อนเดียวจนใช้ Foreign Key ไม่ได้ | ใช้คอลัมน์ปกติสำหรับฟิลด์หลักที่ต้องทำความสัมพันธ์และคำนวณเงิน แล้วใช้ `JSONB` เฉพาะส่วนข้อมูลเสริมที่ยืดหยุ่น |
| **การเลือกฐานข้อมูลตามกระแส** | เลือกใช้ NoSQL กับระบบบัญชีและการตัดสต็อกสินค้าเพราะคิดว่าไม่ต้องออกแบบตารางให้เสียเวลา | วิเคราะห์รูปแบบการเข้าถึงข้อมูล (Access Patterns) และความสำคัญของความถูกต้อง (ACID) ก่อนเลือกเสมอ |
| **การทำ `JOIN` ในแอปพลิเคชันเอง** | ดึงตาราง `orders` ออกมา แล้วเขียนลูป `for` ยิงคิวรีดึง `users` ทีละคนในโค้ดเพราะกลัวการใช้ SQL `JOIN` | ใช้ `JOIN` (หรือ Prisma `include`) ให้ Database Engine ประมวลผลให้เสร็จในคราวเดียว |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ SQL (PostgreSQL 16) เมื่อ:** ข้อมูลมีความสัมพันธ์กันชัดเจน (ลูกค้า -> คำสั่งซื้อ -> รายการสินค้า -> การชำระเงิน), ต้องการความถูกต้องของตัวเลขทางการเงินและสต็อก 100% (ACID), และมีการทำรายงานวิเคราะห์ข้อมูลหลายมิติ
- **ไม่ควรใช้ Relational Table แบบแยกตารางย่อยเป็นร้อยตาราง (Entity-Attribute-Value Anti-pattern) เมื่อ:** เก็บคุณลักษณะเสริมของสินค้าที่แตกต่างกันไปตามแต่ละหมวดหมู่ (ในกรณีนี้ควรใช้คอลัมน์ `JSONB` ใน PostgreSQL หรือใช้ Document Database)

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ใน PostgreSQL ชนิดข้อมูล `JSON` กับ `JSONB` แตกต่างกันอย่างไร และทำไมในระดับ Production เราจึงควรใช้ `JSONB` แทบทุกกรณี?**
  - **แนวคำตอบ:**
    - `JSON` เก็บข้อมูลเป็นข้อความดิบ (Plain Text) ตามที่ส่งเข้ามาทุกตัวอักษร (รวมถึงช่องว่าง) เวลาเขียนจะเร็วกว่าเล็กน้อย แต่เวลาค้นหาฟิลด์ข้างในจะต้องทำการ Parse ข้อความใหม่ทุกครั้งและไม่รองรับการทำ GIN Indexing แบบเต็มรูปแบบ
    - ส่วน `JSONB` (Binary JSON) จะทำการแยกวิเคราะห์และแปลงโครงสร้างให้เป็นไบนารีตั้งแต่ตอนบันทึก ตัดช่องว่างที่ไม่จำเป็นออก แม้จะใช้เวลาตอน `INSERT` เพิ่มขึ้นเสี้ยววินาที แต่ทำให้การอ่านค้นหาข้อมูลข้างในเร็วกว่ามาก และรองรับการสร้าง **GIN Index** รวมถึงตัวดำเนินการ `@>` (Containment) ได้อย่างสมบูรณ์
- **Q2: คำว่า Normalization กับ Denormalization คืออะไร และเกี่ยวพันกับการออกแบบ SQL vs NoSQL อย่างไร?**
  - **แนวคำตอบ:** Normalization (หัวใจของ SQL) คือการจัดระเบียบข้อมูลเพื่อลดความซ้ำซ้อนโดยแยกข้อมูลออกเป็นตารางย่อยแล้วเชื่อมด้วย Foreign Key ทำให้เวลาแก้ไขข้อมูลแก้เพียงจุดเดียวและไม่เกิดความขัดแย้งกัน ส่วน Denormalization (หัวใจของ NoSQL) คือการยอมเก็บข้อมูลซ้ำซ้อนไว้ในเอกสารก้อนเดียวกันเพื่อหลีกเลี่ยงการทำ Join ตอนอ่าน ทำให้การอ่านข้อมูลเร็วขึ้นมากแต่ต้องแลกมาด้วยความซับซ้อนในการตามอัปเดตข้อมูลให้ตรงกันทุกจุดเมื่อเกิดการเปลี่ยนแปลง

## 2. เมื่อไหร่ควรเลือกใช้ MongoDB (Document Database)

### แนวคิด (Concept)
**MongoDB** คือฐานข้อมูลฝั่ง NoSQL ประเภท **Document Store** ที่ได้รับความนิยมสูงสุด โดยจัดเก็บข้อมูลในรูปแบบเอกสาร **BSON (Binary JSON)** ภายในกลุ่มที่เรียกว่า **Collections** (เทียบได้กับตารางใน SQL)
จุดแข็งที่แท้จริงของ MongoDB คือการที่ **"โครงสร้างข้อมูลในฐานข้อมูลมีรูปร่างตรงกับ Object ในโค้ด JavaScript/TypeScript ทันทีโดยไม่ต้องแปลงตาราง"** และการรองรับปริมาณการเขียนข้อมูลขาเข้า (Write-heavy Ingestion) ที่มีโครงสร้างเปลี่ยนแปลงตลอดเวลาและการทำ Horizontal Auto-Sharding ข้ามเซิร์ฟเวอร์หลายเครื่องได้ในตัว

ในระบบ **Smart Butcher Marketplace** แม้เราจะใช้ PostgreSQL 16 เก็บคำสั่งซื้อและการเงิน แต่ถ้าเรามีระบบ **"IoT Cold-Chain Telemetry"** ที่ติดตั้งเซนเซอร์วัดอุณหภูมิ ความชื้น และพิกัด GPS ไว้ในตู้แช่เนื้อและรถขนส่งห้องเย็นทุกคัน ซึ่งยิงข้อมูลเข้ามาวินาทีละหลายหมื่นรายการและเซนเซอร์แต่ละรุ่นส่งฟิลด์มาไม่เหมือนกันเลย งานลักษณะนี้คือพื้นที่ที่ MongoDB (หรือ Time-Series DB) ฉายแสงได้อย่างยอดเยี่ยม

### หลักการเบื้องหลัง (Under the Hood)
1. **WiredTiger Storage Engine & BSON:**
   MongoDB ใช้เอนจินจัดเก็บข้อมูลชื่อ **WiredTiger** ซึ่งใช้การล็อกระดับเอกสาร (Document-level Concurrency Control) และจัดเก็บข้อมูลเป็น BSON ที่รองรับชนิดข้อมูลมากกว่า JSON ปกติ เช่น `ObjectId` (ขนาด 12 ไบต์ที่มีประทับเวลาฝังอยู่), `Date`, `Decimal128` และไบนารี
2. **หลักการออกแบบ: ข้อมูลที่ถูกอ่านด้วยกัน ควรถูกเก็บฝังไว้ด้วยกัน (Data that is accessed together should be stored together):**
   - **Embedding (การฝังเอกสารย่อย):** ยุบรวมข้อมูลย่อยเข้าไปอยู่ในเอกสารแม่ก้อนเดียว ทำให้การดึงข้อมูลทั้งหมดทำได้ในการอ่านดิสก์เพียง 1 ครั้ง (Single Document Atomic Read/Write)
   - **Referencing (การอ้างอิง):** แยกเอกสารออกจากกันเมื่ออาร์เรย์ย่อยมีโอกาสเติบโตแบบไร้ขีดจำกัด (Unbounded Array Growth) เพราะ MongoDB มีข้อจำกัดทางสถาปัตยกรรมที่สำคัญมากคือ **เอกสาร 1 ใบห้ามมีขนาดเกิน 16 MB เด็ดขาด!**
3. **Native Horizontal Sharding:**
   เมื่อข้อมูลเติบโตสู่ระดับหลายสิบ Terabytes MongoDB สามารถกระจายเอกสารไปเก็บตามเครื่องเซิร์ฟเวอร์ต่างๆ (Shards) โดยอัตโนมัติตามค่า **Shard Key** ที่เรากำหนด (เช่น `device_id` ของตู้แช่เนื้อ)

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: โครงสร้างเอกสาร BSON สำหรับเก็บข้อมูลเซนเซอร์ตู้บ่มเนื้อ Dry-Aged (Schema-flexible IoT Logs)
เซนเซอร์ตู้บ่มเนื้อรุ่นที่ 1 ส่งเฉพาะอุณหภูมิและความชื้น ส่วนเซนเซอร์รุ่นที่ 2 ส่งค่าความเร็วพัดลมและระดับแสง UV เพิ่มเข้ามา ซึ่งสามารถบันทึกลงใน Collection เดียวกันได้ทันทีโดยไม่ต้องรัน `ALTER TABLE`:

```typescript filename="src/telemetry/cold-chain-telemetry.schema.ts"
import { MongoClient, ObjectId, Decimal128 } from 'mongodb';

export interface ColdChainSensorEvent {
  _id?: ObjectId;
  chamberId: string; // ใช้เป็น Shard Key และ Index หลัก
  productSkuBatch: string;
  recordedAt: Date;
  temperatureCelsius: number;
  humidityPercent: number;
  // โครงสร้างยืดหยุ่นที่แตกต่างกันไปตามรุ่นของฮาร์ดแวร์เซนเซอร์ในแต่ละห้องเย็น
  hardwareDiagnostics: {
    firmwareVersion: string;
    uvSterilizerActive?: boolean;
    airflowVelocityMps?: number;
    compressorAlerts?: string[];
  };
}

export async function recordColdChainReading(
  mongoClient: MongoClient,
  reading: ColdChainSensorEvent
) {
  const db = mongoClient.db('smart_butcher_telemetry');
  const collection = db.collection<ColdChainSensorEvent>('chamber_logs');

  // บันทึกเอกสารความเร็วสูงแบบไม่ต้องตรวจ Foreign Key ข้ามตาราง
  const result = await collection.insertOne({
    ...reading,
    recordedAt: new Date(),
  });

  return result.insertedId;
}
```

#### ตัวอย่างที่ 2: การสร้าง TTL Index (ลบข้อมูลเก่าอัตโนมัติ) และการรัน Aggregation Pipeline วิเคราะห์อุณหภูมิห้องเย็น
ฟีเจอร์ที่ทรงพลังมากของ MongoDB สำหรับข้อมูล Log คือ **TTL Index (Time-To-Live Index)** ที่สั่งให้ฐานข้อมูลลบเอกสารที่อายุเกิน 90 วันทิ้งให้อัตโนมัติ และการสรุปผลด้วย Aggregation Pipeline:

```typescript filename="src/telemetry/cold-chain-analytics.service.ts"
import { Db } from 'mongodb';

export class ColdChainAnalyticsService {
  constructor(private readonly telemetryDb: Db) {}

  async ensureIndexesAndTtl() {
    const col = this.telemetryDb.collection('chamber_logs');

    // 1. สร้าง Compound Index สำหรับค้นหาตามรหัสตู้บ่มและช่วงเวลา
    await col.createIndex({ chamberId: 1, recordedAt: -1 });

    // 2. สร้าง TTL Index: สั่งให้ MongoDB ลบข้อมูลเซนเซอร์ที่เก่าเกิน 90 วันทิ้งอัตโนมัติ!
    await col.createIndex(
      { recordedAt: 1 },
      { expireAfterSeconds: 90 * 24 * 60 * 60 }
    );
  }

  async findOverheatedChambersLastHour() {
    const oneHourAgo = new Date(Date.now() - 60 * 60 * 1000);

    // ใช้ MongoDB Aggregation Pipeline เพื่อหาตู้บ่มเนื้อที่อุณหภูมิเฉลี่ยเกิน 4.0 องศาเซลเซียส
    return this.telemetryDb
      .collection('chamber_logs')
      .aggregate([
        {
          $match: {
            recordedAt: { $gte: oneHourAgo },
          },
        },
        {
          $group: {
            _id: '$chamberId',
            avgTempCelsius: { $avg: '$temperatureCelsius' },
            maxTempCelsius: { $max: '$temperatureCelsius' },
            sampleCount: { $sum: 1 },
          },
        },
        {
          $match: {
            maxTempCelsius: { $gt: 4.0 },
          },
        },
        {
          $sort: { maxTempCelsius: -1 },
        },
      ])
      .toArray();
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การฝัง Array ที่โตไม่จำกัด** | ฝังอาร์เรย์ `orders` ทั้งหมดของลูกค้าไว้ในเอกสาร `user` ใบเดียว พอลูกค้าซื้อครบหมื่นครั้ง เอกสารทะลุเพดาน **16 MB** จนพัง | ฝัง (Embed) เฉพาะข้อมูลที่มีจำนวนจำกัดแน่นอน (เช่น รายการสินค้าไม่เกิน 50 ชิ้นใน 1 บิล) ส่วนข้อมูลที่โตเรื่อยๆ ต้องแยก Collection |
| **การนำ MongoDB มาจำลองเป็น SQL** | แยกข้อมูลออกเป็น 15 Collections ย่อยๆ แล้วเขียน `$lookup` (Join) ซ้อนกัน 6 ชั้นในทุกคิวรี | หากข้อมูลมีความสัมพันธ์ซับซ้อนและต้อง Join ตลอดเวลา ให้ใช้ **PostgreSQL 16** ตั้งแต่แรก |
| **การใช้ชนิดข้อมูลตัวเลขกับการเงิน** | เก็บยอดเงินใน MongoDB เป็น Number ปกติของ JavaScript (IEEE 754 Float) ทำให้ทศนิยมเพี้ยน | หากต้องเก็บตัวเลขทศนิยมแม่นยำใน MongoDB ต้องใช้ชนิดข้อมูล `Decimal128` เสมอ |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ MongoDB เมื่อ:** ข้อมูลมีลักษณะเป็นเอกสารที่จบในตัวเอง (Self-contained Documents) เช่น ระบบจัดการเนื้อหาบทความ (CMS), ข้อมูลบันทึกเหตุการณ์จากอุปกรณ์ IoT / Event Logs, ระบบแชท หรือแค็ตตาล็อกสินค้าที่มีโครงสร้าง属性แตกต่างกันหลายร้อยรูปแบบและต้องการทำ Horizontal Sharding ขนาดใหญ่
- **ไม่ควรใช้ MongoDB เป็นฐานข้อมูลหลักเมื่อ:** ระบบเป็นงานบัญชี การเงิน การธนาคาร หรือระบบตัดสต็อก E-Commerce ที่ต้องอาศัยการทำ Multi-table Transactions และการตรวจสอบความสัมพันธ์แบบ Referential Integrity อย่างเข้มงวด

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ในการออกแบบ Schema ของ MongoDB เราใช้เกณฑ์อะไรในการตัดสินใจว่าควรใช้วิธี Embedding (ฝังข้อมูลไว้ในเอกสารเดียวกัน) หรือ Referencing (แยกเอกสารแล้วเก็บ ID อ้างอิง)?**
  - **แนวคำตอบ:** พิจารณาจาก 3 ปัจจัยหลัก:
    1. **ความสัมพันธ์และขีดจำกัดขนาด 16 MB:** หากเป็นความสัมพันธ์แบบ 1-to-Few (เช่น ที่อยู่จัดส่ง 2-3 แห่งของลูกค้า หรือรายการสินค้าใน 1 ใบสั่งซื้อ) ให้ใช้ **Embedding** แต่ถ้าเป็น 1-to-Many หรือ 1-to-Squillions ที่เติบโตไปเรื่อยๆ ไม่มีเพดาน (เช่น ประวัติการเข้าชมสินค้า หรือคอมเมนต์รีวิว) ต้องใช้ **Referencing** เพื่อไม่ให้ขนาดเอกสารทะลุลิมิต 16 MB
    2. **รูปแบบการอ่านและเขียน:** หากข้อมูลสองส่วนถูกดึงมาแสดงผลพร้อมกันเสมอและไม่ค่อยถูกแก้ไขแยกกัน ให้ใช้ Embedding
    3. **ความซ้ำซ้อนของการอัปเดต:** หากข้อมูลส่วนนั้นถูกอ้างอิงจากหลายที่และมีการเปลี่ยนค่าบ่อยๆ ให้ใช้ Referencing
- **Q2: หากคุณใช้ PostgreSQL 16 อยู่แล้ว และมีโจทย์ต้องเก็บข้อมูลสเปกสินค้าที่มีฟิลด์ยืดหยุ่นไม่แน่นอนประมาณ 100,000 ชิ้น คุณจำเป็นต้องตั้งเซิร์ฟเวอร์ MongoDB เพิ่มหรือไม่?**
  - **แนวคำตอบ:** ไม่จำเป็นเลย เพราะที่ขนาดข้อมูลระดับนี้ คอลัมน์ `JSONB` พร้อมดัชนี `GIN Index` ใน PostgreSQL 16 สามารถจัดเก็บและสืบค้นข้อมูลโครงสร้างยืดหยุ่นได้ด้วยความเร็วระดับมิลลิวินาทีเทียบเท่า MongoDB โดยไม่ต้องเพิ่มภาระในการดูแลรักษาฐานข้อมูลตัวที่สอง (Operational Overhead) และยังได้ประโยชน์จากการทำ ACID Transaction ร่วมกับตาราง `orders` ในฐานข้อมูลเดียวกันอีกด้วย

## 3. การใช้ Redis สำหรับ Caching, Session, Queue และ Rate Limiting

### แนวคิด (Concept)
ต่อให้เราปรับจูน **PostgreSQL 16** จนเร็วแค่ไหน การดึงข้อมูลจากฐานข้อมูลหลักก็ยังมีต้นทุนในการประมวลผล SQL และการอ่านดิสก์ หากหน้าร้านของ **Smart Butcher Marketplace** มีลูกค้า 50,000 คนเปิดเข้ามาดูหน้าแรกพร้อมกันเพื่อดูรายการ "เนื้อวากิวแนะนำประจำสัปดาห์" (ซึ่งข้อมูลเหมือนเดิมทุกประการสำหรับลูกค้าทุกคน) การปล่อยให้คิวรี `SELECT` แบบเดียวกันวิ่งไปกวน PostgreSQL 50,000 ครั้งต่อวินาทีถือเป็นการใช้ทรัพยากรที่สิ้นเปลืองอย่างยิ่ง

เราจึงนำ **Redis (Remote Dictionary Server)** ซึ่งเป็นฐานข้อมูลแบบ **In-Memory Key-Value Data Structure Store** ที่เก็บข้อมูลทั้งหมดไว้ในหน่วยความจำหลัก (RAM) มาวางไว้ข้างหน้า เพื่อตอบสนองคำขอซ้ำๆ ด้วยความเร็วระดับ **ต่ำกว่า 1 มิลลิวินาที (Sub-millisecond Latency)** และรับภาระงานที่ต้องการความเร็วสูงและข้อมูลมีอายุสั้น (Ephemeral Data)

### หลักการเบื้องหลัง (Under the Hood)
ทำไม Redis ถึงทำงานได้เร็วระดับแสนคำสั่งต่อวินาทีและทำหน้าที่ได้หลากหลาย?
1. **In-Memory & Single-Threaded Event Loop Architecture:**
   Redis เก็บข้อมูลใน RAM และใช้สถาปัตยกรรม **Single-Threaded Event Loop (ร่วมกับ I/O Multiplexing `epoll`/`kqueue`)** ในการประมวลผลคำสั่งหลัก ข้อดีที่คาดไม่ถึงของการใช้เธรดเดียวทำงานใน RAM คือ **ไม่มีการเสียเวลาทำ Context Switching และไม่ต้องมีการขอ Lock/Mutex ใดๆ เลย!** ทุกคำสั่งของ Redis จึงมีคุณสมบัติเป็น **Atomic Operation (ทำงานรวดเดียวจบไม่มีใครแทรกกลางได้)** โดยธรรมชาติ
2. **โครงสร้างข้อมูลขั้นสูง (Rich In-Memory Data Structures):**
   Redis ไม่ได้เก็บได้แค่ String ธรรมดา แต่มีโครงสร้างข้อมูลระดับ алгоритึมในตัว:
   - `STRING`: เก็บ JSON Cache ของรายการสินค้า หรือใช้คำสั่ง `INCR` นับจำนวนการยิง API (Rate Limiting)
   - `HASH`: เก็บข้อมูล Session ของผู้ใช้ หรือตะกร้าสินค้าชั่วคราว (`HSET cart:user_123 product_a5 2`)
   - `LIST` & `STREAM`: ใช้สร้างระบบคิวงานเบื้องหลัง (Message Queue / BullMQ) เช่น คิวส่งอีเมลใบเสร็จหรือคิวแจ้งเตือนเชฟหั่นเนื้อ
   - `SORTED SET (ZSET)`: เก็บอันดับสินค้าขายดีแบบเรียลไทม์ (Real-time Leaderboard) หรือทำ Sliding Window Rate Limiter
3. **กลยุทธ์ Cache-Aside Pattern (Lazy Loading) & Cache Invalidation:**
   ```text filename="docs/database/sql-vs-nosql.txt"
   [ 1. แอปพลิเคชันเช็คข้อมูลใน Redis ก่อน: GET catalog:featured_wagyu ]
            │
            ├──► เจอข้อมูล (CACHE HIT - 0.3ms!) ──► ส่งคืนให้ลูกค้าทันที (ไม่ต้องกวน PostgreSQL เลย!)
            │
            └──► ไม่เจอ (CACHE MISS) ──► 2. คิวรีจาก PostgreSQL 16 (5ms)
                                                  │
                                                  ▼
                                        3. นำผลลัพธ์มาเซฟลง Redis พร้อมตั้งเวลาหมดอายุ (SET ... EX 300)
                                                  │
                                                  ▼
                                        4. ส่งข้อมูลคืนให้ลูกค้า
   ```
   และเมื่อแอดมินแก้ไขราคาเนื้อวากิวใน PostgreSQL 16 โค้ดจะต้องสั่ง **`DEL catalog:featured_wagyu` (Cache Invalidation)** ทันทีเพื่อให้ลูกค้าเห็นราคาใหม่ที่ถูกต้องเสมอ!

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การทำ Cache-Aside Pattern ร่วมกับ Cache Invalidation สำหรับหน้าแค็ตตาล็อกเนื้อพรีเมียม
โค้ดบริการที่ใช้ `ioredis` คู่กับ `PrismaService` เพื่อลดภาระของ PostgreSQL 16 ลงกว่า 95% ในหน้ารายการสินค้ายอดนิยม พร้อมล้างแคชทันทีเมื่อมีการอัปเดตราคาสินค้า:

```typescript filename="src/products/cached-catalog.service.ts"
import { Injectable, Logger } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import Redis from 'ioredis';

const FEATURED_WAGYU_CACHE_KEY = 'smart_butcher:catalog:featured_wagyu:v1';
const CACHE_TTL_SECONDS = 300; // เก็บแคชไว้นาน 5 นาที (300 วินาที)

@Injectable()
export class CachedCatalogService {
  private readonly logger = new Logger(CachedCatalogService.name);

  constructor(
    private readonly prisma: PrismaService,
    private readonly redis: Redis
  ) {}

  async getFeaturedWagyuProducts() {
    // 1. พยายามอ่านจากหน่วยความจำ Redis ก่อน (ใช้เวลา < 0.5ms)
    const cachedJson = await this.redis.get(FEATURED_WAGYU_CACHE_KEY);
    if (cachedJson) {
      return JSON.parse(cachedJson);
    }

    // 2. หากเป็น Cache Miss จึงค่อยวิ่งไปคิวรีจาก PostgreSQL 16
    this.logger.debug('Cache miss for featured Wagyu. Querying PostgreSQL 16...');
    const products = await this.prisma.product.findMany({
      where: {
        marblingScore: { gte: 9 },
        stockWeightGr: { gt: 0 },
      },
      select: {
        id: true,
        sku: true,
        name: true,
        marblingScore: true,
        pricePerKg: true,
        stockWeightGr: true,
        category: { select: { name: true, slug: true } },
      },
      orderBy: { marblingScore: 'desc' },
      take: 20,
    });

    // 3. บันทึกผลลัพธ์ลง Redis พร้อมตั้งเวลาหมดอายุ (EX = Expire in seconds)
    await this.redis.set(
      FEATURED_WAGYU_CACHE_KEY,
      JSON.stringify(products),
      'EX',
      CACHE_TTL_SECONDS
    );

    return products;
  }

  // 4. เมื่อแอดมินปรับราคาเนื้อหรือตัดสต็อก ต้องสั่งลบแคชทิ้งทันที (Cache Invalidation)
  async updateProductPriceAndInvalidateCache(productId: string, newPricePerKg: number) {
    const updated = await this.prisma.product.update({
      where: { id: productId },
      data: { pricePerKg: newPricePerKg },
    });

    // ล้างแคชเพื่อให้คำขอถัดไปดึงราคาใหม่ล่าสุดจาก PostgreSQL 16
    await this.redis.del(FEATURED_WAGYU_CACHE_KEY);
    return updated;
  }
}
```

#### ตัวอย่างที่ 2: การทำ Atomic Rate Limiting และ Distributed Flash-Sale Lock ด้วย Redis Lua Script
เพื่อป้องกันบอทยิง API สั่งซื้อเนื้อวากิวลดราคารัวๆ (Rate Limiting) เราใช้คำสั่งรันภายใน **Redis Lua Script** ซึ่งรับประกันความเป็น Atomic 100% ในระดับไมโครวินาทีโดยไม่เกิด Race Condition:

```typescript filename="src/security/redis-rate-limiter.service.ts"
import { Injectable, HttpException, HttpStatus } from '@nestjs/common';
import Redis from 'ioredis';

// สคริปต์ Lua ที่รันจบแบบ Atomic ในเธรดเดียวของ Redis:
// เพิ่มตัวนับ +1 และถ้าเป็นครั้งแรกของรอบเวลา ให้ตั้งเวลาหมดอายุ (EXPIRE) ทันที
const ATOMIC_RATE_LIMIT_LUA = `
  local current = redis.call("INCR", KEYS[1])
  if current == 1 then
    redis.call("EXPIRE", KEYS[1], ARGV[1])
  end
  return current
`;

@Injectable()
export class RedisRateLimiterService {
  constructor(private readonly redis: Redis) {}

  async enforceOrderRateLimit(userIdOrIp: string, maxRequests = 5, windowSeconds = 10) {
    const rateLimitKey = `smart_butcher:ratelimit:checkout:${userIdOrIp}`;

    const requestCount = (await this.redis.eval(
      ATOMIC_RATE_LIMIT_LUA,
      1,
      rateLimitKey,
      windowSeconds
    )) as number;

    if (requestCount > maxRequests) {
      throw new HttpException(
        {
          statusCode: HttpStatus.TOO_MANY_REQUESTS,
          message: `Too many checkout attempts. Allowed ${maxRequests} requests per ${windowSeconds} seconds.`,
        },
        HttpStatus.TOO_MANY_REQUESTS
      );
    }
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การตั้งเวลาหมดอายุ (TTL)** | สั่ง `redis.set(key, val)` โดยไม่ใส่เวลาหมดอายุ (`EX`) ทำให้ข้อมูลเก่าค้างเต็ม RAM จนเกิด Out of Memory | กำหนดค่า TTL (`EX <seconds>`) ให้กับทุกคีย์ที่เป็น Cache เสมอ และตั้งนโยบาย `maxmemory-policy allkeys-lru` |
| **การใช้คำสั่งค้นหาคีย์บน Production** | รันคำสั่ง `KEYS *` บน Redis ที่มีคีย์อยู่ 5 ล้านตัว ทำให้ Single Thread ของ Redis ค้างไปหลายวินาทีจนเว็บล่ม | ห้ามใช้ `KEYS *` บน Production เด็ดขาด ให้ใช้คำสั่ง `SCAN` ที่ทยอยดึงทีละชุดโดยไม่บล็อกระบบแทน |
| **การใช้ Redis เก็บข้อมูลการเงินหลัก** | เก็บประวัติการโอนเงิน (`payments`) ไว้ใน Redis เพียงที่เดียวโดยไม่บันทึกลง PostgreSQL | ใช้ Redis สำหรับข้อมูลชั่วคราวหรือ Cache เท่านั้น ส่วนข้อมูลหลัก (System of Record) ต้องอยู่ใน PostgreSQL เสมอ |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Redis เมื่อ:** ต้องการทำ Caching ข้อมูลที่ถูกอ่านบ่อยแต่แก้ไขไม่บ่อย, จัดเก็บ User Sessions / Refresh Tokens, ทำระบบคิวงานเบื้องหลัง (BullMQ), ทำ Rate Limiting ป้องกัน API ถูกโจมตี และทำ Pub/Sub แจ้งเตือนแบบเรียลไทม์
- **ไม่ควรใช้ Redis เมื่อ:** ข้อมูลมีขนาดใหญ่ระดับหลายร้อยกิกะไบต์ (เพราะค่าใช้จ่าย RAM แพงกว่า SSD มาก) หรือต้องการค้นหาข้อมูลด้วยเงื่อนไขซับซ้อนหลายคอลัมน์

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ในการทำ Rate Limiting ด้วย Redis ทำไมเราจึงควรใช้ Lua Script รวมคำสั่ง `INCR` และ `EXPIRE` เข้าด้วยกัน แทนที่จะเขียนแยกเป็น `await redis.incr(key)` แล้วตามด้วย `await redis.expire(key, 10)` ในโค้ด Node.js?**
  - **แนวคำตอบ:** หากเขียนแยกเป็น 2 คำสั่งใน Node.js แล้วเกิดเหตุการณ์ที่เซิร์ฟเวอร์แอปพลิเคชันรีสตาร์ทหรือเครือข่ายหลุดหลังจากรัน `INCR` สำเร็จแต่ยังไม่ได้รัน `EXPIRE` คีย์นั้นจะกลายเป็นคีย์อมตะที่ไม่มีวันหมดอายุ (TTL = -1) ส่งผลให้ผู้ใช้งานคนนั้นถูกบล็อกออกจากระบบไปตลอดกาล! การรวมไว้ใน Lua Script บังคับให้ Redis รันทั้งสองคำสั่งแบบ Atomic ในขั้นตอนเดียว จึงไม่เกิดปัญหานี้เด็ดขาด
- **Q2: ปัญหา Cache Stampede (หรือ Thundering Herd) คืออะไร และจะเกิดขึ้นกับระบบร้านค้าเมื่อใด?**
  - **แนวคำตอบ:** เกิดขึ้นเมื่อคีย์แคชของหน้าที่มีคนเข้าดูพร้อมกันจำนวนมาก (เช่น หน้าสินค้า Flash Sale) หมดอายุ (TTL Expired) ลงในเสี้ยววินาทีที่มีผู้ใช้งาน 5,000 คนกดเข้ามาพอดี ทำให้ทั้ง 5,000 Requests เจอสถานะ Cache Miss พร้อมกันทั้งหมดและแห่กันยิงคิวรีทะลุเข้าไปหาฐานข้อมูล PostgreSQL พร้อมกันในเสี้ยววินาทีเดียวจนฐานข้อมูลล่ม วิธีป้องกันคือการใช้ Distributed Mutex Lock ให้มีเพียง 1 Request เท่านั้นที่เข้าไปดึงข้อมูลจาก Postgres มาเติมแคช หรือใช้เทคนิค Stale-While-Revalidate (สุ่มต่ออายุแคชก่อนหมดเวลาจริงเล็กน้อย)

## 4. ฐานข้อมูลเฉพาะทางที่ควรรู้จัก (SQLite, Elasticsearch) และทฤษฎีบท CAP Theorem

### แนวคิด (Concept)
นอกจาก PostgreSQL 16, MongoDB และ Redis แล้ว วิศวกร Fullstack ระดับอาวุโสจำเป็นต้องเข้าใจฐานข้อมูลเฉพาะทางอีก 2 ตัวที่มักพบในสถาปัตยกรรมยุคใหม่ ได้แก่:
1. **SQLite:** ฐานข้อมูล SQL แบบฝังตัว (Embedded Relational Database) ที่ไม่มีเซิร์ฟเวอร์แยก แต่เก็บฐานข้อมูลทั้งก้อนไว้ใน **ไฟล์เพียงไฟล์เดียวบนดิสก์ (`.sqlite` / `.db`)**
2. **Elasticsearch (และ OpenSearch / Meilisearch):** เอนจินค้นหาข้อความเต็มรูปแบบ (Distributed Full-Text Search & Analytics Engine) ที่สร้างขึ้นบนไลบรารี Apache Lucene

ควบคู่ไปกับกฎฟิสิกส์พื้นฐานของระบบกระจายตัว (Distributed Systems) ที่เรียกว่า **CAP Theorem (ทฤษฎีบทของ Brewer)** ซึ่งเป็นเข็มทิศในการตัดสินใจเมื่อระบบเครือข่ายเกิดปัญหา

### หลักการเบื้องหลัง (Under the Hood)
1. **SQLite (Serverless Embedded SQL + WAL Mode):**
   ทำงานอยู่ในโปรเซสเดียวกับแอปพลิเคชันโดยตรง จึงไม่มีความหน่วงของเครือข่าย (Zero Network Latency) เมื่อเปิดโหมด `PRAGMA journal_mode = WAL;` จะอนุญาตให้อ่านข้อมูลพร้อมกันได้รวดเร็วมาก เหมาะกับแอปมือถือ (iOS/Android), โปรแกรม Desktop, อุปกรณ์ Edge/IoT หรือการรัน Unit Testing แต่ **ไม่เหมาะกับระบบเว็บขนาดใหญ่ที่มีหลายเซิร์ฟเวอร์เขียนข้อมูลพร้อมกัน** เพราะล็อกการเขียนระดับไฟล์ทั้งฐานข้อมูล (Single-writer lock)
2. **Elasticsearch (Inverted Index Architecture):**
   แทนที่จะเก็บข้อมูลเป็นแถวเหมือนตารางปกติ Elasticsearch จะทำการตัดคำ (Tokenization & Stemming) แล้วสร้างโครงสร้างที่เรียกว่า **Inverted Index (ดัชนีผกผัน - เหมือนดัชนีคำศัพท์ท้ายเล่มหนังสือ)** ที่ระบุว่าคำว่า `"วากิว"` ปรากฏอยู่ในเอกสารหมายเลขใดบ้าง พร้อมคำนวณคะแนนความเกี่ยวข้องด้วยอัลกอริทึม **BM25** ทำให้ค้นหาบทความหรือสินค้าหลายสิบล้านชิ้นพร้อมจัดกลุ่มตัวกรอง (Faceted Search) ได้ในเสี้ยววินาที
3. **ทฤษฎีบท CAP Theorem (Consistency, Availability, Partition Tolerance):**
   ทฤษฎีบทระบุว่าในระบบฐานข้อมูลแบบกระจายตัวที่มีหลายโหนดเชื่อมต่อกันผ่านเครือข่าย:
   - **C (Consistency):** ทุกโหนดต้องมองเห็นข้อมูลชุดเดียวกันที่เป็นปัจจุบันล่าสุดเสมอ (อ่านจากโหนดไหนก็ต้องได้ค่าล่าสุดที่เพิ่งเขียนเสร็จ)
   - **A (Availability):** ทุกคำขอที่ส่งไปยังโหนดที่ยังไม่ล่ม ต้องได้รับคำตอบกลับมาเสมอ (ห้ามปฏิเสธการทำงาน)
   - **P (Partition Tolerance):** ระบบยังต้องทำงานต่อไปได้แม้สายสัญญาณเครือข่ายระหว่างโหนดจะขาดออกจากกัน (Network Split / Partition)

   **ความจริงทางวิศวกรรม:** เนื่องจากในโลกความจริง สายเครือข่ายมีโอกาสขาดหรือดีเลย์ได้เสมอ ดังนั้น **P (Partition Tolerance) จึงเป็นสิ่งบังคับที่หลีกเลี่ยงไม่ได้!** เมื่อเกิดสายสัญญาณขาดระหว่างโหนดที่ 1 กับโหนดที่ 2 วิศวกรต้องเลือกระหว่าง:
   - **เลือก CP (Consistency + Partition Tolerance):** ยอมปฏิเสธการเขียนหรือการอ่านในโหนดที่ถูกตัดขาด เพื่อป้องกันไม่ให้ข้อมูลสต็อกเนื้อหรือยอดเงินขัดแย้งกัน (เช่น PostgreSQL Synchronous Replication, Redis Cluster ส่วนใหญ่, MongoDB ค่าเริ่มต้นแบบ Majority Write)
   - **เลือก AP (Availability + Partition Tolerance):** ยอมให้ทุกโหนดรับคำสั่งซื้อต่อไปได้แม้มองไม่เห็นกัน แล้วค่อยนำข้อมูลมาหาทางรวมกันทีหลังเมื่อสายสัญญาณกลับมาดี (เช่น Cassandra, DynamoDB โหมด Eventual Consistency)

```text filename="docs/database/sql-vs-nosql.txt"
       [ เกิดเหตุสายสัญญาณเครือข่ายระหว่าง Node A กับ Node B ขาด! (Network Partition = P) ]
                                        │
            ┌───────────────────────────┴───────────────────────────┐
            ▼                                                       ▼
  [ ระบบแบบ CP (เช่น ระบบการเงิน / สต็อกเนื้อ) ]            [ ระบบแบบ AP (เช่น ยอดกดไลก์ / ตะกร้าชั่วคราว) ]
  ยอมหยุดรับคำสั่งในฝั่งที่ขาดการติดต่อ (เสีย A)              ยอมให้ทั้งสองฝั่งเขียนข้อมูลต่อได้ทันที (รักษา A)
  เพื่อรับประกันว่ายอดเงินและสต็อกถูกต้อง 100% (รักษา C)    แต่ข้อมูลสองฝั่งจะไม่ตรงกันชั่วคราว (เสีย C -> Eventual)
```

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การทำ Full-Text Search ใน PostgreSQL 16 (`tsvector` + `tsquery` + `pg_trgm`) ก่อนตัดสินใจลงทุนตั้ง Elasticsearch
สำหรับร้าน **Smart Butcher Marketplace** ที่มีสินค้าเนื้อพรีเมียมหลักพันหรือหลักหมื่นรายการ เราไม่จำเป็นต้องเสียเงินดูแลคลัสเตอร์ Elasticsearch ที่มีราคาแพงและกิน RAM มหาศาล เพราะ PostgreSQL 16 มีระบบ **Full-Text Search (`tsvector`)** และ **Trigram Fuzzy Search (`pg_trgm`)** ในตัวที่เร็วและแม่นยำมากอยู่แล้ว:

```sql filename="01_pg16_builtin_fulltext_search.sql"
-- เพิ่มคอลัมน์ Generated tsvector ในตาราง products ที่อัปเดตตัวเองอัตโนมัติเมื่อชื่อหรือ SKU เปลี่ยน!
ALTER TABLE "products"
ADD COLUMN "search_vector" tsvector
GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce("name", '')), 'A') ||
    setweight(to_tsvector('english', coalesce("sku", '')), 'B')
) STORED;

-- สร้าง GIN Index บนคอลัมน์ search_vector
CREATE INDEX "idx_products_search_vector_gin"
ON "products" USING GIN ("search_vector");

-- ค้นหาสินค้าด้วย Full-Text Search พร้อมจัดอันดับความเกี่ยวข้อง (ts_rank) ใน PostgreSQL 16
SELECT
    id,
    sku,
    name,
    price_per_kg,
    ts_rank("search_vector", websearch_to_tsquery('english', 'wagyu ribeye a5')) AS relevance_score
FROM "products"
WHERE "search_vector" @@ websearch_to_tsquery('english', 'wagyu ribeye a5')
ORDER BY relevance_score DESC
LIMIT 10;
```

#### ตัวอย่างที่ 2: การควบคุมความเข้มงวดของ Consistency (CP) ใน PostgreSQL 16 สำหรับธุรกรรมการเงิน (`synchronous_commit`)
ในระดับ Transaction ของการบันทึกการชำระเงิน (`payments`) เราสามารถสั่งบังคับให้ PostgreSQL 16 ยืนยันการเขียนข้อมูลลงดิสก์และ/หรือ Standby Node อย่างเคร่งครัดตามหลัก **CP** เพื่อไม่ให้ข้อมูลการโอนเงินสูญหายแม้เซิร์ฟเวอร์หลักจะไฟดับกะทันหัน:

```typescript filename="src/payments/strict-cp-payment.service.ts"
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { Prisma } from '@prisma/client';

@Injectable()
export class StrictCpPaymentService {
  constructor(private readonly prisma: PrismaService) {}

  async confirmHighValuePayment(
    orderId: string,
    amount: Prisma.Decimal,
    providerTxId: string
  ) {
    return this.prisma.$transaction(async (tx) => {
      // บังคับระดับความทนทานและการซิงค์สูงสุด (CP Guarantee) สำหรับธุรกรรมรับเงินนี้โดยเฉพาะ
      await tx.$executeRaw`SET LOCAL synchronous_commit = 'on'`;

      const payment = await tx.payment.create({
        data: {
          orderId,
          amount,
          paymentMethod: 'PROMPTPAY_QR',
          providerTxId,
          paidAt: new Date(),
        },
      });

      await tx.order.update({
        where: { id: orderId },
        data: { status: 'PAID' },
      });

      return payment;
    });
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การใช้ SQLite ผิดประเภทงาน** | นำไฟล์ SQLite ไปวางบนเซิร์ฟเวอร์ที่มีหลาย Containers แย่งกันเขียนข้อมูลคำสั่งซื้อพร้อมกันจนเกิด `SQLITE_BUSY: database is locked` | ใช้ SQLite สำหรับ Embedded / Local App / Edge Read-heavy เท่านั้น ส่วนระบบเว็บหลาย Containers ให้ใช้ PostgreSQL 16 |
| **การตั้ง Elasticsearch เกินความจำเป็น** | มีสินค้าในร้านแค่ 2,000 ชิ้น แต่ลงทุนตั้งคลัสเตอร์ Elasticsearch 3 เครื่องและต้องเขียนโค้ดซิงค์ข้อมูลให้ปวดหัว | ใช้ Full-Text Search (`tsvector` + `pg_trgm`) ใน PostgreSQL 16 ก่อน จนกว่าข้อมูลจะแตะหลักหลายสิบล้านแถวจึงค่อยแยก Elasticsearch |
| **การเลือก AP กับระบบตัดสต็อก** | ใช้ฐานข้อมูลแบบ AP (Eventual Consistency) ในการตัดสต็อกเนื้อวากิวที่มีชิ้นเดียว ทำให้ลูกค้า 2 คนกดซื้อชิ้นเดียวกันสำเร็จพร้อมกัน (Overselling) | ระบบตัดสต็อกสินค้าและระบบการเงินต้องเลือกสถาปัตยกรรมแบบ **CP (Strong Consistency / ACID)** เสมอ |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ SQLite เมื่อ:** สร้างแอปพลิเคชันมือถือ, โปรแกรมติดตั้งบนเครื่องลูกค้า, หรือฐานข้อมูลฝังตัวขนาดเล็กที่รันอยู่ในโหนดเดียว
- **ควรใช้ Elasticsearch เมื่อ:** ระบบมีข้อมูลข้อความหลายสิบล้านเอกสารที่ต้องการการค้นหาแบบซับซ้อนหลายภาษา การทำ Autocomplete ความเร็วสูง หรือการวิเคราะห์ Log ขนาดใหญ่ (ELK Stack)
- **ไม่ควรใช้ระบบ Eventual Consistency (AP) กับยอดเงินและจำนวนสินค้าคงคลังเด็ดขาด**

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: จงอธิบายทฤษฎีบท CAP Theorem และตอบว่าทำไมในระบบจริงเราจึงไม่สามารถเลือก CA (ตัด P ทิ้ง) ได้?**
  - **แนวคำตอบ:** CAP Theorem ระบุว่าระบบฐานข้อมูลแบบกระจายตัวสามารถรับประกันคุณสมบัติได้พร้อมกันเพียง 2 ใน 3 ข้อ ได้แก่ Consistency (ข้อมูลตรงกันทุกโหนด), Availability (ทุกโหนดที่ทำงานอยู่ตอบสนองเสมอ) และ Partition Tolerance (ระบบทำงานต่อได้เมื่อเครือข่ายระหว่างโหนดขาด) ในโลกความเป็นจริง เราไม่สามารถเลือก CA ได้เพราะไม่มีเครือข่ายใดในโลกที่ไม่เคยเกิดปัญหาสายขาดหรือแพ็กเกจสูญหาย ดังนั้นเมื่อเกิด Network Partition (P) ขึ้น เราจึงถูกบังคับให้ต้องตัดสินใจเลือกว่าจะยอมหยุดรับคำขอเพื่อรักษาความถูกต้องของข้อมูล (**CP**) หรือจะยอมรับคำขอต่อไปโดยที่ข้อมูลอาจคลาดเคลื่อนกันชั่วคราว (**AP**)
- **Q2: สำหรับระบบ E-Commerce ระหว่างฟีเจอร์ "การตัดสต็อกเนื้อวากิวและชำระเงิน" กับฟีเจอร์ "การนับจำนวนคนกดดูหน้าสินค้า (View Counter)" คุณจะเลือกใช้แบบ CP หรือ AP สำหรับแต่ละฟีเจอร์?**
  - **แนวคำตอบ:**
    - ฟีเจอร์ **การตัดสต็อกและชำระเงิน** ต้องเป็น **CP (Strong Consistency / ACID)** เท่านั้น เพราะห้ามเกิดการขายเนื้อเกินจำนวนที่มีอยู่จริง และยอดเงินห้ามคลาดเคลื่อนแม้แต่สตางค์เดียว หากโหนดฐานข้อมูลหลักติดต่อไม่ได้ ระบบต้องปฏิเสธการทำรายการแทนที่จะรับเงินมาแบบผิดๆ
    - ส่วนฟีเจอร์ **การนับยอดวิวสินค้า** สามารถใช้แบบ **AP (Eventual Consistency)** ได้อย่างสบาย เพราะหากยอดคนดูหน้าเว็บอัปเดตช้าไป 2-3 วินาที หรือคลาดเคลื่อนไป 1-2 ครั้งระหว่างซิงค์ข้อมูล ก็ไม่ส่งผลกระทบใดๆ ต่อความถูกต้องทางธุรกิจ แต่ช่วยให้หน้าเว็บโหลดเร็วและไม่ล่ม

## 5. แนวคิด Polyglot Persistence และเหตุผลที่ระบบร้านค้าเลือก PostgreSQL 16

### แนวคิด (Concept)
ในอดีต องค์กรมักพยายามยัดเยียดงานทุกประเภทลงในฐานข้อมูลยี่ห้อเดียว แต่สถาปัตยกรรมระดับ Enterprise ยุคปัจจุบันใช้แนวคิดที่เรียกว่า **Polyglot Persistence (การใช้ฐานข้อมูลหลายประเภทร่วมกันตามความถนัดของแต่ละงานในระบบเดียว)**
เหมือนกับในร้าน **Smart Butcher Marketplace** ที่เราไม่ได้ใช้มีดเล่มเดียวทำทุกอย่าง:
- เราใช้ **มีดแล่เนื้อญี่ปุ่นความแม่นยำสูง (PostgreSQL 16)** เป็นฐานข้อมูลหลัก (Primary System of Record) สำหรับเก็บข้อมูลลูกค้า หมวดหมู่ สินค้า คำสั่งซื้อ รายการตัดแต่ง และการชำระเงิน เพราะต้องการความถูกต้องระดับ **100% ACID**
- ควบคู่ไปกับการใช้ **ถาดสแตนเลสวางหน้าร้านที่หยิบได้ในเสี้ยววินาที (Redis)** สำหรับทำ Caching แค็ตตาล็อกสินค้า, จัดการคิวงานส่งอีเมลใบเสร็จ และทำ Rate Limiting ป้องกันบอท!

### หลักการเบื้องหลัง (Under the Hood)
ทำไมแกนกลางของระบบร้านค้าออนไลน์ (E-Commerce Core: `users`, `categories`, `products`, `orders`, `order_items`, `payments`) จึงต้องสร้างอยู่บน **PostgreSQL 16** เท่านั้น?
1. **การป้องกันปัญหาขายสินค้าเกินสต็อก (Preventing Overselling via Row-Level Locking & Constraints):**
   เมื่อเนื้อวากิว A5 ชิ้นสุดท้าย (`stock_weight_gr = 500`) ถูกลูกค้า 10 คนกดสั่งซื้อพร้อมกันในเสี้ยววินาทีเดียว PostgreSQL 16 มีกลไก Row-level Lock (`SELECT ... FOR UPDATE` หรือ Atomic `UPDATE ... WHERE stock_weight_gr >= 500`) คู่กับ `CHECK (stock_weight_gr >= 0)` ที่รับประกันในระดับเคอร์เนลของฐานข้อมูลว่าจะมีลูกค้าเพียง 1 คนเท่านั้นที่ตัดสต็อกสำเร็จ ส่วนอีก 9 คนจะถูกปฏิเสธอย่างปลอดภัย ไม่มีทางที่สต็อกจะติดลบ!
2. **ความสมบูรณ์ของธุรกรรมข้ามตาราง (Multi-Table ACID Transaction):**
   การกดสั่งซื้อ 1 ครั้งต้องทำการ: (1) ตัดสต็อกใน `products`, (2) สร้างหัวบิลใน `orders`, (3) สร้างรายการย่อยใน `order_items`, และ (4) บันทึกสถานะใน `payments` ทั้ง 4 ตารางนี้ต้องสำเร็จพร้อมกันทั้งหมดหรือยกเลิกทั้งหมด (`BEGIN ... COMMIT`) ซึ่งเป็นจุดแข็งที่สุดของ PostgreSQL 16
3. **ความถูกต้องทางการเงินและการตรวจสอบย้อนหลัง (Financial Precision & Referential Integrity):**
   ชนิดข้อมูล `NUMERIC(12, 2)` คำนวณเงินได้แม่นยำไร้ข้อผิดพลาดจากการปัดเศษ และ Foreign Key (`ON DELETE RESTRICT`) ป้องกันไม่ให้ใครเผลอลบข้อมูลสินค้าหรือลูกค้าที่มีประวัติการซื้อขายไปแล้วได้

```text filename="docs/database/sql-vs-nosql.txt"

                    │     Smart Butcher Backend (NestJS)       │

                                ▼                  ▼
```

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: โค้ดผสานการทำงานแบบ Polyglot Persistence (Redis Rate Limit + PostgreSQL 16 ACID Transaction + Redis Cache Invalidation)
ตัวอย่างการใช้งานจริงที่สมบูรณ์แบบที่สุดของการผสาน **Redis** และ **PostgreSQL 16 (ผ่าน Prisma)** เข้าด้วยกันในกระบวนการสั่งซื้อเนื้อพรีเมียม:

```typescript filename="src/orders/polyglot-checkout.service.ts"
import { Injectable, BadRequestException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { RedisRateLimiterService } from '../security/redis-rate-limiter.service';
import Redis from 'ioredis';

@Injectable()
export class PolyglotCheckoutService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly redis: Redis,
    private readonly rateLimiter: RedisRateLimiterService
  ) {}

  async placeButcherOrder(params: {
    userId: string;
    productId: string;
    quantityGrams: number;
    paymentMethod: string;
  }) {
    // ขั้นตอนที่ 1 [Redis]: ตรวจสอบ Rate Limit ในหน่วยความจำ (< 0.3ms) เพื่อกันบอทยิงรัวๆ ก่อนถึง Postgres
    await this.rateLimiter.enforceOrderRateLimit(params.userId, 5, 10);

    // ขั้นตอนที่ 2 [PostgreSQL 16]: รัน ACID Transaction ตัดสต็อกและสร้างใบสั่งซื้ออย่างแม่นยำ 100%
    const completedOrder = await this.prisma.$transaction(async (tx) => {
      // ตัดสต็อกแบบ Atomic พร้อมตรวจสอบว่ามีเนื้อพอขายหรือไม่ในคำสั่งเดียว
      const updatedCount = await tx.product.updateMany({
        where: {
          id: params.productId,
          stockWeightGr: { gte: params.quantityGrams },
        },
        data: {
          stockWeightGr: { decrement: params.quantityGrams },
        },
      });

      if (updatedCount.count === 0) {
        throw new BadRequestException('Insufficient Wagyu stock available.');
      }

      const product = await tx.product.findUniqueOrThrow({
        where: { id: params.productId },
        select: { id: true, pricePerKg: true, stockWeightGr: true },
      });

      const totalAmount = product.pricePerKg.mul(params.quantityGrams).div(1000);

      // สร้างใบสั่งซื้อ รายการย่อย และบันทึกการชำระเงินเริ่มต้นใน Transaction เดียวกัน
      const order = await tx.order.create({
        data: {
          userId: params.userId,
          status: 'PENDING',
          totalAmount,
          items: {
            create: {
              productId: product.id,
              quantityGrams: params.quantityGrams,
              unitPricePerKg: product.pricePerKg,
              subtotal: totalAmount,
            },
          },
          payment: {
            create: {
              amount: totalAmount,
              paymentMethod: params.paymentMethod,
            },
          },
        },
        include: { items: true, payment: true },
      });

      return { order, remainingStock: product.stockWeightGr };
    });

    // ขั้นตอนที่ 3 [Redis]: หลังจาก COMMIT ลง Postgres สำเร็จแล้ว จึงค่อยล้างแคชหน้ารายการสินค้าและส่งงานเข้าคิว!
    await this.redis.del('smart_butcher:catalog:featured_wagyu:v1');

    return completedOrder.order;
  }
}
```

#### ตัวอย่างที่ 2: ตารางเปรียบเทียบการตัดสินใจเลือกฐานข้อมูลตามฟีเจอร์ของระบบ (Architecture Decision Matrix)
เราสามารถสรุปกฎการเลือกใช้ฐานข้อมูลสำหรับแต่ละโมดูลในโปรเจกต์ออกมาเป็นโค้ดตั้งค่าสถาปัตยกรรมที่ชัดเจน:

```typescript filename="src/config/storage-architecture.manifest.ts"
export const SMART_BUTCHER_STORAGE_ARCHITECTURE = {
  coreTransactionalData: {
    tables: ['users', 'categories', 'products', 'orders', 'order_items', 'payments'],
    engine: 'PostgreSQL 16',
    rationale: 'Requires strict ACID transactions, NUMERIC financial precision, and Foreign Key integrity.',
  },
  semiStructuredProductSpecs: {
    storageLocation: 'products.origin_metadata (JSONB column)',
    engine: 'PostgreSQL 16 (JSONB + GIN Index)',
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การนำฐานข้อมูลมารวมเกินความจำเป็น** | โปรเจกต์เพิ่งเริ่มต้นแต่ตั้งทั้ง Postgres, MongoDB, Cassandra, Neo4j และ Elasticsearch พร้อมกันจนทีมดูแลไม่ไหว | เริ่มต้นด้วย **PostgreSQL 16** (ใช้ทั้ง Relational + `JSONB` + Full-Text Search) คู่กับ **Redis** เมื่อจำเป็นเท่านั้น |
| **ลำดับการล้างแคชใน Transaction** | สั่งลบแคชใน Redis *ก่อน* ที่บล็อก `prisma.$transaction` จะ `COMMIT` เสร็จ ทำให้มีจังหวะที่แคชกลับไปอ่านค่าเก่ามาเติมใหม่ | สั่งลบหรืออัปเดตแคชใน Redis **หลังจากที่ `prisma.$transaction` ทำการ `COMMIT` สำเร็จแล้วเท่านั้น** |
| **การทำ Dual-Write โดยไม่มีตัวหลัก** | พยายามเขียนข้อมูลใบสั่งซื้อลงทั้ง Postgres และ MongoDB พร้อมกันในโค้ด พอตัวหนึ่งพังข้อมูลสองฝั่งก็ไม่ตรงกัน | กำหนดให้ **PostgreSQL 16 เป็น Single Source of Truth เพียงหนึ่งเดียว** ส่วนระบบรองให้รับข้อมูลผ่าน Cache-Aside หรือ Event Queue |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้สถาปัตยกรรม PostgreSQL 16 + Redis เมื่อ:** พัฒนาระบบ E-Commerce, ระบบจองคิว, ระบบ FinTech หรือระบบ SaaS ระดับ Production ที่ต้องการทั้งความถูกต้องของข้อมูล 100% และความเร็วในการตอบสนองระดับสูงสุด
- **ไม่ควรเพิ่มฐานข้อมูลตัวที่ 3 หรือ 4 เข้ามาในระบบ:** จนกว่าคุณจะมีตัวเลขพิสูจน์ชัดเจน (Benchmark Metrics) ว่าฟีเจอร์ในตัวของ PostgreSQL 16 ไม่สามารถรองรับปริมาณข้อมูลเฉพาะทางส่วนนั้นได้อีกต่อไป

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ในการทำ Polyglot Persistence ระหว่าง PostgreSQL กับ Redis ทำไมเราจึงต้องสั่งลบแคช (`redis.del`) หลังจากที่ `prisma.$transaction` ทำการ `COMMIT` เสร็จแล้วเท่านั้น ห้ามสั่งลบแคชข้างในบล็อก Transaction?**
  - **แนวคำตอบ:** เพราะขณะที่โค้ดยังอยู่ในบล็อก `$transaction` การเปลี่ยนแปลงใน PostgreSQL ยังไม่ถูก `COMMIT` (คนอื่นที่เข้ามาอ่านจะยังเห็นข้อมูลเก่าตามหลัก Isolation) หากเราสั่ง `redis.del()` ข้างในบล็อกก่อนที่จะ `COMMIT` แล้วในเสี้ยววินาทีนั้นมีผู้ใช้งานอีกรายเปิดหน้าเว็บเข้ามาพอดี ผู้ใช้รายนั้นจะเจอ Cache Miss แล้ววิ่งไปดึง **"ข้อมูลเก่าที่ยังไม่ Commit"** จาก PostgreSQL กลับมาเขียนทับลงใน Redis อีกครั้ง! ส่งผลให้แคชเก็บข้อมูลเก่าค้างไปจนกว่าจะหมดอายุ TTL
- **Q2: หากผู้บริหารถามคุณว่า "ทำไมระบบร้านค้าออนไลน์ของเราถึงเลือกใช้ PostgreSQL 16 เป็นฐานข้อมูลหลักแทนที่จะใช้ NoSQL ทั้งหมด?" คุณจะให้เหตุผลทางวิศวกรรมและธุรกิจอย่างไร?**
  - **แนวคำตอบ:**
    1. **ความถูกต้องทางการเงินและสต็อก (ACID & Financial Integrity):** ระบบร้านค้าห้ามขายของเกินสต็อกที่มีและยอดเงินในใบเสร็จต้องตรงกับรายการสินค้าทุกสตางค์ ซึ่ง PostgreSQL 16 รับประกันผ่าน Multi-table ACID Transactions และชนิดข้อมูล `NUMERIC`
    2. **ความยืดหยุ่นที่ครบจบในตัวเดียว (Multi-model Capabilities):** PostgreSQL 16 ไม่ได้เป็นแค่ตารางแบบเก่า แต่รองรับทั้ง `JSONB` (ทำงานแทน Document NoSQL ได้), Full-Text Search (ค้นหาข้อความได้) และ Vector Search (`pgvector`) ทำให้ลดต้นทุนและภาระในการดูแลรักษาฐานข้อมูลหลายยี่ห้อลงได้อย่างมหาศาล

## ข้อผิดพลาดที่พบบ่อย (Anti-patterns)

1. **การเลือกใช้ฐานข้อมูลที่ไม่มี ACID หรือไม่ทำ Transaction กับระบบการเงินและสต็อกสินค้า**
   - **สาเหตุ:** เลือกฐานข้อมูลตามกระแสโดยไม่วิเคราะห์ความต้องการด้านความถูกต้องของข้อมูล (Consistency)
   - **ผลกระทบ:** เกิดปัญหาตัดสต็อกซ้ำซ้อน (Overselling) หรือตัดเงินลูกค้าสำเร็จแต่ใบสั่งซื้อไม่ถูกสร้าง
   - **วิธีแก้:** ใช้ PostgreSQL 16 พร้อมกลไก ACID Transaction สำหรับข้อมูลหลักทางธุรกิจเสมอ

2. **การยัดข้อมูลทุกอย่างลงในคอลัมน์ `JSONB` ก้อนเดียวใน PostgreSQL**
   - **สาเหตุ:** ขี้เกียจออกแบบตารางและรัน Migration เลยสร้างตารางที่มีแค่ `id` กับ `data JSONB`
   - **ผลกระทบ:** สูญเสียการตรวจสอบชนิดข้อมูล การบังคับ `NOT NULL` การเชื่อม Foreign Key และทำให้สถิติของ Query Planner เพี้ยน
   - **วิธีแก้:** แยกฟิลด์หลักที่มีโครงสร้างแน่นอนออกเป็นคอลัมน์ปกติ แล้วใช้ `JSONB` เฉพาะกับข้อมูลส่วนขยายที่มีโครงสร้างหลากหลายเท่านั้น

3. **การฝัง Array ที่เติบโตไปเรื่อยๆ ลงในเอกสารใบเดียวของ MongoDB (Unbounded Array)**
   - **สาเหตุ:** นำทุกคำสั่งซื้อหรือทุกคอมเมนต์มา `push` ต่อท้ายในเอกสารของ `user` หรือ `product`
   - **ผลกระทบ:** เมื่อข้อมูลโตเกินขีดจำกัด **16 MB ต่อเอกสาร** การบันทึกข้อมูลจะพังทันทีและทำให้ประสิทธิภาพการเขียนตกต่ำ
   - **วิธีแก้:** แยกข้อมูลที่เติบโตแบบไร้ขีดจำกัดออกเป็น Collection แยกแล้วอ้างอิงด้วย ID

4. **การใช้คำสั่ง `KEYS *` บน Redis ในสภาพแวดล้อม Production**
   - **สาเหตุ:** ต้องการค้นหาและลบคีย์แคชที่มีคำนำหน้าเหมือนกันทั้งหมดด้วยวิธีง่ายๆ
   - **ผลกระทบ:** เนื่องจาก Redis ทำงานด้วย Single-threaded Event Loop คำสั่ง `KEYS *` จะบล็อกเธรดหลักเพื่อกวาดอ่านคีย์ทั้งหมดใน RAM ทำให้คำขออื่นๆ ทั้งระบบค้างและเกิด Timeout
   - **วิธีแก้:** ใช้คำสั่ง `SCAN` ที่ทยอยดึงคีย์ทีละส่วนโดยไม่บล็อกระบบ หรือเก็บชื่อคีย์ที่เกี่ยวข้องไว้ในโครงสร้าง `SET`

5. **การตั้งฐานข้อมูลแยกหลายตัวตั้งแต่เริ่มโปรเจกต์โดยไม่มีความจำเป็น (Premature Polyglot Sprawl)**
   - **สาเหตุ:** พยายามใช้ฐานข้อมูล 4-5 ยี่ห้อในระบบขนาดเล็กที่มีผู้ใช้งานหลักพันคน
   - **ผลกระทบ:** เสียค่าเซิร์ฟเวอร์สูงมาก เสียเวลาเขียนโค้ดซิงค์ข้อมูลข้ามฐานข้อมูล และเมื่อเกิดปัญหาข้อมูลไม่ตรงกันจะแก้ไขได้ยากมาก
   - **วิธีแก้:** ใช้ขีดความสามารถของ PostgreSQL 16 ให้เต็มที่ก่อน แล้วเพิ่ม Redis หรือฐานข้อมูลเฉพาะทางเมื่อมีคอขวดที่ชัดเจน

## Checklist สรุป

แนวทางตรวจสอบการออกแบบสถาปัตยกรรมฐานข้อมูลสำหรับระบบ **Smart Butcher Marketplace**:

- [ ] **System of Record on PostgreSQL 16:** ตารางหลักที่ต้องการความถูกต้องสูงสุด (`users`, `categories`, `products`, `orders`, `order_items`, `payments`) อยู่บน PostgreSQL 16 พร้อม Foreign Keys และ ACID Transactions
- [ ] **Smart JSONB Usage:** ใช้คอลัมน์ `JSONB` คู่กับ `GIN Index` สำหรับข้อมูลคุณลักษณะเสริมที่ยืดหยุ่น โดยไม่นำมาปนกับคอลัมน์หลักที่ใช้คำนวณเงินหรือเชื่อมตาราง
- [ ] **Redis Cache-Aside with TTL:** ข้อมูลแค็ตตาล็อกที่ถูกอ่านซ้ำบ่อยๆ มีการแคชไว้ใน Redis พร้อมกำหนดเวลาหมดอายุ (`EX`) ทุกคีย์ และมีการสั่ง `DEL` ล้างแคชหลังจบการแก้ไขข้อมูล
- [ ] **Post-Commit Side Effects:** การล้างแคชใน Redis หรือการส่งงานเข้า Queue ถูกเรียกทำงาน **หลังจาก** ที่บล็อก `prisma.$transaction` ทำการ `COMMIT` สำเร็จแล้วเท่านั้น
- [ ] **Zero Blocking Redis Commands:** ในโค้ด Production ไม่มีการเรียกใช้คำสั่ง `KEYS *` บน Redis เด็ดขาด
- [ ] **Right Tool for Media:** ไฟล์รูปภาพและเอกสารขนาดใหญ่ถูกจัดเก็บใน Object Storage (S3 / Supabase Storage / R2) แยกออกจากฐานข้อมูล
