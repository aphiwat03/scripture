## 1. แนวคิด (Concept)
เมื่อเซิร์ฟเวอร์แอปพลิเคชันของ **Smart Butcher Marketplace** ส่งคำสั่งซื้อเนื้อและข้อมูลบัตรกำนัลวิ่งผ่านสายเครือข่ายไปยังเซิร์ฟเวอร์ PostgreSQL 16 หากการเชื่อมต่อนั้นไม่ได้ถูกเข้ารหัส (Plaintext Connection) ข้อมูลรหัสผ่านและรายชื่อลูกค้าจะวิ่งผ่านเครือข่ายในรูปแบบข้อความธรรมดาที่ใครก็ตามที่ดักฟังแพ็กเกจอยู่ในเครือข่ายเดียวกัน (Man-in-the-Middle / Packet Sniffing) สามารถเปิดอ่านได้ทันที

เราจึงต้องบังคับใช้การเข้ารหัส **SSL/TLS (Transport Layer Security)** สำหรับทุกการเชื่อมต่อ และเปลี่ยนวิธีการยืนยันตัวตนของรหัสผ่านจาก `md5` แบบเก่าที่ล้าสมัย มาเป็นมาตรฐาน **`scram-sha-256`** ของ PostgreSQL 16 พร้อมเก็บรักษา `DATABASE_URL` ไว้ในระบบจัดการความลับ (Secret Manager) อย่างปลอดภัย

## 2. หลักการเบื้องหลัง (Under the Hood)
1. **การยืนยันตัวตนด้วย `scram-sha-256` ใน `pg_hba.conf`:**
   ใน PostgreSQL 16 กลไกเริ่มต้นสำหรับการแฮชรหัสผ่านคือ **SCRAM-SHA-256 (Salted Challenge Response Authentication Mechanism)** ซึ่งป้องกันทั้งการดักฟังรหัสผ่านระหว่างทางและการโจมตีแบบ Rainbow Table แม้ไฟล์ตารางระบบจะรั่วไหล
2. **การบังคับใช้ `hostssl` ใน `pg_hba.conf`:**
   ไฟล์ `pg_hba.conf` (Host-Based Authentication) คือปราการด่านแรกของ PostgreSQL หากเรากำหนดบรรทัดเป็น `hostssl` แทนคำว่า `host` เซิร์ฟเวอร์ PostgreSQL 16 จะ **ปฏิเสธการเชื่อมต่อทุกชนิดที่ไม่ได้เข้ารหัสด้วย TLS ทันที**
3. **ความแตกต่างของระดับ `sslmode` ใน Connection String:**
   - `disable`: ไม่เข้ารหัสเลย (อันตรายมาก ห้ามใช้บน Cloud/Production)
   - `require`: บังคับเข้ารหัสข้อมูลที่วิ่งผ่านสาย แต่ไม่ตรวจสอบใบรับรอง (Certificate) ว่าเซิร์ฟเวอร์ปลายทางเป็นตัวจริงหรือไม่ (ยังเสี่ยงต่อการถูกปลอมแปลงเซิร์ฟเวอร์คั่นกลาง)
   - `verify-ca`: เข้ารหัสและตรวจสอบว่าใบรับรองของเซิร์ฟเวอร์ออกโดยผู้ออกใบรับรอง (CA) ที่เราเชื่อถือ
   - **`verify-full` (ปลอดภัยสูงสุด):** เข้ารหัส ตรวจสอบ CA และตรวจสอบว่าชื่อโดเมน (Hostname) ของเซิร์ฟเวอร์ตรงกับที่ระบุในใบรับรองทุกประการ

## 3. ตัวอย่างโค้ด (Smart Butcher Marketplace)

### ตัวอย่างที่ 1: การตั้งค่า `postgresql.conf` และ `pg_hba.conf` เพื่อบังคับใช้ TLS 1.3 และ SCRAM-SHA-256
การกำหนดค่าฝั่งเซิร์ฟเวอร์ PostgreSQL 16 ให้รับเฉพาะการเชื่อมต่อที่เข้ารหัสด้วย TLS 1.2/1.3 และใช้รหัสผ่านแบบ SCRAM-SHA-256 เท่านั้น:

```ini filename="postgresql.conf"
# เปิดใช้งาน SSL/TLS และบังคับเวอร์ชันขั้นต่ำเป็น TLSv1.2 หรือ TLSv1.3
ssl = on
ssl_cert_file = '/etc/postgresql/16/certs/server.crt'
ssl_key_file = '/etc/postgresql/16/certs/server.key'
ssl_ca_file = '/etc/postgresql/16/certs/root-ca.crt'
ssl_min_protocol_version = 'TLSv1.2'

# บังคับการเข้ารหัสรหัสผ่านในระบบเป็น scram-sha-256
password_encryption = 'scram-sha-256'
```

```ini filename="pg_hba.conf"
# TYPE    DATABASE           USER               ADDRESS            METHOD
# อนุญาตให้เชื่อมต่อผ่าน Unix Socket เฉพาะผู้ดูแลระบบภายในเครื่องเท่านั้น
local     all                postgres                              peer

# ปฏิเสธการเชื่อมต่อทุกชนิดที่ไม่ได้ใช้ SSL/TLS (hostnossl) จากเครือข่ายภายนอกทั้งหมด
hostnossl all                all                0.0.0.0/0          reject
hostnossl all                all                ::/0               reject

# อนุญาตเฉพาะการเชื่อมต่อที่เข้ารหัส TLS (hostssl) จากวงเครือข่าย Private Subnet ของแอปพลิเคชันเท่านั้น
hostssl   smart_butcher_db   butcher_app        10.20.1.0/24       scram-sha-256
hostssl   smart_butcher_db   butcher_migrator   10.20.2.0/24       scram-sha-256
```

### ตัวอย่างที่ 2: การตั้งค่า Connection String แบบ `verify-full` และการตรวจสอบความถูกต้องของ Environment Variables ตอนเปิดแอป
การใช้ไลบรารี `zod` ในฝั่ง Backend เพื่อตรวจสอบตั้งแต่จังหวะเริ่มเปิดเซิร์ฟเวอร์ว่า `DATABASE_URL` บน Production ต้องมีการระบุ `sslmode=verify-full` หรือ `sslmode=require` เสมอ:

```typescript filename="src/config/database-env.validator.ts"
import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'staging', 'production']),
  DATABASE_URL: z
    .string()
    .url()
    .refine(
      (url) => url.startsWith('postgresql://') || url.startsWith('postgres://'),
      { message: 'DATABASE_URL must use postgresql:// protocol' }
    ),
  DIRECT_URL: z.string().url().optional(),
}).superRefine((data, ctx) => {
  // บังคับว่าบน Production ต้องเปิดใช้งาน SSL ใน Connection String เสมอ
  if (data.NODE_ENV === 'production') {
    const hasSecureSsl =
      data.DATABASE_URL.includes('sslmode=verify-full') ||
      data.DATABASE_URL.includes('sslmode=require');

    if (!hasSecureSsl) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['DATABASE_URL'],
        message: 'CRITICAL SECURITY ERROR: Production DATABASE_URL must enforce sslmode=verify-full or sslmode=require',
      });
    }
  }
});

export const validatedDbEnv = envSchema.parse(process.env);
```

## 4. ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การเก็บรักษา Connection String** | เผลอ Commit ไฟล์ `.env` ที่มีรหัสผ่านจริงขึ้น GitHub หรือพิมพ์รหัสผ่านตรงๆ ลงในไฟล์ `schema.prisma` | ใช้ `env("DATABASE_URL")` เสมอ และดึงค่าจาก Secret Manager (เช่น AWS Secrets Manager, Vault, GitHub Secrets) |
| **การตั้งค่า `pg_hba.conf`** | ตั้งค่า `host all all 0.0.0.0/0 trust` หรือ `md5` เปิดรับทุก IP โดยไม่ต้องใช้ SSL | ใช้ `hostssl` จำกัดเฉพาะวง IP ของแอปพลิเคชัน และบังคับใช้วิธี `scram-sha-256` |
| **การแสดงผล Log เมื่อเกิด Error** | พิมพ์ `console.log(process.env.DATABASE_URL)` ออกทางหน้าจอ Log ทำให้รหัสผ่านหลุดไปอยู่ในระบบเก็บ Log | ปกปิด (Mask/Redact) ส่วนรหัสผ่านใน URL เสมอก่อนทำการบันทึก Log ใดๆ |

## 5. ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `sslmode=verify-full` และ `hostssl` เมื่อ:** แอปพลิเคชันและฐานข้อมูลสื่อสารกันผ่านเครือข่าย ไม่ว่าจะอยู่ใน Cloud VPC เดียวกันหรือข้ามผู้ให้บริการคลาวด์ (เช่น แอปพลิเคชันรันบน Vercel แต่ฐานข้อมูลอยู่บน Supabase หรือ AWS RDS)
- **ไม่ควรใช้ `sslmode=disable` เมื่อ:** รันอยู่บนสภาพแวดล้อมใดๆ ที่ไม่ใช่ `localhost` บนเครื่องนักพัฒนาส่วนตัว

## 6. คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ใน Connection String ของ PostgreSQL ค่า `sslmode=require` กับ `sslmode=verify-full` ให้ความปลอดภัยแตกต่างกันอย่างไร?**
  - **แนวคำตอบ:** `sslmode=require` บังคับให้เข้ารหัสช่องทางสื่อสาร แต่ไม่ได้ตรวจสอบว่าใบรับรอง (Certificate) ของเซิร์ฟเวอร์ปลายทางเชื่อถือได้หรือไม่ หรือตรงกับโดเมนที่เราเรียกไปหรือไม่ ทำให้หากผู้โจมตีทำ DNS Spoofing หรือปลอมตัวเป็นเซิร์ฟเวอร์ฐานข้อมูลคั่นกลาง (Active Man-in-the-Middle) แอปพลิเคชันก็จะยอมเชื่อมต่อด้วย ในขณะที่ `sslmode=verify-full` จะตรวจสอบทั้งความถูกต้องของใบรับรองผ่าน Root CA และตรวจสอบว่าชื่อ Hostname ตรงกับใบรับรอง 100% จึงป้องกันการปลอมแปลงเซิร์ฟเวอร์ได้อย่างสมบูรณ์
- **Q2: หากคุณเผลอ Commit ไฟล์ `.env` ที่มีรหัสผ่านฐานข้อมูล Production ขึ้นไปบน Git Repository แล้ว แม้จะรีบลบไฟล์นั้นออกใน Commit ถัดมาทันที ทำไมถึงยังไม่ปลอดภัย และต้องทำอย่างไร?**
  - **แนวคำตอบ:** เพราะประวัติของไฟล์ยังคงฝังอยู่ใน Git History (`.git/objects`) และอาจถูกบอทสแกนดูดข้อมูลไปตั้งแต่วินาทีแรกที่ Push ขึ้นไปแล้ว วิธีรับมือที่ถูกต้องคือต้องถือว่ารหัสผ่านนั้นรั่วไหลแล้ว 100% ให้ทำการ **Rotate Password (เปลี่ยนรหัสผ่านใหม่ในฐานข้อมูลและใน Secret Manager ทันที)** จากนั้นค่อยล้างประวัติ Git และตรวจสอบ Audit Log ของฐานข้อมูลว่ามีการเข้าถึงที่ผิดปกติในช่วงเวลาดังกล่าวหรือไม่
