# Security

ฐานข้อมูลคือหัวใจที่เก็บทรัพย์สินที่มีค่าที่สุดของธุรกิจ หากเซิร์ฟเวอร์เว็บแอปพลิเคชันถูกเจาะระบบแต่ฐานข้อมูลมีการวางเกราะป้องกันแบบหลายชั้น (Defense in Depth) ความเสียหายก็จะถูกจำกัดวงไว้ได้ แต่หากฐานข้อมูลใช้บัญชี Superuser ร่วมกันทุกจุดและเปิดพอร์ตทิ้งไว้สู่สาธารณะ เพียงช่องโหว่เล็กน้อยจุดเดียวอาจหมายถึงข้อมูลลูกค้าทั้งหมดของบริษัทหลุดออกสู่ตลาดมืด เอกสารฉบับนี้เจาะลึกสถาปัตยกรรมความปลอดภัยของ **PostgreSQL 16** สำหรับระบบ **Smart Butcher Marketplace** ตั้งแต่การจัดการสิทธิ์ระดับ Role, การเข้ารหัส SSL/TLS, กลไกป้องกัน SQL Injection ระดับโปรโตคอล ไปจนถึงการปฏิบัติตาม พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA)

| หัวข้อในหน้านี้ | สาระสำคัญ |
| :--- | :--- |
| **1. การจัดการ Roles และสิทธิ์ตามหลัก Least Privilege (แยก Role แอปและ Migration)** | การแยกบัญชี `butcher_migrator` (DDL) ออกจาก `butcher_app` (DML) และการตั้งค่า `ALTER DEFAULT PRIVILEGES` |
| **2. การเข้ารหัสการเชื่อมต่อด้วย SSL/TLS และการเก็บรักษา Connection String** | โหมด `sslmode=verify-full`, การตั้งค่า `pg_hba.conf` ด้วย `scram-sha-256` และการจัดการ Secrets |
| **3. กลไกป้องกัน SQL Injection ด้วย Parameterized Queries ในระดับฐานข้อมูล** | การทำงานของ PostgreSQL Extended Query Protocol (Parse / Bind / Execute) และการป้องกันใน `$queryRaw` |
| **4. การปกป้องข้อมูลอ่อนไหว, การจำกัดเครือข่าย (Network Isolation) และกฎหมาย PDPA** | การเข้ารหัสระดับคอลัมน์, Private Subnet, Audit Log และการทำ Data Anonymization (Right to be Forgotten) |

<Callout type="warning" title="การเปลี่ยนแปลงด้านความปลอดภัยครั้งสำคัญใน PostgreSQL 15 และ 16">
ตั้งแต่ PostgreSQL 15 เป็นต้นมาจนถึง PostgreSQL 16 สิทธิ์เริ่มต้นในการสร้างตารางใหม่ (`CREATE`) บน Schema `public` ได้ถูกเพิกถอนออกจากกลุ่ม `PUBLIC` (ผู้ใช้งานทั่วไปทุกคน) โดยอัตโนมัติแล้ว เพื่อป้องกันช่องโหว่การสวมรอยวัตถุ (Trojan-horse Function Attacks via Search Path) ดังนั้นผู้ดูแลระบบต้องมอบสิทธิ์ให้แต่ละ Role อย่างชัดเจนเสมอ
</Callout>

## 1. การจัดการ Roles และสิทธิ์ตามหลัก Least Privilege (แยก Role แอปและ Migration)

### แนวคิด (Concept)
ในร้าน **Smart Butcher Marketplace** เราคงไม่มอบ "กุญแจมาสเตอร์คีย์ที่สามารถสั่งทุบทำลายห้องเย็นและตู้เซฟของบริษัทได้" ให้กับพนักงานแคชเชียร์หน้าร้าน พนักงานแคชเชียร์ควรมีสิทธิ์เพียงแค่การเปิดบิล (`INSERT`), ตัดสต็อกเนื้อ (`UPDATE`), และดูรายการสินค้า (`SELECT`) เท่านั้น ส่วนสิทธิ์ในการรื้อถอนหรือสร้างชั้นวางใหม่ (`CREATE TABLE`, `DROP TABLE`, `ALTER TABLE`) ต้องเป็นของวิศวกรก่อสร้างเพียงผู้เดียว

ในทางฐานข้อมูล หลักการนี้เรียกว่า **Principle of Least Privilege (การให้สิทธิ์เท่าที่จำเป็นต่อการปฏิบัติงานเท่านั้น)** โดยห้ามนำบัญชี Superuser (`postgres`) ไปใส่ไว้ในไฟล์ `.env` ของแอปพลิเคชัน Backend เด็ดขาด แต่ต้องแบ่งแยก Role ออกเป็น 3 ระดับชัดเจน:
1. **`butcher_migrator` (Schema Owner / DDL Role):** ใช้เฉพาะในไปป์ไลน์ CI/CD ตอนรันคำสั่ง `npx prisma migrate deploy` เท่านั้น มีสิทธิ์สร้างและแก้ไขโครงสร้างตาราง
2. **`butcher_app` (Application Runtime / DML Role):** ใช้โดยเซิร์ฟเวอร์ Node.js / NestJS ตลอด 24 ชั่วโมง มีสิทธิ์เฉพาะ `SELECT`, `INSERT`, `UPDATE`, `DELETE` เท่านั้น **ไม่มีสิทธิ์สั่ง `DROP TABLE` หรือ `TRUNCATE` เด็ดขาด**
3. **`butcher_readonly` (Analytics / BI Role):** ใช้สำหรับระบบออกรายงานยอดขาย มีสิทธิ์เพียง `SELECT` อย่างเดียว

### หลักการเบื้องหลัง (Under the Hood)
1. **PostgreSQL Unified Role System:**
   ใน PostgreSQL 16 คำว่า `USER` และ `GROUP` ถูกรวมเข้าด้วยกันภายใต้แนวคิดเดียวคือ **`ROLE`** (โดยคำสั่ง `CREATE USER` มีความหมายเทียบเท่ากับ `CREATE ROLE ... WITH LOGIN`)
2. **กับดักของตารางที่สร้างขึ้นใหม่ในอนาคต (`ALTER DEFAULT PRIVILEGES`):**
   ปัญหาที่วิศวกรส่วนใหญ่มักพลาดคือ เมื่อเราสั่ง `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO butcher_app;` คำสั่งนี้จะมีผลเฉพาะกับ **ตารางที่มีอยู่แล้ว ณ วินาทีนั้นเท่านั้น!** วันรุ่งขึ้นเมื่อ `butcher_migrator` รัน Migration สร้างตารางใหม่ชื่อ `promotions` บัญชี `butcher_app` จะไม่สามารถเข้าถึงตาราง `promotions` ได้เลย (เกิด Error `permission denied for table promotions`)
   เราจึงต้องสั่ง **`ALTER DEFAULT PRIVILEGES FOR ROLE butcher_migrator IN SCHEMA public GRANT ...`** เพื่อบอก PostgreSQL 16 ว่า "ตารางใดๆ ก็ตามที่ถูกสร้างโดย `butcher_migrator` ในอนาคต ให้มอบสิทธิ์ DML แก่ `butcher_app` โดยอัตโนมัติทันที"

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: สคริปต์ SQL สร้างและแยกสิทธิ์ Role สำหรับ Migration, Application และ Analytics
สคริปต์เตรียมความพร้อมระดับ Production ที่จำกัดจำนวนการเชื่อมต่อและแยกสิทธิ์ DDL ออกจาก DML อย่างเด็ดขาด:

```sql filename="01_setup_least_privilege_roles.sql"
-- 1. เพิกถอนสิทธิ์ที่ไม่จำเป็นจากกลุ่ม PUBLIC เพื่อความมั่นคงสูงสุดใน PostgreSQL 16
REVOKE ALL ON DATABASE smart_butcher_db FROM PUBLIC;
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- 2. สร้าง Role สำหรับรัน Migration ใน CI/CD (เจ้าของตารางและโครงสร้าง DDL)
CREATE ROLE butcher_migrator WITH
    LOGIN
    PASSWORD 'StrongMigratorPassword_#2026!'
    NOSUPERUSER NOCREATEDB NOCREATEROLE
    CONNECTION LIMIT 5;

-- 3. สร้าง Role สำหรับแอปพลิเคชัน Backend (ใช้รับคำสั่งซื้อตลอด 24 ชม. มีเฉพาะสิทธิ์ DML)
CREATE ROLE butcher_app WITH
    LOGIN
    PASSWORD 'StrongAppRuntimePassword_#2026!'
    NOSUPERUSER NOCREATEDB NOCREATEROLE
    CONNECTION LIMIT 100;

-- 4. สร้าง Role สำหรับทีม Data Analytics (อ่านได้อย่างเดียว และจำกัดเวลาคิวรีไม่ให้เกิน 10 วินาที)
CREATE ROLE butcher_readonly WITH
    LOGIN
    PASSWORD 'StrongReadOnlyPassword_#2026!'
    NOSUPERUSER NOCREATEDB NOCREATEROLE
    CONNECTION LIMIT 10;
ALTER ROLE butcher_readonly SET statement_timeout = '10s';

-- 5. มอบสิทธิ์การเชื่อมต่อฐานข้อมูลและใช้งาน Schema public
GRANT CONNECT ON DATABASE smart_butcher_db TO butcher_migrator, butcher_app, butcher_readonly;
GRANT USAGE, CREATE ON SCHEMA public TO butcher_migrator;
GRANT USAGE ON SCHEMA public TO butcher_app, butcher_readonly;

-- 6. มอบสิทธิ์บนตารางและ Sequences ที่มีอยู่แล้วในปัจจุบัน
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO butcher_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO butcher_app;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO butcher_readonly;

-- 7. สำคัญที่สุด: ตั้งค่า Default Privileges สำหรับตารางใหม่ที่จะถูกสร้างโดย butcher_migrator ในอนาคต
ALTER DEFAULT PRIVILEGES FOR ROLE butcher_migrator IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO butcher_app;

ALTER DEFAULT PRIVILEGES FOR ROLE butcher_migrator IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO butcher_app;

ALTER DEFAULT PRIVILEGES FOR ROLE butcher_migrator IN SCHEMA public
    GRANT SELECT ON TABLES TO butcher_readonly;
```

#### ตัวอย่างที่ 2: การตั้งค่า Prisma ให้ใช้ `butcher_app` ตอนรันแอป และใช้ `butcher_migrator` ตอนทำ Migration
การแยก Connection String ในไฟล์ `.env` และ `schema.prisma` เพื่อบังคับใช้ Least Privilege จริงในโค้ด:

```prisma filename="prisma/schema.prisma"
datasource db {
  provider  = "postgresql"
  // แอปพลิเคชันรันไทม์จะใช้ DATABASE_URL ซึ่งล็อกอินด้วยบัญชี butcher_app (ทำได้แค่ SELECT/INSERT/UPDATE/DELETE)
  url       = env("DATABASE_URL")
  // คำสั่ง prisma migrate deploy จะใช้ DIRECT_URL ซึ่งล็อกอินด้วยบัญชี butcher_migrator (มีสิทธิ์ ALTER/CREATE)
  directUrl = env("DIRECT_URL")
}
```

```ini filename=".env.example"
# สำหรับ Prisma Client ใน NestJS/Next.js (DML Only - ผ่าน Pooler ได้)
DATABASE_URL="postgresql://butcher_app:StrongAppRuntimePassword@pooler.smartbutcher.internal:6543/smart_butcher_db?pgbouncer=true&sslmode=verify-full"

# สำหรับ CI/CD Pipeline ตอนรัน npx prisma migrate deploy เท่านั้น (DDL Allowed - ต่อตรงเข้า Postgres)
DIRECT_URL="postgresql://butcher_migrator:StrongMigratorPassword@db.smartbutcher.internal:5432/smart_butcher_db?sslmode=verify-full"
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **บัญชีที่แอปพลิเคชันใช้** | ใช้บัญชี `postgres` (Superuser) ในโค้ด Node.js หากเกิดช่องโหว่แฮกเกอร์สามารถสั่ง `DROP TABLE` หรืออ่านไฟล์ใน OS ได้ทันที | ใช้บัญชีเฉพาะ `butcher_app` ที่มีสิทธิ์แค่ DML (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) เท่านั้น |
| **การจัดการตารางใหม่** | ต้องคอยมารัน `GRANT` ด้วยมือทุกครั้งหลัง Deploy เพราะลืมตั้งค่า Default Privileges | ตั้งค่า `ALTER DEFAULT PRIVILEGES FOR ROLE butcher_migrator` ไว้ตั้งแต่เริ่มต้น |
| **การจำกัดทรัพยากรราย Role** | ปล่อยให้ Role สำหรับทำรายงานรันคิวรีหนักๆ ค้างนานหลายชั่วโมงจนเว็บหน้าร้านล่ม | กำหนด `CONNECTION LIMIT` และ `ALTER ROLE ... SET statement_timeout` แยกตามหน้าที่ของแต่ละ Role |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้การแยก Role (App vs Migrator vs Readonly) เมื่อ:** ระบบขึ้นสู่ชั้น Staging และ Production ทุกกรณี
- **ไม่ควรให้สิทธิ์ `DELETE` บนตารางประวัติการเงิน (`payments`) แก่ `butcher_app`:** ในระบบการเงินที่เข้มงวด เราสามารถจำกัดให้ `butcher_app` มีสิทธิ์เพียง `SELECT, INSERT, UPDATE` บนตาราง `payments` และ `orders` โดยไม่อนุญาตให้สั่ง `DELETE` แถวข้อมูลทิ้งเลย (บังคับให้ใช้การเปลี่ยนสถานะ `status = 'CANCELLED'` แทน)

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ทำไมหลังจากที่เราสั่ง `GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA public TO app_user;` เรียบร้อยแล้ว พอสัปดาห์ต่อมามีการรัน Migration สร้างตารางใหม่ `app_user` ถึงขึ้น Error ว่า `permission denied` บนตารางใหม่นั้น?**
  - **แนวคำตอบ:** เพราะคำสั่ง `GRANT ... ON ALL TABLES` มีผลเฉพาะกับตารางที่มีตัวตนอยู่ในแค็ตตาล็อก ณ เวลาที่รันคำสั่งเท่านั้น ไม่ได้มีผลย้อนหลังไปถึงตารางที่จะถูกสร้างขึ้นใหม่ในอนาคต วิธีแก้ไขคือต้องรันคำสั่ง `ALTER DEFAULT PRIVILEGES FOR ROLE <role_ที่ใช้รัน_migration> IN SCHEMA public GRANT SELECT, INSERT ON TABLES TO app_user;`
- **Q2: หากเกิดช่องโหว่ในโค้ดที่ทำให้ผู้โจมตีสามารถรันคำสั่ง SQL ผ่าน Connection ของแอปพลิเคชันได้ การแยก Role `butcher_app` ออกจาก Superuser `postgres` จะช่วยลดความเสียหายได้อย่างไร?**
  - **แนวคำตอบ:** บัญชี Superuser `postgres` สามารถข้ามการตรวจสอบสิทธิ์ทั้งหมดได้ สามารถสั่ง `DROP DATABASE` ล้างข้อมูลทั้งบริษัท หรือที่ร้ายแรงที่สุดคือสามารถใช้คำสั่ง `COPY ... TO PROGRAM` เพื่อสั่งรันคำสั่ง Shell ในระดับระบบปฏิบัติการของเครื่องเซิร์ฟเวอร์ฐานข้อมูลได้ (Remote Code Execution) แต่หากจำกัดไว้เป็น `butcher_app` ผู้โจมตีจะไม่สามารถลบตาราง ไม่สามารถแก้ไขโครงสร้าง และไม่สามารถเข้าถึงระบบปฏิบัติการหรือฐานข้อมูลก้อนอื่นในคลัสเตอร์ได้เลย

## 2. การเข้ารหัสการเชื่อมต่อด้วย SSL/TLS และการเก็บรักษา Connection String

### แนวคิด (Concept)
เมื่อเซิร์ฟเวอร์แอปพลิเคชันของ **Smart Butcher Marketplace** ส่งคำสั่งซื้อเนื้อและข้อมูลบัตรกำนัลวิ่งผ่านสายเครือข่ายไปยังเซิร์ฟเวอร์ PostgreSQL 16 หากการเชื่อมต่อนั้นไม่ได้ถูกเข้ารหัส (Plaintext Connection) ข้อมูลรหัสผ่านและรายชื่อลูกค้าจะวิ่งผ่านเครือข่ายในรูปแบบข้อความธรรมดาที่ใครก็ตามที่ดักฟังแพ็กเกจอยู่ในเครือข่ายเดียวกัน (Man-in-the-Middle / Packet Sniffing) สามารถเปิดอ่านได้ทันที

เราจึงต้องบังคับใช้การเข้ารหัส **SSL/TLS (Transport Layer Security)** สำหรับทุกการเชื่อมต่อ และเปลี่ยนวิธีการยืนยันตัวตนของรหัสผ่านจาก `md5` แบบเก่าที่ล้าสมัย มาเป็นมาตรฐาน **`scram-sha-256`** ของ PostgreSQL 16 พร้อมเก็บรักษา `DATABASE_URL` ไว้ในระบบจัดการความลับ (Secret Manager) อย่างปลอดภัย

### หลักการเบื้องหลัง (Under the Hood)
1. **การยืนยันตัวตนด้วย `scram-sha-256` ใน `pg_hba.conf`:**
   ใน PostgreSQL 16 กลไกเริ่มต้นสำหรับการแฮชรหัสผ่านคือ **SCRAM-SHA-256 (Salted Challenge Response Authentication Mechanism)** ซึ่งป้องกันทั้งการดักฟังรหัสผ่านระหว่างทางและการโจมตีแบบ Rainbow Table แม้ไฟล์ตารางระบบจะรั่วไหล
2. **การบังคับใช้ `hostssl` ใน `pg_hba.conf`:**
   ไฟล์ `pg_hba.conf` (Host-Based Authentication) คือปราการด่านแรกของ PostgreSQL หากเรากำหนดบรรทัดเป็น `hostssl` แทนคำว่า `host` เซิร์ฟเวอร์ PostgreSQL 16 จะ **ปฏิเสธการเชื่อมต่อทุกชนิดที่ไม่ได้เข้ารหัสด้วย TLS ทันที**
3. **ความแตกต่างของระดับ `sslmode` ใน Connection String:**
   - `disable`: ไม่เข้ารหัสเลย (อันตรายมาก ห้ามใช้บน Cloud/Production)
   - `require`: บังคับเข้ารหัสข้อมูลที่วิ่งผ่านสาย แต่ไม่ตรวจสอบใบรับรอง (Certificate) ว่าเซิร์ฟเวอร์ปลายทางเป็นตัวจริงหรือไม่ (ยังเสี่ยงต่อการถูกปลอมแปลงเซิร์ฟเวอร์คั่นกลาง)
   - `verify-ca`: เข้ารหัสและตรวจสอบว่าใบรับรองของเซิร์ฟเวอร์ออกโดยผู้ออกใบรับรอง (CA) ที่เราเชื่อถือ
   - **`verify-full` (ปลอดภัยสูงสุด):** เข้ารหัส ตรวจสอบ CA และตรวจสอบว่าชื่อโดเมน (Hostname) ของเซิร์ฟเวอร์ตรงกับที่ระบุในใบรับรองทุกประการ

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การตั้งค่า `postgresql.conf` และ `pg_hba.conf` เพื่อบังคับใช้ TLS 1.3 และ SCRAM-SHA-256
การกำหนดค่าฝั่งเซิร์ฟเวอร์ PostgreSQL 16 ให้รับเฉพาะการเชื่อมต่อที่เข้ารหัสด้วย TLS 1.2/1.3 และใช้รหัสผ่านแบบ SCRAM-SHA-256 เท่านั้น:

```ini filename="postgresql.conf"
# เปิดใช้งาน SSL/TLS และบังคับเวอร์ชันขั้นต่ำเป็น TLSv1.2 หรือ TLSv1.3
ssl = on
ssl_cert_file = '/etc/postgresql/16/certs/server.crt'
ssl_key_file = '/etc/postgresql/16/certs/server.key'
ssl_ca_file = '/etc/postgresql/16/certs/root-ca.crt'
ssl_min_protocol_version = 'TLSv1.2'

# บังคับการเข้ารหัสรหัสผ่านในระบบเป็น scram-sha-256
password_encryption = 'scram-sha-256'
```

```ini filename="pg_hba.conf"
# TYPE    DATABASE           USER               ADDRESS            METHOD
# อนุญาตให้เชื่อมต่อผ่าน Unix Socket เฉพาะผู้ดูแลระบบภายในเครื่องเท่านั้น
local     all                postgres                              peer

# ปฏิเสธการเชื่อมต่อทุกชนิดที่ไม่ได้ใช้ SSL/TLS (hostnossl) จากเครือข่ายภายนอกทั้งหมด
hostnossl all                all                0.0.0.0/0          reject
hostnossl all                all                ::/0               reject

# อนุญาตเฉพาะการเชื่อมต่อที่เข้ารหัส TLS (hostssl) จากวงเครือข่าย Private Subnet ของแอปพลิเคชันเท่านั้น
hostssl   smart_butcher_db   butcher_app        10.20.1.0/24       scram-sha-256
hostssl   smart_butcher_db   butcher_migrator   10.20.2.0/24       scram-sha-256
```

#### ตัวอย่างที่ 2: การตั้งค่า Connection String แบบ `verify-full` และการตรวจสอบความถูกต้องของ Environment Variables ตอนเปิดแอป
การใช้ไลบรารี `zod` ในฝั่ง Backend เพื่อตรวจสอบตั้งแต่จังหวะเริ่มเปิดเซิร์ฟเวอร์ว่า `DATABASE_URL` บน Production ต้องมีการระบุ `sslmode=verify-full` หรือ `sslmode=require` เสมอ:

```typescript filename="src/config/database-env.validator.ts"
import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'staging', 'production']),
  DATABASE_URL: z
    .string()
    .url()
    .refine(
      (url) => url.startsWith('postgresql://') || url.startsWith('postgres://'),
      { message: 'DATABASE_URL must use postgresql:// protocol' }
    ),
  DIRECT_URL: z.string().url().optional(),
}).superRefine((data, ctx) => {
  // บังคับว่าบน Production ต้องเปิดใช้งาน SSL ใน Connection String เสมอ
  if (data.NODE_ENV === 'production') {
    const hasSecureSsl =
      data.DATABASE_URL.includes('sslmode=verify-full') ||
      data.DATABASE_URL.includes('sslmode=require');

    if (!hasSecureSsl) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['DATABASE_URL'],
        message: 'CRITICAL SECURITY ERROR: Production DATABASE_URL must enforce sslmode=verify-full or sslmode=require',
      });
    }
  }
});

export const validatedDbEnv = envSchema.parse(process.env);
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การเก็บรักษา Connection String** | เผลอ Commit ไฟล์ `.env` ที่มีรหัสผ่านจริงขึ้น GitHub หรือพิมพ์รหัสผ่านตรงๆ ลงในไฟล์ `schema.prisma` | ใช้ `env("DATABASE_URL")` เสมอ และดึงค่าจาก Secret Manager (เช่น AWS Secrets Manager, Vault, GitHub Secrets) |
| **การตั้งค่า `pg_hba.conf`** | ตั้งค่า `host all all 0.0.0.0/0 trust` หรือ `md5` เปิดรับทุก IP โดยไม่ต้องใช้ SSL | ใช้ `hostssl` จำกัดเฉพาะวง IP ของแอปพลิเคชัน และบังคับใช้วิธี `scram-sha-256` |
| **การแสดงผล Log เมื่อเกิด Error** | พิมพ์ `console.log(process.env.DATABASE_URL)` ออกทางหน้าจอ Log ทำให้รหัสผ่านหลุดไปอยู่ในระบบเก็บ Log | ปกปิด (Mask/Redact) ส่วนรหัสผ่านใน URL เสมอก่อนทำการบันทึก Log ใดๆ |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `sslmode=verify-full` และ `hostssl` เมื่อ:** แอปพลิเคชันและฐานข้อมูลสื่อสารกันผ่านเครือข่าย ไม่ว่าจะอยู่ใน Cloud VPC เดียวกันหรือข้ามผู้ให้บริการคลาวด์ (เช่น แอปพลิเคชันรันบน Vercel แต่ฐานข้อมูลอยู่บน Supabase หรือ AWS RDS)
- **ไม่ควรใช้ `sslmode=disable` เมื่อ:** รันอยู่บนสภาพแวดล้อมใดๆ ที่ไม่ใช่ `localhost` บนเครื่องนักพัฒนาส่วนตัว

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: ใน Connection String ของ PostgreSQL ค่า `sslmode=require` กับ `sslmode=verify-full` ให้ความปลอดภัยแตกต่างกันอย่างไร?**
  - **แนวคำตอบ:** `sslmode=require` บังคับให้เข้ารหัสช่องทางสื่อสาร แต่ไม่ได้ตรวจสอบว่าใบรับรอง (Certificate) ของเซิร์ฟเวอร์ปลายทางเชื่อถือได้หรือไม่ หรือตรงกับโดเมนที่เราเรียกไปหรือไม่ ทำให้หากผู้โจมตีทำ DNS Spoofing หรือปลอมตัวเป็นเซิร์ฟเวอร์ฐานข้อมูลคั่นกลาง (Active Man-in-the-Middle) แอปพลิเคชันก็จะยอมเชื่อมต่อด้วย ในขณะที่ `sslmode=verify-full` จะตรวจสอบทั้งความถูกต้องของใบรับรองผ่าน Root CA และตรวจสอบว่าชื่อ Hostname ตรงกับใบรับรอง 100% จึงป้องกันการปลอมแปลงเซิร์ฟเวอร์ได้อย่างสมบูรณ์
- **Q2: หากคุณเผลอ Commit ไฟล์ `.env` ที่มีรหัสผ่านฐานข้อมูล Production ขึ้นไปบน Git Repository แล้ว แม้จะรีบลบไฟล์นั้นออกใน Commit ถัดมาทันที ทำไมถึงยังไม่ปลอดภัย และต้องทำอย่างไร?**
  - **แนวคำตอบ:** เพราะประวัติของไฟล์ยังคงฝังอยู่ใน Git History (`.git/objects`) และอาจถูกบอทสแกนดูดข้อมูลไปตั้งแต่วินาทีแรกที่ Push ขึ้นไปแล้ว วิธีรับมือที่ถูกต้องคือต้องถือว่ารหัสผ่านนั้นรั่วไหลแล้ว 100% ให้ทำการ **Rotate Password (เปลี่ยนรหัสผ่านใหม่ในฐานข้อมูลและใน Secret Manager ทันที)** จากนั้นค่อยล้างประวัติ Git และตรวจสอบ Audit Log ของฐานข้อมูลว่ามีการเข้าถึงที่ผิดปกติในช่วงเวลาดังกล่าวหรือไม่

## 3. กลไกป้องกัน SQL Injection ด้วย Parameterized Queries ในระดับฐานข้อมูล

### แนวคิด (Concept)
**SQL Injection (SQLi)** คือช่องโหว่ระดับตำนานที่เกิดจากการนำข้อความที่ผู้ใช้กรอกเข้ามา (เช่น คำค้นหาชื่อเนื้อสเต๊ก) ไป **"ต่อสตริง (String Concatenation)"** รวมกับคำสั่ง SQL โดยตรง หากลูกค้าผู้ไม่หวังดีกรอกคำค้นหาว่า `Wagyu' OR '1'='1` โครงสร้างประโยคคำสั่ง SQL จะถูกบิดเบือนไปจากความตั้งใจเดิมทันที หรืออาจรุนแรงถึงขั้นแอบดึงข้อมูลจากตาราง `users` และ `payments` ออกไปทั้งหมด

วิธีป้องกันที่สมบูรณ์แบบที่สุดไม่ใช่การพยายามเขียนโค้ดตัดตัวอักษรพิเศษด้วยตัวเอง แต่คือการใช้ **Parameterized Queries (Prepared Statements)** ซึ่งแยก **"โครงสร้างคำสั่ง SQL"** ออกจาก **"ตัวข้อมูล (Data Parameters)"** ในระดับโปรโตคอลของ PostgreSQL 16

### หลักการเบื้องหลัง (Under the Hood)
ทำไม Parameterized Queries ถึงป้องกัน SQL Injection ได้ 100%? คำตอบอยู่ที่การทำงานของ **PostgreSQL Extended Query Protocol** ซึ่งแบ่งการประมวลผลออกเป็น 3 ขั้นตอนแยกจากกันอย่างเด็ดขาด:
1. **ขั้นตอน Parse (สร้าง Syntax Tree ล่วงหน้า):**
   ไดรเวอร์ (หรือ Prisma Client) ส่งเฉพาะโครงร่างคำสั่งที่มีตัวแทนตำแหน่ง เช่น `SELECT id, name, price_per_kg FROM products WHERE sku = $1 AND marbling_score >= $2` ไปให้ PostgreSQL 16 ตัว Engine จะทำการวิเคราะห์ไวยากรณ์ (Lexical & Syntactic Parsing) และสร้าง **Parse Tree (โครงสร้างคำสั่ง)** ให้เสร็จสิ้นตั้งแต่ขั้นตอนนี้!
2. **ขั้นตอน Bind (ผูกค่าข้อมูลเข้ากับช่องตัวแปร):**
   ไดรเวอร์ส่งค่าที่ผู้ใช้กรอกมาแยกในแพ็กเกจข้อมูลอีกชุดหนึ่งเพื่อนำไปใส่ในช่อง `$1` และ `$2` เนื่องจากขั้นตอนการสร้างโครงสร้างคำสั่ง (Parse) จบไปแล้ว PostgreSQL 16 จะปฏิบัติต่อค่าใน `$1` ในฐานะ **"ก้อนข้อมูลตัวอักษรล้วนๆ (Literal Value)"** เท่านั้น ต่อให้ใน `$1` มีเครื่องหมาย `'` หรือคำว่า `OR 1=1; DROP TABLE orders;--` ตัว Engine ก็จะไม่นำมันไปตีความเป็นคำสั่ง SQL อีกต่อไป แต่จะนำไปค้นหาสินค้าที่มีรหัส SKU ชื่อยาวๆ แบบนั้นตรงตัว!
3. **ขั้นตอน Execute:**
   รันแผนการสืบค้นจาก Parse Tree ที่ผูกค่าตัวแปรเรียบร้อยแล้ว

```text filename="docs/database/security.txt"
[ 1. PARSE PHASE ] ──► ส่งโครงสร้าง: SELECT * FROM products WHERE sku = $1
                       (PostgreSQL ล็อกโครงสร้างคำสั่ง SQL ตายตัวตั้งแต่ตรงนี้!)
                                          │
                                          ▼
[ 2. BIND PHASE ]  ──► ส่งค่าตัวแปรแยกต่างหาก: $1 = "' OR 1=1 --"
                       (ถูกมองเป็นเพียงข้อความธรรมดา ไม่สามารถแหกออกมาแก้โครงสร้างคำสั่งได้)
```

ใน Prisma ORM คำสั่งมาตรฐานทั้งหมด (`findMany`, `findUnique`, `create`, `update`) และคำสั่ง **`$queryRaw` แบบ Tagged Template Literal** จะใช้กลไก Parameterized Queries นี้ให้อัตโนมัติ แต่หากนักพัฒนาเผลอใช้ **`$queryRawUnsafe`** ร่วมกับการต่อสตริง `${variable}` ช่องโหว่ SQL Injection จะเปิดขึ้นทันที!

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: เปรียบเทียบโค้ดที่มีช่องโหว่ (`$queryRawUnsafe`) กับโค้ดที่ปลอดภัย (`$queryRaw` Tagged Template)
เมื่อต้องการเขียน Raw SQL ที่ซับซ้อนในระบบ **Smart Butcher Marketplace**:

```typescript filename="src/products/product-search.service.ts"
import { Injectable } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { Prisma } from '@prisma/client';

@Injectable()
export class ProductSearchService {
  constructor(private readonly prisma: PrismaService) {}

  // ❌ อันตรายร้ายแรง (VULNERABLE TO SQL INJECTION):
  // การใช้ $queryRawUnsafe ร่วมกับการต่อสตริงด้วย Template Literal ${...}
  // หากผู้โจมตีส่ง skuInput = "A5' UNION SELECT id, email, password_hash, 0 FROM users --" ข้อมูลรั่วทันที!
  async findBySkuVulnerable(skuInput: string) {
    const unsafeSql = `SELECT id, sku, name, price_per_kg FROM products WHERE sku = '${skuInput}'`;
    return this.prisma.$queryRawUnsafe(unsafeSql);
  }

  // ✅ ปลอดภัย 100% (SAFE PARAMETERIZED QUERY):
  // การใช้ $queryRaw แบบ Tagged Template (ไม่มีวงเล็บครอบตอนเรียกฟังก์ชัน)
  // Prisma จะแปลง ${skuInput} และ ${minMarbling} ให้กลายเป็นตัวแปร $1 และ $2 ในระดับ PostgreSQL Protocol
  async findBySkuAndMarblingSafe(skuInput: string, minMarbling: number) {
    return this.prisma.$queryRaw<
      Array<{ id: string; sku: string; name: string; price_per_kg: Prisma.Decimal }>
    >`
      SELECT id, sku, name, price_per_kg
      FROM products
      WHERE sku = ${skuInput}
        AND marbling_score >= ${minMarbling}
      ORDER BY price_per_kg DESC
    `;
  }
}
```

#### ตัวอย่างที่ 2: การสร้างคิวรีแบบมีเงื่อนไขไดนามิกและการจัดเรียงลำดับ (`ORDER BY`) อย่างปลอดภัยไร้ช่องโหว่
ใน PostgreSQL เราไม่สามารถส่งชื่อคอลัมน์ใน `ORDER BY $1` เป็น Parameter ได้ เพราะ `$1` ใช้แทนได้เฉพาะ "ค่าข้อมูล (Value)" ไม่สามารถใช้แทน "ชื่อคอลัมน์หรือทิศทางการเรียง (Identifier/Keyword)" ได้ ดังนั้นเมื่อต้องทำ Dynamic Sorting จึงต้องใช้ **Strict Allowlist (Whitelist Map)** คู่กับ `Prisma.sql`:

```typescript filename="src/orders/order-report.service.ts"
import { Injectable, BadRequestException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { Prisma, OrderStatus } from '@prisma/client';

// กำหนดรายการคอลัมน์และทิศทางที่อนุญาตให้เรียงลำดับแบบตายตัว (Allowlist)
const ALLOWED_SORT_COLUMNS: Record<string, Prisma.Sql> = {
  createdAt: Prisma.sql`o.created_at`,
  totalAmount: Prisma.sql`o.total_amount`,
};

const ALLOWED_SORT_DIRECTIONS: Record<string, Prisma.Sql> = {
  asc: Prisma.sql`ASC`,
  desc: Prisma.sql`DESC`,
};

@Injectable()
export class OrderReportService {
  constructor(private readonly prisma: PrismaService) {}

  async searchOrdersSecurely(params: {
    status?: OrderStatus;
    minTotalAmount?: number;
    sortBy?: string;
    sortDir?: string;
  }) {
    const sortColumnSql = ALLOWED_SORT_COLUMNS[params.sortBy ?? 'createdAt'];
    const sortDirSql = ALLOWED_SORT_DIRECTIONS[params.sortDir ?? 'desc'];

    if (!sortColumnSql || !sortDirSql) {
      throw new BadRequestException('Invalid sort parameters specified');
    }

    // ประกอบเงื่อนไข WHERE แบบไดนามิกแต่ยังคงใช้ Parameterized Variables ($1, $2) ทุกจุด
    const conditions: Prisma.Sql[] = [Prisma.sql`1 = 1`];

    if (params.status) {
      conditions.push(Prisma.sql`o.status = ${params.status}::"OrderStatus"`);
    }

    if (params.minTotalAmount !== undefined) {
      conditions.push(Prisma.sql`o.total_amount >= ${params.minTotalAmount}`);
    }

    const whereClause = Prisma.join(conditions, ' AND ');

    return this.prisma.$queryRaw`
      SELECT
        o.id,
        o.status,
        o.total_amount,
        o.created_at,
        u.email AS customer_email
      FROM orders o
      INNER JOIN users u ON u.id = o.user_id
      WHERE ${whereClause}
      ORDER BY ${sortColumnSql} ${sortDirSql}
      LIMIT 50
    `;
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การเรียกใช้ `$queryRaw`** | เขียน `prisma.$queryRawUnsafe(\`SELECT * FROM users WHERE email = '\${email}'\`)` | เขียน `prisma.$queryRaw\`SELECT * FROM users WHERE email = \${email}\`` (Tagged Template) |
| **การทำ Dynamic `ORDER BY`** | นำค่า `req.query.sortBy` มาต่อสตริงใส่หลังคำว่า `ORDER BY` ตรงๆ | สร้าง Allowlist Object จับคู่ชื่อฟิลด์ที่อนุญาตเข้ากับ `Prisma.sql` เท่านั้น |
| **การส่งรายการ `IN (...)` ใน Raw SQL** | ใช้ `.join(',')` ต่อสตริงใส่ในวงเล็บ `IN (...)` เอง | ใช้ `WHERE id IN (${Prisma.join(ids)})` เพื่อให้ Prisma แตกเป็น `($1, $2, $3)` อย่างปลอดภัย |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Prisma Client Query API (`findMany`, `create`, ฯลฯ) เป็นหลักเมื่อ:** คิวรีเป็นงาน CRUD และการกรองข้อมูลทั่วไป เพราะปลอดภัยและได้รับการตรวจสอบชนิดข้อมูล (Type-safe) สูงสุด
- **ควรใช้ `prisma.$queryRaw` คู่กับ `Prisma.sql` เมื่อ:** ต้องการเขียนคิวรีวิเคราะห์ข้อมูลขั้นสูงของ PostgreSQL 16 เช่น Window Functions, CTEs หรือ JSONB Operators
- **ไม่ควรใช้ `$queryRawUnsafe` หรือ `$executeRawUnsafe` เด็ดขาด:** ในทุกกรณีที่มีตัวแปรมาจากผู้ใช้งานภายนอก

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: จงอธิบายในระดับ Database Engine ว่าทำไมการใช้ Parameterized Queries (`$1`, `$2`) จึงป้องกัน SQL Injection ได้อย่างเด็ดขาด แม้ผู้โจมตีจะส่งเครื่องหมาย Single Quote (`'`) เข้ามาก็ตาม?**
  - **แนวคำตอบ:** เพราะใน Extended Query Protocol ของ PostgreSQL คำสั่ง SQL ที่มีตัวแปร `$1` จะถูกส่งไปเข้ากระบวนการ **Parse** เพื่อสร้างโครงสร้างคำสั่ง (Syntax Tree) ให้เสร็จสิ้นก่อน จากนั้นค่าข้อมูลที่ผู้ใช้ส่งมาจึงจะถูกส่งตามไปทีหลังในขั้นตอน **Bind** เนื่องจากโครงสร้างคำสั่งถูกล็อกตายตัวไปแล้วตั้งแต่ขั้นตอน Parse ค่าที่อยู่ใน `$1` จึงถูกจำกัดให้เป็นเพียงข้อมูลตัวอักษรภายในโหนดนั้นเท่านั้น ไม่สามารถเปลี่ยนแปลงโครงสร้าง Syntax Tree ของคำสั่ง SQL ได้เลย
- **Q2: ทำไมเราจึงไม่สามารถใช้ Parameter (`$1`) แทนชื่อตารางหรือชื่อคอลัมน์ใน `ORDER BY $1` ได้ และมีวิธีแก้ไขที่ปลอดภัยอย่างไร?**
  - **แนวคำตอบ:** เพราะในการวางแผนคิวรี (Query Planning) PostgreSQL จำเป็นต้องรู้ชื่อตารางและชื่อคอลัมน์ที่ชัดเจนตั้งแต่ขั้นตอน Parse เพื่อตรวจสอบว่าตารางและคอลัมน์นั้นมีอยู่จริงหรือไม่และจะใช้ Index ตัวไหน หากใส่ `ORDER BY $1` PostgreSQL จะตีความว่าให้เรียงลำดับตาม "ค่าคงที่สตริง" ซึ่งไม่มีผลใดๆ ต่อการเรียงแถว วิธีแก้ไขที่ปลอดภัยคือการตรวจสอบค่าที่รับเข้ามากับ **Strict Allowlist (Whitelist)** ในฝั่งโค้ดก่อนนำไปประกอบคำสั่ง

## 4. การปกป้องข้อมูลอ่อนไหว, การจำกัดเครือข่าย (Network Isolation) และกฎหมาย PDPA

### แนวคิด (Concept)
ระบบ **Smart Butcher Marketplace** จัดเก็บข้อมูลส่วนบุคคลของลูกค้า (Personally Identifiable Information - PII) เช่น ชื่อ-นามสกุล, เบอร์โทรศัพท์, อีเมล, ที่อยู่สำหรับจัดส่งรถห้องเย็น และประวัติการชำระเงิน ซึ่งอยู่ภายใต้การบังคับใช้ของ **พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA)** ของประเทศไทย และมาตรฐานสากลอย่าง GDPR

การปกป้องข้อมูลระดับนี้ต้องอาศัยแนวคิด **Defense in Depth** ทั้งในระดับเครือข่าย (การซ่อนฐานข้อมูลไว้ใน Private Subnet), ระดับการเข้ารหัสข้อมูล (Encryption at Rest & Application-level Encryption), การบันทึกประวัติการเข้าถึงข้อมูล (Audit Logging) และการรองรับ **สิทธิในการขอให้ลบหรือทำลายข้อมูลส่วนบุคคล (Right to Erasure / Right to be Forgotten)** โดยไม่ทำให้ข้อมูลทางบัญชีและภาษีของบริษัทเสียหาย

### หลักการเบื้องหลัง (Under the Hood)
1. **การจำกัดเครือข่าย (Network Isolation / VPC Private Subnet):**
   ฐานข้อมูล PostgreSQL 16 บน Production **ต้องไม่มี Public IP Address** และห้ามเปิดพอร์ต 5432 ออกสู่อินเทอร์เน็ตสาธารณะเด็ดขาด เซิร์ฟเวอร์ฐานข้อมูลต้องวางอยู่ในวงเครือข่ายปิด (Private Subnet) ที่อนุญาตเฉพาะ Security Group ของเซิร์ฟเวอร์แอปพลิเคชัน (หรือ Connection Pooler) เท่านั้นที่สามารถวิ่งเข้ามาหาพอร์ต 5432 ได้ หากผู้ดูแลระบบต้องการเชื่อมต่อเข้ามาตรวจสอบต้องผ่าน Bastion Host, VPN หรือ Identity-Aware Tunnel เท่านั้น
2. **การปกป้องข้อมูลอ่อนไหว (Password Hashing & Field-Level Encryption):**
   - รหัสผ่านของลูกค้าในตาราง `users` ห้ามเก็บเป็นข้อความจริงและห้ามเข้ารหัสแบบถอดกลับได้ ต้องทำการแฮชทางเดียวด้วยอัลกอริทึม **`Argon2id`** (หรือ `bcrypt`) เท่านั้น
   - ข้อมูลที่ต้องถอดรหัสกลับมาใช้งานได้แต่มีความอ่อนไหวสูง (เช่น เลขประจำตัวผู้เสียภาษีสำหรับออกใบกำกับภาษีเต็มรูปแบบ) ควรเข้ารหัสระดับแอปพลิเคชันด้วย **`AES-256-GCM`** ก่อนบันทึกลงคอลัมน์ หรือใช้ส่วนขยาย `pgcrypto`
3. **การทำ Pseudonymization / Anonymization เพื่อรองรับ PDPA คู่กับกฎหมายภาษี:**
   เมื่อลูกค้าใช้สิทธิตามกฎหมาย PDPA ขอจบบัญชีและให้ลบข้อมูลส่วนบุคคล (Right to be Forgotten) เรา **ไม่สามารถสั่ง `DELETE FROM users` ที่พ่วง `ON DELETE CASCADE` ไปลบแถวในตาราง `orders` และ `payments` ทิ้งได้!** เพราะตามประมวลรัษฎากร บริษัทมีหน้าที่ตามกฎหมายต้องเก็บรักษาหลักฐานทางบัญชีและยอดเงินไว้ตรวจสอบอย่างน้อย 5 ปี
   ทางออกทางสถาปัตยกรรมที่ถูกต้องคือการใช้เทคนิค **PII Scrubbing & Anonymization**: ลบหรือเขียนทับข้อมูลที่ระบุตัวตนได้ในตาราง `users` (เช่น เปลี่ยนอีเมลเป็น `deleted_user_<uuid>@anonymized.local`, ล้างชื่อและเบอร์โทรศัพท์ทิ้ง) แต่ยังคงรักษา `id` ของผู้ใช้และข้อมูลยอดเงินในตาราง `orders` และ `payments` เอาไว้ครบถ้วนทุกบาททุกสตางค์!

```text filename="docs/database/security.txt"
[ ลูกค้าขอใช้สิทธิลบข้อมูลตาม PDPA ]
         │
         ├──► 1. ตาราง users: ล้างชื่อ, เบอร์โทร, ที่อยู่ และเปลี่ยนอีเมลเป็นค่าสุ่ม (ระบุตัวตนไม่ได้อีกต่อไป)
         │
         └──► 2. ตาราง orders & payments: ข้อมูลยอดขาย, รายการเนื้อวากิวที่ขายไป และยอดเงินคงอยู่ครบ 100%
                                          (ข้อมูลทางบัญชีและภาษีของบริษัทไม่สูญหาย!)
```

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: บริการทำ PDPA Data Anonymization (Right to be Forgotten) โดยไม่กระทบยอดบัญชีใน `orders` และ `payments`
โค้ดบริการในฝั่ง Backend ที่ใช้ Interactive Transaction ของ Prisma เพื่อล้างข้อมูลส่วนบุคคลของลูกค้าและบันทึกหลักฐานการปฏิบัติตามกฎหมายอย่างปลอดภัย:

```typescript filename="src/compliance/pdpa-erasure.service.ts"
import { Injectable, BadRequestException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { createHash, randomUUID } from 'crypto';

@Injectable()
export class PdpaErasureService {
  constructor(private readonly prisma: PrismaService) {}

  async anonymizeCustomerAccount(userId: string, requestReason: string) {
    return this.prisma.$transaction(async (tx) => {
      // 1. ตรวจสอบว่าลูกค้าไม่มีคำสั่งซื้อที่กำลังจัดส่งค้างอยู่
      const activeOrdersCount = await tx.order.count({
        where: {
          userId,
          status: { in: ['PENDING', 'PAID', 'PREPARING_CUT', 'SHIPPING'] },
        },
      });

      if (activeOrdersCount > 0) {
        throw new BadRequestException(
          'Cannot anonymize account while there are active or in-transit orders.'
        );
      }

      // 2. สร้างรหัสอ้างอิงนิรนามที่ไม่สามารถย้อนกลับไปหาตัวตนเดิมได้
      const anonymousToken = createHash('sha256')
        .update(`${userId}:${randomUUID()}`)
        .digest('hex')
        .slice(0, 16);

      // 3. เขียนทับข้อมูลส่วนบุคคล (PII) ในตาราง users แต่คง Primary Key (id) เดิมไว้เชื่อมกับ orders
      await tx.user.update({
        where: { id: userId },
        data: {
          email: `erased_${anonymousToken}@anonymized.smartbutcher.internal`,
          fullName: 'PDPA_ERASED_CUSTOMER',
          phoneNumber: null,
          passwordHash: 'ACCOUNT_PERMANENTLY_DISABLED',
          isAnonymized: true,
          anonymizedAt: new Date(),
        },
      });

      // 4. ล้างชื่อผู้รับและที่อยู่จัดส่งในใบสั่งซื้อเก่าที่ส่งสำเร็จแล้ว แต่คงยอดเงินและรายการสินค้าไว้เพื่อภาษี
      await tx.order.updateMany({
        where: { userId },
        data: {
          shippingAddressText: '[REDACTED_BY_PDPA_REQUEST]',
          recipientPhone: null,
          butcherInstruction: null,
        },
      });

      return {
        status: 'ANONYMIZED',
        anonymizedReference: anonymousToken,
        timestamp: new Date().toISOString(),
      };
    });
  }
}
```

#### ตัวอย่างที่ 2: การสร้างตาราง Audit Log และ Trigger ใน PostgreSQL 16 เพื่อบันทึกการแก้ไขข้อมูลสำคัญ
เพื่อความโปร่งใสและการตรวจสอบความปลอดภัย เราสามารถสร้าง Trigger ในระดับ PostgreSQL 16 ที่คอยบันทึกทุกครั้งที่มีการเปลี่ยนสถานะหรือแก้ไขยอดเงินในตาราง `payments` ลงในตาราง `security_audit_logs` ที่บัญชีแอปพลิเคชันมีสิทธิ์แค่ `INSERT` แต่ห้าม `UPDATE` หรือ `DELETE` (Append-Only Audit Trail):

```sql filename="02_append_only_security_audit_trigger.sql"
-- 1. สร้างตารางเก็บประวัติการเปลี่ยนแปลงข้อมูลสำคัญ (Audit Trail)
CREATE TABLE "security_audit_logs" (
    "id" BIGSERIAL PRIMARY KEY,
    "table_name" VARCHAR(64) NOT NULL,
    "record_id" UUID NOT NULL,
    "operation" VARCHAR(10) NOT NULL,
    "db_user" VARCHAR(64) NOT NULL DEFAULT CURRENT_USER,
    "client_ip" INET DEFAULT inet_client_addr(),
    "old_data" JSONB,
    "new_data" JSONB,
    "changed_at" TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 2. จำกัดสิทธิ์ให้ butcher_app ทำได้แค่เพิ่มแถวบันทึก (INSERT) ห้ามลบหรือแก้ไขประวัติเด็ดขาด!
REVOKE ALL ON TABLE "security_audit_logs" FROM butcher_app;
GRANT INSERT ON TABLE "security_audit_logs" TO butcher_app;
GRANT USAGE, SELECT ON SEQUENCE "security_audit_logs_id_seq" TO butcher_app;

-- 3. สร้างฟังก์ชัน Trigger สำหรับบันทึกข้อมูลก่อนและหลังการแก้ไขตาราง payments
CREATE OR REPLACE FUNCTION fn_audit_payments_changes()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
    IF (TG_OP = 'UPDATE') THEN
        INSERT INTO public.security_audit_logs (table_name, record_id, operation, old_data, new_data)
        VALUES ('payments', NEW.id, 'UPDATE', to_jsonb(OLD), to_jsonb(NEW));
        RETURN NEW;
    ELSIF (TG_OP = 'DELETE') THEN
        INSERT INTO public.security_audit_logs (table_name, record_id, operation, old_data, new_data)
        VALUES ('payments', OLD.id, 'DELETE', to_jsonb(OLD), NULL);
        RETURN OLD;
    END IF;
    RETURN NULL;
END;
$$;

-- 4. ผูก Trigger เข้ากับตาราง payments
CREATE TRIGGER trg_payments_security_audit
AFTER UPDATE OR DELETE ON "payments"
FOR EACH ROW EXECUTE FUNCTION fn_audit_payments_changes();
```

<Callout type="tip" title="ทำไมในฟังก์ชัน SECURITY DEFINER ต้องระบุ SET search_path = public เสมอ?">
ฟังก์ชันที่ระบุ `SECURITY DEFINER` จะทำงานด้วยสิทธิ์ของผู้สร้างฟังก์ชัน (เช่น `butcher_migrator`) หากไม่ล็อกค่า `SET search_path = public` เอาไว้ ผู้ใช้ที่มีสิทธิ์ต่ำอาจแอบสร้างตารางปลอมชื่อเดียวกันใน Schema ชั่วคราว (`pg_temp`) เพื่อหลอกให้ฟังก์ชันที่มีสิทธิ์สูงเขียนข้อมูลลงผิดตาราง การใส่ `SET search_path = public` จึงเป็นแนวปฏิบัติบังคับตามคู่มือความปลอดภัยของ PostgreSQL 16
</Callout>

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ❌ ผิด (Anti-pattern) | ✅ ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การตั้งค่าเครือข่ายฐานข้อมูล** | เปิดพอร์ต `5432` ออกสู่ `0.0.0.0/0` เพื่อให้ตัวเองใช้ DBeaver ต่อจากร้านกาแฟได้ง่ายๆ | ซ่อนฐานข้อมูลใน Private Subnet อนุญาตเฉพาะ IP ของ App Server และเข้าจัดการผ่าน VPN / Bastion Tunnel เท่านั้น |
| **การลบข้อมูลตามคำขอ PDPA** | สั่ง `DELETE FROM users WHERE id = ...` แล้วตั้ง `ON DELETE CASCADE` จนประวัติยอดขายและใบเสร็จหายเกลี้ยง | ใช้เทคนิค **Anonymization (PII Scrubbing)** ล้างเฉพาะข้อมูลระบุตัวตนใน `users` แต่คงข้อมูลการเงินใน `orders`/`payments` ไว้ |
| **การเก็บข้อมูลในตาราง Audit Log** | ให้สิทธิ์ `DELETE` และ `UPDATE` บนตาราง Audit Log แก่บัญชีแอปพลิเคชัน ทำให้แฮกเกอร์ลบร่องรอยตัวเองได้ | กำหนดสิทธิ์แบบ **Append-Only** (ให้เฉพาะสิทธิ์ `INSERT` แก่แอปพลิเคชัน หรือใช้ `SECURITY DEFINER` Trigger) |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Network Isolation (Private Subnet) และ Audit Triggers เมื่อ:** ระบบจัดเก็บข้อมูลลูกค้าจริงและมีธุรกรรมทางการเงิน
- **ไม่ควรเข้ารหัสทุกคอลัมน์ในฐานข้อมูลแบบ Application-level Encryption:** เพราะคอลัมน์ที่ถูกเข้ารหัสเป็น Ciphertext จะไม่สามารถทำ Indexing ค้นหาแบบช่วง (`BETWEEN`, `LIKE`) หรือทำ `SUM()` ในฐานข้อมูลได้ ให้เลือกเข้ารหัสเฉพาะคอลัมน์ที่เป็นความลับระดับสูงจริงๆ (เช่น เลขบัตรประชาชน, เลขบัญชีธนาคาร, หรือ Secret Token) เท่านั้น

### คำถามสัมภาษณ์ (Interview Q&A)
- **Q1: หากลูกค้าขอใช้สิทธิลบข้อมูลส่วนบุคคลตามกฎหมาย PDPA (Right to be Forgotten) แต่ฝ่ายบัญชีของบริษัทยืนยันว่าต้องเก็บข้อมูลคำสั่งซื้อ (`orders`) และรายการชำระเงิน (`payments`) ไว้ 5 ปีตามกฎหมายภาษีอากร ในฐานะสถาปนิกฐานข้อมูลคุณจะออกแบบระบบอย่างไร?**
  - **แนวคำตอบ:**
    1. ตั้งค่า Foreign Key ระหว่าง `orders.user_id -> users.id` ให้เป็น `ON DELETE RESTRICT` เพื่อป้องกันการเผลอลบแถวลูกค้าที่มีประวัติการซื้อขาย
    2. เมื่อลูกค้าขอใช้สิทธิลบข้อมูล ให้ใช้กระบวนการ **Data Anonymization (ทำให้ไม่สามารถระบุตัวตนได้)** โดยอัปเดตแถวในตาราง `users` ให้ล้างชื่อ เบอร์โทร ที่อยู่ และเปลี่ยนอีเมลเป็นรหัสสุ่มที่ไม่ซ้ำกัน พร้อมลบที่อยู่จัดส่งในตาราง `orders`
    3. ข้อมูลตามกฎหมาย PDPA ถือว่าพ้นสภาพการเป็นข้อมูลส่วนบุคคลทันทีที่มันไม่สามารถนำไปเชื่อมโยงกลับหาตัวบุคคลได้อีก ในขณะที่ข้อมูลยอดขาย วันที่ซื้อ รายการเนื้อวากิว และยอดชำระเงินใน `orders` และ `payments` ยังคงอยู่ครบถ้วนสมบูรณ์สำหรับการตรวจสอบทางบัญชีและสรรพากร
- **Q2: การตั้งค่า `SECURITY DEFINER` ในฟังก์ชันของ PostgreSQL คืออะไร และมีข้อควรระวังด้านความปลอดภัยอย่างไร?**
  - **แนวคำตอบ:** โดยปกติฟังก์ชันใน PostgreSQL จะทำงานแบบ `SECURITY INVOKER` คือรันด้วยสิทธิ์ของผู้ที่เรียกใช้ฟังก์ชันนั้น แต่ `SECURITY DEFINER` จะทำให้ฟังก์ชันทำงานด้วยสิทธิ์ของ **"ผู้ที่เป็นเจ้าของฟังก์ชัน"** (คล้ายกับ `sudo` ใน Linux) เหมาะสำหรับงานอย่างการเขียนข้อมูลลงตาราง Audit Log ที่ไม่ต้องการให้ผู้ใช้ทั่วไปเข้าถึงโดยตรง ข้อควรระวังสำคัญคือต้องระบุ `SET search_path = public, pg_temp` หรือล็อก Schema ให้ชัดเจนเสมอเพื่อป้องกันการโจมตีแบบ Search Path Hijacking

## ข้อผิดพลาดที่พบบ่อย (Anti-patterns)

1. **การใช้บัญชี Superuser (`postgres`) ใน Connection String ของแอปพลิเคชัน**
   - **สาเหตุ:** นักพัฒนานำค่าเริ่มต้นจาก Docker Compose ตอนทำ Local Dev ไปใช้ต่อบน Production
   - **ผลกระทบ:** หากเกิดช่องโหว่จุดเดียวในแอปพลิเคชัน ผู้โจมตีจะได้สิทธิ์สูงสุดในการลบฐานข้อมูลทั้งหมดหรือสั่งรันคำสั่งระดับ OS
   - **วิธีแก้:** สร้าง Role แยกต่างหาก (`butcher_app`) ที่มีเฉพาะสิทธิ์ `SELECT, INSERT, UPDATE, DELETE` เท่านั้น

2. **การเปิดพอร์ต 5432 ของฐานข้อมูล Production ออกสู่อินเทอร์เน็ตสาธารณะ (`0.0.0.0/0`)**
   - **สาเหตุ:** ต้องการความสะดวกในการเชื่อมต่อจากเครื่องคอมพิวเตอร์ส่วนตัวโดยไม่ต้องต่อ VPN
   - **ผลกระทบ:** บอทอัตโนมัติทั่วโลกจะทำการสแกนและยิง Brute-force รหัสผ่านตลอด 24 ชั่วโมง รวมถึงเสี่ยงต่อช่องโหว่ Zero-day
   - **วิธีแก้:** วางฐานข้อมูลใน Private Subnet ที่เข้าถึงได้เฉพาะจาก Application Server และใช้ SSH Bastion หรือ VPN สำหรับผู้ดูแลระบบ

3. **การใช้ `$queryRawUnsafe` ร่วมกับ Template Literal `${...}`**
   - **สาเหตุ:** สับสนไวยากรณ์ระหว่าง `$queryRaw\`...\`` (Tagged Template ที่ปลอดภัย) กับ `$queryRawUnsafe(\`...\`)`
   - **ผลกระทบ:** เปิดช่องโหว่ SQL Injection เต็มรูปแบบให้ผู้โจมตีดึงข้อมูลทุกตารางออกไปได้
   - **วิธีแก้:** ใช้ `$queryRaw` แบบ Tagged Template เสมอ และใช้ Strict Allowlist สำหรับชื่อคอลัมน์ใน `ORDER BY`

4. **การเก็บไฟล์ `.env` หรือรหัสผ่านฐานข้อมูลไว้ใน Git Repository**
   - **สาเหตุ:** ลืมเพิ่ม `.env` ลงใน `.gitignore` หรือเผลอใส่รหัสผ่านจริงลงในไฟล์ตัวอย่างและไฟล์ CI
   - **ผลกระทบ:** รหัสผ่านฝังอยู่ในประวัติ Git ตลอดไปแม้จะลบไฟล์ใน Commit ถัดมาแล้วก็ตาม
   - **วิธีแก้:** ใช้ Secret Manager ของผู้ให้บริการคลาวด์ และติดตั้งตัวสแกนหาความลับอัตโนมัติ (เช่น `gitleaks`) ใน Pre-commit Hook

5. **การตั้ง `ON DELETE CASCADE` บนตารางการเงิน (`orders` / `payments`) เพื่อลบข้อมูลลูกค้า**
   - **สาเหตุ:** คิดว่าการทำตามกฎหมาย PDPA คือต้องสั่ง `DELETE` แถวข้อมูลทิ้งทั้งหมด
   - **ผลกระทบ:** ยอดรวมรายได้และประวัติใบเสร็จของบริษัทหายไปจากระบบบัญชี ผิดกฎหมายภาษีอากร
   - **วิธีแก้:** ใช้ `ON DELETE RESTRICT` และใช้วิธีเขียนทับข้อมูลระบุตัวตน (PII Anonymization) แทนการลบแถว

## Checklist สรุป

ตรวจสอบความมั่นคงปลอดภัยของฐานข้อมูล **Smart Butcher Marketplace** ก่อนเปิดให้บริการจริงตามรายการต่อไปนี้:

- [ ] **Role Separation:** แยกบัญชี `butcher_migrator` (สำหรับรัน Migration) และ `butcher_app` (สำหรับรันแอปพลิเคชันที่มีเฉพาะสิทธิ์ DML) ออกจากกันอย่างเด็ดขาด และไม่มีการใช้ `postgres` ในแอปพลิเคชัน
- [ ] **Default Privileges Configured:** ตั้งค่า `ALTER DEFAULT PRIVILEGES` เพื่อให้ตารางใหม่ที่สร้างโดย Migration มอบสิทธิ์ DML แก่ `butcher_app` อัตโนมัติ
- [ ] **Public Schema Hardened:** เพิกถอนสิทธิ์ `CREATE` บน Schema `public` ออกจากกลุ่ม `PUBLIC` (`REVOKE CREATE ON SCHEMA public FROM PUBLIC;`)
- [ ] **TLS & SCRAM Enforced:** บังคับใช้ `hostssl` และ `scram-sha-256` ใน `pg_hba.conf` พร้อมระบุ `sslmode=verify-full` (หรือ `require`) ใน Connection String
- [ ] **Network Isolated:** ฐานข้อมูลอยู่ใน Private Subnet ที่ไม่มี Public IP หรือจำกัด Firewall อนุญาตเฉพาะ IP ของเซิร์ฟเวอร์แอปพลิเคชันและ Pooler เท่านั้น
- [ ] **Zero Unsafe Raw SQL:** โค้ดทั้งหมดใช้ Parameterized Queries ผ่าน Prisma Client หรือ `$queryRaw` Tagged Template และมีการใช้ Allowlist สำหรับ Dynamic `ORDER BY`
- [ ] **PDPA & Audit Ready:** มีกระบวนการทำ Data Anonymization สำหรับคำขอลบข้อมูลลูกค้าโดยไม่กระทบตารางบัญชี และมีตาราง Audit Log แบบ Append-Only สำหรับธุรกรรมสำคัญ

## ลำดับการเรียนที่แนะนำ และ ดูเพิ่มเติมที่

เมื่อฐานข้อมูลของคุณได้รับการปกป้องอย่างรัดกุมแล้ว ขั้นตอนต่อไปคือการออกแบบระบบจัดการการเชื่อมต่อให้สามารถรองรับผู้ใช้งานพร้อมกันจำนวนมากได้โดยที่ฐานข้อมูลไม่ล่ม:

<Callout type="tip" title="เส้นทางการศึกษาต่อสำหรับระบบฐานข้อมูลระดับ Production">
1. **การบริหารจัดการการเชื่อมต่อและป้องกันปัญหาฐานข้อมูลล่มเมื่อคนเข้าเยอะ:**  
   👉 **[Connection Pooling](/docs/database/connection-pooling)** — เจาะลึกต้นทุนของโปรเซสใน PostgreSQL 16, สูตรคำนวณขนาด Pool และสถาปัตยกรรม PgBouncer

2. **การใช้งาน Row Level Security (RLS) และระบบความปลอดภัยบน Supabase:**  
   👉 **[Supabase](/docs/database/supabase)** — เรียนรู้การเขียนนโยบายบังคับสิทธิ์ระดับแถวข้อมูล (RLS Policies) บนแพลตฟอร์ม Supabase

3. **การรักษาความปลอดภัยในฝั่ง Application Layer (Backend Security):**  
   👉 **[Security (Backend)](/docs/backend/security)** และ **[Prisma ORM](/docs/backend/prisma-orm)** — ศึกษาการทำ Authentication, Authorization (RBAC), การแฮชรหัสผ่านด้วย Argon2id และการตรวจสอบ Input ในฝั่งเซิร์ฟเวอร์
</Callout>
