## 1. แนวคิด (Concept)

คอมโพเนนต์กลุ่ม **Core Components** ใน shadcn/ui คือบล็อกตัวต่อพื้นฐานที่สุดในการสร้างส่วนต่อประสานกับผู้ใช้ (User Interface):
- **Form Controls**: `Button`, `Input`, `Label`, `Textarea`, `Select`, `Checkbox`, `Switch`
- **Data & Layout Presentation**: `Card`, `Badge`, `Separator`, `Avatar`, `Skeleton`

คอมโพเนนต์เหล่านี้ถูกออกแบบมาภายใต้มาตรฐานเดียวกัน:
1. **ความสอดคล้อง (Aesthetic Consistency)**: ทุกชิ้นใช้โทนสี, ขอบมน (`rounded-md` / `rounded-xl`), ฟอนต์, และเส้นขอบ (`border-input`) ที่เชื่อมโยงกับตัวแปร CSS เดียวกัน
2. **Accessible Form Associations**: ทุกฟิลด์ Input และ Label รองรับการเชื่อมโยง `htmlFor` และ `id` เพื่อให้ผู้ใช้สามารถคลิกข้อความ Label แล้วเคอร์เซอร์วิ่งไปยังช่องกรอกข้อมูลได้ทันที
3. **Smooth Micro-interactions**: มี Focus Ring (`focus-visible:ring-1`) ชัดเจน ช่วยอำนวยความสะดวกให้ผู้ใช้งานที่ใช้คีย์บอร์ดนำทาง

## 2. หลักการเบื้องหลัง (Under the Hood)

### 1. ความแตกต่างระหว่าง Native HTML vs Radix Select
- ใน HTML ดั้งเดิม `<select>` มีข้อจำกัดร้ายแรง: เบราว์เซอร์ระบบปฏิบัติการ (iOS, Android, Windows) จะบังคับหน้าตาเมนู Dropdown ทำให้เราไม่สามารถใส่ไอคอน, ปรับเงา, หรือทำ Dark Mode ได้อย่างแท้จริง
- ใน shadcn/ui `<Select>` ถูกสร้างขึ้นบน `@radix-ui/react-select`:
  - เรนเดอร์เป็น Custom DOM Nodes ที่ตกแต่งด้วย Tailwind CSS ได้ 100%
  - แต่ยังคงพฤติกรรม Accessibility ระดับสูงสุด: รองรับ Typeahead (พิมพ์ตัวอักษรเพื่อเลื่อนไปยังตัวเลือกนั้น), ปุ่มลูกศรขึ้น-ลง, และประกาศค่าไปยัง Screen Reader ผ่าน Hidden native input เพื่อให้ฟอร์ม submit ได้ตามปกติ

### 2. การทำงานของ `<Skeleton>` ป้องกัน CLS (Cumulative Layout Shift)
- `<Skeleton>` ใน shadcn เป็นเพียง `div` ที่ใส่คลาส `animate-pulse rounded-md bg-muted`
- เมื่อดึงข้อมูลจากเครือข่าย การวาง Skeleton ที่มีมิติ (Width & Height) สอดคล้องกับขนาดจริงของข้อมูล ช่วยลดค่า Core Web Vitals (CLS) ให้เป็นศูนย์ เพราะเบราว์เซอร์จัดสรรพื้นที่ไว้ล่วงหน้าแล้ว

## 4. ผิด vs ถูก

| รูปแบบที่ผิด (Anti-Pattern) | รูปแบบที่ถูกต้อง (Best Practice) |
| :--- | :--- |
| **ใช้ `<label>` ดั้งเดิมโดยไม่ใส่ `htmlFor`**<br/>ทำให้การคลิกที่ข้อความไม่เปิดช่อง Input ส่งผลเสียต่อ Mobile UX และผู้ใช้ที่ใช้เมาส์ลำบาก | **ใช้ `<Label htmlFor="inputId">` คู่กับ `<Input id="inputId">`**<br/>shadcn Label ผูกกับ Radix Label รองรับการโฟกัสอัตโนมัติ |
| **ใช้ `div` ทำปุ่ม Toggle หรือ Switch เอง**<br/>ขาดคุณสมบัติ `role="switch"` และ `aria-checked` ทำให้ผู้พิการทางสายตาไม่ทราบว่าเปิดหรือปิดอยู่ | **ใช้ `<Switch checked={...} onCheckedChange={...} />`**<br/>ได้พฤติกรรม Toggle สากลพร้อมสถานะทาง ARIA ครบถ้วน |
| **ใช้รูปภาพเปล่าๆ สำหรับ Avatar โดยไม่มี Fallback**<br/>หาก URL รูปภาพเสีย (Broken image link) หน้าจอจะแสดงกรอบรูปแตกที่ดูไม่เป็นมืออาชีพ | **ใช้ `<Avatar>` ร่วมกับ `<AvatarFallback>`**<br/>หากรูปโหลดไม่สำเร็จ ระบบจะสลับไปแสดงตัวอักษรย่อ (Initials) สวยงามทันที |

## 5. ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่

### ควรใช้เมื่อ:
- **สร้างแบบฟอร์มการกรอกข้อมูลทุกประเภท**: ตั้งแต่หน้าลงทะเบียน, การตั้งค่าบัญชี, ไปจนถึงฟอร์มชำระเงิน
- **การ์ดแสดงผลข้อมูล Dashboard**: ใช้ `Card`, `Badge`, และ `Avatar` เพื่อจัดระเบียบเนื้อหาให้ดูสะอาดตา
- **หน้าจอที่รอการดึงข้อมูล**: ใช้ `Skeleton` แทน Spinner หมุนๆ ช่วยให้ผู้ใช้รู้สึกว่าเว็บโหลดเร็วขึ้น (Perceived Performance)

### ไม่ควรใช้เมื่อ:
- **ต้องการ Dropdown ของมือถือแบบ Native Wheel**: หากแอปพลิเคชันเป็น Mobile Web ที่เจาะจงว่าต้องการให้เด้ง Native Wheel Picker ของ iOS การใช้ Radix Select อาจให้ประสบการณ์ที่ต่างออกไป

## 6. คำถามสัมภาษณ์งาน (Interview Questions)

### Q1: ทำไม shadcn/ui จึงเลือกสร้าง `<Select>` บน Radix UI แทนที่จะแต่งสไตล์ให้กับแท็ก `<select>` ของ HTML ดั้งเดิม?
**แนวทางตอบ:**
1. **ข้อจำกัดของ Native `<select>`**: แท็กดั้งเดิมของเบราว์เซอร์ไม่สามารถจัดสไตล์ให้สวยงามหรือสอดคล้องกับ Design System ได้ (เช่น ไม่สามารถใส่ Avatar ในตัวเลือก, ปรับความโค้งมนของกรอบป็อปอัป หรือใส่แอนิเมชันตอนเปิดปิด)
2. **การรักษา Accessibility ในระดับสูงสุด**: Radix Select จำลองพฤติกรรมของ ARIA 1.2 Combobox/Listbox อย่างสมบูรณ์แบบ ทั้งการใช้คีย์บอร์ดนำทาง, Typeahead search, และยังคงมี Hidden Input เพื่อส่งค่าไปยัง FormData ของเซิร์ฟเวอร์ได้อย่างไร้รอยต่อ

### Q2: ในการทำ Skeleton Loading Component มีแนวทางปฏิบัติอย่างไรเพื่อป้องกันปัญหา Cumulative Layout Shift (CLS)?
**แนวทางตอบ:**
1. **จับคู่มิติขนาดให้ตรงกับคอนเทนต์จริง (Exact Dimensions Matching)**: กำหนดความสูง (`h-*`) และความกว้าง (`w-*`) ของ Skeleton ให้ใกล้เคียงกับขนาดของ Typography และรูปภาพจริงที่จะโหลดเข้ามา
2. **รักษา Hierarchy และ Spacing**: ใช้ Gap, Padding, และ Margin ใน Container เดียวกันกับข้อมูลจริง เพื่อไม่ให้โครงสร้างเลย์เอาต์กระตุกขยับเมื่อข้อมูลจริงถูกสลับเข้ามาแทนที่ Skeleton
