## 1. Event Loop และ Non-blocking I/O

### แนวคิด (Concept)
ลองจินตนาการถึงเคาน์เตอร์ขายเนื้อของ **Smart Butcher Marketplace** หากร้านมีพนักงานรับออเดอร์เพียงคนเดียว (Single-threaded JavaScript Engine) แต่มีลูกค้ายืนรอคิวเป็นร้อยคน:
- **แบบ Blocking (ดั้งเดิม):** พนักงานรับคำสั่งซื้อเนื้อวากิว A5 จากลูกค้าคนที่ 1 แล้วเดินเข้าไปในห้องเย็นเพื่อแล่เนื้อและบรรจุแพ็กเกจด้วยตัวเองเป็นเวลา 10 นาที ลูกค้าคนที่ 2-100 ต้องยืนรอจนกว่าลูกค้าคนแรกจะได้รับของ ทำให้ระบบช้าและเกิดคอขวดมหาศาล
- **แบบ Non-blocking (Node.js):** พนักงานรับออเดอร์คนที่ 1 จดรายการลงบิล แล้วส่งต่อให้ทีมแล่เนื้อหลังร้าน (libuv Thread Pool / OS Kernel) จากนั้นพนักงานหันมารับคำสั่งซื้อของลูกค้าคนที่ 2, 3, 4 ทันที เมื่อทีมหลังร้านแล่เนื้อเสร็จ จะกดกริ่งเรียก (Callback / Event) ให้พนักงานหน้าร้านส่งมอบเนื้อให้ลูกค้าคนนั้นในจังหวะที่มือว่าง

Node.js ใช้สถาปัตยกรรม **Single-threaded Event-driven Non-blocking I/O** ทำให้เซิร์ฟเวอร์เครื่องเดียวสามารถรองรับการเชื่อมต่อพร้อมกัน (Concurrent Connections) ได้หลายหมื่น Connection โดยใช้ทรัพยากรหน่วยความจำต่ำกว่าเซิร์ฟเวอร์แบบ Multi-threaded แบบดั้งเดิม (เช่น Apache หรือ Java Thread-per-request) อย่างมาก

### หลักการเบื้องหลัง (Under the Hood)
สถาปัตยกรรมภายในของ Node.js ประกอบด้วยส่วนสำคัญ 4 ส่วน:
1. **V8 Engine:** รับผิดชอบคอมไพล์โค้ด JavaScript เป็น Machine Code และจัดการ **Call Stack** (LIFO) กับ Memory Heap
2. **libuv (C Library):** จัดการ **Event Loop**, Task Queues, และ **libuv Thread Pool** (ขนาดเริ่มต้น 4 Threads ควบคุมผ่านตัวแปร `UV_THREADPOOL_SIZE`) สำหรับงานที่ OS ไม่รองรับ Asynchronous แท้จริง เช่น File I/O (`fs`), DNS lookups (`dns.lookup`), และ CPU-bound crypto/zlib operations
3. **OS Kernel:** จัดการ Network I/O (TCP, UDP, HTTP) ผ่าน System Call ที่เป็น Non-blocking ระดับ OS (เช่น `epoll` บน Linux, `kqueue` บน macOS, `IOCP` บน Windows)
4. **Queue Hierarchy:**
   - **Microtask Queue:** มีลำดับความสำคัญสูงสุด ถูกเคลียร์ทันทีหลังจาก Call Stack ว่าง ก่อนจะเปลี่ยน Phase ของ Event Loop แบ่งเป็น:
     1. `process.nextTick` Queue (รันก่อนเสมอ)
     2. Promise Microtask Queue (คำสั่ง `.then()`, `.catch()`, `await`)
   - **Macrotask Queue:** แบ่งออกเป็น 6 Phase ที่ Event Loop วนซ้ำตามลำดับ:

| Phase ใน Event Loop | สิ่งที่เกิดขึ้นใน Phase นี้ | ตัวอย่าง Callback |
| :--- | :--- | :--- |
| **1. Timers** | ตรวจสอบและประมวลผล Callbacks ของตัวจับเวลาที่หมดเวลาแล้ว | `setTimeout()`, `setInterval()` |
| **2. Pending Callbacks** | รัน I/O Callbacks ที่ถูกเลื่อนมาจากการวนรอบก่อนหน้า | Network socket errors เช่น `ECONNREFUSED` |
| **3. Idle, Prepare** | ใช้เฉพาะการทำงานภายในของ libuv เอง | ภายในระบบ libuv (Internal use only) |
| **4. Poll** | ดึงเหตุการณ์ I/O ใหม่, ประมวลผล I/O callbacks, และบล็อกรอหากไม่มีงานอื่น | อ่านข้อมูลไฟล์, รับ Request ใหม่เข้ามาทาง Socket |
| **5. Check** | รัน Callback ที่ถูกสั่งงานโดยเฉพาะให้ทำหลังช่วง Poll ทันที | `setImmediate()` |
| **6. Close Callbacks** | รัน Callback เมื่อ Connection หรือ Resource ปิดตัวลง | `socket.on('close', ...)`, `dbStream.on('close')` |

```text filename="docs/backend/nodejs.txt"
   ┌───────────────────────────┐
┌─>│          Timers           │ (setTimeout, setInterval)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     Pending Callbacks     │ (TCP/Socket level errors)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │       Idle, Prepare       │ (libuv internal)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           Poll            │ (Retrieve new I/O events, execute I/O callbacks)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           Check           │ (setImmediate callbacks)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │      Close Callbacks      │ (socket.destroy(), stream cleanup)
└──┴───────────────────────────┘
   * ระหว่างรอยต่อทุก Phase: เคลียร์ process.nextTick -> Promise Microtasks จนเกลี้ยง *
```

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: ลำดับการประมวลผล Event Loop ในระบบออกใบเสร็จคำสั่งซื้อเนื้อ
ตัวอย่างนี้แสดงลำดับการทำงานของ Call Stack, Microtask (`nextTick`, `Promise`), และ Macrotask (`setTimeout`, `setImmediate`, `fs.readFile`):

```typescript filename="src/event-loop-order-demo.ts"
import fs from 'node:fs';

console.log('1. [Call Stack] สตาร์ทระบบรับออเดอร์ Smart Butcher Marketplace');

// 1. Timer Macrotask
setTimeout(() => {
  console.log('7. [Timers Phase] ตัวจับเวลาแจ้งเตือน: ออเดอร์เนื้อริบอายครบ 30 นาที');
}, 0);

// 2. Check Macrotask
setImmediate(() => {
  console.log('8. [Check Phase] setImmediate: พิมพ์สติกเกอร์บาร์โค้ดเนื้อวากิว');
});

// 3. I/O Poll Phase
fs.readFile(__filename, () => {
  console.log('9. [Poll Phase] I/O Callback: อ่านบันทึกสต็อกเนื้อจากฮาร์ดดิสก์เสร็จสิ้น');

  // ใน I/O Callback: setImmediate จะถูกประมวลผลก่อน setTimeout(..., 0) เสมอ
  setImmediate(() => {
    console.log('10. [Check Phase ภายใน I/O] ตัดยอดสต็อกเนื้อออกจากระบบทันที');
  });

  setTimeout(() => {
    console.log('11. [Timers Phase ภายใน I/O] ส่ง SMS ยืนยันให้ลูกค้า Butcher');
  }, 0);
});

// 4. Microtask: Promise
Promise.resolve().then(() => {
  console.log('4. [Microtask: Promise] ตรวจสอบวงเงินบัตรเครดิตของ User สำเร็จ');
});

// 5. Microtask: process.nextTick (ทำงานก่อน Promise เสมอ)
process.nextTick(() => {
  console.log('2. [Microtask: nextTick] ตรวจสอบสถานะการล็อกอินของ Butcher Customer');
});

process.nextTick(() => {
  console.log('3. [Microtask: nextTick] สำรองคิวสินค้าเนื้อเทนเดอร์ลอยน์ในหน่วยความจำ');
});

// 6. Microtask ซ้อนใน Promise
Promise.resolve().then(() => {
  console.log('5. [Microtask: Promise 2] ดึงประวัติส่วนลดสมาชิก Smart Butcher');
  process.nextTick(() => {
    console.log('6. [Microtask: nextTick ซ้อน] อัปเดตคะแนนสะสม Butcher Rewards');
  });
});

console.log('--- จบการลงทะเบียนคำสั่ง synchronous บน Call Stack ---');
```

#### ตัวอย่างที่ 2: การปรับจูน libuv Thread Pool สำหรับงาน Crypto Hashing ของรหัสผ่าน User
งานคำนวณทางคณิตศาสตร์ เช่น การแฮชรหัสผ่านลูกค้าด้วย `crypto.pbkdf2` หรือ `bcrypt` จะถูกส่งไปรันบน libuv Thread Pool หากมีงานเข้ามาเกินขนาด Thread Pool งานที่เหลือจะต้องเข้าคิวรอ:

```typescript filename="src/threadpool-tuning.ts"
// ตั้งค่า UV_THREADPOOL_SIZE ก่อนโหลดโมดูล crypto หรือรัน Node
// (ปกติควรกำหนดผ่าน Environment Variable: UV_THREADPOOL_SIZE=8 node app.js)
process.env.UV_THREADPOOL_SIZE = '4';

import crypto from 'node:crypto';

interface ButcherCustomerCredentials {
  userId: string;
  passwordPlain: string;
}

const customersToHash: ButcherCustomerCredentials[] = [
  { userId: 'usr_001', passwordPlain: 'WagyuLover2026!' },
  { userId: 'usr_002', passwordPlain: 'RibeyeMaster#99' },
  { userId: 'usr_003', passwordPlain: 'KurobutaKing$$' },
  { userId: 'usr_004', passwordPlain: 'TenderloinTender@1' },
  { userId: 'usr_005', passwordPlain: 'SirloinSpecial*8' },
  { userId: 'usr_006', passwordPlain: 'TomahawkSteak!!' },
];

console.log(`เริ่มแฮชรหัสผ่าน User จำนวน ${customersToHash.length} รายการ (Thread Pool = 4)`);
const startTime = Date.now();

customersToHash.forEach((customer, index) => {
  const hashStart = Date.now();
  // pbkdf2 แบบ async จะส่งงานลง libuv Thread Pool
  crypto.pbkdf2(customer.passwordPlain, 'salt_smart_butcher', 100_000, 64, 'sha512', (err, derivedKey) => {
    if (err) throw err;
    const duration = Date.now() - hashStart;
    const totalElapsed = Date.now() - startTime;
    console.log(
      `[Task ${index + 1}] User: ${customer.userId} แฮชสำเร็จใน ${duration}ms (เวลารวมตั้งแต่เริ่ม: ${totalElapsed}ms)`
    );
  });
});
```

### ผิด vs ถูก (Anti-patterns & Best Practices)

#### ❌ โค้ดที่ผิด: บล็อก Event Loop ด้วยการอ่านไฟล์แบบ Synchronous ใน Request Handler
```typescript filename="bad-order-export.ts"
import fs from 'node:fs';
import http from 'node:http';

// ผิดมหันต์: fs.readFileSync บล็อก V8 Call Stack ทั้งหมด
// ขณะที่กำลังอ่านไฟล์ประวัติออเดอร์ขนาด 50MB ลูกค้าคนอื่นที่ต้องการสั่งซื้อเนื้อจะโหลดหน้าเว็บไม่ได้เลย!
http.createServer((req, res) => {
  if (req.url === '/api/orders/export-sync') {
    const hugeHistoryData = fs.readFileSync('/data/butcher-orders-2025.csv', 'utf-8');
    res.writeHead(200, { 'Content-Type': 'text/csv' });
    res.end(hugeHistoryData);
  }
}).listen(3000);
```

#### ✅ โค้ดที่ถูก: ใช้ Asynchronous Stream ส่งข้อมูลออกไปทีละ Chunk
```typescript filename="good-order-export.ts"
import fs from 'node:fs';
import http from 'node:http';

// ถูกต้อง: fs.createReadStream ทำงานแบบ Non-blocking และส่งข้อมูลแบบ Streaming
// ไม่สะสมไฟล์ทั้งก้อนใน RAM และไม่บล็อกการสั่งซื้อของลูกค้ารายอื่น
http.createServer((req, res) => {
  if (req.url === '/api/orders/export-stream') {
    res.writeHead(200, { 'Content-Type': 'text/csv' });
    const fileStream = fs.createReadStream('/data/butcher-orders-2025.csv');
    fileStream.pipe(res);

    fileStream.on('error', (error) => {
      console.error('เกิดข้อผิดพลาดในการ Stream ไฟล์ออเดอร์:', error);
      if (!res.headersSent) {
        res.writeHead(500, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify({ error: 'ไม่สามารถดาวน์โหลดไฟล์ได้' }));
      }
    });
  }
}).listen(3000);
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้:** ระบบ REST API, WebSockets, Real-time Dashboard คำสั่งซื้อ, การสตรีมไฟล์เนื้อสดหรือใบเสร็จ, ระบบที่ต้องติดต่อ Microservices หรือ Database จำนวนมากพร้อมๆ กัน
- **ไม่ควรใช้:** งานประมวลผล CPU-bound หนักๆ บน Main Thread เช่น การตัดต่อวิดีโอตรวจสอบความสดของเนื้อ, การเทรนโมเดล AI จำแนกลายหินอ่อนของเนื้อ (Marbling score) หากจำเป็นต้องทำบน Node.js ให้แยกออกไปทำบน **Worker Threads** (`worker_threads`) หรือส่งต่อไปยัง Background Worker Service (เช่น Python Service หรือ Go)

### คำถามสัมภาษณ์ (Interview Questions)
- **Q1: `process.nextTick()` ต่างจาก `setImmediate()` อย่างไร และทำงานในจังหวะไหน?**
  - *คำตอบ:* `process.nextTick()` ไม่ได้อยู่ใน Phase ใดของ Event Loop เลย แต่อยู่ใน **Microtask Queue** พิเศษ ซึ่งจะถูกรันทันทีที่การทำงานปัจจุบันบน Call Stack จบลง ก่อนที่ Event Loop จะก้าวข้ามไป Phase ถัดไป ส่วน `setImmediate()` อยู่ใน **Check Phase** ของ Event Loop ซึ่งจะถูกรันหลังจาก Poll Phase จบลงในรอบการหมุนของ Event Loop
- **Q2: หากรันงานคำนวณเข้ารหัสรหัสผ่านพร้อมกัน 8 คำสั่ง บนเครื่องที่มี 8 CPU Cores โดยไม่ตั้งค่าอะไรเพิ่มเติม ทำไม 4 คำสั่งแรกจึงเสร็จพร้อมกัน แล้ว 4 คำสั่งหลังจึงเริ่มทำงาน?**
  - *คำตอบ:* เพราะค่าเริ่มต้นของ libuv Thread Pool (`UV_THREADPOOL_SIZE`) คือ **4 Threads** แม้เครื่องจะมี 8 Cores งาน Crypto ที่เกิน 4 งานแรกจะต้องรอในคิวของ libuv จนกว่า Thread ใน Pool จะว่าง หากต้องการใช้ครบทั้ง 8 Cores ต้องตั้งค่า `UV_THREADPOOL_SIZE=8` ก่อนเริ่มกระบวนการ Node.js

## 2. Async/Await และ Promise

### แนวคิด (Concept)
ในการสั่งซื้อเนื้อออนไลน์ ขั้นตอนการทำงานต้องเกิดขึ้นตามลำดับ: ตรวจสอบข้อมูลลูกค้า (User) -> เช็กสต็อกเนื้อสเต็ก (Product) -> หักเงินผ่านบัตร (Payment) -> สร้างบิลคำสั่งซื้อ (Order)
- **Callback Hell (ยุคเก่า):** ซ้อนฟังก์ชันลึกจนเป็นพีระมิด จัดการ Error ยาก และเกิดปัญหากลืน Error
- **Promise (มาตรฐาน ES6):** เป็นวัตถุตัวแทนของ "ผลลัพธ์ที่จะมาถึงในอนาคต" ทำให้ต่อสายคำสั่งด้วย `.then()` และ `.catch()`
- **Async/Await (ES2017+):** ไวยากรณ์ครอบที่ทำให้โค้ดที่ทำงานแบบ Asynchronous อ่านเรียบง่าย ตรงไปตรงมา เหมือนกับโค้ด Synchronous แต่ยังคงประสิทธิภาพแบบ Non-blocking ทั้งหมด

### หลักการเบื้องหลัง (Under the Hood)
1. **Promise States:** วัตถุ Promise มีได้ 3 สถานะเท่านั้น:
   - `pending`: สถานะเริ่มต้น กำลังรอผลลัพธ์
   - `fulfilled`: ประมวลผลสำเร็จ มีค่า Value ออกมา
   - `rejected`: ประมวลผลล้มเหลว มีข้อผิดพลาด Reason/Error ออกมา
   *หมายเหตุ: เมื่อ Promise เปลี่ยนจาก `pending` เป็น `fulfilled` หรือ `rejected` (เรียกว่า **Settled**) แล้ว สถานะจะไม่สามารถเปลี่ยนแปลงได้อีกตลอดไป*
2. **Async/Await under the hood (Generators + Microtasks):**
   เบื้องหลังของคำสั่ง `async` และ `await` คือการผสมผสานระหว่าง **Generator Functions (`function*`, `yield`)** และ **Promise Runners**:
   - เมื่อเอนจิน V8 เจอคำสั่ง `await promise`:
     - ฟังก์ชันจะถูกบันทึก Execution Context และระงับ (Suspend) ชั่วคราว
     - Call Stack ถูกปล่อยว่างเพื่อให้ Event Loop จัดการงานอื่นต่อ
     - เมื่อ Promise เบื้องหลัง resolve เสร็จ สัญญาณ Callback จะถูกดันเข้า **Promise Microtask Queue**
     - V8 จะดึงฟังก์ชันกลับเข้ามาใน Call Stack และ Resume ต่อจากจุดเดิมพร้อมส่งค่าผลลัพธ์ให้ตัวแปร
3. **Promise Concurrency Methods:**

| Method | พฤติกรรมเมื่อสำเร็จ | พฤติกรรมเมื่อล้มเหลว (Reject) | Use Case เหมาะสม |
| :--- | :--- | :--- | :--- |
| `Promise.all([p1, p2])` | รอจนสำเร็จ **ครบทุกตัว** ถึงจะ resolve ค่าเป็น array | **Fail-fast:** ตัวใดตัวหนึ่ง reject จะ reject ทันที | งานที่ผูกพันกัน ขาดตัวใดตัวหนึ่งไม่ได้ เช่น รวม User + Product + Stock |
| `Promise.allSettled([p1, p2])` | รอจน **ทุกตัวจบงาน** (ทั้ง fulfilled และ rejected) | ไม่มีการ reject คืน array ของ object `{ status, value/reason }` | ส่งอีเมลแจ้งเตือนลูกค้า 100 รายการ ต้องการรู้ว่าใครสำเร็จ ใครล้มเหลว |
| `Promise.race([p1, p2])` | คืนผลลัพธ์ของตัวแรกที่ **Settle** (สำเร็จหรือพังก่อน) | ถ้าตัวแรกสุดล้มเหลว ก็ reject ตามตัวแรก | การทำ Timeout Guard (เช่น แข่ง Request DB กับ Timer 3 วินาที) |
| `Promise.any([p1, p2])` | คืนผลลัพธ์ของตัวแรกที่ **Fulfilled สำเร็จ** | จะ reject ก็ต่อเมื่อ **ล้มเหลวทั้งหมด** (โยน `AggregateError`) | ระบบสำรอง Fallback Payment Gateway (Omise, Stripe, 2C2P) |

    const paymentResult = await processCardPayment(payload.userId, totalAmount);

    const finalizedOrder = {

      userId: payload.userId,
      items: [{ productId: product.id, name: product.name, quantityKg: payload.quantityKg }],
      totalAmount,
      transactionId: paymentResult.transactionId,
      status: 'CONFIRMED',
      createdAt: new Date().toISOString(),
    };

    }
    // ส่งต่อ Error ให้ Controller ชั้นบนแปลงเป็น HTTP 400 หรือ 500

  } finally {
    console.log(`[Audit] เสร็จสิ้นกระบวนการสำหรับลูกค้า ${payload.userId}`);
  }

### ผิด vs ถูก (Anti-patterns & Best Practices)

#### ❌ โค้ดที่ผิด: ใช้ `forEach` กับ `async/await` ทำให้โค้ดไม่รอ และควบคุม Error ไม่ได้
```typescript filename="bad-async-loop.ts"
const meatProductIds = ['beef_01', 'beef_02', 'pork_01'];

// ผิด: forEach ไม่สนใจ Promise ที่ return ออกมาจาก callback!
// บรรทัด "ตัดสต็อกเสร็จสิ้น" จะถูกพิมพ์ออกมาก่อนที่ฟังก์ชันข้างในจะทำงานเสร็จ
// และหากเกิด Error ระบบจะไม่สามารถดักจับด้วย try/catch ภายนอกได้
async function updateAllStock() {
  meatProductIds.forEach(async (id) => {
    await db.updateStock(id, -1);
  });
  console.log('ตัดสต็อกเสร็จสิ้นทุกรายการ (แต่จริงๆ ยังทำงานไม่เสร็จ!)');
}
```

#### ✅ โค้ดที่ถูก: ใช้ `Promise.all` เมื่อต้องการขนาน หรือ `for...of` เมื่อต้องการทำทีละขั้นตอน
```typescript filename="good-async-loop.ts"
const meatProductIds = ['beef_01', 'beef_02', 'pork_01'];

// แบบที่ 1: ต้องการรันขนานกันเพื่อความรวดเร็ว (Parallel)
async function updateAllStockParallel() {
  await Promise.all(
    meatProductIds.map((id) => db.updateStock(id, -1))
  );
  console.log('ตัดสต็อกพร้อมกันเสร็จสิ้นเรียบร้อยทุกรายการ');
}

// แบบที่ 2: ต้องการทำตามลำดับทีละชิ้น (Sequential) เพื่อป้องกัน Deadlock หรือ Race condition
async function updateAllStockSequential() {
  for (const id of meatProductIds) {
    await db.updateStock(id, -1);
    console.log(`ตัดสต็อกชิ้นที่ ${id} สำเร็จ`);
  }
  console.log('ตัดสต็อกทีละชิ้นเรียบร้อย');
}
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้:** การดึงข้อมูล I/O ทุกชนิด เช่น ดึงข้อมูล User, Product, Category, การส่งคำสั่งซื้อไปยัง Payment Provider, การเขียนไฟล์ใบเสร็จ
- **ไม่ควรใช้:** หลีกเลี่ยงการเขียน `return await promise;` เมื่อไม่ได้อยู่ในบล็อก `try/catch` เพราะเป็นการสร้าง Microtask ซ้อนโดยเปล่าประโยชน์ (ยกเว้นในกรณีที่ต้องการให้ Stack Trace สมบูรณ์ขึ้นตอนดีบัก)

### คำถามสัมภาษณ์ (Interview Questions)
- **Q1: อะไรคือความแตกต่างระหว่าง `Promise.all()` และ `Promise.allSettled()` และในระบบการชำระเงินของร้านค้าควรเลือกใช้อย่างไร?**
  - *คำตอบ:* `Promise.all()` จะ Fail-fast ทันทีหากมี Promise ตัวใดตัวหนึ่ง reject เหมาะสำหรับขั้นตอนที่มีความต่อเนื่องสัมพันธ์กัน เช่น ถ้าคำนวณภาษีเนื้อไม่ผ่าน ก็ไม่ต้องหักเงิน ส่วน `Promise.allSettled()` จะรอให้ทุก Promise ทำงานจนเสร็จทั้งหมด ไม่ว่าจะสำเร็จหรือล้มเหลว เหมาะสำหรับงานอิสระที่ต้องการสรุปรายงานผล เช่น การส่งใบเสร็จคำสั่งซื้อให้ 5 หน่วยงานปลายทาง
- **Q2: หากโค้ดมี Unhandled Promise Rejection ใน Node.js จะเกิดอะไรขึ้นกับระบบ?**
  - *คำตอบ:* ใน Node.js เวอร์ชัน 15 เป็นต้นมา ค่าเริ่มต้นจะทำให้ Node.js Process **Crash และหยุดทำงานทันที (Terminate with non-zero exit code)** เพื่อป้องกันไม่ให้แอปพลิเคชันทำงานต่อในสภาวะสถานะข้อมูลผิดเพี้ยน (Corrupted state)

## 3. Module System (ESM vs CommonJS)

### แนวคิด (Concept)
ระบบโมดูลเปรียบเหมือนการจัดระเบียบตู้เก็บเนื้อและอุปกรณ์ในร้าน **Smart Butcher Marketplace**:
- **CommonJS (CJS):** ระบบดั้งเดิมของ Node.js (`require` / `module.exports`) เปรียบเหมือนการเดินไปหยิบมีดจากตู้ตอนที่ต้องการใช้งานทันที (Synchronous) รันโค้ดถึงบรรทัดไหนก็โหลดไฟล์นั้นตอน Runtime
- **ECMAScript Modules (ESM):** ระบบมาตรฐานสากลของโลก JavaScript (`import` / `export`) เปรียบเหมือนการจัดทำผังรายการอุปกรณ์ทั้งหมดตั้งแต่ก่อนเปิดร้าน (Static Analysis) ระบบรู้ล่วงหน้าว่าไฟล์ไหนจำเป็น ไฟล์ไหนไม่ได้ใช้งาน ทำให้สามารถตัดโค้ดส่วนเกินทิ้งได้ (Tree-Shaking)

### หลักการเบื้องหลัง (Under the Hood)
1. **การโหลดและ Parsing:**
   - **CommonJS:** โหลดแบบ Synchronous อ่านไฟล์จากดิสก์ Execute โค้ดทันที และเก็บผลลัพธ์ในหน่วยความจำแคช (`require.cache`) ไม่รองรับ Top-level await ในตัว
   - **ESM:** แบ่งเป็น 3 ขั้นตอน:
     1. *Construction (Parsing):* สแกนหาไฟล์ วิเคราะห์ dependency graph และทำ Static validation
     2. *Instantiation:* จองพื้นที่หน่วยความจำสำหรับทุก `export` และสร้างตัวชี้เชื่อมโยง (Live Bindings)
     3. *Evaluation:* รันโค้ดจริงเพื่อเติมค่าลงในหน่วยความจำ รองรับ **Top-level await**
2. **การตั้งค่าใน Node.js:**
   - กำหนด `"type": "module"` ในไฟล์ `package.json` เพื่อให้ไฟล์ `.js` ทั้งหมดทำงานเป็น ESM
   - ใช้ส่วนขยายไฟล์ `.mjs` สำหรับ ESM และ `.cjs` สำหรับ CommonJS
3. **การเข้ากันได้ (Interop Patterns):**
   - ใน ESM จะไม่มีตัวแปร Global ของ CJS เช่น `__dirname`, `__filename`, `exports`, `module`, `require`
   - ต้องใช้ `import.meta.url` ร่วมกับฟังก์ชัน `fileURLToPath` จาก `node:url` แทน (หรือใช้ `import.meta.dirname` ใน Node.js v20.11.0+)

| คุณสมบัติ | CommonJS (CJS) | ECMAScript Modules (ESM) |
| :--- | :--- | :--- |
| **คำสั่งโหลดโมดูล** | `const pkg = require('./pkg')` | `import pkg from './pkg'` หรือ `import()` |
| **คำสั่งส่งออกโมดูล** | `module.exports = { ... }` | `export const ...` หรือ `export default ...` |
| **กลไกการโหลด** | Synchronous, Runtime evaluation | Asynchronous, Static analysis & compilation |
| **Tree-Shaking** | ทำไม่ได้ หรือทำได้ยากมาก | รองรับสมบูรณ์แบบโดย Bundler |
| **Top-Level Await** | ไม่รองรับ (ต้องห่อใน async IIFE) | รองรับได้ทันทีในระดับ root ของโมดูล |
| **การอ้างอิงตำแหน่งไฟล์** | มี `__dirname` และ `__filename` | ใช้ `import.meta.url` หรือ `import.meta.dirname` |

#### ตัวอย่างที่ 2: Dynamic Import โหลด Payment Driver ปลั๊กอินตามเงื่อนไข (Plugin Architecture)
```typescript filename="src/modules/payment-dispatcher.ts"
export interface PaymentDriver {
  pay(orderId: string, amountThb: number): Promise<{ success: boolean; refId: string }>;
}

export async function processButcherPayment(
  provider: 'omise' | 'stripe' | 'promptpay',
  orderId: string,
  amountThb: number
) {
  let driver: PaymentDriver;

  // โหลด Driver เฉพาะที่ถูกเรียกใช้งานเท่านั้น ช่วยลด Memory Footprint
  switch (provider) {
    case 'omise': {
      const { OmiseDriver } = await import('./drivers/omise.driver.js');
      driver = new OmiseDriver();
      break;
    }
    case 'stripe': {
      const { StripeDriver } = await import('./drivers/stripe.driver.js');
      driver = new StripeDriver();
      break;
    }
    case 'promptpay': {
      const { PromptPayDriver } = await import('./drivers/promptpay.driver.js');
      driver = new PromptPayDriver();
      break;
    }
    default:
      throw new Error(`ไม่รองรับระบบชำระเงิน: ${provider}`);
  }

  return await driver.pay(orderId, amountThb);
}
```

### ผิด vs ถูก (Anti-patterns & Best Practices)

#### ❌ โค้ดที่ผิด: เรียกใช้ `__dirname` ในไฟล์ ESM โดยตรง ทำให้เกิด ReferenceError
```javascript filename="bad-esm-path.js"
// ในไฟล์ package.json ระบุ "type": "module"
import fs from 'node:fs';
import path from 'node:path';

// ผิด: ใน ESM ไม่มีตัวแปร __dirname รันแล้วแอปจะแคชทันที:
// ReferenceError: __dirname is not defined in ES module scope
const certificatePath = path.join(__dirname, 'certs', 'butcher-halal.crt');
const cert = fs.readFileSync(certificatePath);
```

#### ✅ โค้ดที่ถูก: ใช้ `import.meta.dirname` หรือ `fileURLToPath`
```javascript filename="good-esm-path.js"
import fs from 'node:fs';
import path from 'node:path';
import { fileURLToPath } from 'node:url';

// ถูกต้องสำหรับ Node.js 20.11+ หรือ Node 22:
const dir = import.meta.dirname ?? path.dirname(fileURLToPath(import.meta.url));

const certificatePath = path.join(dir, 'certs', 'butcher-halal.crt');
const cert = fs.readFileSync(certificatePath);
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้:** โปรเจกต์ใหม่ทั้งหมดของ Node.js (v20/v22+), Next.js, NestJS ยุคใหม่ รวมถึงไลบรารีสมัยใหม่ที่เป็น ESM-only (เช่น `chalk` v5, `node-fetch` v3)
- **ไม่ควรใช้:** หลีกเลี่ยงการผสมผสาน CJS และ ESM สเปะสปะในโฟลเดอร์เดียวกันโดยไม่มี build tool ช่วย เพราะจะทำให้เกิดปัญหาเรื่อง default export interop

### คำถามสัมภาษณ์ (Interview Questions)
- **Q1: ทำไม ESM จึงสามารถทำ Tree-shaking ได้อย่างมีประสิทธิภาพ แต่ CommonJS ทำไม่ได้?**
  - *คำตอบ:* เพราะโครงสร้าง `import`/`export` ของ ESM เป็นแบบ Static Structure ตัวคอมไพเลอร์สามารถวิเคราะห์ความสัมพันธ์ของโมดูลได้ตั้งแต่ก่อนรันโค้ดจริง (Parse Time) จึงระบุได้อย่างแน่นอนว่าฟังก์ชันไหนไม่มีการเรียกใช้ ในขณะที่ `require()` ของ CommonJS เป็น Dynamic เรียกตอนไหนหรือใส่ตัวแปรใน path ก็ได้ ทำให้เครื่องมือไม่สามารถฟันธงได้ว่าจะมีการเรียกใช้โค้ดส่วนนั้นหรือไม่
- **Q2: หากกำลังรันโปรเจกต์ที่เป็น ESM แต่จำเป็นต้องโหลดไลบรารีเก่าที่เป็น CommonJS และไม่มี named export จะต้องเขียนโค้ดอย่างไร?**
  - *คำตอบ:* ให้ใช้ Default Import เช่น `import cjsPackage from 'legacy-cjs-package';` แล้วดึงคุณสมบัติออกมาจาก default object หรือใช้ฟังก์ชัน `createRequire` จาก `node:module` เช่น `const require = createRequire(import.meta.url); const legacy = require('legacy-cjs-package');`

## 4. npm / pnpm และ package.json

### แนวคิด (Concept)
ในการประกอบธุรกิจร้านค้า **Smart Butcher Marketplace** เราต้องมีการสั่งซื้อวัตถุดิบและอุปกรณ์จากซัพพลายเออร์ภายนอก Package Manager (npm, pnpm) ทำหน้าที่เปรียบเสมือนระบบจัดการจัดซื้อ:
- `package.json` คือ **ใบสั่งซื้อและพิมพ์เขียวประจำร้าน** ที่ระบุว่าเราต้องการเครื่องสไลด์เนื้อรุ่นใด ซอสหมักยี่ห้อใด เวอร์ชันไหน
- `lockfile` (`package-lock.json`, `pnpm-lock.yaml`) คือ **ใบตรวจรับของที่ระบุเลขซีเรียลและ Hash อย่างแม่นยำ** เพื่อให้แน่ใจว่าไม่ว่าพ่อครัวคนไหนในสาขาใดเปิดร้าน จะได้เครื่องมือและวัตถุดิบตรงกัน 100%
- `pnpm` นำเสนอแนวคิด **ศูนย์กระจายสินค้าส่วนกลาง (Content-Addressable Store)** แทนที่จะก๊อปปี้เครื่องสไลด์เนื้อเครื่องเดิมซ้ำๆ ลงทุกสาขา ให้เก็บไว้ที่โกดังกลางที่เดียวแล้วใช้ Hard Link เชื่อมโยง ช่วยประหยัดเนื้อที่ดิสก์มหาศาลและทำงานรวดเร็วกว่า npm ดั้งเดิม

### หลักการเบื้องหลัง (Under the Hood)
1. **Semantic Versioning (SemVer: `MAJOR.MINOR.PATCH`):**
   - `MAJOR` (เช่น 2.0.0): มี Breaking Changes การทำงานเก่าอาจใช้งานไม่ได้
   - `MINOR` (เช่น 1.4.0): เพิ่มฟีเจอร์ใหม่แบบ Backward-compatible ไม่กระทบของเดิม
   - `PATCH` (เช่น 1.4.2): แก้ไขบั๊กหรือปรับปรุงความปลอดภัยโดยไม่เพิ่มฟีเจอร์
   - สัญลักษณ์นำหน้า:
     - `^1.2.3` (Caret): อัปเดต Minor และ Patch อัตโนมัติ (`>= 1.2.3 < 2.0.0`)
     - `~1.2.3` (Tilde): อัปเดตเฉพาะ Patch เท่านั้น (`>= 1.2.3 < 1.3.0`)
     - `1.2.3` (Exact): ล็อกเวอร์ชันเป๊ะ ห้ามขยับเด็ดขาด
2. **ประเภทของ Dependencies ใน `package.json`:**
   - `dependencies`: แพ็กเกจที่จำเป็นสำหรับ Production Runtime (เช่น `prisma`, `express`, `bcrypt`, `dotenv`)
   - `devDependencies`: แพ็กเกจที่ใช้เฉพาะช่วงเวลา Development หรือ Build (เช่น `typescript`, `eslint`, `jest`, `@types/node`)
   - `peerDependencies`: ข้อกำหนดว่า Host application ที่นำไลบรารีนี้ไปใช้ ต้องติดตั้งแพ็กเกจนี้ไว้ด้วย (เช่น ปลั๊กอิน NestJS ต้องการ `@nestjs/common` เป็น peer)
3. **pnpm Content-addressable Store และ Hard Links:**
   - npm แบบเดิมจะวางไฟล์แบบ Flat ในโฟลเดอร์ `node_modules` ทำให้เกิดปัญหา **Phantom Dependencies** (โค้ดสามารถ `import` แพ็กเกจที่ไม่ได้ประกาศใน `package.json` ได้ หากมันเป็น dependency ของ dependency อีกทอดหนึ่ง)
   - pnpm ใช้ **Global Content-addressable Storage** เก็บไฟล์ตาม Hash ของเนื้อหา และสร้าง Symlinks/Hard Links ไปยังโครงสร้างจำลอง ช่วยกำจัด Phantom Dependencies ป้องกันบั๊กซ่อนเร้น และประหยัดพื้นที่ดิสก์ได้ถึง 70-80%

  }
});

  process.exit(1);
} else {
  console.log('[CI Check] โครงสร้าง Dependency ถูกต้องสมบูรณ์');

# อาจทำให้ npm ปรับเวอร์ชันของ dependency ตามเครื่องหมาย ^ หรือ ~

## 5. Environment Variables (.env)

### แนวคิด (Concept)
สูตรหมักเนื้อซอสพริกไทยดำที่เป็นความลับทางการค้า รหัสเปิดตู้เซฟเก็บเงินสด หรือกุญแจ API ตัดบัตรเครดิตของ **Smart Butcher Marketplace** จะต้องไม่ถูกเขียนแปะไว้ที่เคาน์เตอร์ให้ลูกค้าทุกคนเห็น:
- ในโลกของการเขียนโปรแกรม ซอร์สโค้ดจะถูกส่งขึ้น Git Repository (ซึ่งทีมงานทุกคนเข้าถึงได้)
- ข้อมูลที่เป็นความลับ (Secrets), ข้อมูลการเชื่อมต่อฐานข้อมูล (Database Credentials) และการตั้งค่าที่เปลี่ยนแปลงตามสภาพแวดล้อม (Local vs Production) จะต้องแยกออกมาเก็บใน **Environment Variables** ตามหลักการ **The Twelve-Factor App**

### หลักการเบื้องหลัง (Under the Hood)
1. **`process.env`:** วัตถุในตัวของ Node.js ที่แมปตัวแปร Environment จากระดับ Operating System เข้ามาตอนโปรเซสเริ่มต้นทำงาน
2. **การโหลดค่า `.env`:**
   - **ดั้งเดิม:** ใช้ไลบรารี `dotenv` (เช่น `import 'dotenv/config'`)
   - **Node.js Built-in (Node v20.6.0+):** สามารถรันด้วย Flag `--env-file=.env` โดยไม่ต้องติดตั้งไลบรารีภายนอกเลย เช่น `node --env-file=.env dist/server.js`
3. **Type-safe Validation ด้วย Zod (Fail-Fast Principle):**
   บ่อยครั้งที่ Developer ลืมใส่ค่า Config ใน `.env` บน Production เซิร์ฟเวอร์เปิดติด แต่พอลูกค้ากดจ่ายเงินระบบถึงจะพัง การทำ **Type-safe Validation** ร่วมกับ Zod จะช่วยตรวจสอบความถูกต้องของค่าคอนฟิกทั้งหมดตั้งแต่เสี้ยววินาทีแรกที่บูตแอปพลิเคชัน หากค่าไม่ครบจะสั่งหยุดระบบทันทีก่อนเปิดรับทราฟฟิก

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: Schema Validation ของ Environment Variables ด้วย Zod
```typescript filename="src/config/env.ts"
import { z } from 'zod';

// ประกาศ Schema ที่เข้มงวดสำหรับระบบ Smart Butcher
const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  PORT: z.coerce.number().default(4000),
  
  // Database Configuration
  DATABASE_URL: z.string().url('DATABASE_URL ต้องเป็นรูปแบบ Database URI ที่ถูกต้อง (เช่น postgresql://...)'),
  
  // Security Secrets
  JWT_SECRET: z.string().min(32, 'JWT_SECRET ต้องมีความยาวอย่างน้อย 32 ตัวอักษรเพื่อความปลอดภัย'),
  JWT_EXPIRES_IN: z.string().default('1d'),
  
  // Payment Gateway
  OMISE_PUBLIC_KEY: z.string().startsWith('pkey_', 'Omise Public Key ต้องขึ้นต้นด้วย pkey_'),
  OMISE_SECRET_KEY: z.string().startsWith('skey_', 'Omise Secret Key ต้องขึ้นต้นด้วย skey_'),
  
  // Business Settings
  BUTCHER_MARKET_TAX_RATE: z.coerce.number().min(0).max(1).default(0.07),
});

// ฟังก์ชันตรวจสอบและสกัดค่า Config
function validateEnv() {
  const result = envSchema.safeParse(process.env);

  if (!result.success) {
    console.error('❌ ข้อผิดพลาดในการตรวจสอบ Environment Variables ของระบบ Smart Butcher:');
    console.error(JSON.stringify(result.error.format(), null, 2));
    // หยุดการทำงานทันทีตามหลัก Fail-Fast
    process.exit(1);
  }

  return result.data;
}

// Export ค่า Config ที่เป็น Type-safe 100%
export const ENV = validateEnv();
export type Environment = z.infer<typeof envSchema>;
```

#### ตัวอย่างที่ 2: การนำ Object Config ไปใช้ใน Service Layer
```typescript filename="src/services/payment.service.ts"
import { ENV } from '../config/env.js';

export class ButcherPaymentService {
  private secretKey: string;
  private taxRate: number;

  constructor() {
    // ปลอดภัย ไม่ต้องกังวลว่า undefined หรือค่าไม่ถูกต้อง
    this.secretKey = ENV.OMISE_SECRET_KEY;
    this.taxRate = ENV.BUTCHER_MARKET_TAX_RATE;
  }

  public calculateFinalAmount(subtotalThb: number): number {
    const taxAmount = subtotalThb * this.taxRate;
    return subtotalThb + taxAmount;
  }

  public getMaskedKey(): string {
    return this.secretKey.slice(0, 8) + '********';
  }
}
```

## 6. การทำงานของ HTTP Server

### แนวคิด (Concept)
เมื่อลูกค้าเข้าสู่หน้าเว็บไซต์ **Smart Butcher Marketplace** เพื่อดูรายการเนื้อสเต็ก เบราว์เซอร์จะส่ง HTTP Request ข้ามเครือข่ายอินเทอร์เน็ตมายังเซิร์ฟเวอร์ Node.js ของเรา:
- แทนที่ Node.js จะรอให้ข้อมูลอัปโหลดเสร็จสิ้นทั้งหมดก่อนแล้วค่อยประมวลผล Node.js ปฏิบัติต่อ Request และ Response ในฐานะ **Streams** (สายน้ำของข้อมูลที่ไหลมาทีละก้อน หรือ Chunk)
- ช่วยให้เซิร์ฟเวอร์เริ่มอ่านหรือส่งข้อมูลกลับไปได้ทันทีโดยไม่ต้องรอโหลดเนื้อหาทั้งหมดลง RAM ส่งผลให้ใช้หน่วยความจำน้อยและมี Latency ต่ำ

### หลักการเบื้องหลัง (Under the Hood)
1. **`node:http` createServer:**
   - ฟังก์ชัน `http.createServer((req, res) => { ... })` จะสร้างอินสแตนซ์ของ `http.Server`
   - พารามิเตอร์ `req` เป็นอินสแตนซ์ของ `http.IncomingMessage` ซึ่งสืบทอดมาจาก **`stream.Readable`**
   - พารามิเตอร์ `res` เป็นอินสแตนซ์ของ `http.ServerResponse` ซึ่งสืบทอดมาจาก **`stream.Writable`**
2. **Chunked Transfer Encoding:**
   - เมื่อเราใช้ `res.write(chunk)` โดยไม่ได้กำหนด Header `Content-Length` ไว้ล่วงหน้า Node.js จะส่ง Header `Transfer-Encoding: chunked` โดยอัตโนมัติ
   - ทำให้ส่งข้อมูลที่มีขนาดใหญ่มาก (เช่น ไฟล์ประวัติสต็อกเนื้อ) ออกไปได้เรื่อยๆ โดยที่เซิร์ฟเวอร์ไม่ต้องคำนวณขนาดรวมทั้งหมดล่วงหน้า
3. **Handling Raw Buffers & Memory Limits:**
   - ข้อมูลที่ส่งเข้ามาทาง `req` ในอีเวนต์ `'data'` จะเป็น **Raw Buffer** (ไบนารีข้อมูล)
   - หากไม่มีการจำกัดขนาดของ Buffer ที่อ่านเข้ามา ผู้ไม่ประสงค์ดีอาจส่ง Request Body ขนาด 1GB เพื่อทำให้เกิดปัญหา Out of Memory (DoS Attack)

```text filename="docs/backend/nodejs.txt"
Client (Browser / Mobile App)
          │
          │ 1. HTTP Request (TCP Connection)
          ▼
   node:http Server
          │
          ├─► req (Readable Stream) ──► อีเวนต์ 'data' (Buffer chunk) ──► อีเวนต์ 'end'
          │
          └─► res (Writable Stream) ──► res.writeHead() ──► res.write() ──► res.end()
```

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: Native HTTP Server จัดการ Routing และเสิร์ฟข้อมูลรายการเนื้อ (JSON API)
```typescript filename="src/native-http-server.ts"
import http from 'node:http';

interface ButcherProductItem {
  id: string;
  name: string;
  category: 'BEEF' | 'PORK';
  priceThb: number;
}

const butcherCatalog: ButcherProductItem[] = [
  { id: 'cut_01', name: 'สันนอกวากิว A5 (Sirloin)', category: 'BEEF', priceThb: 3800 },
  { id: 'cut_02', name: 'สันคอหมูดำคุโรบูตะ (Collar)', category: 'PORK', priceThb: 420 },
];

const server = http.createServer((req, res) => {
  const { method, url } = req;
  console.log(`[HTTP Request] ${method} ${url}`);

  // CORS Headers พื้นฐาน
  res.setHeader('Access-Control-Allow-Origin', '*');
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, OPTIONS');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type');

  if (method === 'OPTIONS') {
    res.writeHead(204);
    res.end();
    return;
  }

  // Routing: GET /api/products
  if (method === 'GET' && url === '/api/products') {
    const payload = JSON.stringify({
      success: true,
      data: butcherCatalog,
      timestamp: new Date().toISOString(),
    });

    res.writeHead(200, {
      'Content-Type': 'application/json; charset=utf-8',
      'Content-Length': Buffer.byteLength(payload),
    });
    res.end(payload);
    return;
  }

  // Route ไม่ตรงกับที่กำหนด: 404 Not Found
  res.writeHead(404, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ success: false, message: 'ไม่พบ Route ที่ต้องการในระบบ Smart Butcher' }));
});

const PORT = 3001;
server.listen(PORT, () => {
  console.log(`[Server Ready] Smart Butcher Native HTTP รันอยู่ที่ http://localhost:${PORT}`);
});
```

#### ตัวอย่างที่ 2: การอ่าน Stream Body แบบจำกัดขนาด (Safe Body Parser ป้องกัน DoS)
```typescript filename="src/safe-body-parser.ts"
import http from 'node:http';

const MAX_BODY_SIZE_BYTES = 1 * 1024 * 1024; // จำกัดขนาดไม่เกิน 1 MB สำหรับคำสั่งซื้อ

export function parseJsonBody<T>(req: http.IncomingMessage): Promise<T> {
  return new Promise((resolve, reject) => {
    const chunks: Buffer[] = [];
    let receivedBytes = 0;

    req.on('data', (chunk: Buffer) => {
      receivedBytes += chunk.length;

      // ป้องกัน DoS Attack: ตัดการเชื่อมต่อทันทีหากข้อมูลเกินขนาดที่อนุญาต
      if (receivedBytes > MAX_BODY_SIZE_BYTES) {
        req.destroy(); // ปิด Socket ทันที
        reject(new Error('Payload Too Large: ขนาดข้อมูลคำสั่งซื้อเกิน 1MB'));
        return;
      }

      chunks.push(chunk);
    });

    req.on('end', () => {
      try {
        const rawString = Buffer.concat(chunks).toString('utf-8');
        if (!rawString) {
          resolve({} as T);
          return;
        }
        const parsed = JSON.parse(rawString);
        resolve(parsed);
      } catch (err) {
        reject(new Error('Invalid JSON Payload: ข้อมูลที่ส่งมาไม่ใช่ JSON ที่ถูกต้อง'));
      }
    });

    req.on('error', (err) => {
      reject(err);
    });
  });
}

// นำไปใช้ใน Server
const orderServer = http.createServer(async (req, res) => {
  if (req.method === 'POST' && req.url === '/api/orders') {
    try {
      const orderBody = await parseJsonBody<{ productId: string; quantity: number }>(req);
      console.log('[Order Received] ได้รับข้อมูลคำสั่งซื้อ:', orderBody);

      res.writeHead(201, { 'Content-Type': 'application/json' });
      res.end(JSON.stringify({ success: true, message: 'บันทึกคำสั่งซื้อเนื้อสำเร็จ' }));
    } catch (error: any) {
      res.writeHead(400, { 'Content-Type': 'application/json' });
      res.end(JSON.stringify({ success: false, error: error.message }));
    }
  }
});
```

### ผิด vs ถูก (Anti-patterns & Best Practices)

#### ❌ โค้ดที่ผิด: ลืมดักจับอีเวนต์ error บน Stream ทำให้เซิร์ฟเวอร์แครชเมื่อไคลเอนต์กดยกเลิก
```typescript filename="bad-stream-pipe.ts"
import fs from 'node:fs';
import http from 'node:http';

http.createServer((req, res) => {
  // ผิด: ไพพ์ไฟล์ขนาดใหญ่ไปยัง Response โดยไม่ดัก error
  // หากลูกค้าปิดเบราว์เซอร์กะทันหัน Socket จะพัง และส่ง Error 'ECONNRESET' ที่ไม่มีตัวดักจับ
  // ทำให้ทั้งแอปพลิเคชัน Node.js แคชทันที
  const stream = fs.createReadStream('/data/meat-catalog-catalog.pdf');
  stream.pipe(res);
}).listen(3000);
```

#### ✅ โค้ดที่ถูก: ใช้ `stream.pipeline` เพื่อจัดการ Error และปิด Cleanup อัตโนมัติ
```typescript filename="good-stream-pipe.ts"
import fs from 'node:fs';
import http from 'node:http';
import { pipeline } from 'node:stream';

http.createServer((req, res) => {
  const fileStream = fs.createReadStream('/data/meat-catalog-catalog.pdf');
  res.writeHead(200, { 'Content-Type': 'application/pdf' });

  // ถูกต้อง: pipeline จะคอยดักจับ Error และปิด Stream ทั้งสองฝั่งให้อัตโนมัติเมื่อเกิดข้อผิดพลาด
  pipeline(fileStream, res, (err) => {
    if (err) {
      console.warn('[Stream Warning] ลูกค้าตัดการเชื่อมต่อก่อนโหลดไฟล์เสร็จ:', err.message);
    } else {
      console.log('[Stream Success] ส่งไฟล์แค็ตตาล็อกเนื้อสำเร็จ');
    }
  });
}).listen(3000);
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้:** การทำความเข้าใจโครงสร้างพื้นฐานระดับลึก, การสร้าง Lightweight Health Check Server, หรือการทำ Reverse Proxy ขนาดย่อม
- **ไม่ควรใช้:** การสร้าง Business Application ขนาดใหญ่ด้วย Native `node:http` โดยตรง ควรใช้ Framework คุณภาพสูงอย่าง **NestJS 11** หรือ **Fastify** ซึ่งมีระบบ Dependency Injection, Interceptors, Validation Pipes, และ Security Guards มาให้ในตัว

### คำถามสัมภาษณ์ (Interview Questions)
- **Q1: ใน `http.createServer` ทำไมเราจึงต้องดักฟังอีเวนต์ `data` และ `end` แทนที่จะอ่านค่าออกมาเป็นตัวแปรธรรมดา?**
  - *คำตอบ:* เพราะ HTTP Request Body ใน Node.js ถูกส่งมอบในรูปแบบ **Readable Stream** ข้อมูลขนาดใหญ่อาจถูกส่งแยกออกเป็นหลายๆ TCP Packets (Chunks) การดักฟังอีเวนต์ `data` ช่วยให้เรารับข้อมูลทีละส่วน และ `end` เป็นสัญญาณบ่งชี้ว่าส่งข้อมูลครบถ้วนแล้ว รูปแบบนี้ช่วยป้องกันไม่ให้เซิร์ฟเวอร์ต้องโหลดข้อมูลทั้งหมดลง RAM ในครั้งเดียว
- **Q2: `Transfer-Encoding: chunked` คืออะไร และมีประโยชน์อย่างไรในงาน Backend?**
  - *คำตอบ:* เป็นกลไกการส่งข้อมูลของ HTTP/1.1 ที่เซิร์ฟเวอร์ไม่จำเป็นต้องระบุขนาดของเนื้อหา (`Content-Length`) ล่วงหน้า แต่จะส่งข้อมูลเป็นชิ้นๆ (Chunks) พร้อมขนาดของแต่ละชิ้น มีประโยชน์อย่างยิ่งเมื่อต้องสตรีมข้อมูลขนาดใหญ่หรือข้อมูลที่สร้างขึ้นแบบเรียลไทม์ (เช่น การส่งไฟล์ CSV ออเดอร์ขนาดใหญ่ หรือการตอบกลับของ AI Chatbot)

## 7. Process และ Error ที่ไม่ได้จัดการ (Unhandled Errors)

### แนวคิด (Concept)
เซิร์ฟเวอร์ของร้าน **Smart Butcher Marketplace** ต้องเปิดให้บริการตลอด 24 ชั่วโมง หากมีข้อผิดพลาดที่ไม่คาดคิดเกิดขึ้น:
- ปล่อยให้เซิร์ฟเวอร์แครชเฉยๆ ทำให้ลูกค้าที่กำลังเลือกซื้อเนื้อไม่สามารถเข้าใช้งานได้
- หรือดักจับ Error แล้วพยายามฝืนรันต่อทั้งที่หน่วยความจำภายในอาจเสียหายไปแล้ว (เช่น ยอดเงินในบัญชีไม่ตรงกับฐานข้อมูล)
- ทางออกที่ถูกต้องคือ **Graceful Shutdown**: หยุดรับคำสั่งซื้อใหม่ เคลียร์งานที่ค้างอยู่ในมือให้เสร็จ บันทึกข้อมูลลงฐานข้อมูล ปิดการเชื่อมต่ออย่างสุภาพ แล้วให้ระบบ Process Manager (เช่น PM2 หรือ Kubernetes) ชุบชีวิตเซิร์ฟเวอร์ตัวใหม่ขึ้นมาแทนทันที

### หลักการเบื้องหลัง (Under the Hood)
1. **Unhandled Errors Categories:**
   - **`uncaughtException`:** เกิดขึ้นเมื่อมี Error แบบ Synchronous หลุดออกจาก Call Stack โดยไม่มีบล็อก `try/catch` มารับ
   - **`unhandledRejection`:** เกิดขึ้นเมื่อมี Promise ที่ถูก reject แต่ไม่มีคำสั่ง `.catch()` หรือบล็อก `try/catch` ในฟังก์ชัน async
2. **OS Signals (สัญญาณสื่อสารระหว่างระบบปฏิบัติการและ Process):**
   - **`SIGINT` (Signal Interrupt):** มักส่งมาจากแป้นพิมพ์ เช่น เมื่อ Developer กด `Ctrl + C` ใน Terminal
   - **`SIGTERM` (Signal Terminate):** สัญญาณขอให้ปิดตัวลงอย่างสุภาพจาก Orchestrator เช่น Docker หรือ Kubernetes ก่อนที่ Pod จะถูกทำลาย
   - **`SIGKILL` (Signal Kill - Signal 9):** คำสั่งบังคับฆ่า Process ทันที ไม่สามารถดักจับหรือทำ Cleanup ได้
3. **Graceful Shutdown Pattern (วงจรการปิดระบบอย่างสุภาพ):**
   ```text filename="docs/backend/nodejs.txt"
   [รับสัญญาณ SIGTERM / SIGINT]
              │
              ▼
   1. หยุดรับ HTTP Request ใหม่ (server.close())
              │
              ▼
   2. ปล่อยให้ In-flight Requests ทำงานจนจบ (Drain Connections)
              │
              ▼
   3. ปิดการเชื่อมต่อ Database (Prisma/PostgreSQL), Redis, Message Queue
              │
              ▼
   4. ตั้ง Timeout เผื่อฉุกเฉิน (เช่น 10 วินาที) หากงานค้างนานเกินไปให้บังคับปิด
              │
              ▼
   5. สั่ง process.exit(0) อย่างสมบูรณ์
   ```

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การดักจับ Global Unhandled Errors พร้อม Structured Logging
```typescript filename="src/global-error-handlers.ts"
export function registerGlobalErrorHandlers() {
  // ดักจับ Unhandled Promise Rejection
  process.on('unhandledRejection', (reason: unknown, promise: Promise<unknown>) => {
    console.error('🚨 [Unhandled Rejection] ตรวจพบ Promise ที่ไม่มีตัวรับ Error:');
    if (reason instanceof Error) {
      console.error(`ข้อความ Error: ${reason.message}`);
      console.error(`Stack: ${reason.stack}`);
    } else {
      console.error('สาเหตุ:', reason);
    }
    // คำแนะนำของ Node.js: ในอนาคต Unhandled Rejection จะบังคับปิดโปรเซสอัตโนมัติ
  });

  // ดักจับ Uncaught Exception
  process.on('uncaughtException', (error: Error) => {
    console.error('🔥 [FATAL: Uncaught Exception] เกิดข้อผิดพลาดร้ายแรงที่ไม่ได้จัดการ:');
    console.error(`ข้อความ: ${error.message}`);
    console.error(`Stack: ${error.stack}`);

    // สำคัญมาก: เมื่อเกิด uncaughtException สภาพแวดล้อมของโปรเซสถือว่าไม่น่าไว้วางใจอีกต่อไป
    // ต้องเริ่มกระบวนการปิดตัวลงทันที (ห้ามฝืนรันต่อ!)
    console.error('เซิร์ฟเวอร์จะปิดตัวลงเพื่อความปลอดภัยของข้อมูลธุรกรรม...');
    process.exit(1);
  });
}
```

#### ตัวอย่างที่ 2: ระบบ Graceful Shutdown สมบูรณ์แบบสำหรับ Smart Butcher Server
```typescript filename="src/graceful-shutdown.ts"
import http from 'node:http';

// จำลอง Database Client ของ Smart Butcher
const mockDatabase = {
  close: async () => {
    console.log('[Database] กำลังตัดการเชื่อมต่อ PostgreSQL Connection Pool...');
    await new Promise((resolve) => setTimeout(resolve, 500));
    console.log('[Database] ปิด Connection Pool สำเร็จ ปลอดภัย 100%');
  },
};

export function setupGracefulShutdown(server: http.Server) {
  let isShuttingDown = false;

  async function shutdown(signal: string) {
    if (isShuttingDown) return;
    isShuttingDown = true;

    console.log(`\n🛑 ได้รับสัญญาณ [${signal}] กำลังเริ่มกระบวนการ Graceful Shutdown...`);

    // 1. ตั้ง Hard Timeout เผื่อว่ามี Request ค้างแล้วไม่ยอมจบ
    const forceExitTimer = setTimeout(() => {
      console.error('⚠️ บังคับปิดระบบเนื่องจากใช้เวลาเกินขีดจำกัด 10 วินาที (Force Exit)');
      process.exit(1);
    }, 10_000);
    forceExitTimer.unref(); // ป้องกันไม่ให้ timer นี้ขวางการปิดโปรเซส

    // 2. หยุดรับ HTTP Request ใหม่เข้ามาที่ร้าน
    server.close(async (err) => {
      if (err) {
        console.error('เกิดข้อผิดพลาดขณะปิด HTTP Server:', err);
        process.exit(1);
      }
      console.log('✅ [HTTP Server] ปิดรับทราฟฟิกใหม่ และเคลียร์ Request ที่ค้างอยู่เสร็จสิ้น');

      // 3. ปิดการเชื่อมต่อฐานข้อมูลและ External Queues
      try {
        await mockDatabase.close();
        console.log('✅ [Clean Exit] ข้อมูลสินค้าและคำสั่งซื้อทั้งหมดถูกบันทึกอย่างปลอดภัย');
        process.exit(0); // จบการทำงานปกติ รหัส 0
      } catch (dbErr) {
        console.error('❌ ข้อผิดพลาดขณะปิดฐานข้อมูล:', dbErr);
        process.exit(1);
      }
    });
  }

  // ดักฟังสัญญาณจาก OS
  process.on('SIGTERM', () => shutdown('SIGTERM (Kubernetes/Docker)'));
  process.on('SIGINT', () => shutdown('SIGINT (Ctrl+C)'));
}
```

### ผิด vs ถูก (Anti-patterns & Best Practices)

#### ❌ โค้ดที่ผิด: ดัก `uncaughtException` แล้วปล่อยผ่านเพื่อให้เซิร์ฟเวอร์รันต่อเรื่อยๆ
```typescript filename="bad-exception-swallow.ts"
// ผิดมหันต์: การดักจับแล้วไม่สั่ง process.exit()
// เมื่อเกิด uncaughtException ตัวแปรในหน่วยความจำอาจอยู่ในสถานะครึ่งๆ กลางๆ (เช่น ตัดสต็อกเนื้อแล้วแต่ยังไม่ได้ตัดเงิน)
// การปล่อยให้รันต่อไปจะทำให้ข้อมูลในระบบผิดพลาดร้ายแรงขึ้นเรื่อยๆ
process.on('uncaughtException', (err) => {
  console.log('ช่างมัน รันต่อไปเรื่อยๆ:', err.message);
  // ไม่สั่ง process.exit()
});
```

#### ✅ โค้ดที่ถูก: บันทึก Log อย่างละเอียด ทำ Cleanup สั้นๆ แล้วสั่ง `process.exit(1)`
```typescript filename="good-exception-exit.ts"
process.on('uncaughtException', async (err) => {
  console.error('[CRITICAL FAILURE]', err);
  // บันทึก Log ฉุกเฉินลง External Monitoring (เช่น Sentry หรือ Datadog)
  try {
    await sendAlertToPagerDuty(err);
  } finally {
    // ออกจากโปรเซสทันที แล้วปล่อยให้ Docker / Kubernetes รีสตาร์ต Container ใหม่
    process.exit(1);
  }
});
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้:** การติดตั้ง Graceful Shutdown และ Signal Handlers เป็นสิ่งจำเป็นอย่างยิ่งใน Production Application ทุกตัวที่รันบน Docker, Kubernetes, AWS ECS หรือ PM2
- **ไม่ควรใช้:** ห้ามใช้ `uncaughtException` หรือ `unhandledRejection` เป็นเครื่องมือทดแทนการเขียน Error Handling ปกติ (ต้องเขียน `try/catch` ในระดับ Controller และ Service เสมอ)

### คำถามสัมภาษณ์ (Interview Questions)
- **Q1: ทำไมเอกสารทางการของ Node.js จึงแนะนำอย่างจริงจังให้ปิด Process ทันที (`process.exit(1)`) หลังเกิดเหตุการณ์ `uncaughtException`?**
  - *คำตอบ:* เพราะ `uncaughtException` หมายถึงโปรแกรมทำงานในจุดที่ไม่คาดคิด ส่งผลให้ Application State ในหน่วยความจำอาจอยู่ในสภาวะ Corrupted (เสียหายหรือไม่สอดคล้องกัน) เช่น Socket ค้าง, Resource ปิดไม่สมบูรณ์ หรือตัวแปรถูกแก้ไขไปครึ่งเดียว การฝืนรันต่อไปจะทำให้เกิดบั๊กแบบลูกโซ่และอาจทำให้ข้อมูลธุรกรรมของลูกค้าสูญหาย
- **Q2: สัญญาณ `SIGTERM` และ `SIGKILL` มีความแตกต่างกันอย่างไรในการทำ Deployment บน Kubernetes?**
  - *คำตอบ:* `SIGTERM` เป็นสัญญาณแจ้งเตือนล่วงหน้าเพื่อให้ Process ทำ Graceful Shutdown (ปิดการเชื่อมต่อ DB, ตอบกลับ Request เดิมให้เสร็จ) ภายในระยะเวลา Grace Period (ค่าเริ่มต้น 30 วินาทีบน K8s) หากครบเวลาแล้ว Process ยังไม่ยอมปิด Kubernetes จะส่งสัญญาณ `SIGKILL` ซึ่งเป็นคำสั่งเด็ดขาดของ OS ในการทำลาย Process ทันทีโดยไม่สามารถดักจับหรือสั่ง Cleanup โค้ดใดๆ ได้

## ข้อผิดพลาดที่พบบ่อย (Anti-patterns)

ในการพัฒนา Backend ด้วย Node.js ในระดับ Enterprise นักพัฒนามักพบข้อผิดพลาดที่ส่งผลต่อประสิทธิภาพและความเสถียรของระบบ ดังนี้:

### 1. การบล็อก Event Loop ด้วย Synchronous Operations หรือ Complex Regex (ReDoS)
- **พฤติกรรม:** การใช้ `fs.readFileSync`, `crypto.pbkdf2Sync`, หรือ Regular Expression ที่มีปัญหา Catastrophic Backtracking ในการตรวจสอบอีเมลลูกค้า
- **ผลกระทบ:** V8 Call Stack ถูกจองไว้คนเดียว ทำให้ผู้ใช้ทั้งระบบไม่สามารถโหลดหน้าเว็บหรือส่งคำสั่งซื้อได้
- **แนวทางแก้ไข:** ใช้ Asynchronous APIs เสมอ และทดสอบ Regular Expression ด้วยเครื่องมือตรวจสอบ ReDoS

### 2. ปัญหา Memory Leak จาก Unbounded Caching หรือ Event Listeners
- **พฤติกรรม:** การสร้าง Global Map หรือ Array เก็บประวัติออเดอร์ของ User โดยไม่มีการเคลียร์ทิ้ง หรือการสั่ง `socket.on(...)` ซ้ำๆ ทุกครั้งที่มี Request เข้ามาโดยไม่สั่ง `removeListener`
- **ผลกระทบ:** เซิร์ฟเวอร์ใช้ RAM สูงขึ้นเรื่อยๆ จนกระทั่งเกิดข้อผิดพลาด `JavaScript heap out of memory` และ Process แครช
- **แนวทางแก้ไข:** ใช้เครื่องมือเช่น LRU Cache (`lru-cache`) ที่จำกัดขนาด และใช้ `events.once()` หรือถอด Listener ทันทีเมื่อเลิกใช้งาน

### 3. การละเลยและกลืน Error ใน Promise (Error Swallowing)
- **พฤติกรรม:** การเขียน `.catch(() => {})` หรือบล็อก `try { ... } catch (e) {}` ว่างเปล่าไว้เพื่อไม่ให้ระบบฟ้อง Error
- **ผลกระทบ:** เมื่อระบบตัดเงินลูกค้าล้มเหลว หรือฐานข้อมูลเชื่อมต่อไม่ได้ ระบบจะไม่แจ้งเตือนใดๆ ทำให้ตรวจสอบหาสาเหตุยากมาก
- **แนวทางแก้ไข:** ส่งต่อ Error ให้ Global Error Handler เสมอ หรือบันทึก Structured Logging พร้อม Stack Trace

### 4. การผสมผสาน ESM และ CommonJS โดยไม่เข้าใจ Build Pipeline
- **พฤติกรรม:** พยายาม `require()` แพ็กเกจที่เป็น ESM-only หรือการใช้ตัวแปร `__dirname` ในไฟล์ที่ประกาศ `"type": "module"`
- **ผลกระทบ:** เกิด Runtime Error `ERR_REQUIRE_ESM` หรือ `ReferenceError: __dirname is not defined` ตอน Deploy ขึ้น Production
- **แนวทางแก้ไข:** แปลงโปรเจกต์เป็น ESM อย่างสมบูรณ์ และใช้ `import.meta.dirname` แทน

## Checklist สรุป

ก่อนนำบริการ Node.js Backend ขึ้นสู่สภาพแวดล้อม Production ให้ตรวจสอบความพร้อมตามรายการนี้:

- [ ] **Event Loop Hygiene:** ไม่มีคำสั่งตระกูล `*Sync` (เช่น `fs.readFileSync`, `fs.writeFileSync`) ใน Request Handling Path
- [ ] **Thread Pool Tuning:** ปรับแต่งค่า `UV_THREADPOOL_SIZE` ให้เหมาะสมกับ CPU Cores และภาระงาน Crypto/File I/O ของระบบ
- [ ] **Async Flow Consistency:** ไม่มีการใช้ `forEach` กับฟังก์ชัน `async` ให้เปลี่ยนไปใช้ `Promise.all` หรือ `for...of` แทน
- [ ] **Strict Module System:** มีการระบุ `"type": "module"` ใน `package.json` อย่างชัดเจน และไม่มีการเรียกใช้ CJS Globals ใน ESM
- [ ] **Deterministic Dependencies:** ไฟล์ `pnpm-lock.yaml` หรือ `package-lock.json` ถูกบันทึกลง Git และใน CI ใช้คำสั่ง `--frozen-lockfile` หรือ `npm ci`
- [ ] **Type-safe Env Validation:** ตัวแปร `.env` ทั้งหมดได้รับการตรวจสอบผ่าน Schema (เช่น Zod) ทันทีตั้งแต่เริ่มบูตโปรเซส
- [ ] **Stream Error Handling:** ทุก Stream ไปป์ไลน์มีการใช้ `stream.pipeline` เพื่อดักจับ Error และปิด Stream อย่างปลอดภัย
- [ ] **Payload Size Limit:** มีการจำกัดขนาดของ Request Body เพื่อป้องกันการโจมตีแบบ Denial of Service (DoS)
- [ ] **Global Error Trapping:** ลงทะเบียนดักฟังอีเวนต์ `unhandledRejection` และ `uncaughtException` พร้อมระบบแจ้งเตือน
- [ ] **Graceful Shutdown Protocol:** ดักฟังสัญญาณ `SIGTERM` และ `SIGINT` เพื่อเคลียร์ In-flight Requests และปิด Database Connections อย่างปลอดภัย
