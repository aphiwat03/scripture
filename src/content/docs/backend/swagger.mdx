# Swagger

ในการพัฒนาระบบที่แยกส่วนระหว่าง Frontend (Next.js) และ Backend (NestJS 11) ออกจากกันอย่างในระบบ **Smart Butcher Marketplace** ปัญหาคอขวดที่ทำให้ทีมพัฒนาเสียเวลามากที่สุดคือการสื่อสารเรื่องโครงสร้าง API (เช่น ชื่อฟิลด์สะกดไม่ตรงกัน, ชนิดข้อมูลเป็น `string` หรือ `number`, หรือไม่รู้ว่า Endpoint นี้คืนค่า HTTP Status ใดบ้าง) การใช้แพ็กเกจ **`@nestjs/swagger`** ตามมาตรฐาน **OpenAPI 3.0** ช่วยให้เราสร้างเอกสาร API แบบโต้ตอบได้ (Interactive Swagger UI) และสร้างไฟล์สัญญา (API Contract) จากคลาส DTO และ Controller ในโค้ดโดยตรง ทำให้เอกสารตรงกับโค้ดจริงเสมอ (Single Source of Truth)

## 1. การติดตั้งและตั้งค่า SwaggerModule (OpenAPI) ใน NestJS 11

### แนวคิด (Concept)
**OpenAPI Specification (OAS 3.0)** คือมาตรฐานสากลที่ใช้รูปแบบไฟล์ JSON หรือ YAML ในการอธิบายความสามารถทั้งหมดของ RESTful API ส่วน **Swagger UI** คือเครื่องมือที่นำไฟล์สเปกนั้นมาแสดงผลเป็นหน้าเว็บที่สวยงามและกดทดสอบยิง Request (`Try it out`) ได้ทันที ใน NestJS 11 เราใช้คลาส `DocumentBuilder` เพื่อกำหนดข้อมูลพื้นฐานของเอกสาร (เช่น ชื่อระบบ, เวอร์ชัน, เซิร์ฟเวอร์) และใช้ `SwaggerModule` ในการสแกนหา Controller และ DTO ทั้งหมดในแอปพลิเคชันเพื่อสร้างเป็น OpenAPI Document

### หลักการเบื้องหลัง (Under the Hood)
เมื่อแอปพลิเคชัน NestJS เริ่มต้นทำงานและเรียก `SwaggerModule.createDocument(app, config)`:
1. `SwaggerScanner` จะไล่สำรวจ Dependency Graph ของทุก Module เพื่อค้นหา Controller และ Route Handler ทั้งหมด (`@Get()`, `@Post()`, `@Patch()`, `@Delete()`)
2. อ่านข้อมูลจาก TypeScript Reflection Metadata (`emitDecoratorMetadata`) ร่วมกับข้อมูลจาก `@Api*` Decorators เพื่อสร้าง Schema ของพารามิเตอร์และ Body
3. เมื่อเรียก `SwaggerModule.setup('api/docs', app, documentFactory)` NestJS จะเปิดเส้นทาง `/api/docs` สำหรับหน้าเว็บ Swagger UI และเปิดเส้นทาง `/api/docs-json` (และ `/api/docs-yaml`) สำหรับดาวน์โหลดไฟล์ Raw OpenAPI Specification ไปใช้งานต่อ

<Callout type="warning" title="การจำกัดการเข้าถึงหน้า Swagger UI บน Production">
ในสภาพแวดล้อม Production ของระบบอีคอมเมิร์ซ การเปิดหน้า `/api/docs` ทิ้งไว้ให้บุคคลภายนอกเข้าถึงได้โดยอิสระถือเป็นการเปิดเผยโครงสร้างภายในทั้งหมดของระบบ (API Reconnaissance) จึงควรเปิดใช้งาน Swagger เฉพาะเมื่อ `NODE_ENV !== 'production'` หรือป้องกันเส้นทาง `/api/docs` ด้วย Basic Authentication เฉพาะทีมนักพัฒนาเท่านั้น
</Callout>

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

ตัวอย่างที่ 1: การแยกฟังก์ชันตั้งค่า `setupSwagger` ออกเป็นโมดูลที่ชัดเจนพร้อมตั้งค่า `SwaggerCustomOptions` เพื่อให้จดจำ Token เวลา Refresh หน้าเว็บ (`persistAuthorization: true`)

```typescript filename="src/config/swagger.config.ts"
import { INestApplication, Logger } from '@nestjs/common';
import { DocumentBuilder, SwaggerModule, OpenAPIObject } from '@nestjs/swagger';

export function setupSwagger(app: INestApplication): OpenAPIObject | null {
  const logger = new Logger('SwaggerSetup');
  const nodeEnv = process.env.NODE_ENV ?? 'development';

  // ป้องกันการเปิดเผยโครงสร้าง API สู่สาธารณะในโหมด Production
  if (nodeEnv === 'production' && process.env.ENABLE_SWAGGER !== 'true') {
    logger.log('Swagger UI ถูกปิดใช้งานในโหมด Production เพื่อความปลอดภัย');
    return null;
  }

  const config = new DocumentBuilder()
    .setTitle('Smart Butcher Marketplace API')
    .setDescription(
      'ระบบบริหารจัดการร้านค้าเนื้อพรีเมียมออนไลน์ รองรับการจัดการสินค้าเนื้อวากิว (Product), หมวดหมู่ (Category), คำสั่งซื้อ (Order), การชำระเงิน (Payment) และผู้ช่วย AI แนะนำการปรุงเนื้อ',
    )
    .setVersion('1.0.0')
    .addServer('http://localhost:3000', 'Local Development Server')
    .addBearerAuth(
      {
        type: 'http',
        scheme: 'bearer',
        bearerFormat: 'JWT',
        description: 'ระบุ Access Token ที่ได้รับจากการ Login (ไม่ต้องพิมพ์คำว่า Bearer นำหน้า)',
      },
      'jwt-access',
    )
    .addCookieAuth(
      'butcher_refresh_token',
      {
        type: 'apiKey',
        in: 'cookie',
        name: 'butcher_refresh_token',
        description: 'HttpOnly Cookie สำหรับต่ออายุ Access Token',
      },
      'cookie-refresh',
    )
    .build();

  const document = SwaggerModule.createDocument(app, config, {
    operationIdFactory: (controllerKey: string, methodKey: string) =>
      `${controllerKey.replace('Controller', '')}_${methodKey}`,
  });

  SwaggerModule.setup('api/docs', app, document, {
    jsonDocumentUrl: 'api/docs-json',
    swaggerOptions: {
      persistAuthorization: true, // ไม่ต้องกรอก JWT ใหม่ทุกครั้งที่กด Refresh หน้าเว็บ
      docExpansion: 'list',
      filter: true,
      showRequestDuration: true,
    },
    customSiteTitle: 'Smart Butcher API Docs',
  });

  logger.log('Swagger UI พร้อมใช้งานที่ http://localhost:3000/api/docs');
  logger.log('OpenAPI JSON Spec พร้อมใช้งานที่ http://localhost:3000/api/docs-json');

  return document;
}
```

ตัวอย่างที่ 2: การเรียกใช้ `setupSwagger(app)` ร่วมกับ Global Prefix (`/api/v1`) ในไฟล์ `src/main.ts`

```typescript filename="src/main.ts"
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';
import { setupSwagger } from './config/swagger.config';

async function bootstrap(): Promise<void> {
  const app = await NestFactory.create(AppModule);

  // กำหนด Global Prefix ให้ทุก API ขึ้นต้นด้วย /api/v1
  app.setGlobalPrefix('api/v1');

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
    }),
  );

  // เรียกตั้งค่า Swagger หลังจากกำหนด Global Prefix เพื่อให้ Path ในเอกสารมี /api/v1 ครบถ้วน
  setupSwagger(app);

  await app.listen(process.env.PORT ?? 3000, '0.0.0.0');
}

void bootstrap();
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ผิด (Anti-pattern) | ถูก (Best Practice) |
| :--- | :--- | :--- |
| **ลำดับการเรียก `setGlobalPrefix`** | เรียก `SwaggerModule.createDocument()` ก่อน `app.setGlobalPrefix('api/v1')` ทำให้ Path ใน Swagger ขาด `/api/v1` และกดยิงทดสอบแล้วขึ้น 404 | ตั้งค่า `app.setGlobalPrefix()` ให้เรียบร้อยก่อนเรียก `SwaggerModule.createDocument()` เสมอ |
| **การจำกัดสิทธิ์ใน Production** | เปิดหน้า `/api/docs` ทิ้งไว้บน Production Server โดยไม่มีการตรวจสอบสิทธิ์หรือเงื่อนไข Environment | เช็ค `NODE_ENV !== 'production'` ก่อนเปิดใช้งาน หรือตั้งรหัสผ่านป้องกันหน้าเอกสาร |
| **การตั้งค่า `operationIdFactory`** | ปล่อยให้ `operationId` ยาวและซ้ำซ้อน เช่น `ProductsController_findAll_v1` | กำหนด `operationIdFactory` ให้อ่านง่าย เช่น `Products_findAll` เพื่อเวลา Generate Frontend SDK จะได้ชื่อฟังก์ชันที่สะอาด |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้เมื่อ**: พัฒนา RESTful API ที่ต้องทำงานร่วมกับทีม Frontend, Mobile App, หรือทีม QA และต้องการให้ทุกฝ่ายทดสอบ API และตรวจสอบ Schema ได้ด้วยตัวเองทันที
- **ไม่ควรใช้เมื่อ**: เป็น Internal Worker Service ที่สื่อสารผ่าน Message Queue เท่านั้นและไม่มี HTTP Controller เปิดรับ Request

### คำถามสัมภาษณ์ (Interview Q&A)
1. **คำถาม**: ออปชัน `persistAuthorization: true` ใน `swaggerOptions` ช่วยแก้ปัญหาอะไรให้นักพัฒนา?
   - **แนวคำตอบ**: โดยค่าเริ่มต้นของ Swagger UI เมื่อนักพัฒนากดปุ่ม `Authorize` เพื่อใส่ JWT Bearer Token แล้วทำการแก้ไขโค้ดและกด Refresh หน้าเบราว์เซอร์ (`F5`) ค่า Token ที่ใส่ไว้จะหายไปทั้งหมด ทำให้ต้องเสียเวลาก๊อปปี้ Token มาวางใหม่ทุกครั้ง การเปิด `persistAuthorization: true` จะสั่งให้ Swagger UI เก็บค่า Token ไว้ใน `localStorage` ของเบราว์เซอร์ ทำให้ Refresh หน้าเว็บกี่ครั้งก็ยังยิงทดสอบ API ที่ติด Guard ได้ทันที
2. **คำถาม**: ทำไมเราจึงไม่สามารถใช้ TypeScript `interface` สำหรับกำหนด `@Body()` DTO ใน NestJS หากต้องการให้ Swagger สร้าง Schema ได้?
   - **แนวคำตอบ**: เพราะ TypeScript `interface` จะถูกลบทิ้งทั้งหมดหลังผ่านการคอมไพล์เป็น JavaScript (Type Erasure) ทำให้ไม่มีข้อมูลหลงเหลืออยู่ในช่วง Runtime ที่ `SwaggerScanner` และ `class-validator` ทำงาน เราจึงต้องประกาศ DTO ด้วย `class` เสมอ เพื่อให้มี Prototype และ Metadata คงอยู่ในช่วง Runtime

## 2. การใช้ Decorators หลัก (@ApiTags, @ApiOperation, @ApiProperty, @ApiResponse)

### แนวคิด (Concept)
เพื่อให้เอกสาร OpenAPI มีความละเอียดและสื่อความหมายทางธุรกิจของ **Smart Butcher Marketplace** ได้อย่างชัดเจน `@nestjs/swagger` ได้เตรียมชุด Decorators สำหรับตกแต่งใน 3 ระดับ:
1. **ระดับ Controller (`@ApiTags`)**: จัดหมวดหมู่ของ Endpoints เข้าด้วยกัน เช่น หมวด `Products (สินค้าเนื้อพรีเมียม)`, `Orders (คำสั่งซื้อ)`
2. **ระดับ Method (`@ApiOperation`, `@ApiResponse`, `@ApiParam`, `@ApiQuery`, `@ApiConsumes`)**: อธิบายว่า Endpoint นี้ทำอะไร รับพารามิเตอร์อะไร และมีโอกาสคืนค่า HTTP Status Code ใดบ้าง (เช่น `200`, `201`, `400`, `404`, `409`)
3. **ระดับ DTO Property (`@ApiProperty`, `@ApiPropertyOptional`)**: อธิบายรายละเอียดของแต่ละฟิลด์ใน Request/Response เช่น ค่าตัวอย่าง (`example`), คำอธิบาย, ค่าต่ำสุด/สูงสุด และชนิดของ `enum` หรือ Array

### หลักการเบื้องหลัง (Under the Hood)
เมื่อเราใส่ `@ApiProperty({ example: 'A5 Miyazaki Ribeye', minLength: 3 })` ลงบนฟิลด์ของคลาส DTO ตัว Decorator จะใช้แพ็กเกจ `reflect-metadata` บันทึกข้อมูลโครงสร้างนี้ลงใน Metadata Key พิเศษ (`swagger/apiModelProperties`) บน Prototype ของคลาสนั้น เมื่อ `SwaggerModule` สแกนมาพบคลาสนี้ในพารามิเตอร์ `@Body()` หรือในชนิดข้อมูลที่ระบุใน `@ApiOkResponse({ type: ProductResponseDto })` มันจะอ่าน Metadata เหล่านั้นมาแปลงเป็น JSON Schema มาตรฐาน OpenAPI 3.0 โดยอัตโนมัติ

<Callout type="tip" title="การระบุ Type สำหรับ Array และ Enum ใน @ApiProperty">
由于ข้อจำกัดของ TypeScript Reflection Metadata ที่มองเห็นชนิดข้อมูล `string[]` เป็นเพียง `Array` กว้างๆ โดยไม่รู้ว่าข้างในเป็นชนิดใด ดังนั้นเมื่อประกาศฟิลด์ที่เป็น Array หรือ Enum ใน DTO หากไม่ได้เปิด CLI Plugin จะต้องระบุ `{ type: [OrderItemDto] }` หรือ `{ enum: OrderStatus, enumName: 'OrderStatus' }` ให้ชัดเจนเสมอ
</Callout>

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

ตัวอย่างที่ 1: การเขียน Request DTO และ Response DTO สำหรับการสร้างและแสดงผลสินค้าเนื้อพรีเมียม (`Product`) อย่างครบถ้วนด้วย `@ApiProperty` และ `@ApiPropertyOptional`

```typescript filename="src/modules/products/dto/product-swagger.dto.ts"
import { ApiProperty, ApiPropertyOptional } from '@nestjs/swagger';
import {
  IsString,
  IsNotEmpty,
  IsNumber,
  Min,
  IsUUID,
  IsEnum,
  IsOptional,
} from 'class-validator';

export enum MarblingGrade {
  A3 = 'A3',
  A4 = 'A4',
  A5 = 'A5',
  PRIME = 'PRIME',
  CHOICE = 'CHOICE',
}

export class CreateProductDto {
  @ApiProperty({
    description: 'รหัสสินค้า (SKU) ที่ไม่ซ้ำกันในระบบ',
    example: 'WAGYU-MIYAZAKI-A5-RIBEYE',
  })
  @IsString()
  @IsNotEmpty()
  sku!: string;

  @ApiProperty({
    description: 'ชื่อสินค้าเนื้อพรีเมียมสำหรับแสดงหน้าเว็บ',
    example: 'เนื้อวากิวมิยาซากิ A5 ส่วนริบอาย (สเต็กคัท)',
  })
  @IsString()
  @IsNotEmpty()
  name!: string;

  @ApiProperty({
    description: 'เกรดไขมันแทรกของเนื้อ (Marbling Grade)',
    enum: MarblingGrade,
    enumName: 'MarblingGrade',
    example: MarblingGrade.A5,
  })
  @IsEnum(MarblingGrade)
  marblingGrade!: MarblingGrade;

  @ApiProperty({
    description: 'ราคาขายต่อกิโลกรัม (หน่วย: บาท)',
    example: 4800.0,
    minimum: 1,
  })
  @IsNumber({ maxDecimalPlaces: 2 })
  @Min(1)
  pricePerKg!: number;

  @ApiProperty({
    description: 'น้ำหนักสต็อกคงเหลือปัจจุบัน (หน่วย: กรัม)',
    example: 15000,
    minimum: 0,
  })
  @IsNumber()
  @Min(0)
  stockWeightGrams!: number;

  @ApiProperty({
    description: 'รหัสหมวดหมู่เนื้อ (UUID v4 ของตาราง Category)',
    example: 'd290f1ee-6c54-4b01-90e6-d701748f0851',
    format: 'uuid',
  })
  @IsUUID('4')
  categoryId!: string;

  @ApiPropertyOptional({
    description: 'คำแนะนำในการย่างและระดับความสุกที่เหมาะสม',
```

```typescript filename="src/modules/products/products.controller.ts"
import {
  Controller,
  Get,
  Post,
  Param,
  Body,
  ParseUUIDPipe,
  UseInterceptors,
  UploadedFile,
} from '@nestjs/common';
import { FileInterceptor } from '@nestjs/platform-express';
import {
  ApiTags,
  ApiOperation,
  ApiOkResponse,
  ApiCreatedResponse,
  ApiNotFoundResponse,
  ApiConflictResponse,
  ApiUnprocessableEntityResponse,
  ApiParam,
  ApiConsumes,
  ApiBody,
} from '@nestjs/swagger';
import { CreateProductDto, ProductResponseDto } from './dto/product-swagger.dto';
import { ProductsService } from './products.service';
import { createStrictImageParsePipe } from '../../common/pipes/image-upload.pipe';

@ApiTags('Products (สินค้าเนื้อพรีเมียม)')
@Controller('products')

  })

    description: 'สร้างสินค้าสำเร็จและคืนค่าข้อมูลสินค้าที่ถูกบันทึก',
    type: ProductResponseDto,
  })
  @ApiConflictResponse({
    description: 'รหัส SKU ซ้ำกับสินค้าที่มีอยู่ในระบบแล้ว',
  })
  async create(@Body() dto: CreateProductDto): Promise<ProductResponseDto> {
    return this.productsService.create(dto);
  }

  @Get(':id')
  @ApiOperation({
    summary: 'ดึงข้อมูลรายละเอียดสินค้าเนื้อตามรหัส ID',
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ผิด (Anti-pattern) | ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การกำหนด Response Model** | ไม่ใส่ `@ApiOkResponse({ type: ... })` ทำให้ใน Swagger UI แสดง Response Body เป็นค่าว่าง `{}` และทีม Frontend ไม่รู้โครงสร้างข้อมูลที่จะได้รับ | สร้างคลาส `ResponseDto` ที่ชัดเจนและระบุใน `@ApiOkResponse` หรือ `@ApiCreatedResponse` เสมอ |
| **การใส่ `enumName`** | ใส่แค่ `@ApiProperty({ enum: MarblingGrade })` โดยไม่ใส่ `enumName` ทำให้เวลา Generate Code ได้ชื่อ Enum แบบสุ่มซ้ำๆ ในทุก Endpoint | ระบุ `enumName: 'MarblingGrade'` เสมอเพื่อให้ OpenAPI สร้าง Reusable Component Schema เพียงจุดเดียว |
| **เอกสารสำหรับ File Upload** | ใช้ `@UseInterceptors(FileInterceptor('image'))` โดยไม่ใส่ `@ApiConsumes('multipart/form-data')` และ `@ApiBody` ทำให้ไม่มีปุ่มเลือกไฟล์ใน Swagger UI | ระบุ `@ApiConsumes('multipart/form-data')` และกำหนด Schema `format: 'binary'` เพื่อให้กดเลือกไฟล์ทดสอบจากหน้าเว็บได้ทันที |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้เมื่อ**: ทุก Public และ Protected Endpoint ที่ทีม Frontend ต้องเชื่อมต่อ โดยเฉพาะ Endpoint ที่มีการส่งข้อมูลซับซ้อน เช่น การสร้างคำสั่งซื้อ (`Order` พร้อม `OrderItem[]`) หรือการอัปโหลดสลิป (`Payment`)
- **ไม่ควรใช้เมื่อ**: ไม่ควรนำคลาส Entity จากฐานข้อมูลที่มีฟิลด์ความลับ (เช่น `User` ที่มีคอลัมน์ `passwordHash`) มาใส่ใน `@ApiOkResponse({ type: UserEntity })` โดยตรง ให้สร้าง `UserProfileResponseDto` แยกต่างหากเสมอ

### คำถามสัมภาษณ์ (Interview Q&A)
1. **คำถาม**: ถ้าเรามี DTO สำหรับแก้ไขข้อมูลบางส่วน (`UpdateProductDto`) ที่สืบทอดมาจาก `CreateProductDto` ด้วย `PartialType(CreateProductDto)` เราควร import `PartialType` มาจาก `@nestjs/mapped-types` หรือ `@nestjs/swagger` เพราะอะไร?
   - **แนวคำตอบ**: ต้อง import `PartialType` (รวมถึง `PickType`, `OmitType`, `IntersectionType`) มาจาก **`@nestjs/swagger`** เสมอ เพราะถ้า import มาจาก `@nestjs/mapped-types` ตัว `ValidationPipe` จะทำงานได้ถูกต้อง แต่ Metadata ของ Swagger จะไม่ถูกคัดลอกและปรับสถานะเป็น `required: false` ตามไปด้วย ส่งผลให้ในหน้า Swagger UI มองว่า `UpdateProductDto` เป็นคลาสว่างเปล่าไม่มีฟิลด์ใดๆ เลย
2. **คำถาม**: ทำไมเราควรระบุ HTTP Error Responses เช่น `@ApiNotFoundResponse` หรือ `@ApiConflictResponse` ใน Controller ด้วย?
   - **แนวคำตอบ**: เพื่อให้ทีม Frontend ทราบสัญญาที่ชัดเจนว่าแต่ละ Endpoint มีโอกาสเกิด Business Error ใดได้บ้าง เช่น การสร้าง `Product` อาจคืน `409 Conflict` เมื่อ SKU ซ้ำ หรือการจ่ายเงิน `Payment` อาจคืน `422 Unprocessable Entity` เมื่อไฟล์สลิปไม่ถูกต้อง ทำให้ฝั่ง Frontend สามารถเขียนโค้ดดักจับและแสดงข้อความแจ้งเตือนผู้ใช้ได้อย่างแม่นยำตามสถานะจริง

## 3. การเปิดใช้งาน NestJS Swagger CLI Plugin เพื่อลดโค้ดซ้ำซ้อน

### แนวคิด (Concept)
ในโปรเจกต์ขนาดใหญ่ที่มี DTO หลายสิบคลาส การต้องเขียน `@ApiProperty()` และ `@ApiPropertyOptional()` กำกับทุกฟิลด์ด้วยมือ (Boilerplate Code) ทำให้ไฟล์ DTO ยาวขึ้นเป็นสองเท่าและเสี่ยงต่อการที่แก้ชนิดข้อมูลใน TypeScript แล้วลืมแก้ใน `@ApiProperty()` **NestJS Swagger CLI Plugin** ช่วยแก้ปัญหานี้ด้วยการวิเคราะห์โครงสร้างโค้ด (AST - Abstract Syntax Tree) ในจังหวะคอมไพล์เพื่อเติม `@ApiProperty()` และ `@ApiResponse()` ให้โดยอัตโนมัติ

### หลักการเบื้องหลัง (Under the Hood)
เมื่อเราเปิดใช้งานปลั๊กอิน `@nestjs/swagger` ในไฟล์ `nest-cli.json` ตัวคอมไพเลอร์ของ NestJS จะแทรก TypeScript Compiler Plugin เข้าไปในขั้นตอนการ Build เพื่อทำงานดังนี้:
1. สแกนไฟล์ทั้งหมดที่มีนามสกุลตรงกับ `dtoFileNameSuffix` (ค่าเริ่มต้นคือ `['.dto.ts', '.entity.ts']`)
2. อ่านเครื่องหมาย `?` (เช่น `cookingNote?: string`) เพื่อตัดสินใจอัตโนมัติว่าเป็น `required: false` หรือ `required: true`
3. อ่านชนิดข้อมูล (`string`, `number`, `boolean`, `OrderItemDto[]`, `OrderStatus` Enum) และค่าเริ่มต้น (Default Value)
4. หากเปิด `introspectComments: true` ปลั๊กอินจะดึงข้อความจากคอมเมนต์ **JSDoc (`/** ... */`)** และแท็ก `@example` มาใส่เป็น `description` และ `example` ใน OpenAPI Schema ให้ทันทีโดยไม่ต้องเขียน `@ApiProperty()` เลยแม้แต่บรรทัดเดียว

<Callout type="note" title="การทำงานร่วมกันของ CLI Plugin และ @ApiProperty ที่เขียนเอง">
เมื่อเปิดใช้งาน CLI Plugin แล้ว หากฟิลด์ใดมีความต้องการพิเศษที่ต้องการกำหนดค่าเอง คุณยังสามารถใส่ `@ApiProperty({ ... })` ทับลงไปที่ฟิลด์นั้นได้ตามปกติ ค่าที่คุณเขียนระบุเองจะมีความสำคัญสูงสุดและไป Override ค่าที่ CLI Plugin สร้างให้อัตโนมัติ
</Callout>

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

ตัวอย่างที่ 1: การตั้งค่า `nest-cli.json` เพื่อเปิดใช้งาน `@nestjs/swagger` CLI Plugin พร้อมออปชันอ่าน JSDoc Comments และตรวจสอบ `class-validator`

ตัวอย่างที่ 2: การเขียน `CreateOrderDto` และ `OrderItemInputDto` ที่สะอาดตาและได้เอกสาร OpenAPI ครบถ้วน 100% ด้วยการใช้ JSDoc ร่วมกับ `class-validator` (โดยไม่ต้องเขียน `@ApiProperty` ซ้ำซ้อน)

```typescript filename="src/modules/orders/dto/create-order.dto.ts"
import {
  IsArray,
  IsEnum,
  IsInt,
  IsNotEmpty,
  IsOptional,
  IsString,
  IsUUID,
  Min,
  ValidateNested,
  ArrayMinSize,
} from 'class-validator';
import { Type } from 'class-transformer';

export enum DeliveryTimeSlot {
  MORNING_09_12 = 'MORNING_09_12',
  AFTERNOON_13_17 = 'AFTERNOON_13_17',
  EVENING_18_20 = 'EVENING_18_20',
}

export class OrderItemInputDto {
  /**
   * รหัสสินค้าเนื้อพรีเมียมที่ต้องการสั่งซื้อ (UUID v4)
   * @example "7c9e6679-7425-40de-944b-e07fc1f90ae7"
   */
  @IsUUID('4')
  productId!: string;

  /**
   * น้ำหนักเนื้อที่สั่งซื้อ (หน่วยเป็นกรัม ขั้นต่ำ 200 กรัม)
   * @example 500
   */
  @IsInt()
  @Min(200)
  weightGrams!: number;

  /**
   * รูปแบบการหั่นเนื้อที่ลูกค้าต้องการ
   * @example "หั่นสเต็กความหนา 2.5 ซม. แพ็กสุญญากาศแยกชิ้น"
   */
  @IsOptional()
  @IsString()
  cuttingInstruction?: string;
}

export class CreateOrderDto {
  /**
   * ที่อยู่สำหรับจัดส่งรถควบคุมอุณหภูมิ (Cold Chain Delivery)
   * @example "88/9 ถนนสุขุมวิท แขวงคลองตันเหนือ เขตวัฒนา กรุงเทพฯ 10110"
   */
  @IsString()
  @IsNotEmpty()
  shippingAddress!: string;

  /**
   * ช่วงเวลาที่สะดวกรับสินค้าแช่เย็น
   * @example "AFTERNOON_13_17"
   */
  @IsEnum(DeliveryTimeSlot)
  deliverySlot: DeliveryTimeSlot = DeliveryTimeSlot.AFTERNOON_13_17;

  /**
   * รายการเนื้อที่สั่งซื้อในออเดอร์นี้ (ต้องมีอย่างน้อย 1 รายการ)
   */
  @IsArray()
  @ArrayMinSize(1)
  @ValidateNested({ each: true })
  @Type(() => OrderItemInputDto)
  items!: OrderItemInputDto[];
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ผิด (Anti-pattern) | ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การตั้งชื่อไฟล์ DTO** | ตั้งชื่อไฟล์ว่า `create-order.input.ts` หรือ `order-schema.ts` ซึ่งไม่ตรงกับ `dtoFileNameSuffix` ทำให้ CLI Plugin ข้ามการสแกนไฟล์นั้น | ตั้งชื่อไฟล์ลงท้ายด้วย `.dto.ts` เสมอตามมาตรฐานของ NestJS |
| **การซิงค์กฎ Validation กับ Swagger** | เขียน `@Min(200)` ของ `class-validator` แล้วต้องมาเขียน `@ApiProperty({ minimum: 200 })` ซ้ำอีกครั้งด้วยมือ | เปิด `"classValidatorShim": true` ใน `nest-cli.json` เพื่อให้ปลั๊กอินดึงกฎจาก `@Min()`, `@Max()`, `@MaxLength()` ไปใส่ใน OpenAPI Schema อัตโนมัติ |
| **การคืนค่าจาก Controller** | ไม่ระบุ Return Type ของเมธอดใน Controller เช่น `async create(@Body() dto: CreateOrderDto)` | ระบุ Return Type ชัดเจน เช่น `async create(@Body() dto: CreateOrderDto): Promise<OrderResponseDto>` เพื่อให้ CLI Plugin สร้าง `@ApiResponse` ให้ได้ถูกต้อง |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้เมื่อ**: โปรเจกต์คอมไพล์ด้วย `@nestjs/cli` (`nest build` / `nest start`) และต้องการให้โค้ด DTO สะอาด อ่านง่าย และลดความเสี่ยงที่เอกสารจะไม่ตรงกับ Type จริง
- **ไม่ควรใช้เมื่อ**: หากคุณใช้ Custom Bundler ที่ไม่ได้รองรับ TypeScript `before` AST Transformers (เช่น การรันผ่านเครื่องมือบางตัวที่ตัด Type ทิ้งโดยไม่ผ่านปลั๊กอิน) กรณีนั้นจะต้องใช้ `@ApiProperty()` แบบ Explicit หรือรันผ่าน SWC Plugin ที่รองรับ Metadata ของ NestJS

### คำถามสัมภาษณ์ (Interview Q&A)
1. **คำถาม**: ออปชัน `"classValidatorShim": true` ใน Swagger CLI Plugin ทำงานอย่างไร?
   - **แนวคำตอบ**: เมื่อเปิดออปชันนี้ ตัว CLI Plugin จะอ่าน Decorators ของแพ็กเกจ `class-validator` ที่แปะอยู่บนฟิลด์ของ DTO เช่น `@Min(1)`, `@Max(100)`, `@MinLength(3)`, `@MaxLength(50)` แล้วแปลงเป็นข้อกำหนด `minimum`, `maximum`, `minLength`, `maxLength` ใน OpenAPI Schema โดยอัตโนมัติ ทำให้กฎการตรวจข้อมูลขาเข้าและเอกสาร API ตรงกันเสมอโดยไม่ต้องเขียนซ้ำสองรอบ
2. **คำถาม**: หากเปิดใช้งาน CLI Plugin แล้ว ทำไมเมื่อเราแก้ไขโครงสร้าง DTO ในบางครั้งจึงควรลองลบโฟลเดอร์ `dist/` แล้วสั่ง Build ใหม่หากหน้า Swagger ยังไม่อัปเดต?
   - **แนวคำตอบ**: เพราะ CLI Plugin ทำงานในขั้นตอนการแปลง AST ตอนคอมไพล์เป็นไฟล์ `.js` ในโฟลเดอร์ `dist/` หากระบบ Incremental Build (`tsconfig.build.tsbuildinfo`) แคชไฟล์เก่าไว้ การล้างโฟลเดอร์ `dist/` (`deleteOutDir: true`) จะบังคับให้ TypeScript รัน AST Transformer ของ Swagger ใหม่ทั้งหมดอย่างถูกต้อง

## 4. การกำหนด Security Schemes สำหรับ JWT Bearer และ HttpOnly Cookie

### แนวคิด (Concept)
ในระบบ **Smart Butcher Marketplace** เส้นทาง API ส่วนใหญ่ต้องมีการยืนยันตัวตนและตรวจสอบสิทธิ์ เช่น ลูกค้า (`CUSTOMER`) ต้องล็อกอินก่อนสั่งซื้อเนื้อ (`Order`) หรืออัปโหลดสลิป (`Payment`) และผู้ดูแลระบบ (`ADMIN`) ต้องใช้สิทธิ์จัดการสต็อกเนื้อ (`Product`) โดยระบบใช้กลไกความปลอดภัยควบคู่กัน 2 รูปแบบ:
1. **JWT Bearer Token (`Authorization: Bearer <token>`)**: ใช้สำหรับส่ง Access Token อายุสั้น (เช่น 15 นาที) ใน Header ของทุก Request
2. **HttpOnly Cookie (`butcher_refresh_token`)**: ใช้สำหรับเก็บ Refresh Token อย่างปลอดภัยเพื่อขอต่ออายุ Access Token ที่ Endpoint `/auth/refresh`

การตั้งค่า `@ApiBearerAuth` และ `@ApiCookieAuth` ช่วยให้Swagger UI แสดงไอคอนแม่กุญแจและแนบข้อมูลยืนยันตัวตนเหล่านี้ไปกับ Request ตอนกดทดสอบได้ทันที

### หลักการเบื้องหลัง (Under the Hood)
การเชื่อมโยง Security Scheme ใน `@nestjs/swagger` มีกฎสำคัญคือ **ชื่อ (Security Name) ที่ประกาศใน `DocumentBuilder` ต้องตรงกับชื่อที่เรียกใช้ใน Decorator บน Controller ทุกตัวอักษร**:
- หากใน `DocumentBuilder` เราประกาศ `.addBearerAuth({ ... }, 'jwt-access')`
- เวลาใช้งานบน Controller หรือ Method เราต้องระบุชื่อเดียวกันคือ `@ApiBearerAuth('jwt-access')` (หากไม่ใส่พารามิเตอร์เลย ค่าเริ่มต้นจะเป็น `'bearer'` ซึ่งถ้าไม่ตรงกัน Swagger UI จะไม่ส่ง Header `Authorization` ไปให้เมื่อกด `Try it out`)

<Callout type="warning" title="ปัญหาที่พบบ่อย: กด Authorize ใน Swagger UI แล้วแต่ Header ไม่ถูกส่งไป">
สาเหตุอันดับ 1 ที่นักพัฒนากดปุ่ม Authorize ใส่ JWT Token ในหน้า Swagger UI แล้ว แต่พอกดยิง API กลับได้ `401 Unauthorized` เพราะไม่มี Header `Authorization` ถูกส่งออกไป เกิดจากการตั้งชื่อใน `.addBearerAuth(options, 'custom-name')` แต่ใน Controller เขียนแค่ `@ApiBearerAuth()` โดยไม่ใส่ `'custom-name'` ให้ตรงกัน
</Callout>

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

ตัวอย่างที่ 1: การสร้าง Custom Composed Decorator `@ApiAuthRequired()` ที่รวมทั้ง `UseGuards`, `@ApiBearerAuth('jwt-access')`, `@ApiUnauthorizedResponse` และ `@ApiForbiddenResponse` ไว้ในคำสั่งเดียวเพื่อลดการเขียนซ้ำ

```typescript filename="src/common/decorators/api-auth-required.decorator.ts"
import { applyDecorators, UseGuards, SetMetadata } from '@nestjs/common';
import {
  ApiBearerAuth,
  ApiUnauthorizedResponse,
  ApiForbiddenResponse,
} from '@nestjs/swagger';
import { JwtAuthGuard } from '../../modules/auth/guards/jwt-auth.guard';
import { RolesGuard } from '../../modules/auth/guards/roles.guard';

export type UserRole = 'CUSTOMER' | 'ADMIN';
export const ROLES_KEY = 'roles';

export function ApiAuthRequired(...roles: UserRole[]) {
  const decorators: Array<ClassDecorator | MethodDecorator> = [
    SetMetadata(ROLES_KEY, roles),
    UseGuards(JwtAuthGuard, RolesGuard),
    // ชื่อ 'jwt-access' ต้องตรงกับที่ตั้งไว้ใน DocumentBuilder.addBearerAuth(..., 'jwt-access')
    ApiBearerAuth('jwt-access'),
    ApiUnauthorizedResponse({
      description: 'ไม่ได้แนบ Access Token หรือ Token หมดอายุ/ไม่ถูกต้อง (401)',
    }),
  ];

  if (roles.length > 0) {
    decorators.push(
      ApiForbiddenResponse({
        description: `สิทธิ์ไม่เพียงพอ ต้องการสิทธิ์ระดับ: ${roles.join(', ')} (403)`,
      }),
    );
  }

  return applyDecorators(...decorators);
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ผิด (Anti-pattern) | ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การตั้งชื่อ Security Scheme** | ตั้งชื่อใน `main.ts` ว่า `.addBearerAuth({}, 'access-token')` แต่ใน Controller เขียน `@ApiBearerAuth()` เปล่าๆ ทำให้ Swagger ไม่แนบ Header | ใช้ชื่อตรงกันทั้งสองฝั่ง หรือห่อหุ้มไว้ใน Custom Decorator เช่น `@ApiAuthRequired()` |
| **การพิมพ์คำว่า `Bearer` ซ้ำ** | พิมพ์คำว่า `Bearer eyJhbG...` ลงในช่อง Value ของ Swagger UI `http` bearer scheme ทำให้ Header กลายเป็น `Bearer Bearer eyJhbG...` | ใช้ `type: 'http', scheme: 'bearer'` และวางเฉพาะตัว JWT String ล้วนๆ โดยไม่ต้องพิมพ์คำว่า `Bearer` นำหน้า |
| **การแยก Guard ออกจาก Swagger Decorator** | ใส่ `@UseGuards(JwtAuthGuard)` แต่ลืมใส่ `@ApiBearerAuth()` ทำให้ทีม Frontend เข้าใจผิดว่าเป็น Public API ที่ไม่ต้องใช้ Token | ใช้ `applyDecorators()` มัดรวม `UseGuards` และ `@ApiBearerAuth` เข้าด้วยกันเป็น Decorator เดียวเสมอ |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `@ApiBearerAuth` เมื่อ**: Endpoint นั้นตรวจสอบสิทธิ์ผ่าน HTTP Header `Authorization: Bearer <token>`
- **ควรใช้ `@ApiCookieAuth` เมื่อ**: Endpoint นั้นอ่าน Token หรือ Session ID จาก Cookie (ทั้งこのต้องตั้งค่า CORS `credentials: true` ที่ฝั่ง NestJS ด้วยหาก Swagger UI รันคนละ Origin)

### คำถามสัมภาษณ์ (Interview Q&A)
1. **คำถาม**: การใช้ `applyDecorators` ของ `@nestjs/common` เพื่อรวม `@UseGuards(JwtAuthGuard)` และ `@ApiBearerAuth()` เข้าด้วยกันมีประโยชน์อย่างไรในทีมที่มีนักพัฒนาหลายคน?
   - **แนวคำตอบ**: ช่วยบังคับมาตรฐานเดียวกันทั้งโปรเจกต์ (Convention over Configuration) ลดความผิดพลาดที่นักพัฒนาใส่ Guard ป้องกัน API แล้วลืมใส่ `@ApiBearerAuth()` หรือลืมระบุ `@ApiUnauthorizedResponse()` ทำให้ทั้งระบบรักษาความปลอดภัยจริงและเอกสาร OpenAPI สอดคล้องกัน 100% เสมอ
2. **คำถาม**: ข้อจำกัดของการทดสอบ `HttpOnly Cookie` ผ่าน Swagger UI บนเบราว์เซอร์คืออะไร?
   - **แนวคำตอบ**: เนื่องจากจาวาสคริปต์บนเบราว์เซอร์ (รวมถึงโค้ดของหน้าเว็บ Swagger UI) ไม่สามารถเข้าถึงหรือเขียนค่า `HttpOnly Cookie` ได้โดยตรงด้วยเหตุผลด้านความปลอดภัย (ป้องกัน XSS) ดังนั้นในการทดสอบ Endpoint ที่ใช้ `@ApiCookieAuth` นักพัฒนาจะต้องกดยิง Endpoint `/auth/login` ผ่านหน้า Swagger UI ก่อน เพื่อให้เซิร์ฟเวอร์ตอบกลับมาพร้อม Header `Set-Cookie` แล้วเบราว์เซอร์จะเก็บคุกกี้นั้นและส่งต่อไปยัง `/auth/refresh` ให้เองโดยอัตโนมัติ

## 5. การทำงานร่วมกับทีม Frontend และการ Generate TypeScript Client อัตโนมัติ

### แนวคิด (Concept)
ประโยชน์สูงสุดของการทำเอกสาร OpenAPI 3.0 ใน NestJS ไม่ได้หยุดอยู่แค่การเปิดหน้าเว็บ Swagger UI ให้คนอ่าน แต่คือการทำ **Contract-First / Code-First Type Generation** สำหรับทีม Frontend (Next.js) แทนที่นักพัฒนาฝั่ง Frontend จะต้องมานั่งเขียน `interface Product` หรือ `interface Order` ซ้ำด้วยมือในโปรเจกต์ Next.js (ซึ่งมักจะลืมอัปเดตเมื่อฝั่ง Backend แก้ไขฟิลด์) เราสามารถสั่งให้ NestJS ส่งออกไฟล์ `openapi.json` แล้วใช้เครื่องมืออย่าง **`openapi-typescript`** สร้างไฟล์ TypeScript Definitions (`api-schema.d.ts`) ให้ฝั่ง Frontend โดยอัตโนมัติ

### หลักการเบื้องหลัง (Under the Hood)
วงจรการทำงานแบบ End-to-End Type Safety ระหว่าง NestJS 11 และ Next.js มีขั้นตอนดังนี้:
1. นักพัฒนาฝั่ง Backend แก้ไข DTO ใน NestJS (เช่น เปลี่ยนชื่อฟิลด์ `price` เป็น `pricePerKg` ใน `ProductResponseDto`)
2. รันสคริปต์ `pnpm run openapi:export` ซึ่งจะบูต NestJS Context แบบไม่เปิดพอร์ต (`app.init()`) สร้างออบเจกต์ OpenAPI Document แล้วบันทึกลงไฟล์ `openapi.json`
3. ฝั่ง Frontend รัน `npx openapi-typescript ./openapi.json -o ./src/types/api-schema.d.ts`
4. ทันทีที่รันเสร็จ TypeScript Compiler ของฝั่ง Frontend จะแจ้งเตือนจุดที่ยังอ้างอิงชื่อฟิลด์เก่า (`product.price`) ทั้งหมดทันทีตั้งแต่ขั้นตอนเขียนโค้ด (Compile-time Error) ก่อนที่จะปล่อยหลุดไปพังบนหน้าเว็บจริง

<Callout type="tip" title="การรันสคริปต์ Export OpenAPI JSON โดยไม่ต้องเปิดพอร์ตเซิร์ฟเวอร์">
เราสามารถสร้างสคริปต์แยกสำหรับสร้างไฟล์ `openapi.json` ในขั้นตอน CI/CD ได้โดยไม่ต้องสั่ง `app.listen(3000)` เพียงแค่สร้าง Application Context ด้วย `NestFactory.create(AppModule, { logger: false })` เรียก `SwaggerModule.createDocument()` แล้วใช้ `fs.writeFileSync()` บันทึกไฟล์แล้วสั่ง `await app.close()` ได้ทันทีภายในเวลาไม่กี่วินาที
</Callout>

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

ตัวอย่างที่ 1: สคริปต์ `scripts/export-openapi.ts` ในฝั่ง NestJS สำหรับสร้างไฟล์ `openapi.json` อัตโนมัติเพื่อส่งมอบให้ทีม Frontend หรือใช้ตรวจใน CI Pipeline

```typescript filename="scripts/export-openapi.ts"
import { writeFileSync } from 'node:fs';
import { resolve } from 'node:path';
import { NestFactory } from '@nestjs/core';
import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger';
import { AppModule } from '../src/app.module';

async function exportOpenApiSpec(): Promise<void> {
  const app = await NestFactory.create(AppModule, {
    logger: ['error', 'warn'],
  });

  app.setGlobalPrefix('api/v1');

  const config = new DocumentBuilder()
    .setTitle('Smart Butcher Marketplace API')
    .setDescription('OpenAPI 3.0 Contract สำหรับสร้าง TypeScript Client ฝั่ง Frontend')
    .setVersion('1.0.0')
    .addBearerAuth(
      { type: 'http', scheme: 'bearer', bearerFormat: 'JWT' },
      'jwt-access',
    )
    .build();

  const document = SwaggerModule.createDocument(app, config, {
    operationIdFactory: (controllerKey: string, methodKey: string) =>
      `${controllerKey.replace('Controller', '')}_${methodKey}`,
  });

  const outputPath = resolve(process.cwd(), 'openapi.json');
  writeFileSync(outputPath, JSON.stringify(document, null, 2), {
    encoding: 'utf-8',
  });

  console.log(`[OpenAPI Export] สร้างไฟล์สเปกสำเร็จที่: ${outputPath}`);
  await app.close();
}

void exportOpenApiSpec();
```

ตัวอย่างที่ 2: การนำ Type ที่สร้างจาก OpenAPI (`components['schemas']` และ `operations`) ไปสร้างฟังก์ชันดึงข้อมูลสินค้าเนื้อพรีเมียมและสร้างคำสั่งซื้อแบบ Type-safe 100% ในฝั่ง Frontend (Next.js)

```typescript filename="src/lib/api/butcher-client.ts"
// สมมติว่าไฟล์นี้รับ Type ที่ถูก Generate อัตโนมัติด้วยคำสั่ง:
// npx openapi-typescript ./openapi.json -o ./src/types/openapi-schema.d.ts

export interface GeneratedOpenApiComponents {
  schemas: {
    CreateProductDto: {
      sku: string;
      name: string;
      marblingGrade: 'A3' | 'A4' | 'A5' | 'PRIME' | 'CHOICE';
      pricePerKg: number;
      stockWeightGrams: number;
      categoryId: string;
      cookingNote?: string;
    };
    ProductResponseDto: {
      id: string;
      sku: string;
      name: string;
      marblingGrade: 'A3' | 'A4' | 'A5' | 'PRIME' | 'CHOICE';
      pricePerKg: number;
      stockWeightGrams: number;
      categoryId: string;
      cookingNote?: string;
      imageUrl: string | null;
      createdAt: string;
    };
  };
}

export type ProductResponse =
  GeneratedOpenApiComponents['schemas']['ProductResponseDto'];
export type CreateProductInput =
  GeneratedOpenApiComponents['schemas']['CreateProductDto'];

export class SmartButcherApiClient {
  constructor(
    private readonly baseUrl: string,
    private readonly getAccessToken?: () => string | null,
  ) {}

  async getProductById(productId: string): Promise<ProductResponse> {
    const response = await fetch(
      `${this.baseUrl}/api/v1/products/${encodeURIComponent(productId)}`,
      {
        method: 'GET',
        headers: {
          Accept: 'application/json',
        },
      },
    );

    if (!response.ok) {
      throw new Error(`ไม่สามารถดึงข้อมูลสินค้าได้ (HTTP ${response.status})`);
    }

    return (await response.json()) as ProductResponse;
  }

  async createProduct(input: CreateProductInput): Promise<ProductResponse> {
    const token = this.getAccessToken?.();
    const response = await fetch(`${this.baseUrl}/api/v1/products`, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        ...(token ? { Authorization: `Bearer ${token}` } : {}),
      },
      body: JSON.stringify(input),
    });

    if (!response.ok) {
      throw new Error(`สร้างสินค้าเนื้อไม่สำเร็จ (HTTP ${response.status})`);
    }

    return (await response.json()) as ProductResponse;
  }
}
```

### ผิด vs ถูก (Anti-pattern vs Best Practice)

| มิติการเปรียบเทียบ | ผิด (Anti-pattern) | ถูก (Best Practice) |
| :--- | :--- | :--- |
| **การส่งต่อโครงสร้าง API ให้ทีม Frontend** | พิมพ์ตัวอย่าง JSON ส่งในแชทส่วนตัว ซึ่งไม่อัปเดตเมื่อโค้ดเปลี่ยนและไม่มีการตรวจ Type | ใช้ `openapi.json` เป็นตัวกลางในการ Generate TypeScript Types ให้โปรเจกต์ Frontend |
| **การใช้ `any` หรือ `object` ใน DTO** | ประกาศฟิลด์ใน DTO เป็น `metadata: any` หรือ `Record<string, any>` ทำให้สเปก OpenAPI กลายเป็นออบเจกต์ว่างเปล่าไร้ชนิดข้อมูล | สร้าง Nested DTO Class ที่ระบุฟิลด์และชนิดข้อมูลอย่างชัดเจนเสมอ |
| **การตั้งชื่อ `operationId`** | ปล่อยให้ `operationId` เปลี่ยนไปมาโดยไม่มีรูปแบบมาตรฐาน ทำให้โค้ดที่เรียกใช้ SDK พังเมื่อรีเจนเนอเรต | กำหนด `operationIdFactory` ให้คงที่ตามชื่อ Controller และชื่อเมธอด |

### ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่
- **ควรใช้เมื่อ**: ทำงานในโปรเจกต์ Fullstack (เช่น NestJS + Next.js) ที่ต้องการความมั่นใจว่าหาก Backend เปลี่ยนแปลงโครงสร้างข้อมูลของ `Product`, `Order` หรือ `Payment` ฝั่ง Frontend จะตรวจพบจุดที่กระทบทั้งหมดทันทีตอนรัน `tsc --noEmit`
- **ไม่ควรใช้เมื่อ**: ห้ามเข้าไปแก้ไขไฟล์ `openapi-schema.d.ts` ที่ถูก Generate ออกมาด้วยมือโดยตรง เพราะการแก้ไขนั้นจะถูกเขียนทับทันทีที่รันคำสั่ง Generate รอบถัดไป

### คำถามสัมภาษณ์ (Interview Q&A)
1. **คำถาม**: แนวทาง Code-First OpenAPI (เขียนโค้ด DTO ใน NestJS แล้ว Generate `openapi.json`) มีข้อดีอย่างไรเมื่อเทียบกับการเขียนไฟล์ `openapi.yaml` ด้วยมือแยกต่างหาก?
   - **แนวคำตอบ**: การเขียนไฟล์ `openapi.yaml` แยกต่างหากด้วยมือขนาดหลายพันบรรทัดมักเกิดปัญหา **Documentation Drift** คือเมื่อเวลาเร่งด่วน นักพัฒนาแก้โค้ดใน Controller/DTO แต่ลืมอัปเดตไฟล์ YAML ทำให้เอกสารไม่ตรงกับระบบจริง ส่วนแนวทาง Code-First ใน NestJS ใช้คลาส DTO ตัวเดียวกันทั้งในการทำ Runtime Validation (`ValidationPipe`) และการสร้าง OpenAPI Schema จึงรับประกันได้ว่าเอกสารและโค้ดที่ทำงานจริงจะตรงกันเสมอ
2. **คำถาม**: หากต้องการจัดการกับ Generic Paginated Response (เช่น `PaginatedResponseDto<ProductResponseDto>`) ใน `@nestjs/swagger` ต้องใช้ Decorator ใดช่วย?
   - **แนวคำตอบ**: เนื่องจาก TypeScript ลบข้อมูล Generic Type Parameter (`<T>`) ทิ้งตอนคอมไพล์ เราจึงต้องใช้ `@ApiExtraModels(PaginatedResponseDto, ProductResponseDto)` ร่วมกับฟังก์ชัน `getSchemaPath()` ใน `@ApiOkResponse({ schema: { allOf: [{ $ref: getSchemaPath(PaginatedResponseDto) }, ...] } })` เพื่อให้ Swagger รู้จักทั้งโครงสร้าง Pagination หลักและชนิดของข้อมูลภายในอาเรย์ `items`

## ข้อผิดพลาดที่พบบ่อย (Anti-patterns)

1. **การ Import `PartialType`, `PickType`, `OmitType` ผิดแพ็กเกจ**:
   การดึงมาจาก `@nestjs/mapped-types` แทนที่จะเป็น `@nestjs/swagger` ทำให้ฟิลด์ทั้งหมดหายไปจากหน้าเอกสาร Swagger UI
2. **การส่งคืน Prisma Model ออกทาง Controller โดยตรงโดยไม่มี Response DTO**:
   นอกจากจะทำให้ Swagger ไม่รู้โครงสร้าง Response (แสดงเป็น `{}`) แล้ว ยังเสี่ยงต่อการเผลอส่งข้อมูลความลับ เช่น `passwordHash` หรือ `slipStoragePath` ภายในออกไปหา Client
3. **การลืมระบุ `{ type: [ItemDto] }` สำหรับฟิลด์ที่เป็น Array (เมื่อไม่ได้เปิด CLI Plugin)**:
   ทำให้ Swagger รู้แค่ว่าเป็น Array แต่ไม่รู้โครงสร้างของสมาชิกภายใน Array
4. **การเปิดหน้า Swagger UI ทิ้งไว้บน Production โดยไม่มีการป้องกัน**:
   ช่วยให้ผู้โจมตีสามารถสำรวจทุก Endpoint, พารามิเตอร์ และโครงสร้างข้อมูลของระบบได้อย่างง่ายดาย
5. **การตั้งชื่อ Security Scheme ใน `DocumentBuilder` ไม่ตรงกับ `@ApiBearerAuth()`**:
   ทำให้ปุ่ม Authorize ใน Swagger UI ไม่แนบ JWT Token ไปกับ HTTP Request ตอนกดทดสอบ

## Checklist สรุป

- [ ] ตั้งค่า `DocumentBuilder` และ `SwaggerModule.setup()` หลังจากเรียก `app.setGlobalPrefix()` แล้วเสมอ
- [ ] ปิดการเข้าถึงหน้า Swagger UI ในโหมด Production (`NODE_ENV === 'production'`) หรือจำกัดสิทธิ์การเข้าถึงอย่างรัดกุม
- [ ] เปิดใช้งาน `persistAuthorization: true` ใน `swaggerOptions` เพื่อความสะดวกในการทดสอบของทีมพัฒนา
- [ ] ใช้ `PartialType`, `PickType`, `OmitType` จากแพ็กเกจ `@nestjs/swagger` เสมอ
- [ ] เปิดใช้งาน `@nestjs/swagger` CLI Plugin ใน `nest-cli.json` พร้อม `"classValidatorShim": true` และ `"introspectComments": true`
- [ ] ตรวจสอบให้ชื่อใน `.addBearerAuth(..., 'jwt-access')` ตรงกับ `@ApiBearerAuth('jwt-access')` ทุกจุด
- [ ] กำหนด `@ApiConsumes('multipart/form-data')` และ `@ApiBody` สำหรับทุก Endpoint ที่มีการอัปโหลดไฟล์
- [ ] สร้างสคริปต์ Export `openapi.json` เพื่อนำไปใช้สร้าง Type-safe Client ให้ฝั่ง Frontend

## ลำดับการเรียนที่แนะนำ และ ดูเพิ่มเติมที่

เมื่อจัดทำเอกสาร OpenAPI/Swagger ที่ได้มาตรฐานและเชื่อมโยงกับทีม Frontend เรียบร้อยแล้ว แนะนำให้ศึกษาต่อในหัวข้อต่อไปนี้:

1. **หลักการออกแบบ RESTful API และ Validation**: ทบทวนมาตรฐานการออกแบบ URI, HTTP Status Codes และการตรวจข้อมูลด้วย DTO ที่ [REST API](/docs/backend/rest-api) และ [Validation](/docs/backend/validation)
2. **การยืนยันตัวตนและการอัปโหลดไฟล์**: ดูรายละเอียดเบื้องหลังการทำงานของ JWT, Cookie และการรับไฟล์ด้วย Multer ที่ [Authentication](/docs/backend/authentication) และ [File Upload](/docs/backend/file-upload)
3. **การผสานความสามารถด้าน AI เข้าสู่ระบบ Backend**: ศึกษาการนำ Groq SDK (Llama 3.1 8B) มาสร้างฟีเจอร์อัจฉริยะพร้อมทำเอกสาร API ต่อได้ที่ [AI Integration](/docs/backend/ai-integration)
4. **การตรวจสอบชนิดข้อมูลและการทดสอบระบบ**: เรียนรู้การใช้ TypeScript ตรวจจับข้อผิดพลาดและการเขียน E2E Test ทดสอบตามสัญญา API ที่ [Debugging & Type Checking](/docs/testing/debugging-type-checking) และ [Backend Testing](/docs/testing/backend-testing)
