## 1. แนวคิด (Concept)

จุดเด่นอันดับหนึ่งของ Node.js คือสถาปัตยกรรม **Single-threaded Event Loop** ซึ่งยอดเยี่ยมอย่างยิ่งสำหรับงานประเภท **I/O-bound** เช่น การรับส่งคำสั่งซื้อเนื้อสดผ่าน REST API, การคิวรีฐานข้อมูล PostgreSQL, หรือการแคชข้อมูลลงใน Redis เพราะเธรดหลักไม่ต้องบล็อกรอ I/O แต่สามารถสลับไปรับลูกค้ารายอื่นได้ทันที

ทว่า จุดแข็งนี้จะกลายเป็นจุดตายที่อันตรายที่สุดทันทีเมื่อระบบต้องเจอกับงานประเภท **CPU-bound (งานที่ต้องใช้พลังการคำนวณของหน่วยประมวลผลอย่างเข้มข้น)** เช่น:
- ใน **Smart Butcher Marketplace** เมื่อเกษตรกรอัปโหลดภาพชิ้นเนื้อวากิวความละเอียด 4K เพื่อให้ระบบคำนวณคะแนนลายไขมันแทรก (BMS - Beef Marbling Score) ผ่านการวิเคราะห์ความหนาแน่นของเม็ดสีพิกเซล
- การสร้างและลงลายมือชื่อดิจิทัล (Cryptographic Digital Signature) บนไฟล์ใบเสร็จกำกับภาษี PDF จำนวน 5,000 ฉบับพร้อมกัน

หากเราสั่งรันงานเหล่านี้บน Main Thread ตรงๆ ตัว Call Stack ของ V8 Engine จะถูกแช่แข็งเป็นเวลา 5-10 วินาที ส่งผลให้ Event Loop หมุนต่อไม่ได้ และในระหว่างนั้น **ลูกค้าทุกคนทั่วโลกจะไม่สามารถเปิดหน้าเว็บ, จองเนื้อ หรือกดยืนยันการชำระเงินได้เลยแม้แต่คนเดียว!**

เพื่อแก้ไขปัญหานี้ Node.js จึงได้จัดเตรียมเครื่องมือการประมวลผลคู่ขนานแบบ Multi-threading ผ่านโมดูล **`node:worker_threads`** และการสเกลระดับกระบวนการผ่าน **`node:cluster`** ควบคู่ไปกับความเข้าใจเชิงลึกเกี่ยวกับโครงสร้างหน่วยความจำ **V8 Heap Memory** เพื่อตรวจจับและป้องกันปัญหา Memory Leak อย่างยั่งยืน

## 2. หลักการเบื้องหลัง (Under the Hood)

### 1. สถาปัตยกรรม Worker Threads vs Cluster vs Child Process

```text filename="docs/backend/process-thread-models.txt"
1. Single Main Thread (ดั้งเดิม)
   [ V8 Call Stack & Event Loop ] ── (CPU Task ค้าง!) ──► บล็อกทราฟฟิกทั้งเซิร์ฟเวอร์

2. Cluster Module (Multi-Process)
   ┌──────────────────────────────────────────────┐
   │ Master Process (Port 3000 Load Balancer)     │
   └──────┬───────────────────────┬───────────────┘
          │ (IPC)                 │ (IPC)
          ▼                       ▼
   ┌──────────────┐        ┌──────────────┐
   │ Worker Pod 1 │        │ Worker Pod 2 │ (แยก Memory Heap กันเด็ดขาด)
   │ (V8 Engine)  │        │ (V8 Engine)  │
   └──────────────┘        └──────────────┘

3. Worker Threads (Multi-Threading ใน Process เดียว)
   ┌────────────────────────────────────────────────────────┐
   │ Single Node.js Process (Shared OS Process)             │
   │                                                        │
   │  ┌───────────────────────┐  ┌───────────────────────┐  │
   │  │ Main Thread (I/O)     │  │ Worker Thread 1 (CPU) │  │
   │  │ - V8 Isolate 1        │  │ - V8 Isolate 2        │  │
   │  │ - Event Loop 1        │  │ - Event Loop 2        │  │
   │  └───────────┬───────────┘  └───────────┬───────────┘  │
   │              │                          │              │
   │              └────────────┬─────────────┘              │
   │                           ▼                            │
   │            [ SharedArrayBuffer & Atomics ]             │
   │             (Zero-copy Memory Sharing)                 │
   └────────────────────────────────────────────────────────┘
```

- **`node:cluster`:** สร้าง OS Process ใหม่โดยแยก Memory Heap ออกจากกันอย่างเด็ดขาด เหมาะสำหรับการขยายตัวเพื่อใช้งานคอร์ของ CPU ให้ครบทุกคอร์ (Horizontal Scaling บนเครื่องเดียวกัน)
- **`node:worker_threads`:** สร้าง Thread ใหม่ภายใต้ Process เดิม แต่ละ Thread มี **V8 Isolate** และ Event Loop ของตัวเอง แต่สามารถแชร์หน่วยความจำระดับต่ำร่วมกันได้ผ่าน **`SharedArrayBuffer`** โดยไม่ต้องเสีย Overhead ในการคัดลอกข้อมูล (Zero-copy)

### 2. โครงสร้างหน่วยความจำ V8 Heap Memory Architecture
หน่วยความจำของโปรเซส Node.js แบ่งออกเป็น 2 ส่วนหลักคือ **Resident Set Size (RSS)**:
1. **Off-Heap Memory:** C++ Bindings, Libuv Thread Pool, และ Node.js `Buffer` objects
2. **V8 Managed Heap:** พื้นที่ที่ V8 ดูแลการจัดสรรและเก็บกวาดขยะ (Garbage Collection) แบ่งออกเป็นโซนย่อยตามอายุขัยของ Object (Generational Hypothesis):

| โซนใน V8 Heap | หน้าที่และพฤติกรรม | กลไก Garbage Collection |
| :--- | :--- | :--- |
| **New Space (Young Generation)** | ที่อยู่ของ Object ที่เพิ่งถูกสร้างขึ้นใหม่ (อายุสั้น) ขนาดประมาณ 1MB - 64MB แบ่งเป็น 2 ซีกย่อย: `From Space` และ `To Space` | **Minor GC (Scavenger):** รวดเร็วมาก (1-3ms) คัดลอก Object ที่รอดชีวิตสลับไปมาระหว่าง From/To หากรอดครบ 2 รอบจะถูกย้ายไป Old Space |
| **Old Pointer Space** | เก็บ Object ที่มีอายุยืนยาวและมี Pointer ชี้ไปยัง Object ตัวอื่น | **Major GC (Mark-Sweep-Compact):** ตรวจสอบทั้งกราฟ ช้าและใช้ CPU สูง หากเกิดบ่อยจะทำให้เซิร์ฟเวอร์กระตุก |
| **Old Data Space** | เก็บข้อมูลดิบที่ไม่มี Pointer ชี้ไปหาตัวอื่น เช่น Raw Strings หรือตัวเลข | Major GC |
| **Large Object Space** | เก็บ Object ขนาดมหึมาที่ใหญ่เกินกว่าจะใส่ลงใน New Space ได้โดยตรง จะไม่ถูกย้ายที่โดย GC | จัดสรรและทำลายโดยตรง |
| **Code Space** | เก็บ JIT-compiled Machine Code ที่สร้างโดย V8 Turbofan Compiler | จัดการโดย V8 Compiler |

---

### 3. กลไกการเกิด Memory Leak และการสร้าง Heap Snapshot
Memory Leak ใน Node.js ไม่ได้เกิดจาก C++ Memory รั่วไหล แต่มักเกิดจาก **การที่ตัวแปร JavaScript ยังคงถูกอ้างอิง (Referenced) อยู่ใน Root Context (เช่น Global Object, Unclosed Closures หรือ Event Listeners ที่ลืมลบ)** ทำให้ V8 Garbage Collector ไม่สามารถเก็บกวาดหน่วยความจำส่วนนั้นคืนได้

การตรวจจับทำได้โดยการสั่งสร้าง **V8 Heap Snapshot** ผ่านโมดูล `node:v8` แล้วนำไฟล์ `.heapsnapshot` ไปเปิดวิเคราะห์ใน **Chrome DevTools (Memory Tab)** เพื่อเปรียบเทียบหา Object ที่มีค่า **Retained Size** สูงผิดปกติ

## 3. ตัวอย่างโค้ด (Smart Butcher Marketplace)

### ตัวอย่างที่ 1: การใช้ `worker_threads` คำนวณคะแนน Marbling Score ของเนื้อวากิวโดยไม่บล็อก Event Loop

ตัวอย่างนี้แสดงการแยกงานคำนวณวิเคราะห์พิกเซลภาพชิ้นเนื้อออกไปรันบน Worker Thread แบบ Asynchronous

```typescript filename="src/workers/marbling-analysis.worker.ts"
import { parentPort, workerData } from 'node:worker_threads';

interface AnalysisTaskData {
  meatId: string;
  imagePixels: Uint8ClampedArray; // ข้อมูลดิบ RGBA พิกเซลของชิ้นเนื้อ
  width: number;
  height: number;
}

// โค้ดส่วนนี้จะรันอยู่บน Worker Thread แยกต่างหาก มี V8 Isolate ของตัวเอง
function calculateBmsScore(data: AnalysisTaskData): { meatId: string; bmsScore: number; fatPercentage: number } {
  const { meatId, imagePixels, width, height } = data;
  let fatPixels = 0;
  let leanMeatPixels = 0;

  const totalPixels = width * height;

  // วนลูปคำนวณอย่างหนักหน่วงระดับล้านรอบ (Heavy CPU Bound)
  for (let i = 0; i < totalPixels * 4; i += 4) {
    const r = imagePixels[i];
    const g = imagePixels[i + 1];
    const b = imagePixels[i + 2];

    // ตรวจสอบสีไขมันเนื้อ (โทนขาวนวล: RGB มีค่าความสว่างสูงใกล้เคียงกัน)
    if (r > 200 && g > 200 && b > 200) {
      fatPixels++;
    } else if (r > 120 && g < 80 && b < 80) {
      // โทนสีแดงของเนื้อแดงสด (Lean Meat)
      leanMeatPixels++;
    }
  }

  const fatRatio = fatPixels / (fatPixels + leanMeatPixels || 1);
  const fatPercentage = Number((fatRatio * 100).toFixed(2));

  // แปลงอัตราส่วนไขมันเป็นคะแนนมาตรฐาน Japanese BMS (Beef Marbling Score 1 - 12)
  let bmsScore = 3;
  if (fatPercentage > 50) bmsScore = 12; // A5 Super Premium
  else if (fatPercentage > 40) bmsScore = 9; // A4
  else if (fatPercentage > 30) bmsScore = 7; // A3
  else if (fatPercentage > 20) bmsScore = 5;

  return { meatId, bmsScore, fatPercentage };
}

// รับข้อมูลจาก Main Thread คำนวณแล้วส่งผลลัพธ์กลับ
if (parentPort) {
  const result = calculateBmsScore(workerData);
  parentPort.postMessage(result);
}
```

```typescript filename="src/services/meat-inspection.service.ts"
import { Injectable, Logger } from '@nestjs/common';
import { Worker } from 'node:worker_threads';
import path from 'node:path';

@Injectable()
export class MeatInspectionService {
  private readonly logger = new Logger(MeatInspectionService.name);

  /**
   * ส่งงานวิเคราะห์ภาพเนื้อวากิวไปทำบน Worker Thread เพื่อไม่ให้บล็อก Main API
   */
  async analyzeWagyuMarbling(meatId: string, imagePixels: Uint8ClampedArray, width: number, height: number) {
    this.logger.log(`[CPU TASK DISPATCH] เริ่มส่งการวิเคราะห์เนื้อ ${meatId} ลง Worker Thread`);

    return new Promise((resolve, reject) => {
      const workerPath = path.resolve(__dirname, '../workers/marbling-analysis.worker.js');

      // สร้าง Worker Thread ตัวใหม่ พร้อมส่งข้อมูลผ่าน workerData
      const worker = new Worker(workerPath, {
        workerData: { meatId, imagePixels, width, height },
      });

      worker.on('message', (result) => {
        this.logger.log(`[ANALYSIS COMPLETED] เนื้อ ${meatId} ได้รับคะแนน BMS: ${result.bmsScore} (ไขมัน ${result.fatPercentage}%)`);
        resolve(result);
      });

      worker.on('error', (err) => {
        this.logger.error(`Worker ล้มเหลวขณะคำนวณเนื้อ ${meatId}:`, err);
        reject(err);
      });

      worker.on('exit', (code) => {
        if (code !== 0) {
          reject(new Error(`Worker หยุดทำงานด้วย Exit Code: ${code}`));
        }
      });
    });
  }
}
```

### ตัวอย่างที่ 2: ระบบตรวจจับ Memory Leak และบันทึก Heap Snapshot อัตโนมัติเมื่อ RAM เกินเกณฑ์

ในระบบ Enterprise Node.js เราสามารถเขียน Watchdog คอยตรวจสอบขนาด V8 Heap และสั่งเขียน Heap Snapshot ลงฮาร์ดดิสก์อัตโนมัติก่อนที่เซิร์ฟเวอร์จะถูกระบบสั่ง OOMKilled

```typescript filename="src/diagnostics/memory-watchdog.service.ts"
import { Injectable, Logger, OnModuleInit } from '@nestjs/common';
import v8 from 'node:v8';
import fs from 'node:fs';
import path from 'node:path';

@Injectable()
export class MemoryWatchdogService implements OnModuleInit {
  private readonly logger = new Logger(MemoryWatchdogService.name);
  private snapshotTriggered = false;

  onModuleInit() {
    // ตรวจสอบสถานะหน่วยความจำทุกๆ 15 วินาที
    setInterval(() => this.checkMemoryHealth(), 15000).unref();
  }

  private checkMemoryHealth() {
    const mem = process.memoryUsage();
    const heapStats = v8.getHeapStatistics();

    const usedHeapMb = Math.round(mem.heapUsed / 1024 / 1024);
    const totalHeapMb = Math.round(mem.heapTotal / 1024 / 1024);
    const heapLimitMb = Math.round(heapStats.heap_size_limit / 1024 / 1024);
    const rssMb = Math.round(mem.rss / 1024 / 1024);

    this.logger.debug(
      `[MEMORY STATS] Heap Used: ${usedHeapMb}MB / Total: ${totalHeapMb}MB (Limit: ${heapLimitMb}MB) | RSS: ${rssMb}MB`,
    );

    // หาก Heap ที่ใช้เกิน 85% ของ Limit และยังไม่เคยบันทึก Snapshot ในรอบนี้
    const usageRatio = mem.heapUsed / heapStats.heap_size_limit;
    if (usageRatio > 0.85 && !this.snapshotTriggered) {
      this.snapshotTriggered = true;
      this.captureHeapDump(usedHeapMb);
    }
  }

  private captureHeapDump(usedMb: number) {
    this.logger.fatal(`🚨 วิกฤตหน่วยความจำ! Heap พุ่งสูงถึง ${usedMb}MB กำลังบันทึก Heap Snapshot เพื่อการวินิจฉัย...`);

    const dumpDir = path.resolve(process.cwd(), 'dumps');
    if (!fs.existsSync(dumpDir)) {
      fs.mkdirSync(dumpDir, { recursive: true });
    }

    const filename = path.join(dumpDir, `heap-${Date.now()}-${process.pid}.heapsnapshot`);

    // บันทึก Heap Snapshot ลงไฟล์โดยตรง
    const snapshotPath = v8.writeHeapSnapshot(filename);
    this.logger.log(`บันทึก Snapshot เรียบร้อยที่: ${snapshotPath} นำไฟล์นี้ไปเปิดวิเคราะห์ใน Chrome DevTools Memory ได้ทันที`);
  }
}
```

## 4. ข้อผิดพลาดที่พบบ่อย (Anti-pattern vs Best Practice)

### ❌ โค้ดที่ผิด: สปอน Worker ใหม่ทุก Request และทำ Memory Leak จาก Global Event Listeners

```typescript filename="bad-worker-memory.ts"
// ผิดมหันต์ 1: สร้าง new Worker() ใหม่ในทุกๆ HTTP Request ที่เข้ามา
@Post('calculate')
handleCalculation(@Body() data: any) {
  // อันตราย: การสร้าง V8 Isolate ใหม่ต้องกิน RAM ประมาณ 25-30MB และใช้เวลาบูต 50-100ms
  // หากมี 100 คำขอพร้อมกัน เซิร์ฟเวอร์จะ RAM เต็มและแฮงค์ทันที
  const worker = new Worker('./worker.js', { workerData: data });
}

// ผิดมหันต์ 2: ลงทะเบียน Event Listener ใน Global Service โดยไม่เคยลบออก
@Injectable()
export class BadOrderNotificationService {
  private activeOrders: any[] = [];

  watchOrder(order: any) {
    // order object และ closure scope จะถูกเก็บไว้ใน Array ตลอดกาล ไม่มีวันถูก GC เคลียร์!
    globalEventEmitter.on('priceChange', () => {
      this.notify(order);
    });
  }
}
```

### ✅ โค้ดที่ถูก: ใช้ Worker Pool (เช่น Piscina) และใช้ WeakMap/WeakRef จัดการหน่วยความจำ

```typescript filename="good-worker-memory.ts"
// ถูกต้อง 1: ใช้ Worker Pool สำเร็จรูป (เช่น Piscina หรือ custom pool)
// ซึ่งจะเปิด Worker รอไว้ล่วงหน้าตามจำนวน CPU Cores (Warm Workers) และนำกลับมาใช้ซ้ำ (Reuse)
import Piscina from 'piscina';

const marblingPool = new Piscina({
  filename: path.resolve(__dirname, 'marbling.worker.js'),
  maxThreads: 4, // จำกัดจำนวน Worker ให้สอดคล้องกับคอร์ CPU
});

// ถูกต้อง 2: ใช้ WeakMap หรือ WeakSet เพื่อเก็บ Metadata ของ Order
// เมื่อ Order ต้นฉบับถูกทำลาย WeakMap จะปล่อยหน่วยความจำให้ GC เคลียร์อัตโนมัติ ไม่เกิด Leak
const orderMetadataMap = new WeakMap<object, any>();
```

<Callout type="warning" title="หลีกเลี่ยงการสร้าง Worker Threads เกินจำนวน CPU Cores">
Worker Threads ใน Node.js คือ **OS-level Threads แท้จริง** หากเครื่องเซิร์ฟเวอร์มี 4 vCPU Cores แต่เราสร้าง Worker Threads ขึ้นมา 32 Threads ตัวระบบปฏิบัติการจะต้องเสียเวลาทำ **Thread Context Switching** มหาศาล ซึ่งจะทำให้ประสิทธิภาพโดยรวมช้าลงกว่าการรันบน Main Thread เสียอีก
</Callout>

## 5. ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่

### ควรใช้ `node:worker_threads`:
- งานที่ใช้ CPU เข้มข้น (CPU-intensive) เช่น การคำนวณกราฟิก, AI Image Analysis, การเข้ารหัสไฟล์ขนาดใหญ่, การบีบอัด Zip แบบ Batch
- การ Parse ไฟล์ JSON มหึมาขนาด 500MB+ ที่ต้องใช้การประมวลผล String หนักหน่วง
- การคำนวณสูตรคณิตศาสตร์ทางการเงินที่ซับซ้อน เช่น การจำลองผลตอบแทน Monte Carlo Simulation

### ควรใช้ `node:cluster`:
- การรัน HTTP Server ให้เต็มประสิทธิภาพทุก Core ของเครื่อง (เช่น รัน 8 Node.js instances บนเครื่อง 8 Cores) เพื่อรองรับ Throughput ของ API ได้มากขึ้น

### ไม่ควรใช้ทั้งคู่:
- งานที่เป็น I/O-bound ทั่วไป เช่น การคิวรีฐานข้อมูล, การเรียก REST API ภายนอก, หรือการอ่านเขียนไฟล์ผ่าน Streams (งานเหล่านี้ Node.js จัดการได้ยอดเยี่ยมอยู่แล้วบน Single Main Thread ผ่าน Libuv Event Loop)

## 6. คำถามสัมภาษณ์งาน (Interview Q&A)

### Q1: เปรียบเทียบความแตกต่างทางสถาปัตยกรรมระหว่าง `worker_threads`, `cluster`, และ `child_process.fork()` ใน Node.js และเราควรเลือกใช้ในสถานการณ์ใด?
**แนวคำตอบเชิงลึก:**
1. **`child_process.fork()`:** สปอน OS Process ใหม่ มี PID ของตัวเอง แยก Memory Space โดยสิ้นเชิง การส่งข้อมูลหากันต้องผ่าน IPC (Inter-Process Communication) ซึ่งต้อง Serialize ข้อมูลเป็น JSON/Buffer ทำให้มี Serialization Overhead สูง เหมาะสำหรับการสั่งรันสคริปต์ภายนอกหรือโปรแกรมภาษาอื่น
2. **`node:cluster`:** สร้าง Master-Worker Process โดยใช้ `child_process.fork()` ภายใต้พอร์ตเน็ตเวิร์กเดียวกัน โดย Master Process จะรับคำขอ TCP แล้วกระจายไปยัง Worker Processes ตามกลยุทธ์ Round-robin เหมาะสำหรับการ **Scale Throughput ของ HTTP Server** ให้เต็มทุก CPU Cores บนโฮสต์เดียวกัน
3. **`node:worker_threads`:** รันหลาย Threads ภายใต้ OS Process เดียวกัน แต่ละ Thread มี V8 Isolate ของตัวเอง แต่สามารถแชร์หน่วยความจำร่วมกันได้ผ่าน **`SharedArrayBuffer`** ทำให้สามารถส่งข้อมูลขนาดใหญ่หากันได้แบบ Zero-copy เหมาะที่สุดสำหรับ **CPU-bound Computation ภายในแอปพลิเคชันเดิม**

### Q2: จงอธิบายสมมติฐาน Generational Hypothesis ใน V8 Garbage Collection และอธิบายว่าทำไมการเกิด Major GC บ่อยๆ จึงส่งผลกระทบต่อ Latency ของระบบ?
**แนวคำตอบเชิงลึก:**
**Generational Hypothesis** คือสมมติฐานที่พบว่า: *"ในโลกความเป็นจริงของโปรแกรมคอมพิวเตอร์ อ็อบเจกต์ส่วนใหญ่จะมีอายุขัยสั้นมาก (ตายลงทันทีหลังเสร็จงาน) ในขณะที่มีอ็อบเจกต์เพียงส่วนน้อยมากที่จะมีชีวิตอยู่ยาวนาน"*

V8 จึงแบ่งหน่วยความจำ Heap ออกเป็น 2 กลุ่ม:
1. **Young Generation (New Space):** จัดการโดย **Minor GC (Scavenger)** โดยใช้ Cheneys Copying Algorithm ซึ่งทำงานรวดเร็วมากในระดับไมโครวินาที (1-3ms) เพราะกวาดเฉพาะ New Space
2. **Old Generation (Old Space):** อ็อบเจกต์ที่รอดชีวิตจาก Minor GC ครบ 2 รอบจะถูกย้าย (Promoted) มายัง Old Space ซึ่งจะถูกทำความสะอาดโดย **Major GC (Mark-Sweep-Compact)**

**ผลกระทบของ Major GC:**
อัลกอริทึม Mark-Sweep-Compact จำเป็นต้องหยุดการทำงานของ JavaScript ชั่วขณะ (**Stop-The-World Pause**) เพื่อเดินสำรวจ Pointer Graph ทั้งหมดของ Heap และทำการจัดระเบียบพื้นที่หน่วยความจำที่กระจัดกระจาย (Memory Compaction) 

หากแอปพลิเคชันมี Object สะสมใน Old Space มากเกินไป (เช่น เกิด Memory Leak หรือแคชข้อมูลมหาศาล) การเกิด Major GC ในแต่ละรอบอาจกินเวลาหยุดชะงักนานถึง **200ms - 1,000ms (1 วินาที)** ซึ่งจะส่งผลให้ค่า `p99` Response Latency ของระบบกระตุกรุนแรงและเกิด Timeout ขึ้นกับผู้ใช้งาน
