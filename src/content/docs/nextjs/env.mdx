# Next.js 16 Environment Variables & Secret Management

คู่มือระดับ Senior Fullstack ในการบริหารจัดการตัวแปรสภาพแวดล้อม (Environment Variables) การปกป้องความลับของระบบจากภัยเงียบของการรั่วไหลลงสู่ Client Bundle และการทำ Build-time Type Validation ด้วย Zod

---

## 1. แนวคิด (Concept)

ในสถาปัตยกรรม Fullstack ยุคใหม่ของ Next.js 16 โค้ดในโปรเจกต์เดียวกันจะถูกแยกการทำงานออกเป็น 2 ฟากอย่างชัดเจน:
1. **Server Environment:** ทำงานบน Node.js / Edge Runtime เข้าถึงทรัพยากรหลังบ้าน รหัสผ่านฐานข้อมูล และ Payment Gateway Secret Keys ได้อย่างปลอดภัย
2. **Client Environment:** ทำงานบน Web Browser ของผู้ใช้งาน ซึ่งโค้ดทั้งหมดจะถูกส่งผ่านเครือข่ายและเปิดเผยสู่สาธารณะ

### ภัยเงียบของ `NEXT_PUBLIC_*`
Next.js กำหนดกฎว่า ตัวแปรใดก็ตามที่ขึ้นต้นด้วย `NEXT_PUBLIC_` จะถูกถือเป็น **Client-Safe Variable** ซึ่งคอมไพเลอร์ (Turbopack / Webpack) จะนำค่าจริงไปเขียนทับแบบตรงตัว (Inlining) ลงในไฟล์ JavaScript ส่งผลให้ผู้ใช้ทุกคนสามารถเปิด Chrome DevTools แล้วดูค่าเหล่านั้นได้ทันที

หากนักพัฒนาเผลอตั้งชื่อตัวแปร เช่น `NEXT_PUBLIC_STRIPE_SECRET_KEY` หรือ `NEXT_PUBLIC_DATABASE_PASSWORD` รหัสผ่านขององค์กรจะรั่วไหลออกสู่สาธารณะทันทีที่ Build เสร็จสิ้น

```text
+-----------------------------------------------------------------------------------+
|                        Next.js Environment Isolation Map                          |
+-----------------------------------------+-----------------------------------------+
|        Server-Only Boundary             |          Client-Exposed Boundary        |
| (Database, Private Keys, Payment API)   |       (Analytics ID, Public URLs)       |
+-----------------------------------------+-----------------------------------------+
| DATABASE_URL                            | NEXT_PUBLIC_APP_URL                     |
| STRIPE_SECRET_KEY                       | NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY      |
| OMISE_SECRET_KEY                        | NEXT_PUBLIC_GA_MEASUREMENT_ID           |
| JWT_SIGNING_SECRET                      | NEXT_PUBLIC_MEAT_CURRENCY_SYMBOL        |
|                                         |                                         |
| [ Protected by 'server-only' & Node ]   | [ Inlined into Browser JS Chunks ]      |
+-----------------------------------------+-----------------------------------------+
```

### ลำดับความสำคัญของไฟล์ Environment (Precedence Hierarchy)

Next.js โหลดไฟล์ `.env` ตามลำดับความสำคัญจาก **สูงสุดไปต่ำสุด** ดังนี้:

| ลำดับ | ชื่อไฟล์ | วัตถุประสงค์และการทำงาน | จัดเก็บใน Git? |
| :---: | :--- | :--- | :---: |
| **1** | `process.env` (System Env) | ค่าที่ถูกฉีดจาก OS, Docker หรือ Cloud Dashboard (สำคัญที่สุด) | ไม่ |
| **2** | `.env.production.local` / `.env.development.local` | ค่า Override เฉพาะเครื่องตามโหมด `NODE_ENV` | **ห้ามเด็ดขาด** (ใส่ `.gitignore`) |
| **3** | `.env.local` | ค่า Override ประจำเครื่องของนักพัฒนาสำหรับทุกโหมด | **ห้ามเด็ดขาด** (ใส่ `.gitignore`) |
| **4** | `.env.production` / `.env.development` / `.env.test` | ค่าเริ่มต้นเฉพาะ Environment สำหรับแชร์ในทีม | เก็บได้ (ห้ามมี Secret จริง) |
| **5** | `.env` | ค่าเริ่มต้นกลาง (Fallback) ของทุกสภาพแวดล้อม | เก็บได้ (ห้ามมี Secret จริง) |

## 2. หลักการเบื้องหลัง (Under the Hood)

### 2.1 กลไก Static Replacement (Inlining) ของ Turbopack

เมื่อ Turbopack หรือ Webpack ทำการคอมไพล์โค้ดฝั่ง Client:
- คอมไพเลอร์จะไม่ส่งอ็อบเจกต์ `process.env` ไปยังเบราว์เซอร์ทั้งก้อน
- คอมไพเลอร์จะตรวจจับโค้ดที่มีการพิมพ์สตริง `process.env.NEXT_PUBLIC_KEY` แล้วแทนที่ด้วยค่าตัวแปรนั้นโดยตรง (Abstract Syntax Tree string replacement)

```javascript filename="src/lib/turbopack-transform.js"
// โค้ดต้นฉบับก่อนคอมไพล์
const apiUrl = process.env.NEXT_PUBLIC_API_URL;

// โค้ดหลังผ่าน Turbopack build
const apiUrl = "https://api.smartbutcher.com";
```

<Callout type="warning" title="ข้อจำกัดของการทำ Static Inlining">
เนื่องจากการแทนที่ค่าทำงานผ่านการตรวจจับชื่อตัวแปรแบบตรงตัว หากเขียนโค้ดแบบ Dynamic Object Access เช่น `const key = 'NEXT_PUBLIC_API_URL'; const url = process.env[key];` ตัวคอมไพเลอร์จะไม่สามารถตรวจจับได้ และค่าในเบราว์เซอร์จะกลายเป็น `undefined` เสมอ
</Callout>

### 2.2 แพ็กเกจ `server-only` ป้องกัน Secret รั่วไหลในระดับ Compile Time

กลไกที่น่ากลัวที่สุดไม่ใช่การจงใจใช้ `NEXT_PUBLIC_` แต่คือการที่ Client Component เผลอ `import` ฟังก์ชันหรือโมดูลที่มีตัวแปร Private จาก Server เข้ามาใช้งาน

การติดตั้งและเรียกใช้แพ็กเกจ `import 'server-only'` จะทำให้ React/Next.js ตรวจสอบโมดูลนั้น หากพบว่ามี Client Component (`'use client'`) เรียกใช้ไฟล์ดังกล่าว ตัวคอมไพเลอร์จะหยุดการทำงานทันที และขว้างข้อผิดพลาดออกมาตอน `next build` ทันที โดยไม่ยอมปล่อยให้โค้ดหลุดไปถึง Production

### 2.3 Fail-Fast Strategy ด้วย Build-time Validation

แทนที่จะปล่อยให้แอปพลิเคชันบูตขึ้นมาแล้วไปพังตอนผู้ใช้กำลังทำรายการซื้อเนื้อสเต๊ก (เช่น `undefined` error เมื่อเรียก Payment API) แนวคิดระดับ Senior คือการทำ **Fail-Fast Schema Validation** ด้วย Zod ตั้งแต่วินาทีแรกที่สั่ง `next build` หากมีตัวแปรสำคัญขาดหายไปแม้แต่ตัวเดียว ระบบ CI/CD จะต้องหยุดการ Deploy ทันที

## 3. ตัวอย่างโค้ด (Smart Butcher Marketplace)

### ตัวอย่างที่ 1: Schema Validation แบบ Type-Safe ด้วย Zod

สร้างระบบตรวจสอบตัวแปรสภาพแวดล้อมสำหรับระบบจำหน่ายเนื้อพรีเมียม **Smart Butcher Marketplace** เพื่อรับประกันความถูกต้องของทั้ง Server Secrets และ Client Keys

```typescript filename="src/env.ts"
import { z } from 'zod';

// 1. กำหนด Schema สำหรับฝั่ง Server เท่านั้น (ห้ามหลุดไป Client เด็ดขาด)
const serverEnvSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']).default('development'),
  DATABASE_URL: z
    .string()
    .url('DATABASE_URL ต้องเป็น Connection String รูปแบบ PostgreSQL ที่ถูกต้อง')
    .startsWith('postgresql://', 'ฐานข้อมูลต้องเป็น PostgreSQL เท่านั้น'),
  REDIS_URL: z.string().url('REDIS_URL ต้องเป็น URL ที่ถูกต้อง'),
  STRIPE_SECRET_KEY: z
    .string()
    .min(20, 'STRIPE_SECRET_KEY ต้องมีความยาวถูกต้อง')
    .startsWith('sk_', 'Stripe Secret Key ต้องขึ้นต้นด้วย sk_'),
  JWT_SECRET: z
    .string()
    .min(32, 'JWT Secret ต้องมีความยาวอย่างน้อย 32 ตัวอักษรเพื่อความปลอดภัยด้าน Cryptography'),
  BUTCHER_ADMIN_EMAIL: z.string().email('BUTCHER_ADMIN_EMAIL ต้องเป็นอีเมลที่ถูกต้อง'),
});

// 2. กำหนด Schema สำหรับฝั่ง Client (อนุญาตให้เข้าถึงจากบราวเซอร์ได้)
const clientEnvSchema = z.object({
  NEXT_PUBLIC_APP_URL: z.string().url('NEXT_PUBLIC_APP_URL ต้องเป็น Full URL'),
  NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY: z
    .string()
    .startsWith('pk_', 'Stripe Publishable Key ต้องขึ้นต้นด้วย pk_'),
  NEXT_PUBLIC_DEFAULT_CURRENCY: z.enum(['THB', 'USD', 'JPY']).default('THB'),
});

// รวบรวมข้อมูลทั้งหมด
const processEnv = {
  NODE_ENV: process.env.NODE_ENV,
  DATABASE_URL: process.env.DATABASE_URL,
  REDIS_URL: process.env.REDIS_URL,
  STRIPE_SECRET_KEY: process.env.STRIPE_SECRET_KEY,
  JWT_SECRET: process.env.JWT_SECRET,
  BUTCHER_ADMIN_EMAIL: process.env.BUTCHER_ADMIN_EMAIL,
  NEXT_PUBLIC_APP_URL: process.env.NEXT_PUBLIC_APP_URL,
  NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY: process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY,
  NEXT_PUBLIC_DEFAULT_CURRENCY: process.env.NEXT_PUBLIC_DEFAULT_CURRENCY,
};

// ตรวจสอบความถูกต้อง (Fail-Fast Validation)
const isServer = typeof window === 'undefined';

const parsedServer = isServer ? serverEnvSchema.safeParse(processEnv) : { success: true, data: {} as any };
const parsedClient = clientEnvSchema.safeParse(processEnv);

if (!parsedClient.success) {
  console.error('❌ ข้อผิดพลาดในการตั้งค่าตัวแปร Client Environment:');
  console.error(JSON.stringify(parsedClient.error.flatten().fieldErrors, null, 2));
  throw new Error('ตัวแปร Client Environment ไม่ถูกต้อง กรุณาตรวจสอบไฟล์ .env');
}

if (isServer && !parsedServer.success) {
  console.error('❌ ข้อผิดพลาดในการตั้งค่าตัวแปร Server Environment:');
  console.error(JSON.stringify(parsedServer.error.flatten().fieldErrors, null, 2));
  throw new Error('ตัวแปร Server Environment ไม่ถูกต้อง กรุณาตรวจสอบไฟล์ .env หรือการตั้งค่าบน Cloud');
}

// รวม Type และ Export อ็อบเจกต์ env ที่ปลอดภัย
export const env = {
  ...parsedClient.data,
  ...(isServer ? parsedServer.data : {}),
} as z.infer<typeof clientEnvSchema> & (typeof isServer extends true ? z.infer<typeof serverEnvSchema> : {});
```

### ตัวอย่างที่ 2: ป้องกัน Secret รั่วไหลด้วย `server-only`

สร้างโมดูลจัดการธุรกรรมตัดบัตรเครดิตสำหรับเนื้อวากิว โดยใช้ `import 'server-only'` เพื่อให้แน่ใจว่าหากมีใครพยายาม Import ฟังก์ชันนี้ในคอมโพเนนต์ฝั่ง Client จะเกิด Build Error ทันที:

```typescript filename="src/lib/payment-server.ts"
// บังคับให้ไฟล์นี้รันได้เฉพาะบนเซิร์ฟเวอร์เท่านั้น
import 'server-only';
import { env } from '@/env';

interface ChargeButcherOrderParams {
  orderId: string;
  amountInSatang: number; // แปลงสกุลเงินเป็นสตางค์สำหรับ Stripe/Omise
  customerEmail: string;
  meatDescription: string;
}

interface PaymentResult {
  chargeId: string;
  status: 'succeeded' | 'pending' | 'failed';
}

export async function processMeatPayment(
  params: ChargeButcherOrderParams
): Promise<PaymentResult> {
  // เข้าถึง Secret Key ได้อย่างปลอดภัย ไร้กังวลเรื่องการหลุดไปยัง Client
  const secretKey = env.STRIPE_SECRET_KEY;

  const response = await fetch('https://api.stripe.com/v1/charges', {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${secretKey}`,
      'Content-Type': 'application/x-www-form-urlencoded',
    },
    body: new URLSearchParams({
      amount: params.amountInSatang.toString(),
      currency: 'thb',
      description: `Smart Butcher Order: ${params.meatDescription} (${params.orderId})`,
      receipt_email: params.customerEmail,
    }),
  });

  if (!response.ok) {
    const errorData = await response.json();
    throw new Error(`การตัดเงินล้มเหลว: ${errorData.error?.message || 'Unknown Error'}`);
  }

  const result = await response.json();
  return {
    chargeId: result.id,
    status: result.status,
  };
}
```

หากฝั่ง Client Component มีการเผลอเรียกใช้ไฟล์ข้างต้น:

```tsx filename="src/app/checkout/CheckoutButton.tsx"

    </button>
```

## 4. ข้อผิดพลาดที่พบบ่อย (Anti-pattern vs Best Practice)

| ปัญหาที่พบบ่อย | รูปแบบที่ผิดพลาด (Anti-pattern) | แนวทางที่ถูกต้องระดับ Senior (Best Practice) |
| :--- | :--- | :--- |
| **Prefix `NEXT_PUBLIC_` มั่วซั่ว** | เติม `NEXT_PUBLIC_` ให้กับตัวแปร Secret เพียงเพราะต้องการเรียกใช้ในคอมโพเนนต์หน้าบ้านอย่างรวดเร็ว | เก็บ Secret ไว้ใน Server Component หรือ Server Action แล้วส่งเฉพาะข้อมูลที่ประมวลผลเสร็จแล้วกลับมายัง Client |
| **เรียกใช้ผ่าน Dynamic Index** | เขียน `process.env[varName]` ในโค้ดหน้าบ้าน ทำให้ค่าคืนกลับเป็น `undefined` เพราะ Bundler ตรวจจับชื่อไม่ได้ | พิมพ์ชื่อเต็มตรงๆ เช่น `process.env.NEXT_PUBLIC_API_URL` หรือใช้โมดูลกลางที่มี Zod Validation |
| **Commit ไฟล์ความลับขึ้น Git** | ลืมเพิ่ม `.env.local` ลงใน `.gitignore` ทำให้ API Keys และรหัสผ่านฐานข้อมูลขึ้นสู่ Remote Repository | บันทึกเฉพาะ `.env.example` ที่มีแค่ชื่อคีย์และค่าว่างไว้ใน Git ส่วนค่าจริงให้บันทึกผ่าน Secret Manager ของผู้ให้บริการ |
| **Type Cast โดยไม่มีการตรวจจริง** | เขียนโค้ดว่า `const url = process.env.DATABASE_URL as string` เมื่อตัวแปรหลุดหาย แอปจะแครชเงียบๆ กลางทาง | ใช้ Zod ทำ Runtime & Build-time Validation รับประกัน Type ที่แน่นอน พร้อมแจ้งเตือนทันทีเมื่อตัวแปรขาด |
| **ลืมใส่ `import 'server-only'`** | เขียน Utility ช่วยคำนวณราคาเนื้อหรือตัดเงินโดยไม่ใส่ตัวป้องกัน ทำให้เพื่อนร่วมทีมเผลอนำไป Import บนหน้าบ้าน | ใส่ `import 'server-only'` บนหัวไฟล์ที่เป็นความลับทุกไฟล์ เพื่อให้คอมไพเลอร์ดักจับข้อผิดพลาดตั้งแต่ขั้นตอนบิลด์ |

## 5. ควรใช้เมื่อไหร่ และ ไม่ควรใช้เมื่อไหร่

### ควรใช้ Server-Only Environment Variables (ไม่มี `NEXT_PUBLIC_`):
- **Database Connection Strings:** URL เชื่อมต่อ PostgreSQL, Redis, MongoDB
- **Third-Party Secret Keys:** Stripe Secret Key, Omise Secret Key, AWS S3 Secret Access Key
- **Cryptography & Signing:** JWT Secret, Session Cookies Encryption Secret, Webhook Signature Keys
- **Internal Microservice URLs:** URL ที่เรียกใช้งานภายใน Private Subnet หลังบ้าน

### ควรใช้ Client Environment Variables (มี `NEXT_PUBLIC_`):
- **Third-Party Public Keys:** Stripe Publishable Key สำหรับเรนเดอร์ฟอร์มบัตรเครดิตหน้าบ้าน
- **Public Domain URLs:** `NEXT_PUBLIC_APP_URL` สำหรับนำไปใช้แปะแชร์ Social Media หรือ Canonical URLs
- **Analytics & Tracking IDs:** Google Analytics Measurement ID, Facebook Pixel ID
- **Feature Flags ที่กระทบ UI:** เช่น `NEXT_PUBLIC_ENABLE_FLASH_SALE_BANNER="true"`

### ไม่ควรใช้ Environment Variables:
- **ข้อมูลที่เปลี่ยนแปลงตลอดเวลาตามผู้ใช้:** เช่น ข้อมูลสต็อกเนื้อวากิว, ราคาสินค้าประจำวัน (ควรจัดเก็บใน Database)
- **ข้อมูลขนาดใหญ่:** เช่น รายชื่อหมวดหมู่สินค้าทั้งหมด (ควรดึงผ่าน REST/GraphQL หรือ Database Query)

## 6. คำถามสัมภาษณ์งาน (Interview Q&A)

### คำถามที่ 1: การทำงานของตัวแปร `NEXT_PUBLIC_*` ใน Next.js มีกระบวนการอย่างไรตอน Compile และทำไมการเรียกใช้แบบ `process.env[dynamicKey]` ถึงทำงานบน Server ได้แต่ล้มเหลวบน Client?

**แนวคำตอบเชิงลึก:**
การทำงานของ Next.js ต่อตัวแปร `NEXT_PUBLIC_*` ไม่ได้เป็นการส่งอ็อบเจกต์ `process.env` ข้ามเครือข่ายไปยังเบราว์เซอร์ เพราะในสภาพแวดล้อม Client (เบราว์เซอร์) ไม่มีกระบวนการของ Node.js รันอยู่จริง สิ่งที่เกิดขึ้นคือ **Static Analysis และ AST Inlining**:
1. ระหว่างกระบวนการคอมไพล์ (Turbopack หรือ Webpack) ตัว Bundler จะทำการวิเคราะห์โค้ด (Static Code Analysis)
2. เมื่อเจอนิพจน์ที่มีการเข้าถึงคุณสมบัติคงที่ เช่น `process.env.NEXT_PUBLIC_API_URL` ตัว Bundler จะตัดนิพจน์นั้นทิ้ง แล้วแทนที่ด้วยค่าสตริงตรงๆ (String Literal Replacement) เช่น `"https://api.smartbutcher.com"`

ด้วยเหตุนี้ การเขียนแบบไดนามิก เช่น `const key = 'NEXT_PUBLIC_API_URL'; console.log(process.env[key]);`:
- **บน Server:** คำสั่งนี้ทำงานได้ปกติ เพราะ `process.env` เป็น Global Object ของระบบปฏิบัติการ Node.js จริง
- **บน Client:** ล้มเหลวและได้ค่า `undefined` เสมอ เพราะ Bundler ไม่สามารถรู้ล่วงหน้าได้ในขณะสแกนโค้ดว่า `key` จะมีค่าเป็นอะไร จึงไม่สามารถทำ AST Replacement ได้ และเนื่องจากเบราว์เซอร์ไม่มีอ็อบเจกต์ `process.env` ตัวแปรจึงกลายเป็นค่าว่าง

### คำถามที่ 2: แพ็กเกจ `server-only` มีหลักการทำงานเบื้องหลังอย่างไร และทำไมการผสมผสานระหว่าง `server-only` กับ Zod Schema จึงถือเป็นสถาปัตยกรรมแบบ Defense-in-Depth ที่ดีที่สุดในการจัดการความลับ?

**แนวคำตอบเชิงลึก:**
แพ็กเกจ `server-only` มีขนาดเพียงไม่กี่บรรทัด แต่ใช้ประโยชน์จาก **React Component Module Resolution และ Next.js Bundler Constraints**:
- ภายในไฟล์ `package.json` ของโมดูล `server-only` มีการกำหนดฟิลด์ `react-server` ใน export map
- เมื่อคอมไพเลอร์ของ Next.js กำลังสร้าง Client Bundle (สำหรับไฟล์ที่มี `'use client'`) แล้วพบว่ามีการ Import โมดูล `server-only` ไม่ว่าจะทางตรงหรือทางอ้อม ตัว Bundler จะถือว่าโมดูลนั้นไม่รองรับ Client Target และสั่งยกเลิกการคอมไพล์พร้อมขว้าง Error ออกมาทันที

การจับคู่ร่วมกับ **Zod Validation** สร้างการป้องกันแบบสองชั้น (**Defense-in-Depth**):
1. **Zod เป็นด่านหน้า (Value & Type Integrity):** รับประกันตั้งแต่ก้าวแรกของการรันคำสั่ง `next build` ว่าตัวแปรสภาพแวดล้อมทุกตัวต้องมีค่าอยู่จริง ต้องตรงตามฟอร์แมต (URL, Email, ความยาวสตริง) ป้องกันแอปพลิเคชันพังเงียบๆ กลางทางจากค่า `undefined`
2. **`server-only` เป็นตาข่ายนิรภัย (Boundary Isolation):** ป้องกันข้อผิดพลาดของมนุษย์ (Human Error) ที่อาจเผลอ Import โค้ดที่เรียกใช้ Zod server schema นั้นเข้าไปใน Client Component โดยจะหยุดยั้งการส่งมอบโค้ดตั้งแต่ขั้นตอน CI/CD ทำให้ไม่เกิดเหตุการณ์ข้อมูลหรือ Secret รั่วไหลสู่สาธารณะแม้แต่เคสเดียว
