# Anti-patterns

(รวม 7 ข้อผิดพลาดร้ายแรงและวิกฤตที่พบบ่อยในการใช้งาน Git: Merge Conflict, Detached HEAD, ความเสียหายจาก Force Push, และคำถามสัมภาษณ์งานระดับ Senior)

---

## 1. ข้อผิดพลาดร้ายแรงที่พบบ่อยในชีวิตจริง (Top 7 Git Pitfalls)

### 1. การสั่ง `git push --force` บนกิ่งสาธารณะ (Shared Branches)
- **ปัญหา:** การใช้ `--force` จะทับประวัติ Commit บนเซิร์ฟเวอร์ด้วยประวัติในเครื่องคุณ ทำให้โค้ดของเพื่อนร่วมทีมที่เพิ่ง Push ไปก่อนหน้าสูญหายทันที
- **วิธีแก้:** ตั้งค่า **Branch Protection Rules** บน GitHub เพื่อบล็อกการ Force Push บน `main` และหากจำเป็นต้องแก้ประวัติกิ่งของตนเอง ให้ใช้คำสั่งที่ปลอดภัยกว่าคือ `git push --force-with-lease`

### 2. อาการ "Detached HEAD State"
- **ปัญหา:** เกิดจากการสั่ง `git checkout <commit-hash>` เพื่อไปดูโค้ดเก่าโดยไม่ได้แตกกิ่งใหม่ หากคุณเขียนโค้ดและ Commit ในสถานะนี้ โค้ดทั้งหมดจะลอยเคว้งและถูก Git Garbage Collection กวาดทิ้งในอนาคต
- **วิธีแก้:** สั่งสร้างกิ่งรองรับทันทีด้วย `git switch -c new-feature-branch`

### 3. การเผลอ Commit ไฟล์ Secret (`.env`, Private Keys, API Keys)
- **ปัญหา:** แม้จะสั่งลบไฟล์นั้นใน Commit ถัดไป แต่ประวัติใน Git จะยังคงบันทึกไฟล์นั้นไว้ใน `.git/objects` ตลอดกาล ผู้ไม่หวังดีสามารถคุ้ยดูย้อนหลังได้
- **วิธีแก้:** ใช้เครื่องมืออย่าง `git-filter-repo` หรือ BFG Repo-Cleaner ล้างประวัติไฟล์นั้นออกจาก Git ทั้งหมด และ **หมุนเวียน (Rotate) API Key ทันที**

### 4. อาการกลัว Merge Conflict จนไม่กล้าดึงโค้ด
- **ปัญหา:** ปล่อยให้กิ่ง Feature ค้างอยู่นานหลายสัปดาห์โดยไม่ Pull โค้ดจาก `main`
- **วิธีแก้:** หมั่นสั่ง `git pull --rebase origin main` วันละอย่างน้อย 1-2 ครั้ง เพื่อแก้ Conflict ก้อนเล็กๆ ทีละนิด ดีกว่ารอระเบิดครั้งใหญ่ตอนจะปล่อยงาน

### 5. การใช้ข้อความ Commit ที่ไร้ความหมาย
- **ปัญหา:** เขียนข้อความ `fix`, `asdf`, `wip`, `update` ทำให้ไม่สามารถสืบค้นด้วย `git log` ได้
- **วิธีแก้:** บังคับใช้ **Conventional Commits** (`feat`, `fix`, `chore` ฯลฯ) ร่วมกับ Husky และ Commitlint

### 6. การสับสนระหว่าง `git fetch` กับ `git pull`
- **ปัญหา:** ไม่เข้าใจว่า `git pull` คือ `git fetch` + `git merge` รวมกัน
- **วิธีแก้:** หมั่นสั่ง `git fetch` ก่อนเพื่อดูความเคลื่อนไหวบน Remote โดยที่ยังไม่กระทบโค้ดในเครื่อง แล้วจึงตัดสินใจ Merge หรือ Rebase

### 7. การละเลยการตั้งค่า `.gitignore` ตั้งแต่เริ่มโปรเจกต์
- **ปัญหา:** เผลอ Push โฟลเดอร์ `node_modules` หรือ `.next` ขึ้น GitHub ขนาดไฟล์บวมเป็นร้อยเมกะไบต์
- **วิธีแก้:** สร้างไฟล์ `.gitignore` มาตรฐานสำหรับ Node.js / Next.js ตั้งแต่การ Commit ครั้งแรกสุดของโปรเจกต์

## 2. คำถามสัมภาษณ์งาน (Senior Interview Q&A)

### ข้อที่ 1: `git merge --squash` แตกต่างจาก `git rebase` อย่างไร และทำไมหลายบริษัทจึงเลือก Squash Merge เป็นนโยบายหลักของ Pull Request?
**แนวคำตอบเชิงลึก:**
- **ความต่าง:** `git rebase` จะนำทุกลูก Commit ในกิ่งฟีเจอร์มาย้ายฐานต่อท้ายกิ่งหลักทีละลูก ทำให้ประวัติบนกิ่งหลักยังคงมี Commit เล็กๆ (เช่น `fix typo`, `wip`) ติดมาด้วย ส่วน `git merge --squash` จะนำความเปลี่ยนแปลงทั้งหมดในกิ่งฟีเจอร์มารวบเป็น **Snapshot ก้อนเดียว** แล้วให้นักพัฒนาเขียน Commit Message คุณภาพสูงเพียงข้อความเดียวลงบนกิ่งหลัก
- **ทำไมบริษัทจึงเลือก Squash Merge:** ช่วยลดขยะใน Git Log บนกิ่ง `main` ทำให้ประวัติการส่งมอบงานสะอาด เป็น 1 PR = 1 Atomic Commit ซึ่งง่ายต่อการอ่านย้อนหลัง และง่ายต่อการ Revert ทั้งฟีเจอร์ออกทันทีหากเกิดข้อผิดพลาด

### ข้อที่ 2: หากคุณเผลอสั่ง `git reset --hard` และทำโค้ดที่เพิ่งแก้หายไป คุณมีวิธีกู้คืนโค้ดนั้นกลับมาได้อย่างไรใน Git?
**แนวคำตอบเชิงลึก:**
ใน Git โค้ดที่มีการสั่ง `git add` หรือ `git commit` ไปแล้ว จะไม่สูญหายไปในทันที แต่จะกลายเป็น Dangling Objects ที่ถูกเก็บไว้ในฐานข้อมูลของ Git ชั่วคราว เราสามารถกู้คืนได้โดย:
1. สั่งรันคำสั่ง **`git reflog`** (Reference Log) เพื่อดูประวัติการเคลื่อนที่ของ `HEAD` ในเครื่องของเราทุกจังหวะ
2. มองหา SHA Hash ก่อนหน้าที่เราจะสั่ง reset (เช่น `HEAD@{1}`)
3. สั่งสร้างกิ่งใหม่จากจุดนั้นด้วยคำสั่ง `git checkout -b recovered-branch HEAD@{1}`
โค้ดทั้งหมดที่คิดว่าหายไปจะกลับมาอย่างสมบูรณ์แบบ!
