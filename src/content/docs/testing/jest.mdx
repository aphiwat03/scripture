## 1. โครงสร้างพื้นฐานของชุดทดสอบ (describe, it/test, nesting suites)

### แนวคิด (Concept)
หากเปรียบเทียบห้องปฏิบัติการตัดแต่งเนื้อสเต๊กพรีเมียมของ **Smart Butcher Marketplace**:
- **Test File (`*.spec.ts` / `*.test.ts`)**: เปรียบเหมือน "คู่มือการควบคุมคุณภาพประจำแผนก" (เช่น แผนกคำนวณการแล่เนื้อ หรือแผนกตัดสต็อกเนื้อดรายเอจ)
- **`describe` (Test Suite)**: เปรียบเหมือน "โซนปฏิบัติการย่อย" ที่จัดกลุ่มงานทดสอบที่เกี่ยวข้องกันไว้ด้วยกัน เช่น โซนตู้บ่มเนื้อดรายเอจ (Dry-Aging Vault Suite) ซึ่งสามารถซ้อนกลุ่มย่อยลงไปได้ (Nesting Suites) เช่น โซนตรวจนับอายุวันบ่มเนื้อ และโซนคำนวณค่าสูญเสียน้ำหนัก (Moisture Loss)
- **`it` หรือ `test` (Test Case)**: เปรียบเหมือน "รายการตรวจสอบคุณภาพเฉพาะชิ้น" (Specification Item) ที่ระบุพฤติกรรมที่คาดหวังอย่างชัดเจนเพียงเรื่องเดียว เช่น "ควรคำนวณราคาเนื้อริบอายตามน้ำหนักสุทธิได้อย่างถูกต้องเมื่อระบุความหนา 3.5 ซม."

การใช้คำว่า `it` ช่วยให้เราเขียนชื่อการทดสอบต่อเป็นประโยคภาษาอังกฤษเชิงพฤติกรรม (Behavior-Driven Development: BDD) ได้อย่างลื่นไหล เช่น `it('should calculate subtotal correctly...')` (มันควรจะคำนวณยอดรวมย่อยได้อย่างถูกต้อง...)

### หลักการเบื้องหลัง (Under the Hood)
สถาปัตยกรรมการรันเทสต์ของ Jest ทำงานแบบ **Two-Phase Execution**:

```text filename="docs/testing/jest.txt"
┌─────────────────────────────────────────────────────────────────────────────┐
│                       JEST RUNTIME EXECUTION PHASES                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  [ Phase 1: Test Discovery & Registration ]                                │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 1. โหลดไฟล์ *.spec.ts เข้าสู่ Worker Sandboxed VM                      │  │
│  │ 2. รันคำสั่งระดับ Root ของไฟล์ และโค้ดใน describe() Callback ทันที     │  │
│  │ 3. บันทึก it() / test() เข้าสู่ Abstract Syntax Tree (Test Hierarchy)  │  │
│  │    *หมายเหตุ: โค้ดภายใน it() จะยังไม่ถูกรันใน Phase นี้*              │  │
│  └───────────────────────────────────┬───────────────────────────────────┘  │
│                                      ▼                                      │
│  [ Phase 2: Sequential / Isolated Test Execution ]                          │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 1. ประมวลผล beforeAll Hooks                                           │  │
│  │ 2. วนลูปตามคิวการทดสอบ:                                              │  │
│  │    Parent beforeEach ➔ Child beforeEach ➔ it() Callback                 │  │
│  │    ➔ Child afterEach ➔ Parent afterEach                              │  │
│  │ 3. ประมวลผล afterAll Hooks                                            │  │
│  │ 4. ส่งผลลัพธ์ผ่าน IPC ไปยัง Jest Master Process เพื่อสรุป Report        │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Sandboxed Worker Isolation:** ในค่าเริ่มต้น Jest จะแตก Worker Process ตามจำนวน CPU Cores (ผ่านแพ็กเกจ `jest-worker`) แต่ละไฟล์ทดสอบจะถูกรันในบริบท Node.js `vm` (Virtual Machine Context) แยกขาดจากกัน ทำให้ State และตัวแปร Global ในไฟล์หนึ่งไม่ปนเปื้อนข้ามไฟล์
2. **Synchronous Suite Definition:** ใน Phase 1 Jest จะ Execute ทุกฟังก์ชัน Callback ของ `describe` ทันทีเพื่อประกอบเป็น Tree โครงสร้างชุดทดสอบ ดังนั้น ห้ามใส่การคำนวณที่ต้อง `await` หรือ Assertion ไว้ในตัวบอร์ดของ `describe` เด็ดขาด เพราะจะเกิดการรันก่อนที่ Hooks หรือ Fixtures จะถูกเตรียมพร้อม

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การจัดระเบียบ Test Suite ระดับฟังก์ชันคำนวณน้ำหนักเนื้อสเต๊ก
ในระบบ Smart Butcher ช่างแล่เนื้อต้องคำนวณน้ำหนักเนื้อโดยประมาณจากความหนา (thicknessCm) และพื้นที่หน้าตัดของเนื้อแต่ละเกรด:

```typescript filename="src/services/cut-calculator.spec.ts"
// Domain Interfaces
interface SteakCutSpec {
  cutType: 'RIBEYE' | 'STRIPLOIN' | 'T_BONE';
  thicknessCm: number;
  marblingScore: number; // 1 - 5
}

function estimateSteakWeightGrams(spec: SteakCutSpec): number {
  if (spec.thicknessCm <= 0) {
    throw new Error('Steak thickness must be strictly greater than zero');
  }

  // ปัจจัยความหนาแน่นเฉลี่ยของเนื้อวัวพรีเมียม (กรัมต่อความหนา 1 ซม.)
  const densityFactors: Record<SteakCutSpec['cutType'], number> = {
    RIBEYE: 110,
    STRIPLOIN: 95,
    T_BONE: 140, // รวมน้ำหนักกระดูกตัวที
  };

  const baseWeight = spec.thicknessCm * densityFactors[spec.cutType];
  // ไขมันลายหินอ่อน (Marbling) เพิ่มความหนาแน่น 2% ต่อระดับ Marbling Score
  const marblingBonus = 1 + (spec.marblingScore * 0.02);
  
  return Math.round(baseWeight * marblingBonus);
}

describe('CutCalculationService - estimateSteakWeightGrams', () => {
  it('should calculate estimated weight correctly for Ribeye with standard 3cm thickness', () => {
    // Arrange: จัดเตรียมข้อมูล Input
    const spec: SteakCutSpec = {
      cutType: 'RIBEYE',
      thicknessCm: 3.0,
      marblingScore: 4,
    };

    // Act: เรียกฟังก์ชันที่ต้องการทดสอบ
    const weight = estimateSteakWeightGrams(spec);

    // Assert: ตรวจสอบความถูกต้อง (3.0 * 110 = 330, bonus = 1.08 -> 356.4 -> 356g)
    expect(weight).toBe(356);
  });

  it('should throw an explicit error when thickness is zero or negative', () => {
    const invalidSpec: SteakCutSpec = {
      cutType: 'STRIPLOIN',
      thicknessCm: -1.5,
      marblingScore: 3,
    };

    expect(() => estimateSteakWeightGrams(invalidSpec)).toThrow(
      'Steak thickness must be strictly greater than zero'
    );
  });
});
```

#### ตัวอย่างที่ 2: การใช้ Nested Describe จัดกลุ่มตาม Use Cases และสิทธิ์ผู้ใช้งาน
การจัดกลุ่มคลาส `MeatStockService` เพื่อทดสอบการจองสต็อกเนื้อดรายเอจตามสถานะของคำสั่งซื้อ:

```typescript filename="src/services/meat-stock.service.spec.ts"
export interface Product {
  id: string;
  name: string;
  sku: string;
  pricePerKg: number;
  stockQty: number;
  dryAgedDays: number;
  isActive: boolean;
}

export class MeatStockService {
  constructor(private inventory: Map<string, Product>) {}

  public reserveStock(productId: string, requestedKg: number): void {
    const product = this.inventory.get(productId);
    if (!product) {
      throw new Error(`Product with ID ${productId} does not exist`);
    }
    if (!product.isActive) {
      throw new Error(`Product ${product.name} is currently inactive and cannot be reserved`);
    }
    if (product.stockQty < requestedKg) {
      throw new Error(
        `Insufficient stock for ${product.name}. Available: ${product.stockQty}kg, Requested: ${requestedKg}kg`
      );
    }
    product.stockQty -= requestedKg;
  }
}

describe('MeatStockService', () => {
  let inventoryMock: Map<string, Product>;
  let stockService: MeatStockService;

  beforeEach(() => {
    inventoryMock = new Map<string, Product>();
    stockService = new MeatStockService(inventoryMock);
  });

  describe('when reserving dry-aged beef batches', () => {
    const productId = 'prd-dry-ribeye-45d';

    beforeEach(() => {
      inventoryMock.set(productId, {
        id: productId,
        name: '45-Day Dry-Aged Black Angus Ribeye',
        sku: 'BEEF-RIB-45D',
        pricePerKg: 2850,
        stockQty: 12.5,
        dryAgedDays: 45,
        isActive: true,
      });
    });

    it('should successfully decrement available stock quantity when requested within quota', () => {
      stockService.reserveStock(productId, 3.5);

      const updated = inventoryMock.get(productId);
      expect(updated?.stockQty).toBe(9.0);
    });

    it('should throw an error and abort deduction when requested quantity exceeds warehouse capacity', () => {
      expect(() => {
        stockService.reserveStock(productId, 20.0);
      }).toThrow('Insufficient stock for 45-Day Dry-Aged Black Angus Ribeye');

      // ตรวจสอบว่าสต็อกต้องไม่ถูกหักลดลง
      const updated = inventoryMock.get(productId);
      expect(updated?.stockQty).toBe(12.5);
    });
  });

  describe('when product status is marked inactive', () => {
    it('should reject reservation regardless of available stock quantity', () => {
      const inactiveId = 'prd-wagyu-a5-off';
      inventoryMock.set(inactiveId, {
        id: inactiveId,
        name: 'Miyazaki Wagyu A5 Striploin',
        sku: 'WAGYU-A5-STRIP',
        pricePerKg: 5200,
        stockQty: 50.0,
        dryAgedDays: 0,
        isActive: false,
      });

      expect(() => {
        stockService.reserveStock(inactiveId, 1.0);
      }).toThrow('is currently inactive and cannot be reserved');
    });
  });
});
```

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: รัน Async Setup หรือใส่ Assertion ไว้ในตัว Body ของ `describe` โดยตรง
```typescript filename="src/jest.spec.ts"
describe('OrderPricingService', () => {
  // ผิดมหันต์: โค้ดนี้ถูกเรียกใน Phase 1 (Test Discovery) ทันที
  // หากคำสั่งนี้ล้มเหลว จะทำให้ Jest พังทั้งไฟล์ก่อนที่ Hooks หรือการจำลอง Mock จะทำงาน
  const dbConnection = await openDatabase(); 
  expect(dbConnection.isConnected()).toBe(true); // ห้ามใส่ assertion นอก it()

  it('should calculate tax correctly', () => {
    // ...
  });
});
```

#### ✅ สิ่งที่ถูก: ย้ายงาน Setup ไปไว้ใน `beforeAll` / `beforeEach` และใส่ Assertion ใน `it()`
```typescript filename="src/jest.spec.ts"
describe('OrderPricingService', () => {
  let dbConnection: DatabaseConnection;

  beforeAll(async () => {
    dbConnection = await openDatabase();
  });

  afterAll(async () => {
    await dbConnection.close();
  });

  it('should have an active database connection before processing', () => {
    expect(dbConnection.isConnected()).toBe(true);
  });

  it('should calculate tax correctly', () => {
    // ...
  });
});
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Nested `describe`:** เมื่อต้องการแบ่งกลุ่มสภาวะแวดล้อม เช่น `describe('when user is ADMIN')` และ `describe('when user is BUTCHER')` เพื่อให้สามารถแชร์ `beforeEach` ของแต่ละเงื่อนไขได้อย่างเป็นอิสระ
- **ไม่ควรใช้ Nesting ลึกเกิน 3 ชั้น:** การซ้อน `describe` 4-5 ชั้นจะทำให้ลืมลำดับการทำงานของ `beforeEach` เกิดความสับสน และสร้างปัญหา "Test Setup Overhead" ที่ยากแก่การดีบัก

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: เหตุใด Jest จึงรันโค้ดทั้งหมดที่อยู่ในฟังก์ชัน Callback ของ `describe` ก่อนที่ `beforeAll` หรือ `it` เคสแรกจะเริ่มต้นทำงาน?**
  - *แนวคำตอบ:* Jest ออกแบบมาให้แยกการทำงานเป็น 2 ขั้นตอนอย่างเคร่งครัด ได้แก่ **Collection Phase (Discovery)** และ **Execution Phase** ในขั้นตอนแรก Jest ต้องการรวบรวมโครงสร้างของชุดทดสอบ (Test Tree Hierarchy) เพื่อนับจำนวนเคส จัดลำดับการรัน รองรับ Filter Flag เช่น `-t "pattern"` และคำนวณการกระจายงานไปยัง Worker Pool ดังนั้นโค้ดใน `describe` จึงถูกสั่งรันแบบ Synchronous ทันทีเพื่อขึ้นรูป Tree ส่วนโค้ดใน `beforeAll`, `beforeEach` และ `it` จะถูกขึ้นทะเบียนไว้ในคิวเพื่อรอรันจริงในขั้นตอนที่สอง
- **Q2: ระหว่าง `it()` กับ `test()` มีความแตกต่างกันอย่างไรในระดับสถาปัตยกรรม และทีมควรมีแนวปฏิบัติอย่างไร?**
  - *แนวคำตอบ:* ในเชิงโค้ดของ Jest `it` คือ alias ตรงๆ ของ `test` (`const it = test;`) ทำงานเหมือนกันทุกประการ แต่แนวปฏิบัติระดับสากลแนะนำให้ใช้ `describe` คู่กับ `it` เมื่อเขียนเทสต์แบบ BDD (Behavior-Driven Development) เพื่อให้อ่านประโยคต่อกันได้ เช่น `it('should return 404 when product is missing')` และใช้ `test()` เมื่อทดสอบฟังก์ชันทางคณิตศาสตร์หรือ Utility สั้นๆ เช่น `test('formatVat() adds 7 percent')` สิ่งสำคัญคือการรักษาความสม่ำเสมอทั่วทั้งโปรเจกต์

## 2. Jest Matchers ครบวงจร (toBe, toEqual, toThrow, toHaveBeenCalledWith)

### แนวคิด (Concept)
หากเปรียบเทียบการตรวจสอบสินค้าในร้านขายเนื้อ:
- **`toBe` (Referential Identity)**: เปรียบเหมือน "การตรวจเลขไมโครชิปประจำตัววัว" ต้องเป็นวัวตัวเดียวกันที่ตำแหน่งหน่วยความจำเดียวกันเท่านั้น
- **`toEqual` (Deep Structural Equality)**: เปรียบเหมือน "การเทียบสเปกชิ้นเนื้อ" แม้เนื้อสองชิ้นจะตัดมาจากวัวคนละตัว แต่ถ้าเป็นเนื้อสันนอก หนัก 300 กรัม ความหนา 2.5 ซม. เท่ากันทุกประการ ถือว่าตรงกัน
- **`toStrictEqual` (Strict Prototype & Key Check)**: เปรียบเหมือน "การตรวจลึกถึงระดับ DNA และเอกสารรับรองมาตรฐานฟาร์ม" หากอ็อบเจกต์หนึ่งเป็น Class Instance แต่อีกอ็อบเจกต์เป็น Plain Object ธรรมดา หรือมีคีย์ที่เก็บค่า `undefined` ซ่อนอยู่ จะถือว่าไม่ผ่านทันที

### หลักการเบื้องหลัง (Under the Hood)
1. **`toBe(expected)`**: ทำงานผ่าน `Object.is(received, expected)` ใน JavaScript Runtime โดยไม่แปลงชนิดข้อมูล (No Type Coercion) และจัดการ Edge Cases ทางคณิตศาสตร์ได้แม่นยำ เช่น `Object.is(NaN, NaN)` ได้ `true` (ต่างจาก `===` ที่ได้ `false`) และ `Object.is(+0, -0)` ได้ `false`
2. **`toEqual(expected)`**: ใช้อัลกอริทึม Deep Recursive Comparison วนสำรวจทุก Enumerable Property ของอ็อบเจกต์และอาร์เรย์ แต่มีข้อยกเว้นคือ:
   - ไม่สนใจ `undefined` property: `{ a: undefined, b: 2 }` จะเท่ากับ `{ b: 2 }`
   - ไม่เช็คความต่างของ Class Constructor: อ็อบเจกต์ที่สร้างจาก `new ButcherOrder()` จะเทียบเท่ากับ Plain Object `{ ... }` หากค่าข้างในเหมือนกัน
3. **`toStrictEqual(expected)`**: ออกแบบมาเพื่อปิดช่องโหว่ของ `toEqual` โดยตรวจสอบ:
   - ตรวจสอบ Constructor Prototype (`a.constructor === b.constructor`)
   - ตรวจสอบคีย์ที่เป็น `undefined` อย่างเข้มงวด
   - ตรวจสอบ Sparse Arrays (ช่องว่างที่ไม่ได้ถูกกำหนดค่าใน Array)
4. **Floating Point Tolerance (`toBeCloseTo`)**: การคำนวณราคาและน้ำหนักเนื้อต้องเจอกับปัญหา Binary Floating-Point Arithmetic ตามมาตรฐาน IEEE 754 เช่น `0.1 + 0.2 === 0.30000000000000004` ฟังก์ชัน `toBeCloseTo(expected, numDigits)` จะคำนวณค่าคลาดเคลื่อนสัมพัทธ์ `|expected - received| < (10 ** -numDigits) / 2`

### ตารางสรุป Jest Matchers ยอดนิยมในระบบ Enterprise

| หมวดหมู่ Matcher | เมธอด Matcher | วัตถุประสงค์การใช้งาน | ตัวอย่างการใช้งานใน Smart Butcher |
| :--- | :--- | :--- | :--- |
| **Identity & Deep Equality** | `toBe(val)` | ตรวจสอบ Primitive Types หรือ Object Reference เดียวกัน | `expect(order.status).toBe('COMPLETED')` |
| | `toEqual(obj)` | ตรวจสอบโครงสร้างและค่าภายในแบบ Deep Comparison | `expect(cutSpec).toEqual({ thickness: 3, marbling: 4 })` |
| | `toStrictEqual(obj)` | ตรวจสอบเข้มงวด รวม Constructor และ undefined keys | `expect(createdUser).toStrictEqual(new UserEntity(...))` |
| **Truthiness & Nullability** | `toBeNull()` | ต้องมีค่าเป็น `null` เท่านั้น | `expect(payment.slipUrl).toBeNull()` |
| | `toBeUndefined()` | ต้องยังไม่ถูกประกาศค่า (`undefined`) | `expect(product.discountReason).toBeUndefined()` |
| | `toBeDefined()` | ต้องไม่ใช่ `undefined` (อาจเป็น null ได้) | `expect(order.confirmedAt).toBeDefined()` |
| | `toBeTruthy()` | แปลงเป็น Boolean แล้วได้ค่าจริง (`true`) | `expect(product.isActive).toBeTruthy()` |
| | `toBeFalsy()` | แปลงเป็น Boolean แล้วได้ค่าเท็จ (`false`) | `expect(product.isExpired).toBeFalsy()` |
| **Numbers & Math** | `toBeGreaterThan(n)` | ตัวเลขต้องมากกว่า | `expect(product.stockQty).toBeGreaterThan(0)` |
| | `toBeCloseTo(n, p)` | ตรวจสอบทศนิยมโดยไม่ให้บั๊ก IEEE 754 ทำลายผลลัพธ์ | `expect(totalAmount).toBeCloseTo(2450.75, 2)` |
| **Strings & Regex** | `toMatch(regex)` | ตรวจสอบรูปแบบข้อความด้วย Regular Expression | `expect(order.orderNo).toMatch(/^ORD-2026-\d{6}$/)` |
| | `toContain(str)` | ตรวจสอบ Substring หรือสมาชิกใน Primitive Array | `expect(order.tags).toContain('DRY_AGED')` |
| **Arrays & Objects** | `toHaveLength(n)` | ตรวจสอบขนาดของ Array หรือ String | `expect(order.items).toHaveLength(2)` |
| | `toHaveProperty(path, val)` | ตรวจสอบว่ามีคีย์ที่ระบุ และมีค่าตรงกันหรือไม่ | `expect(item).toHaveProperty('cutType', 'RIBEYE')` |
| | `toMatchObject(partial)` | ตรวจสอบเฉพาะฟิลด์ที่สนใจ (Partial Matching) | `expect(order).toMatchObject({ status: 'PAID' })` |
| **Asymmetric Matchers** | `expect.objectContaining` | จับคู่อ็อบเจกต์ย่อยที่ฝังอยู่ใน Arguments | `expect.objectContaining({ userId: 'usr-123' })` |
| | `expect.arrayContaining` | จับคู่อาร์เรย์ที่มีสมาชิกเหล่านี้อยู่ครบ (ไม่สนลำดับ) | `expect(cutList).toEqual(expect.arrayContaining(['RIBEYE']))` |
| | `expect.any(Constructor)` | จับคู่ชนิดข้อมูล เช่น สตริงที่สร้างขึ้นใหม่หรือ UUID | `expect(order.id).toEqual(expect.any(String))` |
| **Exceptions & Errors** | `toThrow(ErrorClass/Msg)` | ฟังก์ชันต้องโยน Error ออกมาตรงตามที่ระบุ | `expect(() => cut()).toThrow(InvalidThicknessException)` |

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การตรวจสอบความแม่นยำของราคา น้ำหนัก และความเข้มงวดของ Object
การคำนวณราคายอดรวมคำสั่งซื้อที่มีส่วนลดโปรโมชันและภาษีมูลค่าเพิ่ม (VAT 7%):

```typescript filename="src/services/pricing-calculator.spec.ts"
export interface OrderItem {
  id: string;
  productId: string;
  cutType: 'RIBEYE' | 'STRIPLOIN' | 'T_BONE' | 'TENDERLOIN' | 'PICANHA';
  thicknessCm: number;
  unitPrice: number;
  quantity: number;
  subtotal: number;
}

export class PricingCalculator {
  public static calculateSubtotal(items: OrderItem[]): number {
    return items.reduce((sum, item) => sum + (item.unitPrice * item.quantity), 0);
  }

  public static calculateVat(subtotal: number): number {
    return subtotal * 0.07;
  }

  public static calculateGrandTotal(items: OrderItem[], discountPercent = 0): {
    subtotal: number;
    discountAmount: number;
    netBeforeVat: number;
    vatAmount: number;
    grandTotal: number;
  } {
    const subtotal = this.calculateSubtotal(items);
    const discountAmount = (subtotal * discountPercent) / 100;
    const netBeforeVat = subtotal - discountAmount;
    const vatAmount = this.calculateVat(netBeforeVat);
    const grandTotal = netBeforeVat + vatAmount;

    return {
      subtotal,
      discountAmount,
      netBeforeVat,
      vatAmount,
      grandTotal,
    };
  }
}

describe('PricingCalculator', () => {
  const sampleItems: OrderItem[] = [
    {
      id: 'itm-001',
      productId: 'prd-dry-ribeye',
      cutType: 'RIBEYE',
      thicknessCm: 3.5,
      unitPrice: 1250.50,
      quantity: 2,
      subtotal: 2501.00,
    },
    {
      id: 'itm-002',
      productId: 'prd-wagyu-picanha',
      cutType: 'PICANHA',
      thicknessCm: 2.0,
      unitPrice: 850.25,
      quantity: 1,
      subtotal: 850.25,
    },
  ];

  it('should calculate floating point VAT and grand total accurately without IEEE 754 precision issues', () => {
    const result = PricingCalculator.calculateGrandTotal(sampleItems, 10); // ลด 10%

    // subtotal = 2501.00 + 850.25 = 3351.25
    expect(result.subtotal).toBeCloseTo(3351.25, 2);

    // discount 10% = 335.125
    expect(result.discountAmount).toBeCloseTo(335.125, 2);

    // netBeforeVat = 3016.125
    expect(result.netBeforeVat).toBeCloseTo(3016.125, 2);

    // vat 7% = 3016.125 * 0.07 = 211.12875
    expect(result.vatAmount).toBeCloseTo(211.13, 2);

    // grandTotal = 3016.125 + 211.12875 = 3227.25375
    expect(result.grandTotal).toBeCloseTo(3227.25, 2);
  });

  it('should differentiate between undefined properties and missing properties with toStrictEqual', () => {
    class MeatDeliveryOrder {
      constructor(
        public orderId: string,
        public specialInstructions: string | undefined
      ) {}
    }

    const orderWithUndefined = new MeatDeliveryOrder('ORD-101', undefined);
    const orderWithoutKey = { orderId: 'ORD-101' };

    // toEqual มองข้าม undefined keys จึงผ่าน (Loose)
    expect(orderWithUndefined).toEqual(orderWithoutKey);

    // toStrictEqual ตรวจสอบละเอียดทั้ง Class Type และ Property จึงตรวจพบความต่างและไม่ผ่าน (Strict)
    expect(orderWithUndefined).not.toStrictEqual(orderWithoutKey);
  });
});
```

#### ตัวอย่างที่ 2: การใช้ Asymmetric Matchers ตรวจสอบ Payload ที่ซับซ้อนและการดักจับ Exceptions
การตรวจสอบการออกใบแจ้งหนี้คำสั่งซื้อเนื้อสัตว์ที่ประกอบด้วยรหัส UUID สุ่ม และ Timestamp ของระบบ:

```typescript filename="src/services/order-dispatch.spec.ts"
import { randomUUID } from 'crypto';

interface DispatchOrderResult {
  orderId: string;
  orderNo: string;
  dispatchTimestamp: Date;
  warehouseHub: string;
  shippedItems: Array<{ sku: string; cutType: string; netWeightKg: number }>;
}

function dispatchButcherOrder(orderNo: string, items: Array<{ sku: string; cutType: string; netWeightKg: number }>): DispatchOrderResult {
  if (!items || items.length === 0) {
    throw new Error('Cannot dispatch an order with zero items');
  }

  return {
    orderId: randomUUID(),
    orderNo,
    dispatchTimestamp: new Date(),
    warehouseHub: 'CENTRAL_COLD_VAULT_BKK',
    shippedItems: items,
  };
}

describe('OrderDispatch - Asymmetric Matching', () => {
  it('should dispatch order and match payload using asymmetric matchers for dynamic attributes', () => {
    const rawItems = [
      { sku: 'BEEF-WAGYU-RIB', cutType: 'RIBEYE', netWeightKg: 1.25 },
      { sku: 'BEEF-ANGUS-TENDER', cutType: 'TENDERLOIN', netWeightKg: 0.85 },
    ];

    const result = dispatchButcherOrder('ORD-2026-998811', rawItems);

    // ตรวจสอบโครงสร้างโดยไม่ต้อง Hardcode UUID และ Date เวลาจริง
    expect(result).toEqual({
      orderId: expect.any(String),
      orderNo: expect.stringMatching(/^ORD-2026-\d{6}$/),
      dispatchTimestamp: expect.any(Date),
      warehouseHub: 'CENTRAL_COLD_VAULT_BKK',
      shippedItems: expect.arrayContaining([
        expect.objectContaining({
          cutType: 'RIBEYE',
          netWeightKg: expect.toBeCloseTo(1.25, 2),
        }),
      ]),
    });
  });

  it('should throw an explicit error wrapped inside an invocation callback', () => {
    // ต้องครอบด้วยลูกศร () => ... เพื่อให้ Jest ดักจับ Error ได้ตอนฟังก์ชันทำงาน
    expect(() => dispatchButcherOrder('ORD-EMPTY', [])).toThrow(
      'Cannot dispatch an order with zero items'
    );
  });
});
```

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: ส่งผลลัพธ์ของฟังก์ชันที่โยน Error เข้า `expect()` ตรงๆ
```typescript filename="src/jest.spec.ts"
// พังทันที: ฟังก์ชัน execute ทันที และโยน Uncaught Exception ทำให้ Test Runner แครช
// ก่อนที่ Matcher toThrow() จะมีโอกาสทำงาน
expect(dispatchButcherOrder('ORD-EMPTY', [])).toThrow();
```

#### ✅ สิ่งที่ถูก: ห่อหุ้มฟังก์ชันด้วย Arrow Function Callback
```typescript filename="src/jest.spec.ts"
// ถูกต้อง: Jest จะนำ Callback ไปสั่งรันในบล็อก try/catch ของ Matcher Engine
expect(() => dispatchButcherOrder('ORD-EMPTY', [])).toThrow(
  'Cannot dispatch an order with zero items'
);
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `toBeCloseTo`:** ในทุกการทดสอบที่เกี่ยวข้องกับเงิน (Currency, Subtotal, VAT, Discounts) หรือน้ำหนักเนื้อ (Gram, Kilogram) เสมอ
- **ควรใช้ `toMatchObject`:** เมื่อรับ Response จาก API หรือ Database แล้วต้องการตรวจสอบเฉพาะฟิลด์ที่เป็นหัวใจหลัก (Core Business Attributes) เพื่อป้องกันไม่ให้เทสต์เปราะบาง (Brittle) เมื่อมีฟิลด์เสริมใหม่ๆ ถูกเพิ่มเข้ามาใน Entity
- **ไม่ควรใช้ `toBe` กับ Object หรือ Array:** เพราะการเปรียบเทียบ Object References จะล้มเหลวเสมอแม้ข้อมูลข้างในจะเหมือนกันทุกประการ

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: จงยกตัวอย่างสถานการณ์ที่ `toEqual` ให้ผลลัพธ์ว่าผ่าน (Passed) แต่ `toStrictEqual` กลับแจ้งว่าล้มเหลว (Failed)?**
  - *แนวคำตอบ:* เกิดขึ้นได้ใน 2 กรณีหลัก:
    1. **ความแตกต่างของ Type Constructor:** เช่น การเปรียบเทียบ Object ที่สร้างจากคลาส `class MeatItem { sku = 'BEEF-01' }` กับ Plain Object `{ sku: 'BEEF-01' }` ในกรณีนี้ `toEqual` จะผ่านเพราะโครงสร้างคีย์-ค่าเหมือนกัน แต่ `toStrictEqual` จะล้มเหลวเพราะ Constructor ไม่ตรงกัน
    2. **คีย์ที่เป็น `undefined`:** วัตถุ `{ id: 1, note: undefined }` กับ `{ id: 1 }` ตัว `toEqual` จะมองข้ามคีย์ที่มีค่า `undefined` และตัดสินว่าเท่ากัน แต่ `toStrictEqual` จะมองว่าโครงสร้างคีย์ไม่เท่ากันอย่างเข้มงวด
- **Q2: ทำไมการใช้ `expect.objectContaining()` จึงเป็นแนวทางที่ดีกว่าการ Assert อ็อบเจกต์ทั้งก้อนใน Integration Testing?**
  - *แนวคำตอบ:* เพราะช่วยลดปัญหา **Test Brittleness** ในระบบจริง Entity มีการพัฒนาอยู่ตลอดเวลาและอาจมีฟิลด์จำพวก `createdAt`, `updatedAt`, `auditId` หรือ Metadata เพิ่มเติม การ Assert ทั้งก้อนด้วย `toEqual` จะทำให้เทสต์พังทุกครั้งที่มีการเพิ่มคอลัมน์ใหม่ในฐานข้อมูล การใช้ `expect.objectContaining()` ช่วยให้เทสต์โฟกัสเฉพาะ Business Invariants (สิ่งที่ฟังก์ชันนั้นต้องรับประกันจริงๆ) ทำให้ชุดทดสอบดูแลรักษาง่ายและทนทานต่อการ Refactor โค้ด

## 3. Setup และ Teardown Lifecycle (beforeAll, beforeEach, afterEach, afterAll)

### แนวคิด (Concept)
ลองจินตนาการถึงกิจวัตรประจำวันของช่างแล่เนื้อในร้าน **Smart Butcher Marketplace**:
- **`beforeAll` (เปิดร้านตอนเช้า)**: ตรวจสอบอุณหภูมิห้องเย็นหลักและเปิดเครื่องทำความเย็นขนาดใหญ่ (ทำครั้งเดียวตอนเริ่มต้นไฟล์ทดสอบ)
- **`beforeEach` (ก่อนตัดเนื้อแต่ละออเดอร์)**: นำเขียงไม้สะอาดและมีดเล่มใหม่ที่ผ่านการฆ่าเชื้อมาวางบนโต๊ะ เพื่อให้การแล่เนื้อเคสนี้บริสุทธิ์ 100% ไม่มีเศษเนื้อหรือคราบไขมันเก่าตกค้าง
- **`afterEach` (หลังตัดเนื้อเสร็จแต่ละออเดอร์)**: เช็ดทำความสะอาดเขียง ล้างมีด และบันทึก Log การผลิต (ล้าง Mock และรีเซ็ตสถานะตัวแปรเพื่อป้องกัน State Leakage)
- **`afterAll` (ปิดร้านตอนค่ำ)**: ปิดระบบไฟฟ้า ล้างทำความสะอาดพื้นโรงเชือด และตัดการเชื่อมต่อกับเซิร์ฟเวอร์สำนักงานใหญ่ (ตัด Database Connection และคืนหน่วยความจำ)

```text filename="docs/testing/jest.txt"
│       ▼                                                                     │
│  [9] Parent afterAll                                                        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**สำคัญมาก:** สังเกตว่า `beforeEach` ทำงานจาก **นอกเข้าใน (Outside-In)** เพื่อให้ระดับ Global เตรียมพร้อมก่อนระดับย่อย แต่ `afterEach` และ `afterAll` จะทำงานย้อนกลับจาก **ในออกนอก (Inside-Out)** เพื่อให้ทรัพยากรระดับย่อยถูกเคลียร์ทิ้งก่อนที่ทรัพยากรหลักจะถูกปิดตัวลง

การจำลองคลังสต็อกเนื้อสัตว์ในหน่วยความจำสำหรับการทดสอบคำสั่งซื้อ:

```typescript filename="src/services/inventory-database.spec.ts"
interface ButcherInventoryRecord {
  sku: string;
  weightAvailableKg: number;
}

class MockButcherDatabase {
  private records = new Map<string, ButcherInventoryRecord>();
  public isConnected = false;

  async connect(): Promise<void> {
    this.isConnected = true;
  }

  async disconnect(): Promise<void> {
    this.isConnected = false;
    this.records.clear();
  }

  async seed(data: ButcherInventoryRecord[]): Promise<void> {
    this.records.clear();
    for (const item of data) {
      this.records.set(item.sku, { ...item });
    }
  }

  async findBySku(sku: string): Promise<ButcherInventoryRecord | null> {
    const item = this.records.get(sku);
    return item ? { ...item } : null;
  }

  async deduct(sku: string, kg: number): Promise<void> {
    const item = this.records.get(sku);
    if (!item || item.weightAvailableKg < kg) {
      throw new Error('Stock unavailable');
    }
    item.weightAvailableKg -= kg;
  }
}

describe('ButcherInventoryManager - Lifecycle Isolation', () => {
  let db: MockButcherDatabase;

  // 1. เชื่อมต่อระบบฐานข้อมูลเพียงครั้งเดียวต่อไฟล์
  beforeAll(async () => {
    db = new MockButcherDatabase();
    await db.connect();
  });

  // 4. ตัดการเชื่อมต่อเมื่อรันครบทุกเคส ป้องกัน Jest ค้าง (Zombie Worker)
  afterAll(async () => {
    await db.disconnect();
  });

  // 2. เติมข้อมูลเริ่มต้น (Seed Fresh Fixtures) ใหม่ทุกครั้งก่อนเริ่มแต่ละเคสทดสอบ

      { sku: 'DRY-AGED-T-BONE', weightAvailableKg: 15.0 },
      { sku: 'A5-WAGYU-PICANHA', weightAvailableKg: 8.0 },

  });

  // 3. เคลียร์ Mock Functions ทั้งหมด ป้องกันการนับจำนวน Call ตกค้าง
  afterEach(() => {
    jest.clearAllMocks();
```

```typescript filename="src/jest.spec.ts"
  const sharedOrder = { orderId: 'ORD-01', totalAmount: 1000, items: [] };

    // ผลลัพธ์ขึ้นอยู่กับลำดับการรันเทสต์ (Order-dependent Flaky Test)
    expect(sharedOrder.totalAmount).toBe(900); // Expected 900, Received 720
  });
});
```

#### ✅ สิ่งที่ถูก: คืนค่าใหม่ (Re-instantiate) ใน `beforeEach` เสมอ
```typescript filename="src/jest.spec.ts"
describe('MeatOrderService', () => {
  let order: { orderId: string; totalAmount: number; items: string[] };

  beforeEach(() => {

    order.totalAmount -= 200;

```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **`beforeAll` / `afterAll`:** ควรใช้เฉพาะงานที่มีต้นทุนสูง (Expensive Operations) และไม่เปลี่ยน State เช่น การสตาร์ท Testcontainer, การต่อ Redis In-Memory หรือการสร้าง Schema
- **`beforeEach` / `afterEach`:** ควรใช้กับทุกสิ่งที่เก็บสถานะชั่วคราว (Stateful Operations), การ Seed ข้อมูล, การรีเซ็ต Mock Spies, และการเคลียร์ Local Storage

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: เหตุใดการทดสอบที่ผ่านเมื่อรันเดี่ยวๆ (`jest path/to/file.spec.ts`) แต่กลับล้มเหลวเมื่อรันรวมทั้งโปรเจกต์ (`jest`) จึงมักมีสาเหตุมาจาก Lifecycle Hooks?**
  - *แนวคำตอบ:* ปัญหานี้เรียกว่า **Test Pollution** หรือ **State Leakage** เกิดขึ้นจากการที่เทสต์หนึ่งไปแก้ไข Global State (เช่น `process.env`, Singleton In-Memory Cache, หรือตารางในฐานข้อมูลทดสอบ) แล้วลืมคืนค่าเดิมใน `afterEach` เมื่อรันไฟล์เดี่ยวๆ เคสอาจเรียงลำดับถูกจึงผ่าน แต่เมื่อรันพร้อมกันหลายร้อยไฟล์ ตัวแปรที่ค้างอยู่จะส่งผลกระทบต่อชุดทดสอบอื่นที่รันตามมา วิธีแก้คือต้องบังคับใช้ `afterEach` ในการ Restore สภาพแวดล้อม และเปิดใช้งาน `clearMocks: true` ใน `jest.config.ts`

## 4. การทดสอบ Async Code (Promises, Async/Await, Rejections)

### แนวคิด (Concept)
ในระบบ **Smart Butcher Marketplace** การดำเนินการหลายอย่างเกิดขึ้นแบบ Asynchronous:
- การส่งคำสั่งตัดเนื้อไปยังหน้าจอเขียงช่างแล่เนื้อ (Message Queue)
- การยืนยันสลิปโอนเงินและการตัดยอดบัตรเครดิตผ่าน Payment Gateway
- การคำนวณอายุและน้ำหนักเนื้อดรายเอจที่ต้องดึงประวัติจากฐานข้อมูล

ในการเขียนเทสต์ หากเราไม่ "รอ" (await) ให้คำสัญญา (Promise) ทำงานเสร็จสิ้นก่อน ตัว Test Runner จะด่วนสรุปผลลัพธ์ว่าเทสต์ผ่านไปแล้ว ส่งผลให้เกิด **False Positive** (เทสต์เขียว ทั้งที่ระบบมีบั๊กซ่อนอยู่) หรือเกิด **Unhandled Promise Rejection** กลางอากาศหลังจากเทสต์จบไปแล้ว

### หลักการเบื้องหลัง (Under the Hood)
Jest ตระหนักถึง Promise เมื่อฟังก์ชันใน `it` หรือ `test` มีการ `return` ค่า Promise หรือใช้คีย์เวิร์ด `async`:
1. **Async/Await Engine:** เมื่อฟังก์ชันถูกประกาศเป็น `async () => { ... }` ตัว JavaScript V8 Engine จะคืนค่าเป็น Promise อัตโนมัติ Jest จะหยุดรอให้ Promise ดังกล่าว Settled (Resolved หรือ Rejected) จึงจะปิดเคสการทดสอบ
2. **`resolves` และ `rejects` Unwrap Matchers:** Jest มีตัวช่วยแกะกล่อง Promise ในตัว:
   - `await expect(promise).resolves.toBe(expected)`
   - `await expect(promise).rejects.toThrow(ExpectedError)`
   เบื้องหลังคือ Jest จะผูก `.then()` และ `.catch()` เข้ากับ Promise ดังกล่าว แล้วนำค่าที่คลี่ออกมาได้ส่งต่อเข้าสู่กระบวนการ Assert ตามปกติ
3. **เลิกใช้ `done` Callback:** ในอดีต Jest รองรับการส่งพารามิเตอร์ `(done) => { ... done(); }` แต่ในโมเดิร์น TypeScript รูปแบบนี้ถือเป็น Anti-pattern เพราะเสี่ยงต่อการลืมเรียก `done()` ทำให้เทสต์ติด Timeout และไม่รองรับ Type Safety เท่ากับ `async/await`

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การทดสอบ Async Order Processing ที่คืนค่า Promise สำเร็จ
การสร้างคำสั่งซื้อเนื้อและบันทึกลงระบบคลาวด์:

```typescript filename="src/services/async-order.service.spec.ts"
export interface CreateOrderDto {
  userId: string;
  items: Array<{ productId: string; cutType: string; quantity: number }>;
}

export interface OrderConfirmation {
  orderId: string;
  orderNo: string;
  status: 'PENDING' | 'CONFIRMED';
  estimatedPreparationMinutes: number;
}

export class OrderProcessingService {
  async processCustomerOrder(dto: CreateOrderDto): Promise<OrderConfirmation> {
    if (dto.items.length === 0) {
      throw new Error('Order must contain at least one meat item');
    }

    // จำลอง I/O Network Delay ในการบันทึกลงระบบ
    await new Promise((resolve) => setTimeout(resolve, 50));

    return {
      orderId: 'ord-uuid-2026',
      orderNo: 'ORD-2026-8899',
      status: 'CONFIRMED',
      estimatedPreparationMinutes: 45, // เวลาเตรียมแล่เนื้อและแพ็กสุญญากาศ
    };
  }
}

describe('OrderProcessingService - Async Resolves', () => {
  const service = new OrderProcessingService();

  // แบบที่ 1: มาตรฐานที่ดีที่สุด (Async / Await ตรงไปตรงมา)
  it('should successfully process and confirm order using direct async/await', async () => {
    const dto: CreateOrderDto = {
      userId: 'usr-customer-01',
      items: [{ productId: 'prd-angus-ribeye', cutType: 'RIBEYE', quantity: 2 }],
    };

    const confirmation = await service.processCustomerOrder(dto);

    expect(confirmation.status).toBe('CONFIRMED');
    expect(confirmation.estimatedPreparationMinutes).toBe(45);
    expect(confirmation.orderNo).toMatch(/^ORD-2026-\d{4}$/);
  });

  // แบบที่ 2: ใช้ Jest .resolves Matcher Unwrap
  it('should resolve order confirmation using Jest unwrap matcher', async () => {
    const dto: CreateOrderDto = {
      userId: 'usr-customer-02',
      items: [{ productId: 'prd-wagyu-striploin', cutType: 'STRIPLOIN', quantity: 1 }],
    };

    await expect(service.processCustomerOrder(dto)).resolves.toMatchObject({
      status: 'CONFIRMED',
      estimatedPreparationMinutes: 45,
    });
  });
});
```

#### ตัวอย่างที่ 2: การทดสอบ Rejection เมื่อชำระเงินไม่สำเร็จ
การดักจับข้อผิดพลาดเมื่อบัตรเครดิตถูกปฏิเสธ หรือวงเงินไม่เพียงพอในการชำระค่าเนื้อพรีเมียม:

```typescript filename="src/services/payment-rejection.spec.ts"
export class PaymentDeclinedException extends Error {
  constructor(public readonly reasonCode: string, message: string) {
    super(message);
    this.name = 'PaymentDeclinedException';
  }
}

export interface PaymentRequest {
  orderId: string;
  amount: number;
  cardNumber: string;
}

export class PaymentGatewayService {
  async chargeCreditCard(req: PaymentRequest): Promise<{ transactionId: string }> {
    await new Promise((resolve) => setTimeout(resolve, 30));

    // จำลองบัตรที่มียอดเงินไม่พอ
    if (req.cardNumber.endsWith('0000')) {
      throw new PaymentDeclinedException(
        'INSUFFICIENT_FUNDS',
        'Your credit card has insufficient funds for this luxury meat purchase'
      );
    }

    return { transactionId: 'txn-mock-9988' };
  }
}

describe('PaymentGatewayService - Async Rejections', () => {
  const paymentService = new PaymentGatewayService();

  it('should cleanly catch rejection using await expect().rejects.toThrow()', async () => {
    const failingRequest: PaymentRequest = {
      orderId: 'ord-099',
      amount: 4500,
      cardNumber: '4111-2222-3333-0000', // บัตรวงเงินไม่พอ
    };

    // ต้องมี await ด้านหน้า expect เสมอเพื่อรอให้ Promise Reject
    await expect(paymentService.chargeCreditCard(failingRequest)).rejects.toThrow(
      PaymentDeclinedException
    );

    // ตรวจสอบข้อความ Error Message ใน Rejection
    await expect(paymentService.chargeCreditCard(failingRequest)).rejects.toThrow(
      'Your credit card has insufficient funds for this luxury meat purchase'
    );
  });

  it('should inspect custom error properties through try/catch assertion pattern', async () => {
    const failingRequest: PaymentRequest = {
      orderId: 'ord-100',
      amount: 8900,
      cardNumber: '4111-2222-3333-0000',
    };

    // บังคับว่าต้องมี Assertion ทำงานอย่างน้อย 2 จุด (ป้องกันกรณีลืมโยน Error แล้วเทสต์ผ่านลอยๆ)
    expect.assertions(2);

    try {
      await paymentService.chargeCreditCard(failingRequest);
    } catch (err) {
      const error = err as PaymentDeclinedException;
      expect(error.name).toBe('PaymentDeclinedException');
      expect(error.reasonCode).toBe('INSUFFICIENT_FUNDS');
    }
  });
});
```

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: ลืมใส่ `await` หน้า `expect(...).rejects.toThrow()`
```typescript filename="src/jest.spec.ts"
it('should reject invalid card', () => {
  // อันตรายระดับวิกฤต: ฟังก์ชันใน it ไม่ได้เป็น async และไม่มี await
  // บรรทัดนี้จะส่งคืน Promise ที่ลอยค้างอยู่ เทสต์นี้จะ "ผ่านฉลุยเสมอ" 
  // แม้ฟังก์ชันข้างในจะไม่ได้โยน Error ออกมาก็ตาม! (Silent False Positive)
  expect(paymentService.chargeCreditCard(badReq)).rejects.toThrow();
});
```

#### ✅ สิ่งที่ถูก: เติม `async` ที่ Callback และใส่ `await` หน้า `expect` เสมอ
```typescript filename="src/jest.spec.ts"
it('should reject invalid card', async () => {
  // ปลอดภัยและถูกต้อง 100%: Jest จะหยุดรอให้เกิด Rejection จริง
  await expect(paymentService.chargeCreditCard(badReq)).rejects.toThrow();
});
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `expect.assertions(n)`:** เมื่อเขียนเทสต์แบบ `try/catch` หรือมีเงื่อนไข Callback เพื่อรับประกันว่าจะไม่มีกรณีที่โค้ดหลุดข้ามบล็อก `catch` ไปโดยที่ไม่มีการตรวจสอบผลลัพธ์
- **ไม่ควรใช้ `done` Callback:** ในโปรเจกต์ใหม่ทุกกรณี ให้แปลงเป็น Promise และใช้ `async/await` แทนทั้งหมด

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: อะไรคืออันตรายของการเขียน `expect(async () => await service.pay()).rejects.toThrow()` และไวยากรณ์ที่ถูกต้องคืออะไร?**
  - *แนวคำตอบ:* การส่ง `async () => ...` เข้า `expect()` จะทำให้ค่าที่ `expect()` ได้รับเป็นฟังก์ชัน (Function Reference) ไม่ใช่ Promise ตัว matcher `.rejects` ของ Jest ต้องการ **Promise Object** โดยตรง ดังนั้นเมื่อเราครอบด้วยฟังก์ชัน ตัว Jest จะประเมินผิดพลาด ไวยากรณ์ที่ถูกต้องคือต้องส่ง Promise เข้าไปตรงๆ: `await expect(service.pay()).rejects.toThrow()`
- **Q2: หากในระบบมี Async Operation ที่ค้างอยู่ (เช่น Unhandled Background Job) แล้วทำให้เกิดข้อความ "Cannot log after tests are done" แก้ไขอย่างไร?**
  - *แนวคำตอบ:* ข้อความนี้เกิดขึ้นเมื่อมีโค้ด Asynchronous (เช่น Background Task หรือ Logging) ยังทำงานอยู่หลังจากที่ฟังก์ชันใน `it()` จบไปแล้ว และ Jest ได้ทำลาย Environment ของ Worker ทิ้งไปแล้ว การแก้ปัญหาคือต้องตามหา Background Task นั้น แล้วทำให้ระบบรอจนกระทั่ง Task นั้นเสร็จสิ้นอย่างสมบูรณ์ (`await task`) หรือทำการ Mock Background Service นั้นเพื่อไม่ให้มีการเตะ Event หลุดออกไปนอก Lifecycle ของการทดสอบ

## 5. Mock Functions (jest.fn และ jest.spyOn)

### แนวคิด (Concept)
การจำลองการทำงานในร้านขายเนื้อ **Smart Butcher Marketplace**:
- **`jest.fn()` (หุ่นยนต์จำลองสร้างใหม่)**: เปรียบเหมือน "การจ้างผู้ช่วยชั่วคราวขึ้นมาทำงานเฉพาะกิจ" ฟังก์ชันนี้ไม่มีตัวตนอยู่จริงในระบบมาก่อน เราสร้างขึ้นมาเพื่อดูว่ามีคนเรียกใช้งานเขาหรือไม่ เรียกด้วยพารามิเตอร์อะไร และสั่งให้เขาตอบคำพูดตามสคริปต์ที่เตรียมไว้ (Stubbing)
- **`jest.spyOn()` (สายลับติดกล้องวงจรปิด)**: เปรียบเหมือน "การติดกล้องเฝ้าสังเกตการณ์พนักงานตัวจริงในร้าน" เมธอดของคลาสนั้นยังมีตัวตนอยู่จริงและทำงานได้ตามปกติ แต่เราส่งสายลับเข้าไปประกบเพื่อแอบจดบันทึกว่าพนักงานคนนั้นถูกเรียกใช้งานกี่ครั้ง และเมื่อทดสอบเสร็จ เราสามารถถอดกล้องวงจรปิดออก (`mockRestore()`) เพื่อคืนสภาพการทำงานของพนักงานให้กลับมาเป็นปกติได้ 100%

### หลักการเบื้องหลัง (Under the Hood)
ฟังก์ชันจำลองที่สร้างจาก Jest จะมี Property พิเศษชื่อ `.mock` คอยบันทึกสถานะทั้งหมด:

```text filename="docs/testing/jest.txt"
┌─────────────────────────────────────────────────────────────────────────────┐
│                          JEST MOCK INSTANCE INTERNALS                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  const mockFn = jest.fn();                                                  │
│                                                                             │
│  mockFn('RIBEYE', 2.5);                                                     │
│                                                                             │
│  mockFn.mock = {                                                            │
│    calls: [                                                                 │
│      ['RIBEYE', 2.5]       // ➔ เก็บลำดับ Arguments ของการเรียกแต่ละครั้ง   │
│    ],                                                                       │
│    results: [                                                               │
│      { type: 'return', value: 750 } // ➔ ผลลัพธ์หรือ Exception ที่ส่งกลับ   │
│    ],                                                                       │
│    instances: [ thisContext ],                                              │
│    contexts: [ thisContext ],                                               │
│    lastCall: ['RIBEYE', 2.5]                                                │
│  };                                                                         │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **`jest.fn(implementation?)`**: สร้าง Standalone Mock Function มีประโยชน์มากในการส่งเป็น Callback พารามิเตอร์ หรือใช้ทำ Mock Dependency Injection
2. **`jest.spyOn(object, methodName)`**: ทำงานโดยการสำเนา Pointer ของฟังก์ชันดั้งเดิมเก็บไว้ในตัว แล้วแทนที่ Property บน Object นั้นด้วย Mock Function ชั่วคราว เมื่อเรียก `spy.mockRestore()` ตัว Jest จะนำ Original Pointer กลับมาทับที่เดิม คืนค่าความบริสุทธิ์ของ Object
3. **การล้างสถานะ Mock (Cleaning APIs)**:
   - `mockFn.mockClear()` หรือ `jest.clearAllMocks()`: ล้างเฉพาะประวัติการเรียก (`calls` และ `results` กลายเป็นว่างเปล่า) แต่ยังคง Mock Implementation เดิมไว้
   - `mockFn.mockReset()` หรือ `jest.resetAllMocks()`: ล้างประวัติการเรียก **พร้อมทั้งลบล้าง Implementation ทิ้ง** กลายเป็นฟังก์ชันว่างๆ ที่ return `undefined`
   - `mockFn.mockRestore()` หรือ `jest.restoreAllMocks()`: ใช้ได้กับ `jest.spyOn` เท่านั้น จะยกเลิกการ Mock ทั้งหมดและกู้คืน Original Function ดั้งเดิมกลับมา

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: ใช้ `mockImplementation` กับ `jest.spyOn()` แต่ลืมสั่ง `restoreAllMocks()`
```typescript filename="src/jest.spec.ts"
it('test 1', () => {
  jest.spyOn(service, 'calculatePrice').mockReturnValue(100);
  // ... เทสต์แรกผ่าน แต่ spy ยังคงติดอยู่บน service!
});

it('test 2', () => {
  // พังทันที: เทสต์ที่สองต้องการทดสอบ Real Implementation 
  // แต่ค่ากลับถูก Stub เป็น 100 ตลอดเวลาจากเทสต์แรก!
  const price = service.calculatePrice(item);
  expect(price).toBe(250); // ได้ 100 เพราะ Mock ค้าง
});
```

#### ✅ สิ่งที่ถูก: สั่ง `jest.restoreAllMocks()` ใน `afterEach` เสมอ
```typescript filename="src/jest.spec.ts"
afterEach(() => {
  jest.restoreAllMocks(); // กู้คืนฟังก์ชันดั้งเดิมทุกลำดับอย่างหมดจด
});
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `jest.fn()`:** เมื่อสร้าง Mock Callback, Event Listener, หรือ Dependency ที่ฉีดเข้ามาผ่าน Constructor Interface
- **ควรใช้ `jest.spyOn()`:** เมื่อต้องการสังเกตหรือแทรกแซงเมธอดของ Class Instance, Object หรือ Library ที่มีอยู่แล้ว และต้องการความมั่นใจว่าจะสามารถถอดกล้องส่องออกได้สมบูรณ์

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: อะไรคือความแตกต่างที่แท้จริงระหว่าง `mockClear()`, `mockReset()` และ `mockRestore()`?**
  - *แนวคำตอบ:*
    1. **`mockClear()`**: ล้างประวัติการเรียกทั้งหมด (`calls`, `instances`, `results`) แต่ยังคง Mock Logic เดิมที่ตั้งไว้ เช่น `mockReturnValue(100)` จะยังคงตอบ 100 เหมือนเดิม
    2. **`mockReset()`**: ล้างทั้งประวัติการเรียก และ**ลบล้าง Mock Logic ทิ้ง** ฟังก์ชันจะกลายเป็น Empty Function ที่คืนค่า `undefined`
    3. **`mockRestore()`**: ทำงานเฉพาะกับ Mock ที่สร้างจาก `jest.spyOn` เท่านั้น โดยจะถอด Mock Wrapper ออก และนำฟังก์ชันดั้งเดิม (Original Implementation) ที่มีอยู่จริงก่อนถูก Spy กลับคืนมา
- **Q2: `mockReturnValueOnce()` มีประโยชน์อย่างไรในการจำลอง Transient Network Faults?**
  - *แนวคำตอบ:* ใช้จำลองสถานการณ์ที่การเรียกครั้งแรกเกิดข้อผิดพลาด (Transient Error) แต่การเรียกครั้งถัดไปทำงานสำเร็จ (Retry Mechanism) เช่น `spy.mockRejectedValueOnce(new TimeoutError()).mockResolvedValueOnce(successResponse)` ช่วยให้เราสามารถทดสอบตรรกะ Circuit Breaker หรือ Exponential Backoff ได้อย่างแม่นยำในการทดสอบเพียงเคสเดียว

## 6. Mock Modules (jest.mock) และ Dependency Interception

### แนวคิด (Concept)
เมื่อร้าน **Smart Butcher Marketplace** จำเป็นต้องส่ง SMS แจ้งลูกค้าว่า "เนื้อดรายเอจของท่านตัดแต่งเสร็จแล้วและกำลังจัดส่ง":
- ในระบบจริง โค้ดจะเรียกใช้โมดูลบุคคลที่สาม (Third-party Modules) เช่น `twilio`, `axios` หรือ `nodemailer` เพื่อส่งข้อมูลผ่านระบบเครือข่ายจริง
- ใน Unit Test เราไม่ต้องการเสียค่าส่ง SMS จริง ไม่ต้องการพึ่งพาอินเทอร์เน็ต และต้องการให้เทสต์ทำงานได้เร็วระดับมิลลิวินาที
- **`jest.mock('module-name')`**: เปรียบเหมือน "การตัดสายเคเบิลอินเทอร์เน็ตที่เชื่อมออกไปข้างนอก แล้วเสียบกล่องจำลองสัญญาณเสมือนจริงเข้าไปแทนที่" ระบบภายในจะคิดว่ามันกำลังคุยกับ `axios` ตัวจริง แต่แท้จริงแล้วคือ Mock Module ของ Jest ที่พร้อมให้เราตรวจสอบข้อมูลที่ส่งออกไป

### หลักการเบื้องหลัง (Under the Hood)
กลไกที่สำคัญที่สุดและสร้างความสับสนให้ผู้เริ่มต้นมากที่สุดคือ **Babel / ts-jest Hoisting**:

```text filename="docs/testing/jest.txt"
┌─────────────────────────────────────────────────────────────────────────────┐
│                          JEST HOISTING MECHANISM                            │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  [ สิ่งที่โปรแกรมเมอร์เขียนในโค้ด ]                                         │
│  ─────────────────────────────────                                          │
│  import axios from 'axios';                                                 │
│  const mockPort = 8080;                                                     │
│  jest.mock('axios', () => ({ post: jest.fn() }));                           │
│                                                                             │
│                                      ▼                                      │
│  [ สิ่งที่ Jest Transpiler แปลงและนำไปรันจริง (Hoisted to Top) ]            │
│  ─────────────────────────────────────────────────────────────              │
│  // 1. Jest จะยก jest.mock() ขึ้นไปบนสุดของไฟล์ ก่อนคำสั่ง import ใดๆ เสมอ  │
│  jest.mock('axios', () => ({ post: jest.fn() }));                           │
│                                                                             │
│  // 2. คำสั่ง Import จะถูกแปลงและโหลดหลังจาก Mock ถูกแทนที่ใน Module Cache    │
│  import axios from 'axios';                                                 │
│  const mockPort = 8080; // บรรทัดนี้จะถูกประกาศทีหลัง!                      │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Hoisting Rule:** Jest จะดึงคำสั่ง `jest.mock()` ไปทำงานก่อนคำสั่ง `import` อื่นๆ ทั้งหมด เพื่อดักจับ Module ตั้งแต่จังหวะที่ Node.js ทำการ `require()` ครั้งแรก
2. **OutOfScope Variable Restriction:** ด้วยเหตุที่ถูก Hoist ทำให้ฟังก์ชัน Factory ใน `jest.mock()` ไม่สามารถเข้าถึงตัวแปรภายนอกได้ เว้นแต่ตัวแปรนั้นจะขึ้นต้นด้วยคำว่า `mock` (เช่น `const mockApiKey = '...'`) ซึ่ง Jest Transpiler จะยกเว้นให้ถูก Hoist ตามขึ้นไปด้วย
3. **Manual Mocks (`__mocks__` directory):** Jest รองรับการสร้างโฟลเดอร์ `__mocks__` ไว้ข้างโมดูลที่ต้องการจำลอง หากเราเรียก `jest.mock('./sms.service')` โดยไม่ระบุ Factory function ตัว Jest จะวิ่งไปหาไฟล์จำลองในโฟลเดอร์ `__mocks__/sms.service.ts` มาใช้งานอัตโนมัติ

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: อ้างอิงตัวแปร Scope ทั่วไปภายใน Factory ของ `jest.mock()`
```typescript filename="src/jest.spec.ts"
const defaultVipDiscount = 15; // ตัวแปรทั่วไป

jest.mock('./discount.service', () => {
  // พังทันที: Jest Transpiler จะโยน ReferenceError ออกมา
  // "The module factory of `jest.mock()` is not allowed to reference any out-of-scope variables"
  return {
    calculateVipDiscount: () => defaultVipDiscount,
  };
});
```

#### ✅ สิ่งที่ถูก: ประกาศค่าข้างใน Factory หรือตั้งชื่อตัวแปรนำหน้าด้วย `mock`
```typescript filename="src/jest.spec.ts"
// อนุญาต: ตัวแปรที่ขึ้นต้นด้วย 'mock' Jest จะยอมให้ถูก Hoist พร้อมกับ Factory
const mockVipDiscount = 15;

jest.mock('./discount.service', () => {
  return {
    calculateVipDiscount: () => mockVipDiscount,
  };
});
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้ `jest.mock`:** กับ External I/O Libraries (Stripe, Twilio, AWS S3, Axios, Prisma/TypeORM) เพื่อหลีกเลี่ยง Side Effects บนเครือข่ายจริง
- **ไม่ควรใช้ `jest.mock`:** กับ Pure Domain Utilities หรือ Entity Classes ภายในระบบ เพราะจะทำให้สูญเสียความมั่นใจในการทดสอบ (Over-mocking) และทำให้เทสต์กลายเป็นเพียงการตรวจเช็กกระดาษคำตอบเปล่าๆ

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: เหตุใด Jest จึงต้องทำ Hoisting คำสั่ง `jest.mock()` และกลไกนี้กระทบกับโค้ดอย่างไร?**
  - *แนวคำตอบ:* ใน Node.js เมื่อไฟล์ถูกโหลด คำสั่ง `import` หรือ `require()` จะทำงานทันทีและเก็บผลลัพธ์ไว้ใน Module Cache ของ Node.js หาก Jest ไม่ทำการ Hoist คำสั่ง `jest.mock()` ขึ้นไปไว้บนสุดก่อน โมดูลจริงจะถูกคอมไพล์และแคชไว้ในหน่วยความจำก่อนที่ Mock จะถูกกำหนด ทำให้การดักฟังโมดูลล้มเหลว การ Hoist ทำให้ Jest สามารถแทรก Mock Implementation เข้าไปใน Module Cache ได้ก่อนที่โค้ดจริงจะถูกเรียกใช้
- **Q2: หากต้องการทำ Mock โมดูลที่สร้างขึ้นจาก Third-party ที่ไม่มี ESM Export (เป็น CommonJS) ใน TypeScript มีเทคนิคใดที่ช่วยให้ Type Inference ยังคงถูกต้อง?**
  - *แนวคำตอบ:* ใช้ `jest.mocked()` Utility Function ที่มาพร้อมกับ `ts-jest` หรือ Jest 29+:
    `const mockedLib = jest.mocked(myLibrary, { shallow: false });`
    ตัวช่วยนี้จะทำ Deep Mock Typing ให้อัตโนมัติ ทำให้เราเรียกใช้ `.mockResolvedValue` หรือตรวจสอบ `.mock.calls` ได้โดยไม่ต้องใช้ Type Assertion แบบ `as unknown as jest.Mock` ให้สูญเสีย Type Safety

## 7. Fake Timers และการควบคุมเวลา (jest.useFakeTimers)

### แนวคิด (Concept)
ในร้าน **Smart Butcher Marketplace** ปัจจัยเรื่อง "เวลา" มีความสำคัญอย่างยิ่ง:
- กระบวนการบ่มเนื้อ Dry-Aging ต้องใช้เวลา 21 วัน, 30 วัน, หรือ 45 วัน ในการควบคุมอุณหภูมิและความชื้น
- คำสั่งซื้อเนื้อสดจะมีอายุการจองสต็อก (Payment Reservation Window) ภายใน 15 นาที หากลูกค้าไม่ชำระเงิน ระบบต้องปล่อยสต็อกคืนหน้าร้าน
- ระบบ Cron Job ตรวจสอบเนื้อหมดอายุในห้องเย็นทุกๆ เที่ยงคืน

หากเราต้องทดสอบโค้ดเหล่านี้ในโลกจริง เราไม่สามารถสั่งให้เทสต์หลับ (`sleep`) รอ 15 นาที หรือรอ 45 วันได้ **Fake Timers** เปรียบเหมือน "นาฬิกาวิเศษข้ามมิติเวลา" ที่อนุญาตให้เราหมุนเข็มเวลาไปข้างหน้า 45 วันได้ภายในเสี้ยววินาทีเดียว!

### หลักการเบื้องหลัง (Under the Hood)
Jest 27+ ขับเคลื่อนระบบ Fake Timers ด้วยแพ็กเกจระดับโลก `@sinonjs/fake-timers`:

```text filename="docs/testing/jest.txt"

│                       MODERN FAKE TIMERS ARCHITECTURE                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │

│  [ คืนระบบเวลาจริงกลับสู่ Node.js Runtime ]                                  │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**ฟังก์ชันควบคุมเวลาที่สำคัญ:**
1. `jest.useFakeTimers()`: เริ่มต้นการสลับมาใช้นาฬิกาจำลอง
2. `jest.setSystemTime(date)`: ตั้งเวลาปัจจุบันของระบบ (`new Date()`, `Date.now()`) ไปยังจุดเวลาที่กำหนด
3. `jest.advanceTimersByTime(ms)`: เร่งเวลาในระบบไปข้างหน้าตามจำนวนมิลลิวินาทีที่ระบุ
4. `jest.runAllTimers()`: สั่งรันทุก Timer ที่กำลังรออยู่ในคิวจนหมด (ระวัง Infinite Loop หากมี `setInterval`)
5. `jest.runOnlyPendingTimers()`: รันเฉพาะ Timer ที่ถูกจองไว้ ณ วินาทีนี้เท่านั้น ไม่รวม Timer ใหม่ที่อาจถูกสั่งต่อเนี่อง
6. `jest.useRealTimers()`: สลับคืนสู่นาฬิกาจริงของระบบปฏิบัติการ

#### ตัวอย่างที่ 1: การทดสอบระบบยกเลิกออเดอร์เนื้อและคืนสต็อกอัตโนมัติภายใน 15 นาที

```typescript filename="src/services/stock-reservation-timer.spec.ts"
export class StockReservationManager {
  private timers = new Map<string, NodeJS.Timeout>();

  constructor(private onTimeoutCallback: (orderId: string) => void) {}

  public scheduleReservationExpiry(orderId: string, timeoutMinutes = 15): void {
    const timeoutMs = timeoutMinutes * 60 * 1000;

    const timer = setTimeout(() => {
      this.onTimeoutCallback(orderId);
      this.timers.delete(orderId);
    }, timeoutMs);

    this.timers.set(orderId, timer);
  }

  public cancelReservation(orderId: string): void {
    const timer = this.timers.get(orderId);
    if (timer) {
      clearTimeout(timer);
      this.timers.delete(orderId);
    }
  }
}

describe('StockReservationManager - Fake Timers (15-Minute Expiry)', () => {
  let callbackMock: jest.Mock;
  let manager: StockReservationManager;

  beforeEach(() => {
    // 1. เปิดใช้นาฬิกาจำลอง
    jest.useFakeTimers();
    callbackMock = jest.fn();
    manager = new StockReservationManager(callbackMock);
  });

  afterEach(() => {
    // 2. ล้าง Timer และคืนสู่นาฬิกาจริงเสมอ
    jest.clearAllTimers();
    jest.useRealTimers();
  });

  it('should not release meat stock before 15 minutes have elapsed', () => {
    manager.scheduleReservationExpiry('ORD-T-BONE-101', 15);

    // เร่งเวลาไป 14 นาที 59 วินาที
    jest.advanceTimersByTime(14 * 60 * 1000 + 59 * 1000);

    expect(callbackMock).not.toHaveBeenCalled();
  });

  it('should trigger stock release callback precisely when 15 minutes pass', () => {
    manager.scheduleReservationExpiry('ORD-T-BONE-101', 15);

    // เร่งเวลาไปครบ 15 นาทีพอดี
    jest.advanceTimersByTime(15 * 60 * 1000);

    expect(callbackMock).toHaveBeenCalledTimes(1);
    expect(callbackMock).toHaveBeenCalledWith('ORD-T-BONE-101');
  });

  it('should abort timer if customer pays and reservation is cancelled before timeout', () => {
    manager.scheduleReservationExpiry('ORD-PAID-EARLY', 15);

    // ลูกค้าโอนเงินตอนผ่านไป 5 นาที จึงสั่งยกเลิก Timer
    jest.advanceTimersByTime(5 * 60 * 1000);
    manager.cancelReservation('ORD-PAID-EARLY');

    // เร่งเวลาต่อจนเลย 15 นาที
    jest.advanceTimersByTime(20 * 60 * 1000);

    // ต้องไม่มีการเรียก Callback คืนสต็อก
    expect(callbackMock).not.toHaveBeenCalled();
  });
});
```

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: เรียก `jest.runAllTimers()` กับโค้ดที่มี `setInterval` รันต่อเนื่อง
```typescript filename="src/jest.spec.ts"
it('test cron polling', () => {
  jest.useFakeTimers();
  setInterval(() => pollVaultTemp(), 1000); // ทำงานวนลูปไม่สิ้นสุด

  // หายนะ: Jest จะพยายามรัน Interval ต่อไปเรื่อยๆ จนเต็มหน่วยความจำ
  // และเทสต์จะค้างแบบ Infinite Loop (Process Out of Memory)
  jest.runAllTimers(); 
});
```

#### ✅ สิ่งที่ถูก: ใช้ `advanceTimersByTime()` หรือกำหนดจำนวนรอบที่ชัดเจน
```typescript filename="src/jest.spec.ts"
it('test cron polling', () => {
  jest.useFakeTimers();
  setInterval(() => pollVaultTemp(), 1000);

  // ควบคุมได้แม่นยำ: ก้าวไปข้างหน้า 5 วินาที เพื่อทดสอบ 5 รอบเท่านั้น
  jest.advanceTimersByTime(5000);
  expect(pollVaultTemp).toHaveBeenCalledTimes(5);
});
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Fake Timers:** เมื่อทดสอบ Logic ที่เกี่ยวข้องกับ `setTimeout`, `setInterval`, Debounce/Throttle ฟังก์ชันค้นหารายการเนื้อ, ตรวจสอบอายุเนื้อดรายเอจ, และการทดสอบ Expire Token
- **ไม่ควรใช้ Fake Timers:** เมื่อโค้ดเป็นการรอคำตอบทาง I/O จริง (เช่น รอ Real Database Query หรือ Real HTTP) การใช้ Fake Timers จะไม่ช่วยให้ I/O ทำงานเร็วขึ้น และอาจทำให้ระบบ Network Client เกิดข้อผิดพลาด

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: อะไรคือความแตกต่างระหว่าง Modern Fake Timers (`@sinonjs/fake-timers`) กับ Legacy Fake Timers ใน Jest?**
  - *แนวคำตอบ:* ใน Jest 26 ลงไป ระบบ Legacy Fake Timers จะ Mock เฉพาะฟังก์ชันจับเวลาพื้นฐาน เช่น `setTimeout` และ `setInterval` แต่ไม่แตะต้อง `new Date()`, `Date.now()`, หรือ `process.hrtime` ทำให้การทดสอบโค้ดที่สร้างเวลาปัจจุบันต้องใช้การ Mock Constructor แบบแมนนวล แต่ใน Jest 27+ เป็น Modern Fake Timers แบบเบ็ดเสร็จ ซึ่งทำการ Patch ลึกถึงระดับแกนเวลาของระบบ ทำให้คำสั่ง `jest.setSystemTime(date)` สามารถควบคุมเวลาของ `new Date()` และ High-resolution timers ทั้งหมดได้อย่างแม่นยำ
- **Q2: หากในเทสต์มีทั้ง Fake Timers และ Promise Microtasks (เช่น `await Promise.resolve()`) เหตุใดการสั่ง `advanceTimersByTime` จึงอาจไม่เรียก Promise ทันที?**
  - *แนวคำตอบ:* เพราะ Node.js มีการแบ่งลำดับความสำคัญของ Event Loop ต่างกัน: Timers อยู่ใน **Macro-task Queue** ส่วน Promises อยู่ใน **Micro-task Queue** เมื่อเวลาใน Timer ถูกเร่ง Callback ของ Timer จะถูกหย่อนลงใน Macro-task Queue หากใน Callback นั้นมีการสร้าง Promise ซ้อนอยู่ เราอาจจำเป็นต้องคั่นด้วย `await Promise.resolve()` หรือ `jest.advanceTimersByTimeAsync()` ใน Jest 29.5+ เพื่อบังคับให้ Event Loop เคลียร์ Micro-tasks จนหมด

## 8. Snapshot Testing (เมื่อไหร่ควรใช้และเมื่อไหร่ไม่ควรใช้)

### แนวคิด (Concept)
หากเปรียบเทียบการตรวจสอบในร้าน **Smart Butcher Marketplace**:
- **Assertion ปกติ (`toBe`, `toEqual`)**: เปรียบเหมือน "ช่างตรวจสอบสเปก" เดินตรวจทีละจุด น้ำหนักตรงไหม ชนิดเนื้อตรงไหม
- **Snapshot Testing (`toMatchSnapshot`)**: เปรียบเหมือน "การถ่ายภาพสแกน 3 มิติของก้อนเนื้อทั้งชิ้นเก็บไว้ในอัลบั้ม" ในการทดสอบครั้งถัดไป ระบบจะหยิบภาพถ่ายเดิมมาทาบกับชิ้นเนื้อใหม่ หากรูปทรง รอยบาก หรือตำแหน่งไขมันผิดเพี้ยนไปแม้แต่มิลลิเมตรเดียว ตัวระบบจะส่งเสียงเตือนว่าชิ้นเนื้อมีการเปลี่ยนแปลง

Snapshot Testing ถูกออกแบบมาเพื่อตรวจสอบว่าข้อมูลโครงสร้างขนาดใหญ่ (เช่น เอกสารใบกำกับภาษีเต็มรูปแบบ, Response จาก GraphQL หรือ Complex DTOs) ไม่ถูกเปลี่ยนแปลงโดยไม่ตั้งใจ (Regression Guard)

### หลักการเบื้องหลัง (Under the Hood)
1. **ไฟล์จัดเก็บ Snapshot:** เมื่อรันเทสต์ครั้งแรก Jest จะแปลงข้อมูล (Serialization) เป็นข้อความ Text แล้วบันทึกลงในโฟลเดอร์ `__snapshots__/*.spec.ts.snap` ข้างๆ ไฟล์ทดสอบ
2. **การเปรียบเทียบในรอบถัดไป:** ทุกครั้งที่รันเทสต์ Jest จะ Serialize ค่า Output ใหม่ แล้วนำไปเปรียบเทียบ Diff บรรทัดต่อบรรทัดกับ Snapshot ในไฟล์ `.snap`
3. **Inline Snapshots (`toMatchInlineSnapshot`):** แทนที่จะแยกไฟล์ `.snap` Jest จะใช้ไลบรารีวิเคราะห์โค้ด (Prettier AST) เพื่อเขียนข้อความ Snapshot แทรกกลับเข้ามาในไฟล์ Source Code ของตัวเทสต์เองแบบอัตโนมัติ
4. **Asymmetric Property Matchers in Snapshot:** หากข้อมูลมีฟิลด์จำพวก Dynamic UUID หรือ Date Timestamp เราสามารถระบุรูปร่างข้อมูลเฉพาะฟิลด์นั้นใน Snapshot ได้ เพื่อไม่ให้เทสต์พังทุกรอบ

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การใช้ Snapshot ตรวจสอบใบสั่งตัดเนื้อดรายเอจระดับพรีเมียม (Master Cutting Slip)
การตรวจสอบโครงสร้าง DTO ใบสั่งงานของช่างแล่เนื้อ:


### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: อัปเดต Snapshot แบบไม่คิด (`jest -u`) เมื่อเทสต์ล้มเหลว
```bash filename="terminal.sh"
# เมื่อมีคนแก้โค้ดคำนวณภาษีผิดพลาด ทำให้ Snapshot ไม่ตรง
# นักพัฒนากดอัปเดตทันทีโดยไม่อ่าน Diff เพื่อให้เทสต์ผ่านไปเร็วๆ
npm test -- -u
# ผลลัพธ์: บั๊กการเงินถูกเซฟเป็น Snapshot มาตรฐานใหม่ นำไปสู่ความเสียหายบน Production!
```

#### ✅ สิ่งที่ถูก: ตรวจสอบ Diff บรรทัดต่อบรรทัดก่อนกดยืนยันอัปเดต Snapshot
```markdown filename="docs/testing/jest.txt"
- "totalVat": 210.00,
+ "totalVat": 0.00,  <-- ตรวจพบว่าโค้ดทำบั๊ก ลืมคิด VAT! ต้องแก้ที่โค้ดจริง ไม่ใช่กด -u
```

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **ควรใช้ Snapshot Testing เมื่อ:**
  - ตรวจสอบโครงสร้าง **API Response Contracts / DTOs** ขนาดใหญ่ที่มีความเสถียรแล้ว
  - ตรวจสอบข้อความแจ้งเตือน Error Message ที่ยาวและมีฟอร์แมตหลายบรรทัด
  - ตรวจสอบการแปลง AST หรือ SQL Query Generator
- **ไม่ควรใช้ Snapshot Testing เมื่อ:**
  - ข้อมูลมีขนาดเล็ก (เช่น ตัวเลขราคา 1 บรรทัด ควรใช้ `toBe(250)` ชัดเจนกว่า)
  - ข้อมูลมีการเปลี่ยนแปลงตลอดเวลาและไม่มีรูปแบบตายตัว
  - สภาพแวดล้อมที่ทีมงานมักกดยืนยัน `jest -u` โดยไม่อ่าน ทำให้เกิดปัญหา **Snapshot Fatigue** (สูญเสียความเชื่อมั่นในเทสต์)

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: อะไรคือความเสี่ยงหลักของการนำ Snapshot Testing มาใช้ในทีมขนาดใหญ่ และมีนโยบายป้องกันอย่างไร?**
  - *แนวคำตอบ:* ความเสี่ยงสูงสุดคือ **Snapshot Fatigue** เมื่อชุดทดสอบมี Snapshot มากเกินไป เมื่อมีการแก้ไขโค้ดเล็กน้อยจะทำให้ Snapshot นับสิบไฟล์พังพร้อมกัน วิศวกรจะเริ่มไม่อ่าน Diff และกด `jest -u` ผ่านๆ ทำให้บั๊กหลุดรอดเข้าไปในระบบ นโยบายป้องกันระดับ Senior ได้แก่:
    1. ห้ามใช้ Snapshot กับ UI Component Tree ขนาดยักษ์
    2. ใช้ Snapshot เฉพาะ Contract หรือ Serialized Payload สำคัญ
    3. บังคับทำ Code Review ไฟล์นามสกุล `*.snap` ใน Pull Request อย่างเข้มงวดเสมือนเป็นโค้ดโปรดักชัน
- **Q2: Inline Snapshot แตกต่างจาก External Snapshot อย่างไร และมีข้อได้เปรียบอย่างไรในการพัฒนาซอฟต์แวร์?**
  - *แนวคำตอบ:* External Snapshot จะบันทึกไฟล์แยกในโฟลเดอร์ `__snapshots__` ทำให้อ่านยากเพราะต้องเปิดสลับไฟล์ไปมา ส่วน Inline Snapshot จะใช้ AST Parser ทำการเขียนผลลัพธ์ Snapshot ฝังไว้ในไฟล์โค้ดทดสอบโดยตรง ข้อได้เปรียบคือผู้อ่านสามารถเห็น Input และ Expected Output อยู่ในหน้าจอเดียวกันทันทีตามหลัก Co-location ช่วยเพิ่ม Developer Experience (DX) และทำให้การทำ Code Review ทำได้ง่ายขึ้น

## 9. การตั้งค่า Jest และ TypeScript Config (jest.config.ts, ts-jest vs swc, path aliases)

### แนวคิด (Concept)
การติดตั้งสายพานและระบบควบคุมในโรงงานตัดแต่งเนื้อ **Smart Butcher Marketplace**:
- **`jest.config.ts`**: เปรียบเหมือน "คู่มือการตั้งค่าเครื่องจักรของโรงงาน" ระบุว่าจะให้ใครเป็นผู้ตรวจเนื้อ ค้นหาไฟล์จากโฟลเดอร์ไหน และจำลองสภาพแวดล้อมแบบใด
- **`ts-jest` (เครื่องตรวจละเอียดแบบดั้งเดิม)**: เปรียบเหมือน "ช่างตรวจสอบคุณภาพที่ตรวจเช็กไทป์และกฎเกณฑ์ TypeScript ละเอียดยิบทุกกระเบียดนิ้ว" ก่อนจะเริ่มรันเทสต์ ข้อดีคือปลอดภัยสูงสุด แต่ข้อเสียคือรันช้าเมื่อโรงงานมีขนาดใหญ่
- **`@swc/jest` (เครื่องจักรความเร็วแสงขับเคลื่อนด้วย Rust)**: เปรียบเหมือน "เครื่องจักรอัตโนมัติพลังสูง" ที่ทำหน้าที่แปลงโค้ด TypeScript เป็น JavaScript เพียงอย่างเดียวโดยไม่ตรวจไทป์ (ปล่อยให้ `tsc --noEmit` ทำงานใน CI แทน) ทำให้ความเร็วในการรันเทสต์พุ่งสูงขึ้นกว่าเดิม **5 ถึง 10 เท่า**
- **Path Aliases (`@/...`)**: เปรียบเหมือน "ระบบสายพานลำเลียงด่วน" แทนที่จะต้องเขียนเส้นทางไฟล์ย้อนหลังซับซ้อน `../../services/meat.service` เราสามารถสั่งดึงจาก `@/services/meat.service` ได้ทันที

### หลักการเบื้องหลัง (Under the Hood)
1. **`moduleNameMapper` (Path Aliasing Engine):** ในโปรเจกต์ TypeScript เรามักตั้งค่า `paths` ใน `tsconfig.json` เพื่อใช้ `@/*` แต่ Jest ทำงานบน Node.js Runtime จึงไม่รู้จัก Path เหล่านี้ Jest จึงมีกลไก `moduleNameMapper` เพื่อใช้ Regular Expression แปลงเส้นทาง เช่น `'^@/(.*)$': '<rootDir>/src/$1'`
2. **`testEnvironment` ('node' vs 'jsdom'):**
   - `'node'`: สภาพแวดล้อม Node.js บริสุทธิ์ เหมาะกับ Backend Services (Fastest, Leanest)
   - `'jsdom'`: จำลอง Browser DOM, Window, Document ในหน่วยความจำ เหมาะกับ React Frontend
3. **`setupFilesAfterEnv`:** สคริปต์ที่จะถูกรันก่อนเริ่มไฟล์ทดสอบทุกไฟล์หลังจากที่ Jest Test Framework ถูกติดตั้งลงใน Environment เรียบร้อยแล้ว นิยมใช้ใส่ Custom Matchers หรือ Global Teardown Logic

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การกำหนดค่า `jest.config.ts` แบบมาตรฐานองค์กรด้วย `ts-jest`
การตั้งค่าสำหรับการทดสอบระบบ Backend ของ Smart Butcher:

```typescript filename="jest.config.ts"
import type { Config } from 'jest';

const config: Config = {
  // 1. ระบุให้ Jest ทำงานในโหมด Node.js Environment สำหรับ Backend Testing
  testEnvironment: 'node',

  // 2. กำหนดรากของโฟลเดอร์ Source Code
  rootDir: '.',
  roots: ['<rootDir>/src'],

  // 3. รูปแบบชื่อไฟล์ที่จะถูกมองว่าเป็นชุดทดสอบ
  testMatch: [
    '**/__tests__/**/*.+(ts|tsx|js)',
    '**/?(*.)+(spec|test).+(ts|tsx|js)',
  ],

  // 4. คอมไพล์ TypeScript ด้วย ts-jest
  transform: {
    '^.+\\.(ts|tsx)$': [
      'ts-jest',
      {
        tsconfig: '<rootDir>/tsconfig.json',
        isolatedModules: false, // เปิด Type-checking อย่างสมบูรณ์
      },
    ],
  },

  // 5. แปลง Path Aliases ให้ตรงกับ tsconfig.json (@/ -> src/)
  moduleNameMapper: {
    '^@/(.*)$': '<rootDir>/src/$1',
    '^@test/(.*)$': '<rootDir>/test/$1',
  },

  // 6. กำหนดไฟล์ Setup เพื่อรันการล้าง Mock อัตโนมัติทุกรอบ
  setupFilesAfterEnv: ['<rootDir>/test/jest.setup.ts'],

  // 7. นโยบายการวัด Code Coverage
  collectCoverageFrom: [
    'src/**/*.{ts,js}',
    '!src/**/*.d.ts',
    '!src/**/*.interface.ts',
    '!src/main.ts',
  ],
  coverageDirectory: '<rootDir>/coverage',
  coverageReporters: ['text', 'lcov', 'html'],

  // 8. เคลียร์สถานะ Mock อัตโนมัติหลังจบแต่ละเคสทดสอบ
  clearMocks: true,
  restoreMocks: true,

  // 9. ป้องกัน Worker ค้างนานเกินไป
  testTimeout: 10000,
};

export default config;
```

```typescript filename="test/jest.setup.ts"
  // บังคับ Timezone ให้เป็น UTC เสมอ เพื่อป้องกันปัญหา Date คลาดเคลื่อนระหว่าง Dev กับ CI
  process.env.TZ = 'UTC';

afterEach(() => {

```

#### ตัวอย่างที่ 2: การตั้งค่า High-Performance ด้วย `@swc/jest` สำหรับ Monorepo หรือโปรเจกต์ขนาดใหญ่
เมื่อโปรเจกต์มีไฟล์ทดสอบหลักร้อยไฟล์ การสลับมาใช้ SWC จะช่วยลดเวลา CI จาก 5 นาทีเหลือไม่ถึง 40 วินาที:

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: ตั้งค่า Path Aliases ใน `tsconfig.json` แต่ละเลย `moduleNameMapper` ใน `jest.config.ts`
```typescript filename="src/jest.spec.ts"
// ใน tsconfig.json: "paths": { "@/*": ["src/*"] }
// แต่ใน jest.config.ts ไม่ได้ใส่ moduleNameMapper
```

- **ควรใช้ `ts-jest`:** ในโปรเจกต์ขนาดเล็กถึงปานกลางที่ต้องการความมั่นใจสูงสุดว่า Type Errors ทั้งหมดจะถูกตรวจจับได้ทันทีในจังหวะรันเทสต์

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: อะไรคือความแตกต่างสำคัญระหว่าง `setupFiles` และ `setupFilesAfterEnv` ใน Jest?**
  - *แนวคำตอบ:*
    - `setupFiles`: จะถูกสั่งรันก่อนที่ Test Framework (Jest Runtime) จะถูกติดตั้งเข้าสู่ Environment เหมาะสำหรับการกำหนด Environment Variables พื้นฐาน หรือ Polyfill ชนิดข้อมูล Global (เช่น `process.env.NODE_ENV = 'test'`) ในจุดนี้เราจะยังไม่สามารถเรียกใช้คำสั่ง `beforeEach` หรือ `expect` ได้
    - `setupFilesAfterEnv`: จะถูกสั่งรันหลังจากที่ Jest Test Framework ถูกติดตั้งเรียบร้อยแล้ว ในไฟล์นี้เราจึงสามารถประกาศ Global Lifecycle Hooks เช่น `beforeAll`, `afterEach` หรือติดตั้ง Custom Matchers เพิ่มเติมเข้าสู่ `expect.extend(...)` ได้อย่างสมบูรณ์
- **Q2: หากเปลี่ยนมาใช้ `@swc/jest` แล้วพบว่า NestJS Dependency Injection พัง หรือ Custom Decorators ไม่ทำงาน มีสาเหตุมาจากอะไร?**
  - *แนวคำตอบ:* เกิดจาก Decorator Metadata ของ TypeScript ไม่ถูกสร้างขึ้นมา ใน NestJS ตัวระบบต้องพึ่งพา `reflect-metadata` เพื่อทำ Dependency Injection ผ่าน Type Definition ของ Constructor เมื่อใช้ `@swc/jest` เราต้องเปิดค่า `legacyDecorator: true` และ `decoratorMetadata: true` ภายในบล็อกคอนฟิก `jsc.transform` เสมอ เพื่อให้ SWC สร้าง Reflection Metadata ที่จำเป็นสำหรับการทำงานของ NestJS Container

## 10. คำสั่ง CLI, Watch Mode และ Coverage Report

### แนวคิด (Concept)
แผงหน้าปัดควบคุมและเครื่องมือวัดผลในโรงงาน **Smart Butcher Marketplace**:
- **Watch Mode (`jest --watch`)**: เปรียบเหมือน "ช่างตรวจสอบคุณภาพที่ยืนเฝ้าสายการผลิตตลอดเวลา" เมื่อไหร่ก็ตามที่มีการตัดเนื้อชิ้นใหม่หรือแก้ไขโค้ด ตัว Watcher จะฉลาดพอที่จะรันเฉพาะเทสต์ของไฟล์ที่เพิ่งถูกบันทึกเท่านั้น โดยไม่ต้องเสียเวลารันใหม่ทั้งโรงงาน
- **Filter Flag (`jest -t "pattern"`)**: เปรียบเหมือน "คำสั่งตรวจเฉพาะเนื้อริบอาย" ไม่ต้องเสียเวลาตรวจเนื้อส่วนอื่น
- **Code Coverage Report**: เปรียบเหมือน "รายงานการตรวจสอบความปลอดภัยของอาหารอย่างละเอียด" ที่ระบุเป็นเปอร์เซ็นต์ว่า ในโรงงานมีเนื้อกี่ชิ้นที่ผ่านการตรวจ มีทางแยกหรือเงื่อนไขตรงไหนที่ยังไม่เคยถูกทดสอบเลยแม้แต่ครั้งเดียว

### หลักการเบื้องหลัง (Under the Hood)
1. **Git-Aware Watch Engine:** Jest เชื่อมต่อกับ Git Tracking โดยตรง ในโหมด Watch Jest จะวิเคราะห์ `git status` และ Dependency Graph เพื่อตรวจสอบว่าไฟล์ใดบ้างที่มีความเปลี่ยนแปลง (Uncommitted Changes) และรันเฉพาะไฟล์ที่มีผลกระทบ
2. **Interactive CLI Controls ใน Watch Mode:**
   - กด `a` : สั่งรันทุก Test Suites ในระบบ
   - กด `o` : รันเฉพาะไฟล์ที่มีการแก้ไขตามสถานะ Git (ค่าเริ่มต้น)
   - กด `p` : พิมพ์ Regex กรองชื่อไฟล์ทดสอบ (Filename Pattern)
   - กด `t` : พิมพ์ Regex กรองชื่อเคสการทดสอบ (Test Name Pattern)
   - กด `u` : สั่งอัปเดต Snapshot ที่ล้มเหลวทั้งหมด
   - กด `q` : ออกจาก Watch Mode
3. **การอ่านตาราง Code Coverage Matrix (Istanbul Engine):**

- **% Branch (Branch Coverage):** เปอร์เซ็นต์ของเส้นทางการตัดสินใจเงื่อนไข (`if/else`, `switch/case`, `ternary ? :`) ที่ถูกรันครบทุกทิศทาง **(ตัวชี้วัดที่สำคัญที่สุดในระบบ Enterprise)**

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: เหตุใดการที่โค้ดมี Line Coverage 100% จึงไม่ได้การันตีว่าระบบจะปราศจากข้อผิดพลาดใน Production?**
  - *แนวคำตอบ:* Line Coverage ตรวจสอบเพียงว่าบรรทัดนั้นเคยถูกอ่านผ่านหรือไม่ แต่ไม่ได้การันตีว่า **Condition Combinations** หรือขอบเขตของข้อมูล (Boundary Values) ถูกทดสอบครบถ้วน ตัวอย่างเช่น โค้ด `if (isVip && hasCoupon) { ... }` หากเราส่งเฉพาะกรณีที่เป็นจริงทั้งคู่ บรรทัดนั้นจะถูกรันและได้ Line Coverage 100% ทันที แต่ระบบจะยังไม่เคยถูกทดสอบเลยว่าเกิดอะไรขึ้นถ้า `isVip` เป็นจริงแต่ `hasCoupon` เป็นเท็จ หรือค่าเป็น `null/undefined` ดังนั้น **Branch Coverage** และการคิด Edge Cases จึงเป็นหัวใจสำคัญที่แท้จริง
- **Q2: คำสั่ง `--runInBand` ใน Jest ทำงานอย่างไร และเมื่อไหร่ที่วิศวกรควรตัดสินใจเลือกใช้คำสั่งนี้?**
  - *แนวคำตอบ:* ปกติ Jest จะแตก Worker Processes เพื่อรันแต่ละไฟล์ทดสอบแบบขนานกัน (Parallel Execution) แต่เมื่อใส่ Flag `--runInBand` (หรือ `-i`) Jest จะรันทุกไฟล์ทดสอบแบบเรียงคิวทีละไฟล์ (Serially) ภายใน Main Process เดียวกัน ควรเลือกใช้ใน 2 กรณี:
    1. **Integration Tests ที่ใช้ฐานข้อมูลร่วมกัน:** เพื่อป้องกัน Race Conditions ที่ไฟล์เทสต์ 2 ไฟล์แย่งกันเขียนทับตารางเดียวกัน
    2. **สภาพแวดล้อม CI ที่มีทรัพยากรจำกัด:** เช่น Docker Container ที่มี RAM 1-2GB การรัน Process เดียวจะเร็วกว่าและไม่เสี่ยงต่อการถูกระบบปฏิบัติการสั่ง Kill เพราะ Memory หมด

## 11. เปรียบเทียบ Jest vs Vitest แบบสรุป (เมื่อไหร่ควรเลือกตัวไหน)

### แนวคิด (Concept)
การเลือกระบบทดสอบสำหรับสถาปัตยกรรมระดับ Enterprise:
- **Jest (รถบรรทุกสิบล้อเกรดอุตสาหกรรม)**: ผ่านการทดสอบสมบุกสมบันมานานกว่า 10 ปี มีระบบนิเวศขนาดใหญ่ที่สุดในโลก เสถียรอย่างยิ่ง และเป็นค่าเริ่มต้นของเฟรมเวิร์กยอดนิยมอย่าง NestJS
- **Vitest (รถสปอร์ตไฟฟ้าพลังสูง)**: ถูกสร้างขึ้นมาสำหรับยุคสมัยใหม่ โดยใช้ขุมพลังของ **Vite Engine** ทำงานกับโมดูลแบบ ESM ได้อย่างเป็นธรรมชาติ มีความเร็วในการเปิดระบบและ Hot Module Replacement (HMR) ที่เร็วกว่ามาก และสามารถแชร์ Configuration ร่วมกับ Vite ได้ 100%

### หลักการเบื้องหลัง (Under the Hood)
1. **Module Bundling:** Jest เกิดขึ้นในยุค CommonJS (CJS) จึงต้องใช้ Babel หรือ `ts-jest` แปลงโค้ดทั้งหมดใหม่ก่อนนำไปรันใน Node.js `vm` ในขณะที่ Vitest รันบน Vite Pipeline ซึ่งประมวลผลโค้ดผ่าน ES Modules (ESM) และใช้ esbuild/Rollup แปลงโค้ดด้วยความเร็วสูง
2. **API Parity (ความเหมือนของชุดคำสั่ง):** Vitest ถูกออกแบบมาให้เป็น Drop-in Replacement ของ Jest แทบจะ 98% ฟังก์ชัน `describe`, `it`, `expect`, `beforeEach` เขียนเหมือนกันทุกประการ ต่างกันเพียงแค่ฟังก์ชัน Mock ใน Vitest จะใช้ `vi` แทน `jest` (เช่น `vi.fn()`, `vi.spyOn()`, `vi.mock()`)

### ตารางเปรียบเทียบเชิงลึก: Jest vs Vitest

| มิติการเปรียบเทียบ | Jest 29.x | Vitest 1.x / 2.x |
| :--- | :--- | :--- |
| **หัวใจการทำงาน (Core Engine)** | Custom Sandboxed VM + jest-worker | Vite Dev Server + Worker Threads / Tinypool |
| **การรองรับ Native ESM** | ยังคงเป็น Experimental Flag (ตั้งค่ายาก) | **รองรับ Native ESM 100%** ตั้งแต่วินาทีแรก |
| **ความเร็วในการเริ่มรัน (Startup Speed)** | ปานกลาง (มี Overhead ในการสร้าง VM Sandbox) | **รวดเร็วมาก** (Instant Transformation ผ่าน esbuild) |
| **Watch Mode Performance** | ดี (วิเคราะห์ผ่าน Git Changes) | **เป็นเลิศ** (ใช้ Vite HMR Re-run เฉพาะ Function Graph) |
| **ระบบนิเวศ Backend (NestJS)** | **มาตรฐานหลัก (First-class Citizen)** | ต้องปรับแต่ง Config เพิ่มเติมเพื่อรองรับ Decorators |
| **ระบบนิเวศ Frontend (Vite/Next.js)** | ต้องตั้งค่า Babel/SWC แยกต่างหาก | **แชร์ Config เดียวกันกับ Vite ได้ทันที** |
| **ความพร้อมในการใช้งานระดับ Enterprise** | **สูงมาก** มีเอกสาร ชุมชน และปลั๊กอินรองรับทุกปัญหา | เติบโตอย่างรวดเร็ว นิยมมากในโปรเจกต์สมัยใหม่ |

### ตัวอย่างโค้ด (Smart Butcher Marketplace)

#### ตัวอย่างที่ 1: การเขียนชุดทดสอบเดียวกันใน Jest vs Vitest
การคำนวณส่วนลดเนื้อสเต๊กพรีเมียม:


```typescript filename="vitest.config.ts"
});
```

### ผิด vs ถูก (Common Pitfalls & Best Practices)

#### ❌ สิ่งที่ผิด: ตัดสินใจย้ายโปรเจกต์ NestJS Enterprise ขนาดยักษ์ไป Vitest โดยไม่ประเมินความเสี่ยง
```typescript filename="src/jest.spec.ts"
// สถาปัตยกรรม NestJS ผูกติดกับ reflect-metadata และ TypeScript Experimental Decorators อย่างแน่นหนา
// การย้ายไป Vitest ในระบบเดิมที่มี Jest Custom Matchers นับร้อยตัวอาจทำให้เสียเวลาแก้ปัญหา Tooling 
// มากกว่าเวลาที่ประหยัดได้จากการรันเทสต์
```

#### ✅ สิ่งที่ถูก: เลือกเครื่องมือให้ตรงกับสแต็กเทคโนโลยีของระบบ
- ใช้ **Jest** เป็นแกนหลักสำหรับ **Backend NestJS / Express Enterprise Services**
- ใช้ **Vitest** เป็นแกนหลักสำหรับ **Frontend (Vite, React, Vue, SvelteKit)** หรือโมเดิร์น Fast-Paced Next.js Apps

### ควรใช้เมื่อไหร่ / ไม่ควรใช้เมื่อไหร่
- **เลือกใช้ Jest เมื่อ:**
  - กำลังพัฒนาแอปพลิเคชัน Backend ด้วย NestJS ซึ่งมี Template และ Best Practices ส่วนใหญ่ผูกติดกับ Jest
  - โปรเจกต์เดิมใช้ CommonJS หรือมี Dependency ภายนอกที่ยังไม่รองรับ ESM อย่างสมบูรณ์
- **เลือกใช้ Vitest เมื่อ:**
  - โปรเจกต์พัฒนาด้วย Vite เป็น Build Tool อยู่แล้ว
  - ต้องการความเร็วสูงสุดในการทำ TDD บนเครื่องพัฒนา
  - โปรเจกต์เขียนด้วยโมเดิร์น Pure ESM (`"type": "module"`)

### คำถามสัมภาษณ์ (Senior Level Questions)
- **Q1: เหตุใดการทดสอบโค้ดที่เป็น Pure ESM (`"type": "module"`) ใน Jest จึงมีความซับซ้อนกว่าใน Vitest?**
  - *แนวคำตอบ:* สถาปัตยกรรมดั้งเดิมของ Jest ถูกสร้างขึ้นบนพื้นฐานของ CommonJS (`require`) การที่จะรองรับ Native ESM ใน Node.js ตัว Jest จำเป็นต้องพึ่งพา Node.js Experimental VM Modules API (`--experimental-vm-modules`) ซึ่งยังคงมีข้อจำกัดเรื่อง Module Mocking และไม่เสถียร 100% ในขณะที่ Vitest ถูกสร้างขึ้นบน Vite ซึ่งใช้ Rollup และ esbuild ในการจัดการ Module Graph ทำให้สามารถ Resolve โค้ดแบบ ESM ได้อย่างเป็นธรรมชาติและไร้รอยต่อ
- **Q2: หากต้องการทยอยย้าย (Gradual Migration) จาก Jest ไปยัง Vitest ในองค์กร มีกลยุทธ์อย่างไรที่ไม่กระทบการส่งมอบงาน?**
  - *แนวคำตอบ:*
    1. เริ่มต้นด้วยการเปิดใช้งาน `globals: true` ใน `vitest.config.ts` เพื่อให้สามารถใช้คำสั่ง `describe`, `it`, `expect` ร่วมกันได้โดยไม่ต้องแก้ Source Code ของไฟล์ทดสอบเดิม
    2. ใช้ Codemod เช่น `jest-to-vitest` เพื่อแปลงคำสั่งจำลองจาก `jest.` เป็น `vi.` แบบอัตโนมัติ
    3. ปรับแต่ง Path Aliases ให้ตรงกัน
    4. ย้ายไปทีละ Package ในกรณีของ Monorepo โดยเริ่มจาก Shared Utilities และ Frontend ก่อนจะขยับเข้าสู่ Backend Services

## ข้อผิดพลาดที่พบบ่อย (Anti-patterns)

ในการตรวจสอบชุดทดสอบ Jest ระดับ Enterprise ของระบบ **Smart Butcher Marketplace** สถาปนิกซอฟต์แวร์ระดับ Senior มักพบ Anti-patterns สำคัญดังต่อไปนี้:

### 1. The Liar Test (False Positive จากการลืมใส่ `await`)
- **พฤติกรรม:** เขียน `expect(promiseFunction()).rejects.toThrow()` โดยลืมใส่คำว่า `await` ด้านหน้า
- **ผลกระทบ:** ตัวฟังก์ชันคืนค่าเป็น Promise ที่ยังไม่ได้ Resolve ตัว Jest จะประเมินว่าการทดสอบผ่านไปแล้ว เทสต์นี้จะ "เขียวตลอดกาล" แม้ฟังก์ชันจริงในระบบจะพังยับเยิน
- **แนวทางแก้ไข:** เติม `async/await` เสมอ และติดตั้งกฎ ESLint `jest/valid-expect` เพื่อดักจับข้อผิดพลาดนี้ตั้งแต่จังหวะพิมพ์โค้ด

### 2. The Leaky Cauldron (Test Pollution จากการแชร์ Mutable State)
- **พฤติกรรม:** การประกาศตัวแปร Array หรือ Object ขนาดใหญ่ไว้นอก `describe` แล้วให้ทุก `it` เข้าไป `push` หรือแก้ไขค่าในตัวแปรเดียวกัน
- **ผลกระทบ:** เคสทดสอบที่ 5 จะผ่านได้ก็ต่อเมื่อเคสที่ 1, 2, 3, 4 ทำงานเรียบร้อยแล้วเท่านั้น เมื่อสั่งรันเทสต์แบบสุ่มลำดับหรือรันแยกไฟล์เดี่ยวๆ เทสต์จะล้มเหลวทันที (Flaky Test)
- **แนวทางแก้ไข:** สร้าง Fixture ใหม่ทั้งหมดใน `beforeEach` เสมอ ห้ามแชร์ Mutable State ข้ามเคสการทดสอบเด็ดขาด

### 3. The Over-Mocker (Mock ทุกอย่างจนไม่ได้ทดสอบอะไรจริง)
- **พฤติกรรม:** การสั่ง `jest.mock()` ทุกคลาส แม้กระทั่ง Entity เล็กๆ, ฟังก์ชันคำนวณราคา, หรือ Utility ภายใน Service เดียวกัน
- **ผลกระทบ:** ชุดทดสอบกลายเป็นการ Assert "สิ่งที่นักพัฒนาคิดว่าจะเกิดขึ้น" ไม่ใช่พฤติกรรมจริงของระบบ เมื่อมีการ Refactor โค้ดภายใน แต่ Business Output ยังเหมือนเดิม เทสต์จะพังทั้งหมด (Fragile Tests) และเมื่อระบบมีบั๊กตรรกะจริง เทสต์กลับไม่เตือน
- **แนวทางแก้ไข:** Mock เฉพาะ External I/O Boundaries (Database, Third-party HTTP, S3, Email) และปล่อยให้ Pure Business Logic ทำงานจริง

### 4. The Snapshot Hoarder (การสะสม Snapshot ไร้สาระ)
- **พฤติกรรม:** สั่ง `expect(everything).toMatchSnapshot()` กับทุกอย่าง ทั้ง HTML ก้อนใหญ่, DOM Tree ทั้งหน้าจอ, หรือข้อมูลที่เปลี่ยนบ่อย
- **ผลกระทบ:** เกิดอาการ **Snapshot Fatigue** เมื่อทีมงานต้องพบกับ Snapshot พังทุกสัปดาห์ จะไม่มีใครอ่าน Diff อีกต่อไป และทุกคนจะพร้อมใจกันกด `jest -u` เพื่อให้งานเสร็จ ทำให้ระบบสูญเสียเครื่องมือตรวจสอบความถูกต้องไปโดยสิ้นเชิง
- **แนวทางแก้ไข:** ใช้ Snapshot อย่างจำกัดเฉพาะ Fixed Data Contracts และหลีกเลี่ยงการทำ Snapshot กับข้อมูล UI ที่ไม่แน่นอน

### 5. The Ghost Process (ละเลย Open Handles จน Jest ปิดไม่ลง)
- **พฤติกรรม:** เปิด Database Connection Pool หรือตั้ง `setInterval` ทิ้งไว้ใน Service แต่ไม่มีการปิดใน `afterAll`
- **ผลกระทบ:** บน CI Process ของ Jest จะค้างเติ่งนับสิบนาทีจนระบบติด Timeout สิ้นเปลืองงบประมาณ CI Runners
- **แนวทางแก้ไข:** สั่งรัน `jest --detectOpenHandles` เพื่อค้นหาตำแหน่งที่ลืมปิด Connection แล้วจัดการ Clean Up ให้เรียบร้อยใน Lifecycle Hooks

## Checklist สรุป

ก่อนนำชุดทดสอบ Jest ขึ้นสู่สภาพแวดล้อม CI/CD ของระบบ **Smart Butcher Marketplace** ให้ตรวจสอบความสมบูรณ์ตามรายการนี้:

- [ ] **Descriptive Naming:** ทุกเคสทดสอบตั้งชื่อเป็นประโยคภาษาอังกฤษเชิงพฤติกรรม (`it('should do X when Y')`) ชัดเจน ปราศจากการตั้งชื่อแบบ `test 1`, `test 2`
- [ ] **AAA Pattern Enforced:** โครงสร้างภายในแต่ละ Test Case ถูกจัดระเบียบตามหลัก **Arrange - Act - Assert** ชัดเจน
- [ ] **State Cleanliness:** มีการใส่ `clearMocks: true` ใน `jest.config.ts` หรือเรียก `jest.clearAllMocks()` / `jest.restoreAllMocks()` ใน `afterEach`
- [ ] **No Floating Point Bashing:** ทุกการ Assert ที่เกี่ยวข้องกับเงินและน้ำหนักเนื้อสัตว์ใช้ `toBeCloseTo()` ไม่ใช้ `toBe()` เพื่อป้องกันปัญหา IEEE 754
- [ ] **Strict Typing:** ชุดทดสอบใช้ TypeScript Strict Mode ปราศจากการใช้ `any` และมีการใช้ `jest.Mocked<T>` เพื่อ Type-safe Mocks
- [ ] **Async Awaited:** ทุกการทดสอบที่เป็น Asynchronous มีการใส่คีย์เวิร์ด `await` ครบถ้วน โดยเฉพาะหน้า `expect(...).rejects.toThrow()`
- [ ] **No Leaky Timers:** การใช้งาน `jest.useFakeTimers()` มีการคืนค่าด้วย `jest.useRealTimers()` ใน `afterEach` เสมอ
- [ ] **Proper Module Mocking:** การเรียกใช้ `jest.mock()` มีการปฏิบัติตามกฎ Hoisting และไม่มีการอ้างอิงตัวแปรนอก Scope โดยไม่ตั้งใจ
- [ ] **Path Aliases Sync:** ค่าใน `moduleNameMapper` บน `jest.config.ts` ตรงกับ `paths` ใน `tsconfig.json` ครบทุกเส้นทาง
- [ ] **CI Resource Optimization:** มีการระบุ `--maxWorkers=2` หรือ `--runInBand` ในสคริปต์ทดสอบบน CI เพื่อป้องกัน Memory Thrashing
- [ ] **Branch Coverage Targets:** มีการกำหนด `coverageThreshold` ที่เน้น % Branch Coverage ไม่ใช่เพียงแค่ Line Coverage

## ลำดับการเรียนที่แนะนำ และ ดูเพิ่มเติมที่

หลังจากเข้าใจแกนหลัก กลไกการ Matcher, Mocking และ Lifecycle ของ Jest อย่างลึกซึ้งแล้ว ขอแนะนำให้ศึกษาการนำ Jest ไปประยุกต์ใช้งานในเลเยอร์เฉพาะทางตามลำดับดังนี้:

<Callout type="tip" title="ศึกษาต่อในหัวข้อถัดไป">
1. **การทดสอบฝั่ง Backend เชิงลึก (Controller, Service, Repository, E2E HTTP):**  
   👉 **[Backend Testing (NestJS + Supertest)](/docs/testing/backend-testing)** — เรียนรู้วิธีการใช้ Jest ร่วมกับ `@nestjs/testing` Module, การทำ Dependency Injection Mocking สำหรับ Service, และการยิงจำลอง HTTP Request ทดสอบ REST APIs ด้วย Supertest

2. **การทดสอบฝั่ง Frontend เชิงลึก (Component, Hooks, User Events):**  
   👉 **[Frontend Testing (React Testing Library)](/docs/testing/frontend-testing)** — เรียนรู้วิธีการนำ Jest มาทดสอบ React Components ตามปรัชญา "ทดสอบในมุมมองของผู้ใช้งานจริง", การจำลอง User Interaction ด้วย `@testing-library/user-event`, และการดักจับ Custom Hooks

3. **การทดสอบระบบแบบครบวงจรจากหน้าจอสู่ฐานข้อมูล:**  
   👉 **[E2E Testing (Playwright)](/docs/testing/e2e-playwright)** — ก้าวข้าม Unit Test ไปสู่การควบคุม Real Browser เพื่อทดสอบเส้นทางสั่งซื้อเนื้อดรายเอจตั้งแต่เปิดเว็บจนกระทั่งพิมพ์ใบเสร็จสำเร็จ
</Callout>
